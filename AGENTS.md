## Структура проекта

Монорепозиторий `synth/` (pnpm workspaces). Единый стек TypeScript.

```
synth/
├── packages/
│   ├── shared/    @synth/shared   # Типы, Zod-схемы, протоколы, конфигурация
│   ├── core/      @synth/core     # Ядро: сессии, очередь, LLM, TSM, MCP, FileStore
│   │                              #   HTTP API v2 (Hono), CLI (synth chat/serve)
│   ├── backend/   @synth/backend  # Hono API Hub: OIDC, RBAC, Runner Registry, LLM Proxy
│   ├── ui/        @synth/ui       # React 19 SPA + админка (Vite)
│   ├── runner/    @synth/runner   # Gateway: адаптеры opencode/cline, LLM Proxy
│   │                              #   Импортируется in-process из @synth/core
│   └── synth/     @itphx/synth    # Публикуемая CLI-обёртка (bin: synth). Тонкая —
│                                  #   зависит от core+ui+shared, не бандлит их, не копирует ассеты
├── pnpm-workspace.yaml
├── tsconfig.base.json
├── eslint.config.js
└── .prettierrc
tmp/                               # Каталог для временных файлов. Всегда используй его, а не /tmp в корне ФС
```

Все 6 пакетов публикуются в npm (см. «Публикация npm»). `@itphx/synth` — тонкая
CLI-обёртка над `@synth/core`/`@synth/ui`/`@synth/shared`; она не бандлит core
внутрь `cli.js` (core/ui/shared — external) и не копирует ассеты (промпты/UI/docs)
в свой каталог — всё резолвится из npm-зависимостей (см. AD-038).

### Слои зависимостей

```
@synth/shared  ←  только контракты, никакой логики
       ↑
@synth/core    ←  импортирует shared, содержит всю общую логику
       ↑
┌──────┴──────┐
@synth/backend │ @synth/ui     ←  импортируют core
@synth/runner (in-process)     ←  опционально импортируется в core
       ↑
@itphx/synth   ←  тонкая CLI-обёртка: core + ui + shared (npm-потребители)
```

## Команды

Из корня `synth/`:

```bash
# Разработка
./dev.sh                    # backend (:5000) + UI (:5002)
./dev.sh backend | ui | core | all

# Сборка, тесты, линтинг
pnpm install                # установка зависимостей
pnpm build                  # сборка всех пакетов
pnpm typecheck              # проверка типов
pnpm lint                   # ESLint
pnpm test                   # Vitest
pnpm clean                  # очистка dist/
```

Сборка core по-прежнему копирует `prompts/` и `definitions/*.json` в `dist/`; backend — аналогично для `definitions/`. Это **fallback для Docker** (где рядом с `package.json` нет `prompts/`, а есть только `dist/`): источник истины промптов — `packages/core/prompts`, который публикуется в npm через поле `files`. Дубликатов ассетов в репозитории больше нет (см. AD-038).

Логи: `tmp/backend.log`, `tmp/ui.log`, `tmp/core.log`. Каталог `tmp/` не коммитится.

### Скрипт запуска

Корень проекта — `/mnt/data/Agent/dev/Synth`. Запуск через `dev.sh`:

```bash
./dev.sh            # backend (:5000) + UI (:5002)
./dev.sh backend    # только backend
./dev.sh core       # synth-core standalone (:4300)
./dev.sh all        # backend + UI + core
```

Скрипт устанавливает ключевые переменные окружения:
- `SYNTH_AUTH_DEBUG=true` — debug-режим аутентификации с тестовыми пользователями

- `SYNTH_PORT`, `SYNTH_CORE_PORT`, `VITE_PORT` — порты компонентов

Все runtime-данные (сессии, проекты, провайдеры, модели) — в `$SYNTH_DATA_DIR`.

Провайдеры: JSON-файлы в `$SYNTH_DATA_DIR/providers/`. Модели: файлы в `$SYNTH_DATA_DIR/models/`.

Основные провайдеры для разработки:

| Имя | Тип | Назначение |
|-----|-----|------------|
| `itphx` | openai | Рабочий провайдер (ai.itphx.ru), модель `local.qwen3:14b` |
| `ollama` | ollama | Локальный Ollama (owu.itphx.loc:11434) |

Для добавления нового провайдера достаточно создать JSON-файл в `providers/`, для модели — в `models/`.

### Автономный цикл разработки и тестирования

Каждая задача проходит 5 стадий. Переход между стадиями — **только после
удовлетворения критерия** и явной команды пользователя (или молчаливого согласия,
если пользователь не отвечает на уточняющий вопрос).

#### Стадия 1: Исследование (Investigate)

**Что делать:**
- Прочитать затронутые файлы, понять текущую реализацию
- Найти похожий код, понять паттерны
- Проверить прототип (`~/dev/aic/t11`) если задача связана с существующей фичей
- Задать уточняющие вопросы пользователю

**Что НЕ делать:**
- НЕ править код
- НЕ запускать сервер
- НЕ строить догадки — спрашивать

**Критерий перехода:** я могу сформулировать, какие именно файлы менять и почему.

#### Стадия 2: Планирование (Plan)

**Что делать:**
- Сформулировать список атомарных изменений (todo-лист)
- Оценить, не сломает ли изменение другие части
- Предложить план пользователю, получить подтверждение

**Что НЕ делать:**
- НЕ начинать кодить до подтверждения

**Критерий перехода:** пользователь явно подтвердил план (или сказал «приступай»).

#### Стадия 3: Реализация (Implement)

**Что делать:**
- Внести изменения строго по плану, минимальными правками
- Следовать код-стилю проекта (именование, структура, импорты — см. «Соглашения по коду»)
- Собрать: `pnpm build` (из `synth/`)
- Убедиться что нет ошибок компиляции

**Что НЕ делать:**
- НЕ менять код за пределами плана
- НЕ добавлять комментарии без явной просьбы
- НЕ коммитить (если не попросили)

**Критерий перехода:** `pnpm build` проходит без ошибок.

#### Стадия 4: Проверка (Verify)

**Что делать — в строгом порядке:**

1. `pnpm typecheck` — проверка типов
2. `pnpm lint` — линтинг
3. `pnpm test` — unit-тесты Vitest
4. Запустить `./dev.sh backend` для API-тестов
5. Проверить затронутые эндпоинты через curl
6. Запустить `./dev.sh` (backend + UI) и быстро проверить UI в браузере —
   открыть страницу, убедиться что интерфейс загружается и ключевые элементы
   отображаются корректно.

**Что НЕ делать:**
- НЕ устанавливать новые инструменты (playwright, браузеры, npm-пакеты)
- НЕ писать сложные bash-скрипты — достаточно curl и визуальной проверки
- НЕ прогонять AI-запросы через LLM без явной просьбы
- НЕ писать в JSON-файлы сессий/провайдеров/моделей вручную — для создания
  провайдера/модели использовать API, для сообщений — `POST /sessions/:id/prompt`

**Критерий перехода:** все тесты typecheck+lint+test проходят, ключевые эндпоинты
отвечают ожидаемым кодом и форматом.

#### Стадия 5: Документирование (Document)

**Что делать:**
- Обновить `AGENTS.md` если изменилось окружение или процессы
- Зафиксировать неочевидные решения в задаче (не в коде)

**Критерий перехода:** всё готово к следующей сессии.

#### Типичные ошибки (чего избегать)

1. **Переход к реализации без исследования** — приводит к переделкам
2. **Автоматизация ради автоматизации** — скрипты на 100 строк python/bash когда
   достаточно 3 строк curl и визуальной проверки в браузере
3. **Установка зависимостей для тестирования** — все инструменты уже настроены,
   если чего-то не хватает - скажи пользователю
4. **Запуск сервера без `dev.sh`** — порты и переменные уже настроены в скрипте,
   не изобретать свой способ
5. **Прямая запись в JSON-хранилище** — категорически запрещена. Единственные
   исключения: исправление багов в самом JSON-хранилище или миграция на новую
   схему. Во всех остальных случаях — только через API
6. **Игнорирование стадий** — нельзя одновременно исследовать, кодить и тестировать

### AD-025: Plan/Act как глобальный permission toggle

**Решение:** Plan/Act режимы — глобальное состояние сессии, не привязанное к конкретному синту. При переключении режима меняется набор доступных инструментов, но роль и промпт агента остаются прежними.

**Контекст:** в OpenCode Plan и Act — это разные агенты (plan agent ↔ build agent) со своими permissions и системными промптами. В Claude Code — один и тот же агент, но с переключением permissionMode. И тот и другой подход сошлись на одном: plan mode — это ограничение инструментов, а не отдельная личность. Synth идёт по пути Claude Code.

**Реализация:**

```yaml
# config.yaml
session:
  mode: "auto"  # plan | act | yolo | auto

agents:
  analyst:
    description: "Анализирует код, архитектуру, находит проблемы"
    systemPrompt: "..."
    # tools — максимальный набор для синта
    # в plan mode write-тулы будут заблокированы глобально
```

| Режим | Поведение | Переключение |
|---|---|---|
| `plan` | **Read-only.** Все write/edit/delete → deny. Синт исследует, задаёт вопросы, пишет план в `.synth/plans/`. Единственное исключение — сам plan-файл | Пользователь (`/plan`) или синт через tool `plan_enter` |
| `act` | **Полный доступ.** Набор тулов из конфига синта + глобальные permissions | Пользователь (`/act`) или tool `plan_exit` |
| `yolo` | **Автоподтверждение.** Все ask → allow автоматически (без события `permission.asked` и ожидания пользователя), deny остаётся deny | Пользователь (`/yolo`) |
| `auto` | Синт **сам решает**, когда войти в план. Вызывает `plan_enter` если задача сложная, требует исследования или архитектурных решений | Автоматически (аналог EnterPlanModeTool) |

**SessionMode:** `'plan' | 'act' | 'yolo'`. В сериализации сессии есть поле `mode_applicable` — `false` для read-only агентов (нет `shell`/`file_write`/`web`): toggle режима в UI деактивируется.

**Системный промпт режима:** контекстные файлы `prompts/modes/{plan,act,yolo}.md` (встроенные, копируются в `dist/`), переопределяются через `{dataDir}/context/modes/{mode}.md` и локализованные `{mode}.{lang}.md`. Встраиваются в system prompt через `_buildPlanSystemPrompt`.

**События:** `plan.approved` (план утверждён через `plan_exit`), `todos.updated` (обновлён список ToDo через `todo_write`).

**Почему не N×2 агентов:** создание отдельных plan-версий для каждого синта даёт квадратичный рост конфигурации. С глобальным toggle — N синтов × 3 режима = те же N в конфиге, а режим переключается сессионно.

### AD-026: Режимы контекста саб-агента

**Решение:** три режима передачи контекста при запуске саб-агента.

**Контекст:** fork-модель Claude Code (агент наследует всю историю родительской сессии) удобна на коротких диалогах, но на длинных — саб-агент получает 50K+ токенов мусора. Изоляция OpenCode (агент — чистый лист, только prompt) дешевле, но легко упустить важный контекст. Synth даёт выбор.

| Режим | Поведение | Токены | Когда использовать |
|---|---|---|---|
| `inherit` | Саб-агент получает полную историю родительской сессии + свой prompt | Много (fork-модель) | Короткие диалоги (<10K токенов), продолжение разговора, тесная связь с родителем |
| `summary` | Контекст сжимается через отдельную LLM перед отправкой саб-агенту. В саммари попадают: ключевые решения, соглашения, результаты предыдущих шагов | Среднее (авто-саммари) | Длинные диалоги, нужно сохранить суть без мусора. **Дефолт для продакшена** |
| `none` | Саб-агент получает только prompt. Никакого контекста родителя | Минимальное | Самодостаточные задачи, параллельные workers, чистое выполнение по спецификации |

**Выбор режима:**

```bash
synth task "Исправь баг в auth.ts" --context summary
synth task "Проверь build"         --context none
synth task "Продолжи рефакторинг"   --context inherit
```

**Внутренняя механика:** `summary` реализуется через дополнительный вызов LLM (быстрой/дешёвой модели) для компрессии контекста перед spawn-ом саб-агента. Саммари кешируется до следующего значимого изменения родительской сессии.

### AD-027: Двойная передача плана

**Решение:** после утверждения план записывается в файл `.synth/plans/{timestamp}-{slug}.md` **и** вставляется в system prompt исполнителя.

**Контекст:** Claude Code встраивает план в `tool_result` выхода из plan mode — модель видит план сразу, но он существует только в контексте сессии. OpenCode пишет план на диск, модель должна прочитать его отдельным tool call. Synth берёт оба подхода.

```
plan (план написан)
  │
  ├─1─→ .synth/plans/{ts}-{slug}.md    ← файл на диске
  │       • персистентность между сессиями
  │       • аудит: видно что и когда планировали
  │       • возобновление: можно продолжить через неделю
  │
  └─2─→ system prompt исполнителя       ← встроен в контекст
          • немедленная видимость без tool call
          • не тратит токены на чтение файла
```

**Формат плана:**

```markdown
# План: {краткое описание}
> Создан: 2026-07-22 14:30 (analyst)
> Утверждён: 2026-07-22 14:35

## Подход
...

## Критические файлы
- src/auth/validate.ts:42
- src/auth/types.ts:15

## Шаги
1. ...
2. ...

## Верификация
- Прогнать тесты auth/*.test.ts
- Проверить edge cases: ...
```

**Защита от потери:** при возобновлении сессии план восстанавливается из файла. Если файл не найден (CCR/remote сессия) — ищется в снапшотах и истории сообщений (аналог `copyPlanForResume` из Claude Code).

### AD-028: Настраиваемая строгость цикла Plan → Build

**Решение:** три режима строгости, настраиваются глобально или на уровне проекта.

| Режим | Поведение | Когда синт может писать | Аналог |
|---|---|---|---|
| `auto` | Синт сам решает, нужен ли план. Для простых задач — сразу делает. Для сложных — вызывает `plan_enter` | После того как сам решил (или без плана для простых) | Claude Code (EnterPlanMode + ExitPlanMode) |
| `strict` | **План обязателен** перед любым write. Без утверждённого плана все write/edit/delete → deny. Исследовать (read) можно | Только после `plan_exit` (план утверждён) | OpenCode (принудительный Plan→Build цикл) |
| `off` | Планирование отключено. Всегда act mode | Всегда | — (для тривиальных фиксов, Personal/personal) |

```yaml
# config.yaml
session:
  plan_mode: "auto"  # auto | strict | off
```

**Рекомендации по выбору:**
- `strict` — командная работа, сложные проекты, новички в команде. Не даст наломать дров
- `auto` — продвинутые пользователи, balance между скоростью и безопасностью
- `off` — персональные скрипты, прототипы, одноразовые задачи

**Вход в план в режиме `auto`:** синт получает промпт-инструкцию (аналог EnterPlanModeTool prompt): «Если задача сложная, затрагивает несколько файлов или требует архитектурных решений — вызови `plan_enter`. Для простых фиксов — делай сразу.»

### AD-029: Гранулярные permissions

**Решение:** права доступа на основе модели OpenCode — allow/deny/ask для каждого инструмента с поддержкой glob-паттернов для файлов.

**Контекст:** у Claude Code система прав — `disallowedTools` (простой список запрета). У OpenCode — allow/deny/ask на каждый инструмент + паттерны файлов с разрешением на glob-уровне. Модель OpenCode **строго лучше** — даёт точный контроль без оверхеда.

```yaml
permission:
  # Глобальные правила
  "*": "allow"                    # всё разрешено по умолчанию
  doom_loop: "ask"                # подозрительные циклы — переспросить
  question: "deny"                # саб-агентам нельзя переспрашивать пользователя
  plan_enter: "deny"              # саб-агентам нельзя входить в план
  plan_exit: "deny"               # саб-агентам нельзя выходить из плана

  # Внешние директории
  external_directory:
    "*": "ask"                    # любые внешние файлы — спросить
    "/tmp/*": "allow"             # кроме tmp

  # Чтение файлов
  read:
    "*": "allow"
    "*.env": "ask"                # .env — всегда спрашивать
    "*.env.example": "allow"      # .env.example — можно
    "**/credentials.*": "deny"    # credentials файлы — никогда

  # Редактирование (переопределяется в plan mode)
  edit:
    "*": "deny"                   # plan mode: ничего не трогаем
    ".synth/plans/*.md": "allow"  #   кроме plan-файла
```

**Три уровня действия (action):**

| Action | Поведение | Пример |
|---|---|---|
| `allow` | Выполняется без спроса | `read: "*": "allow"` |
| `deny` | Блокируется с пояснением причины | `edit: "*.env": "deny"` |
| `ask` | Показывается пользователю на подтверждение | `external_directory: "*": "ask"` |

**Наследование саб-агентами:** саб-агент получает permissions родительской сессии + свои deny-правила (edit-ограничения от plan mode родителя) + блокировку `question`, `plan_enter`, `task`. Реализуется через `deriveSubagentSessionPermission()` по аналогии с OpenCode.

**«Разрешить в сессии» (once:false):** при ответе пользователя на `ask` с `once:false` в сессию добавляется allow-правило для тула — повторные вызовы не спрашивают. `once:true` — разрешение только на один вызов.

**Deny от пользователя:** при отказе (ask → deny) обработка завершается (`stopped_by_deny`), файл не создаётся, промежуточные результаты сохраняются в истории.

**Саб-агенты:** проходят permission-check; `ask` публикуется в родительскую сессию (`permission.asked`), ответ пользователя применяется к дочерней сессии.

**MCP-инструменты:** доступность по режимам plan/act — `SessionSettings.mcpToolSettings[server].default|tools[tool] = { plan, act }` (настройки в UI). В текущем режиме недоступный тул → deny.

### AD-030: Hooks для событий агента

**Решение:** система хуков на ключевые события жизненного цикла агента. На основе Claude Code (20+ событий), адаптированная под архитектуру Synth.

**Контекст:** у Claude Code — богатейшая система: PreToolUse, PostToolUse, Notification, Stop, PreCompact и 15+ других. У OpenCode — только `plugin.trigger("experimental.chat.system.transform")`. Synth реализует модель Claude Code на своей Plugin SDK.

**События:**

| Событие | Момент | Контекст | Назначение |
|---|---|---|---|
| `pre_tool_use` | Перед вызовом тула | `{tool, input, agent}` | Валидация, аудит, блокировка опасных команд |
| `post_tool_use` | После выполнения тула | `{tool, input, output, duration}` | Логирование, метрики, алертинг |
| `session_start` | Создание сессии | `{session_id, project, agent}` | Инициализация контекста, загрузка memory |
| `session_end` | Завершение сессии | `{session_id, summary, usage}` | Очистка, сохранение контекста, нотификация |
| `plan_approved` | План утверждён | `{plan_path, plan_content}` | Запуск verification, CI хуки, оповещение команды |
| `plan_rejected` | План отклонён | `{plan_path, reason?}` | Нотификация, возврат в plan mode |
| `agent_spawned` | Запуск саб-агента | `{agent_id, agent_type, parent_id}` | Настройка окружения, мониторинг |
| `agent_completed` | Саб-агент завершён | `{agent_id, result, usage}` | Сбор результатов, цепочка dependent tasks |
| `agent_failed` | Ошибка саб-агента | `{agent_id, error, retries}` | Алертинг, автоматический ретрай |
| `permission_denied` | Отказ в доступе | `{tool, input, reason}` | Аудит безопасности, оповещение ИБ |

**Регистрация через Plugin SDK:**

```typescript
// plugin.ts
export default function myPlugin(synth: SynthPlugin) {
  synth.hooks.on('pre_tool_use', async (ctx) => {
    if (ctx.tool === 'bash' && ctx.input.includes('rm -rf')) {
      return { block: true, reason: 'Потенциально опасная команда' }
    }
  })

  synth.hooks.on('post_tool_use', async (ctx) => {
    await metrics.increment(`tool.${ctx.tool}`, { duration: ctx.duration })
  })

  synth.hooks.on('plan_approved', async (ctx) => {
    await slack.notify(`План утверждён: ${ctx.plan_path}`)
    await ci.triggerVerification(ctx.session_id)
  })
}
```

**Важно:** хуки не должны блокировать основной поток. Для тяжёлых операций (CI, нотификации) — асинхронный fire-and-forget с таймаутом.

### AD-031: Verification синт

**Решение:** встроенный синт `verifier`, запускаемый автоматически после завершения реализации. Аналог VerificationAgent из Claude Code, адаптированный под архитектуру Synth.

**Поведение:**
- Запускается через hook `plan_approved` или вручную пользователем
- **Read-only** — не модифицирует проект (edit → deny, можно писать только в `/tmp`)
- Проверяет: билд, тесты, линтеры, typecheck
- Применяет **адверсальные пробы**: граничные значения, конкурентные запросы, идемпотентность
- Выносит вердикт: `VERDICT: PASS` / `FAIL` / `PARTIAL`
- `PARTIAL` — только когда проверка физически невозможна (нет тестов, сервер не стартует)

**Стандартный промпт** (адаптирован из Claude Code):

```
Ты verification specialist. Твоя задача — НЕ подтвердить что всё работает,
а ПОПЫТАТЬСЯ СЛОМАТЬ.

1. Прочитай план реализации из .synth/plans/ — это критерий успеха
2. Запусти build, полный test suite, linter, typecheck
3. Примени стратегию проверки под тип изменений:
   - Frontend: подними dev server → проверь через браузер → curl API
   - Backend: curl/fetch endpoints → проверь response shapes → error handling
   - Bug fix: воспроизведи баг → проверь фикс → регрессия
4. Адверсальные пробы (выбери подходящие):
   - Конкурентность: параллельные запросы → дубликаты? потерянные записи?
   - Граничные значения: 0, -1, "", очень длинные строки, unicode
   - Идемпотентность: повтори мутирующий запрос → дубликат создался?
5. Каждый чек: Command run + Output observed + Expected vs Actual
6. Финальная строка: VERDICT: PASS | FAIL | PARTIAL

Ты не подтверждаешь что код работает. Ты доказываешь что он НЕ работает.
```

**Интеграция в цикл:**

```
plan_exit (план утверждён)
  │
  ├─→ hook: plan_approved
  │     └─→ spawn verifier (background)
  │
  ├─→ исполнитель начинает работу по плану
  │
  └─→ verifier завершается
        ├─ PASS → результат принят
        ├─ FAIL → уведомление + возврат исполнителю
        └─ PARTIAL → только то что смогли + список не покрытого
```

**Почему не просто тесты:** тесты для реализации пишет та же LLM. Verification синт — независимая вторая пара глаз со свежим контекстом.

### AD-032: Хранение истории сессий

**Решение:** нормализованная модель «сессия → сообщения → части» с parent-child связями.

**Контекст:** Claude Code хранит историю в плоских JSONL-файлах (`~/.claude/transcripts/{sessionId}.jsonl`), саб-агенты — в sidechain. Это просто, но не даёт parent-child связей и запросов между сессиями. OpenCode использует нормализованную модель с parent_id — лучшая основа для командной работы.

**Логическая модель:**

```
Сессия (id, parent_id, project_id, agent, title, ...)
  │
  ├── parent_id → Сессия (parent-child дерево)
  ├── plan_path → путь к plan-файлу
  ├── branch_point → точка развилки для дочерних веток
  │
  └─1:N──→ Сообщение (id, session_id, seq, role, content, origin, source_msg_id, ...)
              │
              ├── seq — порядковый номер, уникален внутри сессии
              ├── origin: local | inherited | merged | crosspost
              ├── source_msg_id → Сообщение (откуда пришло)
              │
              └─1:N──→ Часть (id, message_id, type, data)
                          ├── type: text | tool_use | tool_result | reasoning
                          └── data — содержимое блока
```

**Ключевые сущности:**

| Сущность | Назначение |
|---|---|
| **Сессия** | Контейнер диалога. Имеет `parent_id` — дерево сессий. Хранит `agent`, `plan_path`, `branch_point` |
| **Сообщение** | Одна реплика (user/assistant/tool/system). Имеет `seq` — порядок внутри сессии. Имеет `origin` — откуда пришло |
| **Часть (part)** | Блок контента внутри сообщения: text, tool_use, tool_result, reasoning. Одно сообщение → много частей |
| **context_snapshot** | Сжатый контекст для summary-режима саб-агентов. Создаётся через отдельный LLM-вызов |

**Origin tracking — отслеживание происхождения сообщения:**

| origin | Как попало в сессию | source_msg_id |
|---|---|---|
| `local` | Создано в этой сессии (дефолт) | NULL |
| `inherited` | Унаследовано от родительской сессии (ветвление) | ID оригинального сообщения |
| `merged` | Скопировано из другой сессии пользователем (smart paste) | ID оригинального сообщения |
| `crosspost` | Существует в нескольких сессиях одновременно | Синхронизировано |

**Способы хранения (физический уровень — отдельное решение):**
- Локально: SQLite (одна embedded БД, не требует сервера)
- Командный режим: PostgreSQL (через drizzle — смена драйвера)
- Вариант: JSON-файлы с индексацией (как сейчас в прототипе)

### AD-033: Ветвление сессий и межсессионное слияние

**Решение:** три слоя наследования истории + операция слияния по инициативе пользователя.

**Контекст:** OpenCode поддерживает parent-child через `parent_id` и `ForkInput`, но fork копирует все сообщения целиком и не поддерживает слияние. Claude Code передаёт контекст саб-агента через копирование `initialMessages` в runtime. Synth добавляет: ветвление без копирования данных, ссылочное наследование, и ручной merge по инициативе пользователя.

#### Слой 1: Результаты саб-агента → в основную сессию

**Как сейчас:** результат возвращается через `tool_result`. Родитель видит итоговый ответ, но не видит промежуточных шагов (tool_use, tool_result, reasoning).

```
Родитель:
  tool_use → task({prompt: "исправь auth.ts"})
  tool_result ← "<task id='ses_child' state='completed'>
                   <task_result>Готово, починил в validate.ts:42</task_result>
                 </task>"
```

**Это ок для MVP.** Промежуточные шаги доступны в дочерней сессии при необходимости.

#### Слой 2: Наследование контекста (ветвление)

При запуске саб-агента с `--context inherit` или `--context summary` — создаётся дочерняя сессия:

```
ses_main (родитель)
  ├── msg_1..msg_42 — родительская история
  └── ses_branch (дочерняя, parent_id=ses_main, branch_point=msg_42)
        ├── msg_1..msg_42 — унаследованы (origin=inherited, ссылки на ses_main)
        ├── msg_43 — origin=local, prompt саб-агента
        └── msg_44..50 — origin=local, работа саб-агента
```

**Экономия:** не дублируем содержимое сообщений — храним ссылки на оригинал через `source_msg_id`.

#### Слой 3: Межсессионное слияние (по инициативе пользователя)

**Сценарий:** пользователь провёл анализ в сессии A, хочет передать выводы в сессию B (где коллега ведёт разработку).

Три способа:

**a) Smart paste — копирование сообщений**

```bash
# В сессии A: выбрать сообщения для копирования
synth msg select 4..8
synth msg copy 4..8

# В сессии B: вставить
synth msg paste --after last
synth msg paste --before 3
synth msg paste --summarize    # сжать через LLM перед вставкой
```

Механика: копирует выбранные сообщения в целевую сессию с `origin='merged'`, `source_msg_id=<original>`. `--summarize` прогоняет через быструю модель для компрессии.

**b) Ссылочный блок — вставка без копирования**

```bash
synth ref ses_analysis:4..8   # вставить ссылку на диапазон сессии
```

В сессию B добавляется attachment:

```json
{
  "type": "session_reference",
  "session_id": "ses_analysis",
  "label": "Выводы по auth модулю",
  "range": [4, 8],
  "auto_summary": "Анализ auth модуля. Найден null pointer в validate.ts:42..."
}
```

Модель видит ссылку и может прочитать referenced-сессию через tool call. **Не тратит токены** на вставку больших блоков.

**c) Crosspost — параллельное связывание**

```bash
synth crosspost ses_analysis:4..8 --to ses_dev --label "Выводы по auth"
```

Сообщение существует в обеих сессиях с `origin='crosspost'`. Обновление в одной — видно в другой. Для параллельных веток одного исследования.

**Таблица: операции слияния**

| Операция | Инициатор | Источник → Цель | Что происходит |
|---|---|---|---|
| **subagent result** | Система (авто) | Дочерняя → Родительская | Итог через `tool_result`. Промежуточные шаги НЕ копируются |
| **smart paste** | Пользователь | Любая → Любая | Копирование сообщений с `origin='merged'`. Опционально `--summarize` |
| **reference** | Пользователь | Любая → Любая | Ссылочный блок, модель читает через tool call. Не копирует данные |
| **crosspost** | Пользователь | N ↔ M | Сообщение в нескольких сессиях, синхронизация изменений |

**Реализация merge (smart paste):**

```typescript
async function mergeMessages(
  targetSessionId: SessionID,
  sourceSessionId: SessionID,
  options: {
    sourceRange: [number, number],    // какие seq копировать
    position: 'after' | 'before',
    anchorMsgId?: MessageID,          // после/перед какого сообщения
    summarize?: boolean,              // сжать через LLM
    model?: string,                   // модель для саммаризации
  }
): Promise<MessageID[]> {
  // 1. Прочитать source-сообщения
  // 2. Если summarize — сжать через LLM в одно сообщение
  // 3. Пересчитать seq в target (раздвинуть)
  // 4. Вставить с origin='merged', source_msg_id
}
```

**Порядок реализации:**
1. Базовое хранение: логическая модель сессия + сообщение + часть
2. Ветвление: parent_id + branch_point + наследование через ссылки
3. Subagent result — через tool_result (без изменений)
4. Reference — ссылочные блоки между сессиями
5. Smart paste — копирование сообщений по инициативе пользователя
6. Crosspost — синхронизация между сессиями

### Модель Runner

Раннер — мост между бэкендом и движками. Два режима: локальный (прямой доступ к ФС) и облачный (K8s pod, per-user).

Движки — stateless: история на бэкенде, на вход получают историю + новое сообщение + контекст.

### AD-034: Routing между моделями

**Решение:** Router-слой между синтом и LLM — три стратегии: content-based, escalation by confidence, cost-aware.

**Контекст:** разные модели имеют разную специализацию и стоимость. Небольшие fine-tuned локальные модели работают быстро и лучше разбираются в конкретной области, облачные большие модели сильнее в логике и рассуждениях, большие локальные модели — баланс между скоростью и стоимостью. Выбор правильной модели на этапе запроса даёт выигрыш в качестве без удорожания. Мультимодальные модели - стоимость больше, но распознавание картинок нужно не в каждом запросе.

**Три стратегии роутинга:**

| Стратегия | Суть | Когда срабатывает |
|---|---|---|
| **Content** | Тип запроса → выбор модели | Кодинг → DeepSeek, сленг → Qwen, исследование → Gemma |
| **Confidence** | Quality check → FAIL → эскалация | Неуверенный или невалидный ответ Qwen → DeepSeek |
| **Cost** | Простые запросы → дешёвая, сложные → дорогая | < 10 слов → Qwen, > 50 слов → DeepSeek/MiniMax |

**Архитектура Router:**

```
Request
  │
  ▼
┌──────────────────────────────────────────────┐
│  Router                                        │
│  ┌──────────────┐  ┌────────────────────────┐ │
│  │  Content      │  │  Provider Pool          │ │
│  │  Classifier   │──│  ├─ Qwen3-4B (local)   │ │
│  └──────┬───────┘  │  ├─ DeepSeek (API)      │ │
```

### AD-035: Micro-model first — дешёвый слой перед LLM

**Решение:** двухуровневый каскад: **микро-модель** (правила / embedding / словарь) обрабатывает запрос первой и зовёт LLM только при неуверенности. LLM — не дефолт, а fallback.

**Контекст:** большинство запросов к LLM на самом деле простые и структурируемые (классификация, интент, извлечение полей, enum-решения). Гонять их через большую модель — тратить токены и время. Двухуровневый каскад отсекает 60-80% трафика до LLM.

**Архитектура:**

```
Запрос
  │
  ▼
┌──────────────────────────────────┐
│  Уровень 1: MICRO-MODEL           │
│  (правила / словарь / embeddings) │
│  → структурированный результат    │
│  → enum / label / score           │
│  → confidence: OK | UNSURE        │
└──────┬───────────────────────────┘
       │
  ┌────┴────┐
  │         │
 OK        UNSURE
  │         │
  │    ┌────▼─────────────────────┐
  │    │  Уровень 2: LLM fallback  │
  │    │  → маршрутизация (AD-034) │
  │    │  → верификация результата │
  │    └────┬─────────────────────┘
  │         │
  ▼         ▼
 Ответ    Ответ + метка "fallback"
без LLM
```

**Требования к микро-модели:**
- Возвращает **структурированный результат**: `{label: enum, confidence: 0.0-1.0}`
- Возвращает **статус уверенности**: `OK` (порог пройден) или `UNSURE`
- Работает **без вызова LLM** (0 токенов)

**Варианты реализации микро-модели (по возрастанию сложности):**

| Вариант | Скорость | Стоимость | Когда использовать |
|---|---|---|---|
| **Правила + словарь** | мс | 0 | Классификация по ключевым словам, форматные проверки |
| **Embedding-классификатор** (sentence-transformers) | ~50 мс | 0 (локально) | Семантика: интенты, темы, похожесть |
| **Микро-LLM** (1-3B, local) | ~0.5 с | ~0 | Контекстные решения, когда правил мало |

**Логика confidence:**

```
confidence >= 0.8  → OK     → ответ без LLM
confidence < 0.8   → UNSURE → fallback на LLM
формат невалиден    → UNSURE → fallback на LLM
```

Порог конфигурируется per-task.

**Интеграция с AD-034 (routing):**

```
Запрос
  │
  ├─ AD-035: Micro-first
  │     ├─ OK → ответ (0 токенов)
  │     └─ UNSURE ↓
  ├─ AD-034: Routing
  │     └─ content/confidence/cost → выбор провайдера
  └─ LLM ответ
```

**Конфигурация (synth.yaml):**

```yaml
micro_first:
  enabled: true
  tasks:
    classify_intent:
      type: embedding       # rules | embedding | micro_llm
      model: local-embed    # для embedding
      confidence_threshold: 0.8
      labels: [bug, feature, question, spam]
    extract_fields:
      type: rules
      patterns:
        - email
        - phone
        - url
      confidence_threshold: 0.8
```

**Метрики (что логируем):**
- % запросов, обработанных микро-моделью (target: 60-80%)
- % fallback на LLM
- Средняя latency по уровням
- Стоимость токенов сэкономленная

**Реализация (2026-08-03):**

Код: `packages/core/src/engine/router/micro/`

```
micro/
├── index.ts              # MicroPipeline — каскад rules→embedding→micro_llm
├── types.ts              # MicroInput, MicroResult, PipelineResult
├── task-classifier.ts    # Классификация: small_talk | classify | enum_decision | llm_task
├── models/
│   ├── base.ts           # Интерфейс MicroModel
│   ├── rules-model.ts    # Правила + словарь (DictionaryStore), 0 токенов
│   ├── embedding-model.ts # Lazy import @huggingface/transformers
│   └── micro-llm-model.ts # Локальная LLM через ProviderPool
└── tasks/
    ├── small-talk.ts     # Приветствия / прощания / благодарности → готовый ответ
    ├── classify-intent.ts # Вопрос / команда / ревью / объяснение → label + confidence
    └── enum-decision.ts  # Да / нет / режим → enum + score
```

**Включение:** `session.microFirst: true` (в Settings сессии или config.yaml). По умолчанию `false` — обратная совместимость.

**Каскад:** rules (0 токенов, ~1 мс) → embedding (~50 мс, ленивый импорт) → micro_llm (~0.5 с, локальная) → LLM fallback через AD-034.

**Метрики:** в DebugCollector (`micro.handled`, `micro.fallback`, `micro.latency_by_model`).

**Бенчмарк:** `npx tsx scripts/micro-benchmark.mjs` — 25 запросов, таблица результатов + сводка.

**Что не делаем в демо:**
- Обучение кастомных микро-моделей (берём готовые embeddings)
- Динамический подбор порога (фиксированный per-task: 0.8)

### AD-036: LLM Gateway — независимый слой безопасности ✅ Реализовано

**Решение:** декоратор `GatewayProvider extends BaseProvider` в `@synth/core`, оборачивающий все LLM-вызовы (покрывает 11 точек: tool-loop, fallback-эскалация, debug, суммаризация, auto-title, саб-агенты, micro-LLM). Защита данных: детекция секретов, обфускация, деобфускация в точках потребления, rate limiting, аудит и cost tracking. Полностью независимый компонент — не связан с выбором модели, маршрутизацией или фильтрацией запросов. **HTTP-прокси не нужен** — весь LLM-трафик in-process, backend/runner получают gateway «бесплатно» через `ChatOrchestrator`.

**Контекст:** промпты и ответы агентов могут содержать секреты (API-ключи, токены, карты, email). При прямом вызове LLM-провайдера секрет уходит наружу и оседает в логах провайдера. Gateway перехватывает трафик и не допускает утечки, при этом пользователи продолжают работать со своими данными внутри доверенной зоны.

**Принципы:**
- **Выключен по умолчанию.** Весь слой защиты — опция. Пока не включён — трафик идёт напрямую, без задержек.
- **Если включён — по умолчанию обфусцируем**, а не блокируем. Блокировка — отдельный режим.
- **Независимость.** Работает на уровне «запрос → провайдер → ответ → потребление».
- **Наследование секретов.** Карта обфускации живёт в сессии независимо от глобального тумблера — после отключения шлюза старые плейсхолдеры остаются раскрываемыми.

**Точка перехвата:** `ProviderPool.getProvider` + `orchestrator._getProvider/_routeProvider` оборачивают провайдер в `GatewayProvider`. Если шлюз выключен — возвращается оригинальный провайдер без изменений (обратная совместимость).

**Два режима Input Guard:**

| Режим | Поведение |
|---|---|
| **obfuscate** (default при включении) | Секрет заменяется на `⟦SYNTH_SECRET_N⟧`, карта сохраняется, запрос идёт в LLM |
| **block** | Секрет найден → запрос блокируется, возвращается warning, в LLM ничего не уходит |

**Плейсхолдер:** `⟦SYNTH_SECRET_N⟧` (юникод-скобки U+27E6/27E7 + префикс `SYNTH_`). Выбран вместо `{{SECRET_N}}` — двойные фигурные скобки конфликтуют с шаблонными движками (Mustache/Handlebars/Vue), юникод-скобки не встречаются в коде. Regex: `⟦SYNTH_SECRET_(\d+)⟧`.

**Обфускация:**

```
Вход:  "мой ключ sk-abc123 используй для подключения"
       ↓ obfuscate (карта: ⟦SYNTH_SECRET_1⟧ → sk-abc123)
       "мой ключ ⟦SYNTH_SECRET_1⟧ используй для подключения"
       ↓ LLM
Ответ: "Подключение с ⟦SYNTH_SECRET_1⟧ установлено"
       ↓ деобфускация НЕ в стриме, а в точках потребления
```

**Карта обфускации (словарь):**
- Хранится в **`Session.obfuscationMap`** (`Record<string, string>`), сериализуется в `FileStore` как `obfuscation_map`. Живёт всю сессию, не теряется.
- Сама карта — секрет: доступ только у админов и аудиторов (вкладка «Словарь обфускации» в правой панели UI).
- Сгенерированные моделью `⟦SYNTH_SECRET_N⟧` (которых нет в карте) — **не восстанавливаются**.

**Отображение в UI:**
- В ответе и в сообщениях пользователя секрет отображается как плейсхолдер `⟦SYNTH_SECRET_N⟧` — бейдж `SecretPlaceholder`.
- Реальные значения встраиваются в `message.metadata.secrets` — клик раскрывает локально.
- Раскрытие логируется в аудит (`type: revealed`).

**Деобфускация — только в точках потребления:**

| Точка | Когда |
|---|---|
| Запись файла | Перед write_file/edit_file — restore |
| Shell-команда | Перед exec — restore аргументов |
| Веб-запрос | Перед web_fetch/web_search — restore url/query |
| Git-операции | Перед exec — restore |
| Поиск | Перед grep — restore |
| MCP-вызов | Перед callTool — restore аргументов |

Стриминг ответа идёт как есть (с плейсхолдерами) — никаких буферов и задержек. Деобфускация только на финальном собранном ответе (chat) и в точках потребления.

**Output Guard:**
- Детекция секретов в ответе модели (галлюцинированные ключи, extraction-попытки) — пишется в аудит `output_guard`
- Подозрительные URL и команды

**Rate Limiting:**
- **Индивидуальный** — N запросов/мин на пользователя (`rateLimit.userPerMinute`)
- **Общий** — M запросов/мин на провайдера (`rateLimit.providerPerMinute`, защита от исчерпания квоты)
- Реализация: in-memory sliding window на уровне провайдера в core — покрывает и внутренние LLM-вызовы (суммаризация, auto-title, саб-агенты), а не только HTTP-запросы

**Аудит и Cost:**
- Хранение: **JSONL-файл** `{dataDir}/audit/llm-gateway.jsonl`, append-only, одна строка = одна запись (атомарный append, tail-friendly)
- Просмотр: `GET /api/v2/audit` (RBAC ADMIN/AUDITOR, фильтры `userId/sessionId/since/until/limit`) + CLI `synth audit`
- Формат записи: `{ts, type, sessionId, userId, provider, model, secretsFound, placeholders, tokensIn, tokensOut, costUsd, reason}`. Типы: `obfuscated`, `blocked`, `revealed`, `rate_limited`, `output_guard`
- Секреты в логах — только как плейсхолдеры
- Cost-трекинг: счётчики `inputCost/outputCost` в `_saveAssistantMessage`

**Конфигурация:**

```yaml
# config.yaml
llmGateway:
  enabled: false          # выключен по умолчанию
  inputMode: "obfuscate"  # obfuscate | block
  rateLimit:
    userPerMinute: 60
    providerPerMinute: 120
  audit:
    enabled: true
    logPath: ""           # по умолчанию {dataDir}/audit/llm-gateway.jsonl
```

- Глобальный тумблер вкл/выкл: секция «Шлюз безопасности» в настройках UI (только ADMIN)
- Per-session override — не требуется, тумблер глобальный

**Реализация:** каталог `packages/core/src/engine/gateway/` (`secret-detector.ts`, `obfuscator.ts`, `input-guard.ts`, `output-guard.ts`, `rate-limiter.ts`, `audit-logger.ts`, `gateway-provider.ts`, `obfuscation-map-store.ts`).

**Что не делаем в демо:**
- ML-детекция секретов (только regex)
- Распределённый rate limit (per-process)

### AD-037: Security step перед коммитом

**Решение:** гарантированная security-проверка между генерацией кода и коммитом. Три слоя: инструмент `git_commit` с security-сабагентом (основная проверка), git pre-commit hook с маркером-хешем (железная гарантия), автоустановка хука при открытии сессии. Управляется настройками, по умолчанию включено.

**Контекст:** LLM-агент недетерминирован — нельзя полагаться, что он вызовет security-сабагента перед коммитом или не закоммитит через shell в обход инструмента. Гарантию даёт не агент, а уровень git: pre-commit hook, который невозможно обойти, потому что он срабатывает при любом `git commit` — и через инструмент, и через shell.

**Принципы:**
- **По умолчанию включено.** Контроль безопасности репозиториев активен, пока не выключен в настройках
- **Настройка:** глобальный тумблер вкл/выкл (только ADMIN), аналогично шлюзу безопасности
- **Гарантия на уровне git**, а не на уровне агента

**Три слоя:**

```
agent
 ├─ git_commit (инструмент)
 │    ├─ вызывает security-сабагента
 │    ├─ Critical/High → возврат на генерацию с фидбеком
 │    ├─ Medium/Low → пропуск с warning в логе
 │    ├─ OK → пишет маркер .synth/security-checked.json
 │    │       { hash: sha256(staged files), verdict, timestamp }
 │    └─ коммит
 │
 ├─ shell: git commit ← даже если пойдёт сюда, git запустит hook!
 │
 ▼
git pre-commit hook (уровень git, обойти нельзя)
 ├─ считает sha256 staged-файлов
 ├─ сравнивает с маркером
 ├─ совпало  → коммит разрешён
 └─ не совпало → БЛОК + stderr:
       "SECURITY CHECK REQUIRED: run /security-check before commit"
       (агент видит это как ошибку git commit → обязан отреагировать)
```

**Маркер-хеш (самопротухающий флаг):**

| Поле | Назначение |
|---|---|
| `hash` | sha256(staged files) — что именно проверяли |
| `verdict` | PASS / WARN (Medium/Low) |
| `timestamp` | когда проверяли |

Инвалидация **автоматическая**: любое изменение файлов после проверки меняет хеш → hook считает проверку недействительной. Никто не снимает флаг вручную — он самопротухает фактом изменения кода.

**Автоустановка хука:**

```
Открытие сессии в проекте
  → раннер сканирует проект на git-репозитории (их может быть несколько)
  → для каждого: проверяет наличие .git/hooks/pre-commit
  → если нет — устанавливает guard
  → генерирует событие repo.guard_installed / repo.guard_ok для каждого репозитория
```

Установка не зависит от воли LLM — выполняется системой при старте сессии. Хук самодостаточен: живёт в `.git/hooks/`, работает при каждом коммите, не требует запущенного агента.

**Инструмент `repo_setup` (переустановка):**
- Для случаев, когда репозиторий появился после старта сессии (агент клонировал новый)
- Переустановка guard, если он был удалён
- Ручной контроль: `synth repo guard install`

**Закрытие обходов:**

| Обход | Что ловит |
|---|---|
| Агент не вызвал сабагента | Маркера нет → hook блокирует |
| Агент закоммитил через shell | Hook срабатывает — он на уровне git |
| Файлы изменены после проверки | Хеш не совпал → маркер протух → блок |
| Несколько репозиториев в проекте | Guard ставится в каждый при старте сессии |

**Без дублирования:** hook не вызывает LLM — он только считает sha256 (микросекунды) и сравнивает с маркером. Проверка одна (в инструменте `git_commit`), hook лишь удостоверяет артефакт.

**Статическая часть hook (опционально):**
- gitleaks / secret-scan / eslint-security — детерминированные проверки без LLM
- Выполняются мгновенно вместе с проверкой маркера

**Порядок реализации:**
1. Инструмент `git_commit` + security-сабагент (основная проверка)
2. Маркер `.synth/security-checked.json` + запись после проверки
3. Pre-commit hook: sha256 staged → сравнение → блок/разрешение
4. Автоустановка при старте сессии + события `repo.guard_*`
5. Инструмент `repo_setup` для переустановки
6. Настройка: глобальный тумблер (по умолчанию включено)
7. Тесты: 3 задачи с небезопасным кодом (токен, логирование, API-запрос)

**Что не делаем в демо:**
- Фильтры shell-команд (`bash: "git commit*": deny`) — расширение AD-029, отдельной задачей
- Статический анализ в hook (gitleaks) — опционально, по желанию
- Подпись маркера ключом (достаточно хеша)

### AD-038: Монорепо как набор публикуемых npm-пакетов ✅ Реализовано

**Решение:** каждый пакет монорепозитория публикуется в npm независимо и владеет

транзитивные npm-зависимости. Никакого дублирования файлов и бандла core внутрь CLI.

**Контекст:** исторически `@itphx/synth` собирался как самодостаточный пакет —
скрипт сборки через `cp -r` копировал в него промпты, собранный UI, docs и README
из соседних пакетов, а `cli.js` бандлил core через `noExternal`. Это порождало
несколько источников истины: одни и те же файлы (промпты, UI-ассеты, документация)
существовали и в `packages/core`, и в `packages/ui`, и в `packages/synth`. Любая
правка промпта требовала пересборки и перекопирования, а рассинхронизация копий
давала трудноуловимые баги. Кроме того, бандл core внутрь `cli.js` раздувал пакет
и ломал дерево зависимостей для npm-потребителей.

**Решение:**

```
@synth/shared  ←  только контракты (types/schemas/protocols/config)
       ↑
@synth/core    ←  владеет prompts/, dictionaries/, definitions/ (files)
       ↑
┌──────┴──────┐
@synth/backend │ @synth/ui   ←  core и ui владеют своими ассетами
@synth/runner (in-process)
       ↑
@itphx/synth   ←  тонкая обёртка: dependencies = core + ui + shared
                  bin: synth → dist/cli.js (external: core/ui/shared)
```

**Принципы:**
- **Каждый пакет владеет своими ассетами.** Ассеты перечислены в поле `files`
  (`dist`, `prompts`, `dictionaries` и т.д.) и доставляются через npm.
- **`@itphx/synth` — тонкая обёртка.** В `dependencies` — только `@synth/core`,
  `@synth/ui`, `@synth/shared` (и runtime-библиотеки). Сборка tsup помечает
  `@synth/*` как `external` — core **не** бандлится в `cli.js`.
- **Никакого копирования ассетов.** `cp -r prompts`, `cp -r ui/dist`, копирование
  README/docs при сборке synth — удалены. В репозитории больше нет идентичных файлов.
- **Резолвинг из node_modules.** `@synth/core` находит свои промпты по
  `{packageRoot}/prompts` (поиск package.json вверх от `import.meta.url`, fallback
  на `dist/prompts` для Docker). `@itphx/synth` резолвит собранный UI через
  `require.resolve('@synth/ui/package.json')` → `dist/`.
- **Docker из npm-публикации.** Образ ставит `npm install -g @itphx/synth@<version>`,
  зависимости резолвятся npm-ом — не из workspace-сборки.

**Порядок публикации** (строгая иерархия зависимостей):

```
shared → core → ui → backend → runner → synth
```

**`pnpm publish` вместо `npm publish`:** `npm publish` не переписывает
`workspace:*` в зависимостях — опубликованные пакеты падают у npm-потребителей
(не резолвится `workspace:*`). `pnpm publish` автоматически заменяет
`workspace:*` на фактические версии workspace-пакетов, поэтому используется именно
он (с флагом `--no-git-checks`, т.к. публикация идёт не из чистого git-дерева).

**Реестры:**
- npmjs.org: `https://registry.npmjs.org` (токен `NPM_TOKEN`)
- GitVerse: `https://gitverse.ru/api/packages/itphx/npm/` (токен `GV_TOKEN`)

**Что не делаем:**
- Не публикуем workspace-сборку как единый артефакт — только npm-пакеты
- Не копируем ассеты между пакетами при сборке
- Не используем `noExternal`-бандл core/ui/shared в `@itphx/synth`

### Отказ от JSON-блока

Механизм JSON-блока (модель возвращает JSON со статусом в конце ответа) не перенесён из прототипа. Причины: хрупкий парсинг, трата токенов, загрязнение промпта. Замена: Tool Use / Function Calling, TSM управляется бэкендом.

## Аутентификация

Все запросы к API (кроме `GET /health`) аутентифицированы. 401 для неаутентифицированных.

Роли: `ADMIN`, `USER`, `LEAD`, `AUDITOR`. Middleware: `requireAuth`, `requirePermission`.

### Режимы

| Режим | Где | Когда | Механизм |
|-------|-----|-------|----------|
| Debug | backend | `SYNTH_AUTH_DEBUG=true` | Тестовые ключи (admin-key-123, user-key-456, lead-key-789, auditor-key-012) |
| API Key | backend | Продакшен без OIDC | Один `SYNTH_API_KEY` → роль ADMIN |
| OIDC | backend | Продакшен с Keycloak | JWT + cookie `user_session` |
| Local | core | `synth serve --api-key` | Один ключ → роль USER |

Auth middleware — первый в цепочке после CORS/logging.

## Сборка и публикация

### Скрипты (в корне `/Agent/dev/Synth/`)

| Скрипт | Назначение |
|--------|------------|
| `build.sh` | Полная сборка: shared → core → ui → synth. Опции: `--clean`, `--check`, `--docker`, `--docker-tag=X` |
| `publish.sh` | Публикация в npm. Опции: `--dry-run`, `--no-build`, `--registry=both\|npmjs\|gitverse`, `--docker` |
| `version-bump.sh` | Bump версии: `./version-bump.sh patch\|minor\|major\|X.Y.Z`. Обновляет `version.ts` + все `package.json` |
| `dev.sh` | Dev-запуск: backend (:5000) + UI (:5002). Аргументы: `backend\|ui\|core\|all` |

### Версионирование

Единая константа `SYNTH_VERSION` в `packages/shared/src/version.ts`.
Текущая версия: из `packages/synth/package.json`.

При bump-е версии обновляются:
1. `packages/shared/src/version.ts` — константа `SYNTH_VERSION`
2. `packages/*/package.json` — поле `version` во всех 6 пакетах

Все hardcoded строки версии в коде заменены на импорт `SYNTH_VERSION` из `@synth/shared`.

### Публикация npm

Публикуются **все 6 пакетов** монорепозитория в строгом порядке зависимостей:

```
shared → core → ui → backend → runner → synth
```

Для публикации используется **`pnpm publish`** (а не `npm publish`), т.к. он
автоматически переписывает `workspace:*` в зависимостях на фактические версии
workspace-пакетов — опубликованные пакеты корректно резолвятся npm-потребителями.

Два реестра:
- `https://registry.npmjs.org` — токен `NPM_TOKEN`
- `https://gitverse.ru/api/packages/itphx/npm/` — токен `GV_TOKEN` (единый для всего GitVerse)

### Docker

Образ собирается из npm-публикации: `npm install -g @itphx/synth@<version>`
(зависимости `@synth/core`/`@synth/ui`/`@synth/shared` ставятся как транзитивные
npm-зависимости, промпты и UI резолвятся из node_modules) — **не** из
workspace-сборки. Образ: `registry.gitverse.ru/itphx/synth:<version>` (latest).
Токен: `GV_TOKEN`.

## CI/CD (GitVerse)

### Workflow-файлы

| Файл | Назначение | Триггер |
|------|------------|---------|
| `.gitverse/workflows/ci.yaml` | CI: typecheck, lint, тесты | `push`, `pull_request` |
| `.gitverse/workflows/release.yaml` | Релиз: bump, сборка, npm, Docker, Release | `workflow_dispatch`, `push tags v*` |

### Секреты (настроены в репозитории)

| Secret | Назначение |
|--------|------------|
| `NPM_TOKEN` | Публикация в npmjs.org |
| `GV_TOKEN` | Единый токен GitVerse (API, Docker Registry, npm registry, git push от бота) |

**Важно:** префикс `GITVERSE_` запрещён в именах секретов GitVerse. Использовать `GV_`.

### Особенности GitVerse CI

1. **`actions/setup-node@v4`** — не использовать. Вместо этого: `npm install -g pnpm@latest`
2. **`${{ env.VAR }}`** — не работает, резолвится в Go-строку `%!t(string=...)`. Значения хардкодить.
3. **`${...}` в inline bash** — GitVerse парсит как Go-шаблон, скрипт падает. Выносить сложный bash в отдельный файл (см. `scripts/changelog.sh`).
4. **`${GITHUB_REF_NAME}`** — синтаксис GitHub, в GitVerse: `echo "${{ gitverse.ref }}" | sed 's|refs/tags/v||'`
5. Версия Node.js в раннере: 22 (предустановлена).

### Порядок сборки в CI

```
pnpm install --frozen-lockfile
pnpm --filter @synth/shared build    # обязательно перед typecheck!
pnpm --filter @synth/core build      # нужно для backend и runner
pnpm typecheck                       # рекурсивно по всем пакетам
pnpm lint
pnpm test
```

Без сборки `shared` и `core` перед `typecheck` — `@synth/runner` и `@synth/backend` не найдут типы.

### Запуск релиза

1. Dry-run: `workflow_dispatch` с `dry_run: true` — проверка без публикации
2. Реальная публикация: `workflow_dispatch` с `dry_run: false`
3. Или вручную: создать тег `vX.Y.Z` и запушить — workflow запустится автоматически

### Локальная проверка перед пушем

```bash
pnpm typecheck && pnpm lint && pnpm test
```

## GitVerse MCP

### Подключение к opencode

Конфигурация в `~/.config/opencode/opencode.jsonc`:

```jsonc
"mcp": {
  "gitverse": {
    "type": "remote",
    "url": "https://mcp.gitverse.ru",
    "headers": {
      "Authorization": "Bearer <токен>"
    },
    "oauth": false,
    "enabled": true
  }
}
```

**Важно:** `"oauth": false` обязательно для GitVerse MCP (не поддерживает OAuth flow).
Изменения в `opencode.jsonc` требуют перезапуска opencode.

### Токен

Получить: `https://gitverse.ru/settings/tokens`
Права: для read-only достаточно «Чтение», для записи — «Запись».
