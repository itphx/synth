# Промпт независимого аудита релиза

Материал к `docs/security/AUDIT-CHECKLIST.md` и `docs/security/README.md`: процедура
запуска независимого аудита релиза агентом `release-auditor`
(`.opencode/agents/release-auditor.md`) — двумя независимыми моделями.

Аудит выполняется **вне контура релиза**: в отдельном клоне репозитория на коммите-кандидате,
с полной историей git (`secret-scan` и проверка «коммит записи аудита — предок релиза»
историю требуют). Запись аудита по итогам коммитит релиз-менеджер **до тега**.

Один и тот же текст (раздел «Текст промпта» ниже) подаётся двум моделям. Запускать
из корня клона репозитория `synth` на коммите-кандидате релиза, **с полной историей**
(`git clone`, не shallow) — `secret-scan` и проверка «коммит записи аудита — предок
релиза» историю требуют.

```bash
cd <clone>/synth
git log --oneline -1                     # убедиться, что вы на коммите-кандидате

# Текст промпта — раздел «Текст промпта» этого файла, сохранить в audit-prompt.txt
# (или скопировать оттуда и подставить <КОММИТ_SHA> и <ПРЕДЫДУЩИЙ_ТЕГ>)

# Аудит 1
opencode run --agent release-auditor -m minimax/MiniMax-M3.1-Flash "$(cat audit-prompt.txt)"

# Аудит 2 — тот же промпт, другая модель
opencode run --agent release-auditor -m opencode/deepseek-v4.1-flash "$(cat audit-prompt.txt)"
```

Модель в агенте **не закреплена** — она наследуется от сессии, поэтому `--model` выше
перекрывает её явно. Список доступных моделей: `opencode models`.

Агент работает read-only и не публикует наружу: права на `edit`/`write` запрещены, а
из `shell` отдельно запрещены `git commit`/`git push`/`git reset`/`git rebase`/
`git tag -a`/`rm`/`npm publish`/`pnpm publish`/`docker push`/`helm publish|install|upgrade`.
Запреты на уровне прав, а не только в тексте промпта.

## Текст промпта

```
Проведи независимый аудит безопасности релиза Synth.

ГРАНИЦЫ
- Кандидат релиза: <КОММИТ_SHA> (тот, на котором стоит тег релиза).
- Предыдущий опубликованный релиз: <ПРЕДЫДУЩИЙ_ТЕГ> (найди сам: git tag --sort=-v:refname).
- Дельта: git diff --stat <ПРЕДЫДУЩИЙ_ТЕГ> <КОММИТ_SHA>.
- Ожидаемый артефакт на выходе: вердикт APPROVE / APPROVE_WITH_EXCEPTIONS / BLOCK,
  находки по severity с file:line, ответы на семь вопросов §3 из
  docs/security/AUDIT-CHECKLIST.md, таблица выполненных проверок (команда → код
  выхода → наблюдаемый результат), список того, что ты не смог проверить, и готовый
  к вставке текст для checks.security-review.result записи аудита.

НЕЗАвисиСИМОСТЬ
Ты — не автор этого релиза. Если тебе покажут готовую запись аудита
(docs/security/releases/<version>.json), описание релиза (docs/releases/<version>.md)
или любой чужой разбор дельты — считай это УТВЕРЖДЕНИЯМИ, КОТОРЫЕ НАДО ПРОВЕРИТЬ,
а не фактами. Перепрогони проверки и сверь с кодом. Отсутствие находки в чужом отчёте
само по себе кандидат в находку: ищи участки, куда не смотрели (обработчики без
теста, маршруты вне негативной матрицы, allowlist-правила сканера, которые
подавляют слишком много, исключения с вялым followUp, ограничения, которые в коде
шире, чем заявлено).

ЧТО ПРОВЕРИТЬ (минимум)
1. Дельту релиза и семь вопросов §3 из docs/security/AUDIT-CHECKLIST.md — по каждому
   ответ с file:line и коммитами.
2. Классы уязвимостей: авторизация/IDOR (негативная матрица по всем маршрутам ресурса,
   проверка на границе, а не в хендлере), containment путей (realpath против
   лексического startsWith), SSRF/egress (все точки исходящих запросов, TOCTOU),
   секреты (дерево и вся история; allowlist сканера не должен скрывать настоящий
   секрет), инъекции, supply-chain (прямые и транзитивные, наличие patched_versions,
   и — отдельно — что заявленные блокирующие проверки действительно могут
   сработать), публичный контракт (OpenAPI/SDK/экспорты).
3. Гейт и запись аудита:
   node scripts/security-gate.mjs --version <VERSION> --ref refs/tags/v<VERSION> --skip-tests
   node scripts/security-gate.mjs --lint-records
   node scripts/secret-scan.mjs --mode worktree,commits,blobs
   Проверь не только схему, но и содержание: result описывает наблюдаемый результат
   команды; justification объясняет, почему риск приемлем; followUp — конкретное
   действие; dueRelease — достижимая дата; исключение не используется как «не успели».
4. Известные ограничения релиза: сверь каждое с кодом — точно ли оно описано,
   раскрыто ли в описании релиза (пользователь) и в записи аудита (аудитор), не
   маскирует ли оно большую проблему.

ОГРАНИЧЕНИЯ
Только чтение. Ничего не меняй, не коммить, не пушь, не тегируй. Не обращайся к
внешней сети. Не публикуй ничего наружу (npm/docker/helm publish). Найденное не
исправляй — только сообщи.

ВАЖНО
- Указывай и то, что проверил и не нашёл нарушений: «проверил X — нарушений нет»
  полезно и повышает доверие к отчёту.
- Не выдумывай: если не успел или не смог — помечай результат PARTIAL и говори, что
  именно не проверено.
- Если не согласен с выводом в чужом отчёте — так и напиши, с обоснованием.
- В конце дай готовый к вставке текст на русском для поля checks.security-review.result.
```

## Что делать с результатами

1. Сравнить два вердикта. Расхождения — предмет отдельного разбора; в запись аудита
   идёт **сводный** вывод, а расхождения перечисляются явно.
2. Формат записи: `docs/security/releases/<version>.json`, схема
   `synth.security.audit/v1` (см. `scripts/security-gate.mjs` → `validateRecord`).
   `auditor.name` — например `minimax M3.1 Flash + deepseek v4.1 Flash`,
   `auditor.role` — `AUDITOR`.
3. В `summary` (преамбуле) указать **состав промпта**: текст задачи, модель, способ
   запуска, какая часть вывода от какой модели. Это делает аудит воспроизводимым.
4. В `checks.security-review.result` — ответы на семь вопросов §3 со ссылками на
   файлы и коммиты.
5. `checks.ci-baseline.result` и `artifacts.ci_run` — реальный URL прогона CI.
6. Файл записи коммитит **релиз-менеджер**, до тега: гейт читает её из чекаута тега.
