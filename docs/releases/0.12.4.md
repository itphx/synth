## 0.12.4 (2026-10-28)

**Кумулятивные заметки волны 0.12.x (0.12.0–0.12.4), а не дельта одного патча.** 468 коммитов после
v0.11.3 (1305 файлов, +250 050 / −6 424 строк) закрывают пять крупных направлений: **расширяемость**
(слой плагинов, память, пайплайны, пакеты расширений), **автономную работу агента** (фоновые прогоны,
вопросы посреди хода, steering, git worktrees), **мультимодальные вложения и состояние инстанса в SQL**,
**инструментальное окружение** (исполнитель, flavor-образы, all-in-one) и **ядро шлюзов**. Внутри волны
последовательно появились слой плагинов, память и пайплайны, фоновые прогоны и вопросы, worktrees и
исполнитель, вложения и blob-подложка. Версия 0.12.3 тоже публиковалась в npm; отдельных заметок для
неё нет — она входит в этот документ.

### Слой плагинов (ADR-090)

- **Extension API v1 доведён до полного контура** — фазы Ф0–Ф7 и долги Д1–Д3. Манифест `synth.pack`
  (`kind: "plugin"`), загрузчик `PluginHost` (resolve → integrity → semver-гейт → trust/scan → политика
  режима → import → facade → disposers → аудит), bundle-only дистрибуция: плагин приезжает одним
  бандлом и не тянет зависимости хоста.
- **Три точки расширения:** `promptBlocks` (блоки системного промпта, сборка в `SystemPromptComposer`),
  `llmFilters` (фазы `pre_request` / `post_response` / `embedding`) и `tools` (namespace
  `plugin_<ns>_<tool>`, инструмент виден permission-слою). Состав вкладов сверяется с объявленным
  `provides` при активации — «заявил, но не зарегистрировал» не проходит.
- **Два режима исполнения:** `inline` (код в процессе core) и `out-of-process` (отдельный процесс,
  wire-протокол HTTP/1.1 + JSON по образцу исполнителя ADR-077, токен-файл). Выбор — в манифесте;
  тяжёлый или недоверенный код можно вынести за границу процесса.
- **Модель доверия:** уровни `builtin` → `verified` → `trusted` → `community`, trust-floor инстанса
  (по умолчанию `trusted`) и статический скан бандла. Право вето (`deny`/`redact`) есть только у
  плагина с фактическим trust ≥ `trusted`; у `community` вердикт понижается до `allow` с записью в
  журнал. Вердикт `caution` → карантин и подтверждение ADMIN, привязанное к **content-hash** бандла
  и действующее **24 часа**; подтверждение проверяется и при установке, и при активации.
- **Установка и жизненный цикл:** источники — локальный каталог/`.tgz`, npm-пакет и https-URL архива;
  `update` из источника записи lock и `rollback` на предыдущую ступень; снятие идемпотентно.
  CLI — `synth plugin scan|install|update|rollback|approve|enable|disable|remove|list`; HTTP —
  `/api/v2/plugins*` (установка, подтверждение, включение/выключение, откат, update, токен) с
  RBAC-матрицей; журнал действий — append-only `GET /api/v2/plugins/audit`
  (`{dataDir}/audit/plugins.jsonl`, в PostgreSQL — таблица `plugin_audit`).
- **UI и эксплуатация:** админ-раздел «Плагины» (версия, режим, доверие, вердикт скана, content-hash,
  активность, журнал) и CLI. Политика инстанса — `plugins.executionEnabled`, `trustFloor`, `scan`,
  `runtimeInstall`, `deployDir`/`deployTrust`, `managedReadonly`; изменения вступают в силу **после
  перезапуска**. В managed установка — deploy-time, runtime-install по умолчанию запрещён.
- **Гибрид:** сервер публикует политику (`/auth/oidc-meta`, `GET /api/v2/settings/plugins`). Уровень 1 —
  кооперативный allow-list (локальный core не активирует плагин вне списка, но при недоступном сервере
  работает); уровень 2 — server-scoped токен, привязанный к `plugin_id` (scope `plugins:invoke`,
  заголовок `X-Synth-Plugin-Id`); уровень 3 (attestation клиента) — вне объёма v1.
- Документация: [docs/PLUGINS.md](../PLUGINS.md) и EN-зеркало [docs/en/PLUGINS.md](../en/PLUGINS.md),
  HTTP-контур — [docs/API_V2.md](../API_V2.md) §5.36, конфигурация — [docs/CONFIGURATION.md](../CONFIGURATION.md).

### Память (ADR-107, реализованное ядро PROP-047)

- **Память — плагин, а не подсистема ядра.** Ядро даёт доменные порты
  `MemoryFactRepository`/`MemoryIndexRepository` (факты с версиями и provenance, индексы с поколениями,
  фингерпринтом и чанками; file/memory/PostgreSQL, миграции `017`–`020`), scoped-доступ
  `facade.memory` (namespace `plugin:<имя>` навязывает хост), `facade.embed` **только** через
  `GatewayProvider.embed`, `facade.getSettings` и `facade.security`. Логика памяти живёт в плагине
  `@itphx/synth-plugin-memory` (private, deploy-time и dev).
- **Ванильный RAG в плагине:** markdown-aware чанкер (1200 символов / перекрытие 200), эмбеддинги
  батчами до 32 текстов, атомарная смена поколения, фингерпринт `модель + размерность + версия чанкера`
  (смена модели помечает индекс `stale` даже при той же размерности), гибридный поиск keyword (BM25-lite)
  + cosine через RRF (`k = 60`), evidence с путём, диапазоном строк и score. Без модели эмбеддингов
  индекс не строится, recall деградирует до keyword.
- **Область индекса:** `project` (по умолчанию — виден только проекту) и `instance` (общий корпус
  инстанса). Инстансный индекс по `files` берёт корпус из workspace указанного проекта и осознанно
  раскрывает его всем пользователям (действие ADMIN, в UI — предупреждение); по `facts` — все активные
  факты инстанса (потолок 1000). Recall и `memory_search` сливают проектную и инстансную выдачу с
  дедупом по `indexId:chunkId`.
- **Портал в ядре:** `GET /api/v2/memory/{status,facts,facts/:id,indexes}`, `POST /memory/indexes`,
  `POST /memory/indexes/:id/rebuild`, `DELETE /memory/indexes/:id`, `POST /memory/consolidate`,
  `GET /memory/graph`. Чтение — `requireAuth` (core) / ADMIN (managed); проектные операции проверяются
  **на границе** (`read`/`write`, `VIEWER` только читает). Мутации индексов идут через админ-тул
  плагина; плагин не активен → `409 MEMORY_PROVIDER_UNAVAILABLE`, портов нет → `503 MEMORY_UNAVAILABLE`.
- **CLI `synth memory`** — тонкий клиент портала: `status`, `list`, `index`, `rebuild`, `drop`
  (опции `--scope project|instance`, `--wait`, `--timeout`, `--json`; `drop` без `--yes` — отказ).
  Подключение — `--url`/`--token`/config/`{dataDir}/secrets/api-key`.
- **Консолидация и граф:** дедуп фактов по эмбеддингам, граф сущностей без LLM, SVG-визуализация в
  админке памяти. Встроенные шаблоны пайплайнов: `builtin:memory-consolidation` (сессия → факты),
  `builtin:memory-consolidate-facts` (дубли фактов), `builtin:memory-reindex` (все проектные индексы).
- **Наблюдаемость и UI:** вкладка «Память» в правой панели (`GET /sessions/:id/memory` — агрегаты без
  текстов), блок `memory.guide` в системном промпте (только при доступной памяти), тумблер памяти
  проекта, метрики `synth_memory_*` и Grafana-дашборд «Synth — Память».
- **Секреты:** каталоги и файлы секретов не индексируются (политика в ядре, плагин спрашивает
  `facade.security`); обфускации при индексации **нет** — чанки уходят провайдеру эмбеддингов как есть.
  Рекомендация — локальные эмбеддинги (Ollama). Устройство — [docs/MEMORY.md](../MEMORY.md).

### Пайплайны (ADR-100/101)

- **Два контура.** Пакет расширения `synth.pack` (`provides`: mcp/skills/agents/pipelines) ставится одной
  операцией `POST /api/v2/packs` с одобрением ADMIN; scope service-key `automation:install`; legacy-контур
  «декларация + учёт» остаётся рабочим и показывает определения/экземпляры. Новый движок — ADR-101.
- **Движок прогонов** (`engine/pipelines/`): граф `PipelineSpec`, узлы `agent`/`script`/`tool`/`human`,
  условия переходов (структурированный DSL, fail-soft), ретраи и таймауты шага, лимит переходов, HITL-пауза
  `awaiting_human` и `resume`, отмена через `AbortSignal`, append-only журнал прогона с санитизацией
  payload'а от секретов. Прогон идёт только по **опубликованной** версии; одновременно у пайплайна не
  более одного активного прогона.
- **Версии:** черновик правится без bump'а; `publish` создаёт неизменяемую опубликованную версию и
  следующую версию черновика; повторная публикация без изменений идемпотентна.
- **HTTP и права:** `/api/v2/projects/:id/pipelines*`, `/api/v2/pipeline-runs/:runId*` (заголовок,
  журнал, HITL `resume`, `cancel`), `/api/v2/pipeline-templates*` (список и инстанцирование). Чтение —
  право чтения проекта (`VIEWER` читает), запись — право изменения содержимого; проверки на границе,
  service-key — scope `automation:install` + `allowedProjects`.
- **Визуальный редактор:** собственный IR — `PipelineSpec`, а не формат React Flow (адаптер
  `specToFlow`/`flowToSpec` без потерь); палитра узлов, инспектор, редактор условий, рёбра,
  переключатель «Визуальный / JSON», кнопка «Проверить» (`validatePipelineSpec`). Атрибуция React Flow
  сохранена (лицензия).
- **Шаблоны:** шаблоны инстанса + legacy-определения пакетов конвертируются на лету при
  инстанцировании (шаги `agent` → узлы; `loop` не конвертируется → `409 PIPELINE_TEMPLATE_UNSUPPORTED`
  со списком проблем). Провенанс `installedBy` сохраняется.
- **Расписание с целью `pipeline`:** `ScheduleTarget = {mode:'pipeline', projectId, pipelineId, version?,
  payload?}` — шедулер запускает прогон **напрямую** (сессия не создаётся, событие в Router не
  публикуется), Job получает `runId`; пайплайн должен быть опубликован. `payload` статический.
- **Артефакты и вложения прогона:** байты артефактов — в blob-порте
  (`artifacts/<runId>/<name>`, учёт `blob_refs`), метаданные — в заголовке прогона;
  `GET /api/v2/pipeline-runs/:runId/artifacts/:name` отдаёт объект с `ETag`/`304` и
  `Content-Disposition: attachment`. Прогон принимает `attachments[]` (проверка ссылок до старта,
  гидратация как у сессий, `ownerKind: 'pipeline-run'`).
- **Инструменты и скиллы:** 12 `pipeline_*` и 6 `schedule_*` (capability `pipeline`/`schedule`), мутации
  запрещены в plan-режиме, `pipeline_run_resume` — действие `approve` (ADR-106); встроенные скиллы
  `synth-pipelines` (`/pipelines`) и `synth-schedules` (`/schedules`).
- **UI:** вкладка «Пайплайны» левой панели, center-tabs пайплайна и прогона, HITL-кнопки
  «Одобрить»/«Отклонить», живой прогресс по событиям `pipeline.run.*` без отдельного транспорта.
  Устройство — [docs/PIPELINES.md](../PIPELINES.md), API — [docs/API_V2.md](../API_V2.md) §5.35.

### Фоновые прогоны и вопрос пользователю (ADR-111/112/113)

- **Фоновые саб-агенты:** `task({background: true})` возвращает управление сразу; у прогона свой
  `AbortController`, `streamId` и отмена, ребёнок помечен занятым, глубина — 1, действуют лимиты.
  Завершение приходит родителю одним уведомлением (`child.completed|failed|cancelled` + сообщение и
  автоход), терминальный переход идемпотентен. `task({task_id})` продолжает ребёнка. После рестарта
  незавершённые записи помечаются `orphaned` — фоновые прогоны не возобновляются.
- **Фоновые процессы:** `execute_shell({background: true})` → запись в общем реестре
  (`{dataDir}/processes/registry.json`, PostgreSQL `021`/`022`), лог в blob, лимит `maxLogBytes`,
  остановка `SIGTERM` → `SIGKILL` через 5 с. Гейт `background.enabled`; события `process.started`,
  `process.exited`, `process.stopped`, `process.detached`.
- **Перевод идущего прогона в фон (detach):** `POST /api/v2/sessions/:id/background` переводит
  foreground-вызов `task` или `execute_shell` в фоновый режим; перевод **односторонний**, в канал
  публикуется `process.detached`. «Стоп» родителя переведённый прогон не останавливает — у него свой
  «Стоп». В UI — кнопка «В фон» и `ctrl+b` для всех блокирующих прогонов активной сессии.
- **Вопрос пользователю:** тул `question` (1–5 вопросов, до 8 вариантов, свободный ответ ≤ 1000
  символов, опциональный `timeout` ≥ 5 мин; по умолчанию таймаута нет) блокирует ход до ответа.
  Запись персистентна (`questions.json`/PostgreSQL `021`), при рестарте незавершённые вопросы
  помечаются `interrupted`; HTTP — `GET/POST /sessions/:id/questions[/:qid/answer|cancel]`, события
  `user_question.*`. Саб-агентам тул запрещён, в plan-режиме разрешён.
- **Реестр и UI:** единый `GET /api/v2/processes` (процессы и фоновые саб-агенты) с граничным guard'ом,
  вкладка «Процессы» правой панели: статусы, остановка/удаление, лог с автоподгрузкой, открытие дочерней
  сессии, уведомления на старт и терминальный переход. Док вопроса — над композером, с сворачиванием,
  сегментами, шагом проверки «вопрос → ответ» и обратным отсчётом.

### Worktrees и steering (ADR-114/104)

- **Git worktrees:** каждая сессия может работать в собственном рабочем каталоге с общей историей.
  Корень — `{workspacesRoot}/.worktrees/<projectId>/<slug>`, запись `WorktreeRecord` хранится в порту
  `WorktreeRepository` (три backend'а, без новой миграции). Привязка — аддитивное
  `Session.worktree`; приоритет резолва каталога — worktree → `project.workspace` → default; саб-агенты
  наследуют привязку родителя. Исчезнувший каталог — fail-closed, а не тихий фоллбек.
- **Тулы и API:** `git_worktree_list|create|remove|prune` (capability `git_read`/`git_write`, в plan
  мутации запрещены), `GET/POST /api/v2/projects/:id/worktrees`, `DELETE .../:wid`,
  `POST .../prune`, привязка — `PATCH /api/v2/sessions/:id {worktreeId}`. Событие `worktree.updated`
  инвалидирует дерево Files; каталог `.worktrees` скрыт из дерева и поиска.
- **Lifecycle:** удаление «грязного» worktree — двухшаговое (`forceRequired`), при активной привязке
  сессии — 409; `prune` — только записи без каталога; sweep осиротевших записей при старте; опциональный
  `project.worktreeSetupScript` через `ExecutionPort`.
- **UI:** инвентарь worktrees в правой панели (вкладки «Проект» и «Сессия»), селектор рабочего каталога,
  индикатор secondary worktree, скрытие `.worktrees`. Устройство — [docs/WORKTREES.md](../WORKTREES.md).
- **Steering:** режим отправки — поле `mode` (`queue`/`steer`/`interrupt`) в `POST /prompt` и WS
  `send_message`; `steer` вплетает ввод в текущий ход на границе шага, `interrupt` прерывает генерацию,
  не завершая ход. Порядок — `interrupt` раньше `steer`, внутри класса FIFO; лимит инъекций 5
  (`429 STEER_LIMIT_EXCEEDED`). Работает и для дочерней/фоновой сессии саб-агента (общая точка
  `engine/steering/apply.ts`). В гибриде `mode` доезжает до удалённой стороны, ответ несёт
  `mode_applied`. Неприменённые инъекции снимаются в конце хода/по «Стопу» (`steer.dropped`).
  В UI — иконочный тумблер «Вмешаться» и маркеры вмешательства/прерывания.

### Внешние доступы и Authority (ADR-105/106)

- **Внешние доступы (OAuth-коннекторы):** сущность `ExternalCredential` со сроком и статусом
  (`active`/`expired`/`revoked`/`error`), порт (file/memory/PostgreSQL, миграция `012`), OAuth-клиент
  PKCE/device flow/refresh с CAS/revoke через `egressFetch`, шифрование at-rest (`enc:v1:` в
  `secrets/oauth/`). Секретные заголовки не уходят на redirect-хост; plaintext-секрет в реестре MCP
  запрещён (`400 MCP_SECRET_HEADER_FORBIDDEN`) с миграцией в доступ. Каталог провайдеров —
  `oauth.providers`.
- **MCP-биндинг:** access-токен подставляется в транспорт динамически, refresh по `401` — ровно один
  на запрос. HTTP-контур — `/api/v2/oauth/credentials*` (выдача, список, метаданные, refresh, отзыв,
  привязка к коннектору); журнал операций — append-only `{dataDir}/audit/credentials.jsonl` (не
  публичный API). Ротация мастер-ключа (`synth secrets rotate`) покрывает внешние доступы и
  signing-секреты вебхуков; бэкап и экспорт проекта токены не выносят. UI — раздел «Доступы».
- **Authority-слой:** полномочия сведены к одной модели — принципал хода (`Turn.principal`),
  участники сессии (`Session.participants`), потолок сессии и ограничение `PATCH mode`, подтверждения
  `permission.asked`, привязанные к принципалу и ходу. Резолвер прошёл shadow-режим и включён в
  permission-слой; решения видны в метриках. Контент: `provides.authority` при установке пакета,
  `pending_approval` «по существу» (сводка ролей/действий/целей), активация в политике инстанса с
  trust-floor, порты PostgreSQL. UI — раздел «Полномочия» (read-only). Остаток — flavor-роли (PROP-082).
  Устройство — [docs/AUTHORITY.md](../AUTHORITY.md), [docs/EXTERNAL_ACCESS.md](../EXTERNAL_ACCESS.md).

### Мультимодальные вложения и состояние инстанса (ADR-115/116)

- **Модель контента расширена аддитивно:** `PartType` + `image`/`audio`/`video`/`file`; медиа-часть
  несёт **ссылку** (`blobPath`, `sha256`, `mime`, `size`, `name?`), а `content` — плейсхолдер
  (`[image: name.png]`), поэтому строковые производные (БД, экспорт, поиск) не теряют факт вложения.
  Контракт LLM-вызова дополнен `LLMMessage.attachments`.
- **Blob-подложка:** оригиналы — content-addressed `{dataDir}/blobs/attachments/<sha2>/<sha256>`,
  дедуп, sidecar с именем, учёт ссылок `blob_refs` (миграция `024`) и GC по ссылкам +
  `attachments.gcDays`. В БД и сообщении — только ссылка. Метаданные (EXIF/IPTC/XMP) срезаются
  **только на границе отправки провайдеру**; выдача через API и материализация в workspace отдают
  оригинал.
- **HTTP:** загрузка в сессию и раздача с `Range`/`206`/`416`, `ETag`/`304`, `HEAD`; staging-загрузка
  **вне сессии** (`POST /api/v2/attachments`, `GET/HEAD /api/v2/attachments/:sha256` — для шлюзов и
  пайплайнов); `attachments: string[]` в `POST /prompt` превращается в медиа-части; наружу —
  `stream.done.attachments` и раздача по sha. Gateway не обфусцирует и не логирует base64 — только
  сводку `{mime,name,sizeBytes}`.
- **Гидратация: native → aux-текст → отброс.** Модальности берутся из каталога провайдера. Модель
  принимает модальность — вложение уходит как есть; не принимает — aux-модель семейства из
  `attachments.modalityModels` (`image`/`pdf`/`audio`/`video`) даёт текст; обработки нет — вложение
  материализуется в `<workspace>/attachments/` с блоком `[ATTACHMENTS NOT DELIVERED]`. Тихая потеря
  запрещена; модель сессии не меняется.
- **Аудио и видео:** форматы аудио — по предикату провайдера (OpenAI wav/mp3, RouterAI + ogg/opus,
  Anthropic-протокол — только wav и только RouterAI); при заданной aux-модели аудио всегда идёт через
  неё. Видео — нативно у RouterAI (`video_url`), иначе кадры через `ffmpeg`; для модели с `video`, но
  без `audio`, дорожка извлекается и транскрибируется aux-моделью (`[video-audio: <name>]`).
  «Аудио-в-видео» (MP4 с чёрным кадром) отменено — оно жгло токены без пользы.
- **Медиа из инструментов и контуров:** `ToolResult.attachments` + `web_fetch({include_media})`,
  инъекция в **текущий** ход; MCP-вложения (протокол исполнителя 5); вложения внешнего события
  (`attachments[]`, требуется явный `dedupKey`); вложения прогона пайплайна. Тулы: `attach_workspace_file`
  (файл workspace → вложение), `save_attachment` (вложение → файл workspace), `send_attachment`
  (файл → вложение ответа, `stream.done.attachments`).
- **UI:** кнопка/драг-н-дроп/вставка в композере, подготовка файлов (HEIC→JPEG, office→текст+картинки),
  чипы и галерея, рендер в ленте (изображения сеткой, audio/video `controls`, файлы чипом), гейт
  модальностей по каталогу. Runtime-настройки — `/api/v2/settings/attachments` (лимиты, allowlist,
  `modalityModels`, `workspaceFallback`, `gcDays`).
- **Состояние инстанса в SQL (ADR-116):** в PostgreSQL переведены четыре порта — `packs`,
  legacy `pipelines`, `skills` (метаданные; содержимое — в blob-порте) и `contextFiles`
  (пользовательская часть; системные промпты образа остаются на ФС). Миграции `024`–`027`:
  `blob_refs`, `packs`/`pipelines`, `instance_skills`, `context_files`. `blobs` остаётся **файловым по
  конструкции**: байты на томе, в БД — только ссылки; при деградации хранилища вложения читаются.
- **Перенос и чарт:** `synth storage migrate` переносит новые порты в обе стороны (`blobs` — никогда);
  драйвер PostgreSQL больше не собирает файловый контекст — импорт core сужен до `FileBlobStore` и
  `ContextConfig`. В чарте — опция отдельного блоб-тома (`backend.blobs.*`), при `replicaCount > 1`
  требуется `ReadWriteMany` (иначе рендер падает). Портативный экспорт/импорт проекта (формат 2)
  переносит байты вложений и `blob_refs`.

### Исполнитель и топологии развёртывания (ADR-077)

- **Порт исполнения `ExecutionPort`:** режимы `inline` и `remote`, переключатель `execution.mode`,
  динамический `import()` пакета `@itphx/synth-executor`, fail-closed проверка при старте (тихого
  возврата к локальному исполнению нет). Git-операции control plane переведены на порт, `simple-git`
  удалён из core.
- **Протокол исполнителя вырос до 5:** 2 — MCP-эндпоинты, 3 — фоновые процессы, 4 — секреты вызова
  (`secrets[]`, SSH-ключи; старый исполнитель → fail-closed `ESECRETS`), 5 — вложения MCP-результата
  (`features.mcpAttachments`). Совместимость — по полю `protocol` в `GET /capabilities` и аддитивным
  `features`; исполнитель ≤ 4 отдаёт текстовый результат без падения.
- **MCP в исполнителе:** stdio-серверы хостятся у исполнителя, инструменты и вызовы идут по HTTP
  (`GET /mcp/servers`, `GET /mcp/tools`, `POST /mcp/call`); control plane получает их через
  `ExecutorMcpSource`. Доступность инструментов определяется составом пула (`requires`, `probe()`),
  браузерные тулы Playwright проверены в контейнере.
- **Фоновые процессы в remote:** `BackgroundExecService`, `POST /exec/spawn`, статус/логи/stop;
  клиент опрашивает состояние и журнал, `stop` уважает сигнал. Остановка гасит **группу процессов**,
  а не только оболочку (см. «Надёжность»).
- **Наблюдаемость:** метрики `synth_executor_*` на обеих сторонах, собственный `/metrics` исполнителя,
  скрейп пула; серия `synth_executor_commands_total` считается по-разному на control plane и
  исполнителе — суммировать нельзя.
- **Развёртывание:** пул в Helm (`execution.*`/`executor.*`), общий RWX-том workspace, токен доверия из
  Secret/файла, опциональный `NetworkPolicy`; профили compose `all-in-one` и `split`; flavor-образы
  `slim`/`core`/`dev`/`devops`/`browser`/`full` и мультистадийный all-in-one. Детали —
  [docs/EXECUTION.md](../EXECUTION.md).

### Безопасность

- **Внутренний аудит релиза** — обязательный гейт `security-gate` в `release.yaml`. Запись
  [docs/security/releases/0.12.4.json](../security/releases/0.12.4.json): статус
  `approved_with_exceptions`, одно исключение `historical-test-fixture-allowlists`
  (срок — 0.12.5), гейт `5 pass / 0 fail`.
- **Secret-scan** дерева и всей истории: находок нет; 83 подавления — узкие блоки «путь + dummy-тело»
  для тестовых фикстур прошлых коммитов. Рабочее дерево переписано на генерацию PEM/токенов в рантайме.
- **Матрица авторизации сессий** — 93 теста (негативная и позитивная матрица + перепись по
  смонтированному приложению); диф относительно master — только добавления маршрутов вложений и
  артефактов, новых `:id`-маршрутов вне матрицы нет.
- **Зависимости:** критических уязвимостей 0; high — 27 при baseline 31; прямых уязвимых модулей 0.
  В релизе снят high `GHSA-27r3-jxmh-p828` (`body-parser` 2.3.0 → 2.4.0) и обновлены транзитивные
  патчи в пределах semver.
- **Найдено и закрыто аудитом:** недокументированный `415 attachments_disabled` в API_V2 §5.6.1;
  буферизация видео-blob целиком при derive (теперь поток во временный файл с уборкой в `finally`).
- **Контур вложений:** base64 не попадает в payload-лог и карту обфускации Gateway; blob-пути
  ограничены префиксом `attachments/`; имена артефактов и `runId` санитайзятся; материализация
  отброшенных вложений — strict containment внутри workspace.

### Надёжность и исправления

- **Исполнитель и фоны.** `stop` и таймаут гасят **группу процессов** (`kill(-pid)`), а не только
  оболочку: раньше потомок `sh -c` переживал остановку, держал пайпы и оставлял запись в `running`.
  Чтение журнала сразу после закрытия процесса больше не теряет хвост (гонка снимка цепочки записи).
  PostgreSQL хранит `processId`, `timeoutMs: 0` (фон без таймаута) принимается, гейт
  `background.enabled` и событие `process.stopped` согласованы, уведомление о завершении — одно,
  отказ фона и свободный ответ вопроса не оставляют побочных эффектов.
- **Вложения и медиа.** Видео-транскрипт идёт через временный файл, а не буфер целиком; убран
  «аудио-в-видео»; allowlist `video/` и извлечение кадров из MP4; Ollama получает `images[]`;
  `attach_workspace_file` вставляет вложение в текущий ход; аудио из Telegram — media-only без JSON,
  с aux-моделью и транспортными форматами; PDF — `file`-блок у OpenAI-типа и `pdf` в модальностях
  Anthropic-типа; модальности берутся из каталога провайдера, а не по грубому префиксу; маркер
  вложения в композере и возврат вложений при повторе; «Размышления» в стриме и финале считаются
  одинаково.
- **События и контекст.** Telegram-сообщение без текста даёт маркер, а не JSON; отключение
  user-реплики выключает весь её ход (а не только текст).
- **Память.** Политика исключения секретов живёт в ядре, а не в бандле плагина (сканер расширений
  больше не блокирует плагин за список имён секретных файлов); фингерпринт индекса берёт фактическую
  модель эмбеддингов хоста — смена модели помечает индекс `stale` даже при той же размерности.
- **Плагины.** Подтверждение установки учитывается и при активации; относительный `identifier` не
  делает плагин управляемым; путь deploy-плагинов не задаётся ENV в образе; контрактный suite не
  попадает в прод-бандл; живые бюджеты фильтров и `promptBlockMaxChars` работают.
- **MCP и egress.** Сетевая политика MCP — fail-open для одиночного IP-правила исправлен;
  `egressFetch` больше не теряет заголовки ответа (HTTP-MCP не работал ни с одним сервером);
  секретные заголовки не уходят на redirect-хост.
- **Пайплайны, worktrees, агенты.** Создание пайплайна из UI больше не даёт 400 «Некорректное тело»;
  переключение вкладок не показывает stale-состояние; артефакты прогонов подключены в managed;
  worktree-тулы возвращают id, событие несёт action, prune-схема и гонка `PATCH` исправлены; реестр
  агентов видит runtime-агентов при `storage.backend=postgres`.
- **Локализация.** Строки движка и уведомлений новых подсистем добавлены в `shared/i18n` (вопрос,
  фоны, вложения), EN-переводы разделов API/CONFIGURATION и дока вопроса синхронизированы.
- **CI и релиз.** Публикация npm — fail-closed, проверка видимости — отдельный неблокирующий шаг;
  релиз больше не зависит от квоты CI-артефактов (страница релиза и GitHub-зеркало собираются без них);
  `docker-cleanup` не удаляет публикуемую версию (`GV_KEEP_TAGS`); в CI собирается flavor `core`
  обоих образов, полная матрица — на релизе. Три красных теста первого прогона оказались зависимостью
  от окружения раннера (git identity, argv-форма kill, каретка React) — исправлены в тестах без
  ослабления проверок.

### Ограничения и открытые пункты

- **Гибрид не переносит байты вложений.** `remote/transfer.ts` (publish/fork) переносит сессии и
  сообщения, но не blob-объекты: медиа-части на удалённой стороне остаются с неразрешённым `blobPath`.
  Остаток ADR-115.
- **Multi-replica не поддерживается полноценно.** Состояние инстанса для четырёх портов теперь в SQL
  (ADR-116), cron-лидерство и привязка клиента работают, но auth-сессии backend живут в памяти
  процесса, очередь не имеет claim-семантики (падение реплики «залипает» до `resume`), лимиты и шина
  событий — in-process. Нужны PROP-104/105, а не только общий том.
- **Память требует предусловий:** `plugins.executionEnabled: true` и настроенные эмбеддинги
  (`plugins.embeddingProvider`/`embeddingModel`). Без модели индекс не строится, recall — только
  keyword. Инстансный индекс по `files` раскрывает workspace всем пользователям — это действие ADMIN.
- **`@itphx/synth-gateway-core` не опубликован в npm** — публикация блокируется правами токена на
  scope `@itphx`; потребители используют локальную связь. HA через leader election — остаток.
- **Пайплайны:** нет цепочечного rollback/exit-стратегии, мониторинг-дашборда и отдельного хранилища
  артефактов (артефакты — в общем blob-порте, retention не введён); legacy-шаги `loop` не
  конвертируются; форма вложения в UI запуска — остаток.
- **Плагины:** сервисы фасада (`memory`/`embed`/`getSettings`) доступны только `inline`; паритет с
  `out-of-process` потребует wire-протокола v2. Attestation клиента (уровень 3) — вне объёма v1.
- **Вложения:** серверной предобработки ASR/OCR/sharp нет (только внешний `ffmpeg` для аудио/видео);
  черновики вложений не переживают переключение сессии; видео нативно только у RouterAI, у остальных —
  кадры; `transcript` и стоимость aux-вызова в счётчиках сессии — остаток.
- **Аналитика:** лимитов, квот и алертов по расходу нет; серверного PDF/XLSX нет (PDF — печать
  браузера).
- **Worktrees:** общий `.git` (refs, hooks, stash, конфиг), ignored-файлы в новый worktree не
  копируются, автоудаления при архивации сессии нет.
- **Исполнитель:** квоты, workspace-v2 и runbook переключения топологии — шаги 10–12 ADR-077; реестр
  фоновых процессов исполнителя живёт в памяти (переживание рестарта требует внешнего состояния).
- **Артефакты релиза:** flavor-образы в приватном Gitea и arm64-образы в `gitverse.ru` в этом прогоне
  не опубликованы из-за квоты реестра; см. «Артефакты».

### Как обновиться

- **npm (8 пакетов):** `npm i -g @itphx/synth@0.12.4` — обёртка подтягивает `@itphx/synth-core`,
  `@itphx/synth-shared` и `@itphx/synth-ui`; отдельно публикуются `@itphx/synth-backend`,
  `@itphx/synth-sdk`, `@itphx/synth-storage-postgres` и `@itphx/synth-executor`.
- **Docker:** `ghcr.io/itphx/synth{,-backend,-ui}:0.12.4` — multi-arch (`amd64`+`arm64`);
  `gitverse.ru/itphx/synth{,-backend,-ui}:0.12.4` — `amd64`. Flavor-образы (`slim`/`dev`/`devops`/
  `browser`/`full`, образы исполнителя) публикуются в приватный Gitea отдельной релизной джобой; в
  этом прогоне она не прошла из-за квоты — test-контур работает на 0.12.4 из локальной сборки.
- **Helm:** чарт `synth` 0.12.4 (`helm upgrade synth <репозиторий>/synth --version 0.12.4`).
- **Перед обновлением** — бэкап (`synth backup`): миграции `024`–`027` применяются при старте и меняют
  схему данных. Откат данных — только restore из бэкапа; откат версии — `helm rollback` или
  `synth update --to <prev> --apply`.
- **После обновления:** `synth doctor`, `GET /health`, `GET /ready`. Для памяти включите
  `plugins.executionEnabled` и задайте модель эмбеддингов, затем перезапустите инстанс и проверьте
  `synth memory status`. Для плагинов проверьте `plugins.trustFloor`/`runtimeInstall`/`deployTrust` —
  изменения политики применяются после перезапуска.
