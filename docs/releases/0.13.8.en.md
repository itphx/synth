## 0.13.8 (2026-11-11)

**Cumulative release for the 0.13.x wave — notes for the whole v0.13.4..HEAD range (more than 120 commits), not a single patch delta.**
Versions 0.13.5–0.13.7 were never published to npm (only betas in the internal npm registry), so this
document covers the entire wave.

The headline of 0.13.8 is that the instance can now service itself: from chat, the agent sees and
repairs its own instance (self-help tools, the MCP registry, projects and sessions), the owner gets a
first-class update channel with a choice of channel and a systemd `--user` service for always-on
operation. The second storyline is the approval bar: a request now shows **what exactly** triggered
it, “Allow for this session” grants by the culprit’s directory, and pending approvals survive an
instance restart.

### Release focus

- **The agent services its own instance**
  ([ADR-131](../arch_decisions/adr-131-self-management-tools.md)): `synth_info`, `synth_mcp_*`,
  project and session discovery — without curl, without hand-inspecting `dist`, and without reading
  secrets. The built-in `/instance` skill is a runbook right inside chat.
- **Updating and always-on operation are standard workflows**
  ([ADR-133](../arch_decisions/adr-133-update-channels.md),
  [ADR-134](../arch_decisions/adr-134-instance-service-systemd-user.md)): `stable`/`beta` channels,
  `synth service` (systemd `--user`), restart from the UI/CLI via exit code 75.
- **The approval bar became understandable and survives a restart**
  ([ADR-029](../arch_decisions/adr-029-granular-permissions.md)): a structural “culprit”, the
  offending token highlighted in the command, a grant scoped to a directory, persistent approval
  requests.
- **Standalone caught up with managed in API surface**: the MCP registry and the remaining
  backend-only routes now live in core ([ADR-071](../arch_decisions/adr-071-mcp-servers-prompt.md)
  §2.5).
- **Caps on search and read tools** — after an incident in which a single minified line carried
  243 KB into the context.

### Self-help tools for the instance, MCP and projects/sessions (ADR-131)

A new `instance` capability and permission group: read tools are available in `plan` mode, write
tools (`synth_mcp_add`/`update`/`remove`/`enable`) are not.

- **Instance tools:** `synth_info` (version, mode, data directory, authentication flags, storage
  backend, counters) and `synth_mcp_list`/`synth_mcp_test` — the MCP registry, status, effective
  scope, reason and policy. **Secrets are never read or returned**: authentication exposes flags only
  (`localKeyPresent`, `apiKeyConfigured`), the URL is editable, `headers`/`env` are not returned.
- **Managing MCP:** `synth_mcp_add`/`update`/`remove`/`enable`/`reconnect`. An `instance`-level entry
  and `stdio` require `ADMIN`; user HTTP/SSE servers are checked against the MCP network policy; a
  newly added server is **not** enabled in a session automatically (opt-in).
- **Auto-reconnect:** an expired MCP session (`Session not found`) is reconnected once and the call
  is retried; `synth_mcp_reconnect` is the manual path.
- **Projects and sessions:** `list_projects`, `get_project`, `list_sessions`, `get_session_info`,
  `session_rename` — compact summaries without message history, project log or secrets.
  `project_attach` accepts **an id or an exact name**; on ambiguity it returns the candidates instead
  of silently choosing one. In hybrid mode, discovery merges the local and remote worlds (`origin`,
  ids of the form `remote:<uuid>`, `remote_offline`/`remote_truncated`), but a cross-world move is
  forbidden.
- **The `synth-instance` skill** (command `/instance`, trigger `auto`) — a runbook: what this instance
  is, which MCP servers it has, how to add/enable/reconnect one, how to find a project and a session.
- **CLI `synth mcp list|add|test|remove|reconnect`** — a thin client of the local API; the key is
  read inside the process and never printed. `synth config show` redacts secrets by default
  (disclosure only with an explicit `--show-secrets`).

### Update channels (ADR-133)

- **The channel is derived from the installed version** (`-beta.` ⇒ `beta`, otherwise `stable`); the
  override is the `updates` config section or `SYNTH_UPDATES_*`. There is no separate marker file:
  the state cannot drift from the fact of installation.
- **Sources per channel:** `stable` — the `latest` dist-tag from npmjs, `beta` — the `beta` dist-tag
  from the Gitea npm registry. **The beta registry is readable without a token** — the token is only
  needed for publishing.
- **The background check is off by default** (`updates.check: false`): an offline instance does not
  spam requests. An explicit check (`synth update --check`, the “Check” button) always works and
  ignores the cache; the cache lives for 24 hours, a failed entry for 1 hour, and an offline instance
  degrades silently.
- **Installation is an explicit action** and only with a user-level npm prefix: a system/root
  installation is left untouched. In Docker/Helm/managed self-update is forbidden
  (`409 UPDATE_UNSUPPORTED`).
- **A `beta → stable` switch is a rollback**: it is marked as such and requires confirmation instead
  of being treated as an “update”.
- **CLI:** `synth update --check|--apply|--channel auto|stable|beta|--registry <url>|--to <version>
  --dry-run|--json`; **UI:** the “Updates” block in the “Control Panel” (channel, auto-check toggle,
  “Check”, “Update” plus a restart checkbox). The installation runs as an SSE stream, and the
  instance restart is scheduled automatically.

### Instance service: `synth service` and systemd `--user` (ADR-134)

The only supported way to provision “let it always run” — instead of a hand-written unit.

- **Commands:** `install|status|start|stop|restart|enable|disable|logs|uninstall`, flags
  `--print-unit`/`--dry-run`/`--json`/`--force`/`--no-autostart`/`--no-start`/`--no-linger`.
  Installation waits for `GET /health`; the output shows the unit and env-file paths, the URL and the
  **path** to the API key (never the value; the key is not printed into the systemd journal either).
- **A fixed unit template:** `Restart=on-failure`, `RestartForceExitStatus=75`, `RestartSec=3`,
  `KillMode=mixed`, `TimeoutStopSec=30`, `SYNTH_RESTART_MODE=process`, `EnvironmentFile` (`0600`,
  no secrets) and the marker `# Managed by synth service install` — a foreign unit is not overwritten
  without `--force`.
- **Linger** (`loginctl enable-linger`) is enabled best-effort: without it the service lives until
  logout and does not start after a reboot; a failure is a warning, not an error.
- **Only `--user`:** the root/system mode is not supported (the “one user — own instances” model).
  On non-systemd platforms the command reports that it is unsupported.
- **Hybrid:** the unit holds no tokens — authorization goes through the saved credentials after
  `synth connect` (device flow).
- **Restart via exit code 75** now works out of the box: `POST /api/v2/maintenance/restart
  {confirm:true}` (or `synth service restart`) ends the process with code 75 and the supervisor
  starts a new one. The npm CLI gained `synth serve --restart-mode disabled|process|supervisor`.

### Permission approvals: the bar, grants and surviving a restart (ADR-029)

- **A structural “culprit”** (`messageId`/`params`/`matchedRule`/`askKind`) reaches the UI in the
  `permission.asked` event and in the recovery DTO — the bar shows **what** triggered the question and
  highlights the offending token right in the command and in the reason. The reason is now in plain
  human language, the command is a separate block, and technical details are collapsed.
- **The grant is computed from the culprit segment:** command templates (“for the whole command”) are
  never issued at all — such a template is wider than what was approved (for `rm -rf /srv/data` it
  would be a permanent `rm *`). Instead, a dynamic ask (an unverifiable glob, `$(...)`) yields the
  culprit’s directory, and the session gets the rule `external_directory: "<dir>/*" = allow`. The
  question can only be lifted if all actual glob matches are inside the perimeter or covered by an
  **explicit** `external_directory` rule; `protected`/`mutation`/`cwd`/`deny` are never lifted. The
  issued grant is written to the audit log (`scope=permission`, `action=grant`) together with the
  directories.
- **Approval requests survive an instance restart**: a dedicated storage port
  (`{dataDir}/pending-approvals.json`; PostgreSQL — the `pending_approvals` table, migration 034).
  After a restart the request comes back as restored: `allow` applies as a grant in the session,
  `deny` removes it, `hold` → `400`. The session DTO gained a `pending_approvals` counter, and the UI
  shows an “the instance was restarted” note.
- **A grant on a restored request is never wider than what was approved.** “Allow for this session” on
  a request that survived a restart is computed by the same plan as a live one: a dynamic path gets a
  directory grant, while `mutation`/`protected`/`cwd` are not lifted by a grant — the question is
  asked again. If there is no snapshot of the reason, a shell command gets no grant at all
  (fail-closed).
- **Indicator in the session tree:** the `approval` status — an orange dot **and** a label, not color
  alone; color is never the only signal.

### The MCP registry and backend-only routes moved into core (ADR-071 §2.5)

- Standalone no longer answers `404` on `/api/v2/mcp/registry*`.
- **The registry is the source of truth in both modes**: in standalone, servers from
  `config.mcpServers` are seeded into the registry at startup (`seedFromConfig`, idempotent), and the
  MCP manager is filled from the registry maps — editing the registry no longer erases servers from
  the config.
- Also moved into core: `/logs/:name` and `/logs/llm`, `/audit` and `/audit/revealed`,
  `/gateway/patterns`, `/context/files*` and `/context/enabled`, `/admin/debug/config`,
  `POST /providers/fetch-icon`. Only guards and texts differ.

### The server announces the instance’s capabilities (`/meta`, ADR-118 §8)

- The instance reports in `GET /api/v2/meta` which optional surfaces it serves (`features.users`);
  settings sections declare the features they need (`requiresFeatures`) and are hidden when the
  server does not serve them. Previously the UI guessed from the deployment type and broke in hybrid
  mode.
- A single point of access to `/meta` — `instanceCapabilitiesStore` (TTL 60 s plus deduplication);
  previously two different paths called `/meta`.
- The allowlist of public paths moved into core (the single source of truth for both builds).

### Caps on search and read tools

- **A 2000-character line cap** for `grep_files` and `read_file` (marker `search.line_truncated`); the
  `metadata.matches` counter is now real.
- **A tool can no longer cancel the overall output limit**: the `metadata.truncated` flag the tool set
  itself was removed — a tool can no longer disable the limit; truncation markers move to the tail
  (`metadata.truncationNote`).
- **Search no longer walks into noise**: the directories `node_modules`, `dist`, `build`, `out`,
  `coverage`, `.venv`, `venv`, `__pycache__`, `.next`, `.turbo`, `.cache` and the files `*.map`,
  `*.min.js` and lock files are excluded. An explicit path wins over the exclusion; hidden matches are
  not lost silently — marker `search.matches_excluded` and `metadata.excludedMatches`. `glob` and
  `list_directory` are untouched: listing answers the question “what is in the project”.
- Incident regression: 242,999 → 1,930 characters; a gigantic line 236,564 → 2,097.

### SSH access to remote hosts (ADR-124)

- Per-agent keys are stored encrypted (`secrets/ssh-keys/`); two modes — `tools` (`ssh_exec`,
  `ssh_copy`, `ssh_tunnel`) and `agent` (ephemeral forwarding agent); the images now ship `ssh`/
  `rsync`.
- A key without a trailing newline no longer breaks `ssh-add`, `user` is required by the SSH tools,
  and the agent runs in the foreground.

### Server-side MCP servers in local hybrid sessions (ADR-125)

Local sessions can use the server’s MCP registry (tool-level proxy and protocol relay) under the same
enable/scope rules as remote ones; existing projects are seeded idempotently, and a failed relay
degrades to tool level with a stated reason.

### Parallel tool execution within a step (ADR-127)

Independent calls of one step execute concurrently (parity with opencode) while the step’s events keep
the declared order; mutating calls (`plan_*`, `project_*`) keep the barrier — the next segment waits
for them.

### Compaction at the step boundary (ADR-128)

Context compaction triggers at the step boundary when the window is nearly full instead of at the end
of the turn; a failed or degraded compaction is reported explicitly instead of passing unnoticed.

### To Do lists of child sessions (ADR-129)

A subagent keeps its own list (`task.todos` at start, the `todo` capability, `<todos>` in the result
and in the background notification) and does not merge into the parent’s list.

### Work panel: plan, To Do, journal, invariants (ADR-130)

Compact lists in the right-hand panel, a modal workspace (board / To Do / journal / invariants /
stats), Markdown editors, a point API with events, and a header button. The project journal is moved
out of the project detail; for `remote:` projects and sessions, the plan, journal, invariants and To Do
are forwarded to the remote backend.

### Heavy-operation limit and batch import (0.13.7)

The limit for heavy operations is configurable (`limits.sessionOpsPerMinute`, runtime setting
“Security → Request limits”, applied without a restart). Batch session import deduplicates entries by
`source_session_id`; publishing a project transfers sessions by dependency level with one request per
level.

### Security

- **Shell-guard:** deny-list bypasses are closed (merged redirections, embedded executors, shell
  prefixes, heredocs, `/proc/<pid>/root`, positional parameters) — and false asks are removed at the
  same time (pattern arguments of `sed`/`grep`/`awk`/`jq`, `find` values, workspace globs, variables
  from `NAME=value`/`for`/`read`). A dynamic command name is resolved when the bindings yield a
  finite set of simple values.
- **A session grant does not widen prohibitions**: it lifts only the dynamic ask; `deny`,
  `approvalPaths`, find mutations and a dynamic `cd` stay in force. The grant is issued by directory
  (`external_directory: "<dir>/*" = allow`), never as a command-wide template; for
  `mutation`/`protected`/`cwd` — and whenever the reason is unknown — no rule is written at all and
  only the one-time approval is issued.
- **Auth boundary:** a single fail-closed `/api/*` gate with a shared allowlist of public paths by
  method+path in core — a router mounted without a guard does not become anonymous; the access census
  fails when an `:id` route appears outside the matrix.
- **API keys:** roles are set by `auth.apiKeyRoles` (default `USER`, ADMIN only explicitly), and the
  key comparison is constant-time; shell-guard deny-list bypasses and session boundaries are closed
  (0.13.4 P0 audit, findings F3–F13).
- **Secrets:** the instance key is not printed into the systemd journal or into CLI output;
  `synth config show` redacts secrets; the secret-scan allowlist was extended with dummy SSH-key
  fixtures only (tests only).
- **The 0.13.8 internal security audit was carried out**, and both problems it found in this wave are
  closed in code **before the release** rather than accepted as a risk:
  - *The grant on a restored approval was wider than what was approved.* Answering “Allow” on a
    request that survived an instance restart issued a permanent session-wide grant as a whole (a
    command like `rm -rf /srv/data` turned into the rule `rm *`, including mutation operations where
    a grant is forbidden). The restored branch now computes the grant by the same plan as a live one,
    from the stored snapshot of the reason; with no snapshot for a shell command, no rule is written at
    all (fail-closed). For an administrator: **a grant issued after a restart is never wider** —
    dynamics are covered by a directory, and `mutation`/`protected`/`cwd` are not lifted by a grant.
  - *Bypassing the overall tool output limit.* The limit could be disabled by a flag the tool set
    itself (`metadata.outputBounded`), so a plugin tool could carry hundreds of kilobytes into the
    context. The limit is now computed from the actual output size, and forged counters are
    overwritten. For an administrator: **the output limit cannot be cancelled from a tool**.
- **The audit record is attached to the release** (`docs/security/releases/0.13.8.json`) and is
  finalized by the gate at tagging time; the residual accepted exceptions of the previous wave are
  tracked in that same record. The audit policy and procedure —
  [docs/security/README.md](../security/README.md).

### Fixed

- **Profile in standalone** (`GET/PUT/PATCH/DELETE /auth/profile`) — saving the profile no longer
  requires a managed deployment.
- **The LLM error `internal server error` inside a provider’s 400 wrapper** is classified as
  `server_error` and treated as recoverable: the turn retries instead of dying. Client-side 400s
  (`no_user_query`, `validation`, `context_length`, `auth_error`) remain unrecoverable.
- **One reload after an update/restart** instead of two: shell cache reset, a one-shot marker and a
  quiet `SKIP_WAITING` of the waiting service worker.
- **Skill availability** is computed from the agent’s capabilities: the DTO gained
  `missingCapabilities`, and “unavailable” is no longer shown falsely.
- **Installation from the beta registry** uses the scoped key `--@itphx:registry` — public
  dependencies are no longer pulled from the closed registry.
- **The mobile approval bar** fits the screen (the timer and the actions wrap), and commands no longer
  expand a heredoc over the whole screen; the reason for code on stdin is now readable in plain words;
  the questionnaire hint appears after the first attempt.
- **Localization:** the empty-screen subtitle is translated, and the worktree form in Russian strings
  is brought to the invariant shape.
- **Other:** a stuck streaming step is fixed in the data, not only in the UI; a terminal step status
  is no longer rolled back by a late draft; the pagination cursor works for legacy sessions with a
  non-unique `seq`; connection-loss indication in the PWA is restored; project management rights in
  the local world of a hybrid instance are no longer blocked for a plain `USER`; publishing a project
  in hybrid mode is no longer bound by the 15 s timeout and reports progress in percent.

### Upgrade and compatibility

- **The data schema is extended** by migrations 031–034 (SSH key policy, MCP remote mode,
  `source_session_id` for import deduplication, `pending_approvals`). When upgrading from 0.13.4, run
  `synth migrate` (for PostgreSQL — before starting the new version).
- **Configuration:** the new `updates.*` and `limits.sessionOpsPerMinute` fields have defaults —
  existing configs stay valid. Priority: env > runtime (UI) > `config.yaml` > defaults.
- **API contracts are extended additively**: `permission.asked` and the recovery DTO gained
  `trigger`, `commands`, `saveDirectories`, `restored`; the session DTO gained `pending_approvals`;
  `/meta` gained `features`; `/api/v2/updates/*` and `/api/v2/settings/updates` are new routes. Older
  clients keep working.
- **Known limitations:** cross-world project moves and remote MCP merging are not implemented
  (ADR-131); an update or a restart still interrupts an active turn; self-update is available to
  standalone only. `PROP-133` (project access) is a proposal and is not part of this release.
