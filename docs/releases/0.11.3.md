### Наблюдаемость и метрики (ADR-094)

- **Экспорт Prometheus.** `GET /metrics` — текстовый формат exposition 0.0.4, вне `/api/v2`, на том же
  порту. Выключен по умолчанию (`metrics.enabled=false`, env `SYNTH_METRICS_ENABLED`): при выключенном
  отдаётся 404, а не 401. Опциональный bearer-токен (env `SYNTH_METRICS_TOKEN` или файл
  `{dataDir}/secrets/metrics-token`, 0600) → 401 при неверном токене; ответ с `Cache-Control: no-store`.
  Скрейп самого `/metrics` в HTTP-метриках не учитывается.
- **Свой мини-реестр без новых зависимостей** (`packages/core/src/metrics/`): counter/gauge/histogram,
  фиксированные `labelNames`, предел 2000 серий и счётчик `synth_metrics_series_dropped_total`;
  корректность рендера закреплена golden-тестами.
- **Контракт кардинальности.** У HTTP-метрик только лейблы `method`, шаблон `route` и `status`;
  `session_id`, `user_id`, сырые пути и query запрещены, неизвестный маршрут сводится к `other`.
  SSE `/api/v2/events` и `/ws/*` исключены из гистограммы длительности (долгоживущие соединения искажают
  p95) — вместо них gauge активных стримов.
- **`/ready` отдельно от `/health`.** `/health` — liveness (процесс жив), `/ready` — 200, когда
  приложение инициализировано (storage context собран, миграции применены, очередь готова); 503 — только
  на старте и при fail-closed. Деградация хранилища **не** выводит pod из балансировки: `/ready`
  остаётся 200, а деградация сигнализируется метрикой и алертом.
- **Домены метрик:** HTTP; процесс/Node (RSS, heap, CPU, event loop lag, uptime, `build_info`); сессии и
  очередь; LLM (провайдер/модель/outcome, латентность, токены, ретраи, стоимость); хранилище (объём
  `{dataDir}`, записи по сторам, degraded/backend); события (ingested/decisions/journal); шедулер; webhooks;
  гибрид; зеркало decision-метрик (ADR-084).
- **Runtime-включение из UI.** Админ-раздел **«Метрики»** (Настройки → Администрирование, категория
  `metrics`, роль ADMIN): статус (`running`, `/ready`, storage, версия, uptime, `series`/`bytes`/
  `droppedSeries`), тумблер, write-only токен, копирование `/metrics`, пример `scrape_config`. Приоритет
  `SYNTH_METRICS_ENABLED` > runtime (`settings.json`/PG) > `config.yaml` > `false`; изменение
  применяется **после рестарта** процесса (`restartRequired` → баннер и кнопка graceful restart).
  API: `GET/PUT/DELETE /api/v2/settings/metrics`, `GET /api/v2/settings/metrics/status`,
  `PUT/DELETE /api/v2/settings/metrics/token` (при env-токене → 409 `CONFLICT`; значение не
  возвращается).
- **Поставка.** Grafana-дашборды (`charts/synth/files/dashboards/`: overview, LLM, events-ops) и правила
  алертов (`charts/synth/files/alerts/synth-rules.yaml`, 19 правил) — в репозитории; dev-стенд
  `docker-compose.observability.yml` и каталог `deploy/observability/`; runbook —
  [docs/OBSERVABILITY.md](../OBSERVABILITY.md).
- **Helm.** Флаги `metrics.enabled`, `metrics.existingSecret`/`tokenKey`/`tokenOptional`,
  `metrics.ingress` (отдельный Ingress только на `/metrics` — ведёт напрямую на Service backend,
  UI-nginx `/metrics` не проксирует) и опциональный `ServiceMonitor` с аннотациями
  `prometheus.io/*`. Дашборды и алерты умеют выбирать окружение и инстанс (`env`/`instance`) — один
  Prometheus обслуживает и dev, и test.
- Остаток ADR-094: JSON-логи с `request_id`/`session_id` и OpenTelemetry-трейсинг — отдельные задачи.

### Единый egress-слой: адресная политика, TLS/CA, прокси (ADR-099)

- **Адресная политика исходящих запросов.** Секции `egress.tools` и `egress.webhooks` и ключ
  `mcp.networkPolicy` — в одном формате `{mode, list, exceptions}`, режимы `deny`/`allow` (для webhooks
  ещё `off` — только dev). Политика применяется **live**, per-request, и действует **на каждый хоп**
  редиректа. Адрес нормализуется единым хелпером (обход через IPv4-mapped IPv6 закрыт), DNS резолвится
  по всем A/AAAA, каждый адрес сверяется с CIDR (fail-closed на ошибку или пустой резолв). Один guard
  (`engine/net/egress-guard.ts`) вместо трёх разных реализаций: через него идут `web_fetch`, webhooks,
  remote-скиллы и URL-источники инструкций, favicon провайдера.
- **Единый канонический список заблокированных диапазонов.** Дефолтный список приватных диапазонов не
  покрывал мультикаст, reserved и broadcast, а в core жил второй, мёртвый список (применялся только когда
  политика не передана — в рантайме этого не бывает), создавая ложное впечатление полноты покрытия. Теперь
  источник истины один — `packages/shared/src/types/mcp.ts`, `DEFAULT_MCP_PRIVATE_CIDRS`: **26 диапазонов**
  (мультикаст, reserved, broadcast, `192.0.0.0/24` с NAT64-префиксами, `198.18/15`, IANA-блоки IPv6), списки в
  core удалены. NAT64-префиксы `64:ff9b::/96` и `64:ff9b:1::/48` намеренно **не** заблокированы: на
  IPv6-only сетях с DNS64 резолвер отдаёт синтезированные AAAA именно из них — блокировка сломала бы egress
  к публичным хостам.
- **Журнал и аудит.** Append-only `{dataDir}/audit/egress.jsonl`: scope, host, url без query и userinfo,
  method, status (`allowed`/`blocked`/`error`), httpStatus, bytes, durationMs, причина, сработавшее
  правило, sessionId/projectId/actor. Тела и заголовки не логируются; retention — `egress.log.retentionDays`.
  Изменения политик пишутся в `{dataDir}/audit/security.jsonl`. Чтение —
  `GET /api/v2/audit/security` и `GET /api/v2/audit/egress` (ADMIN/AUDITOR).
- **Offline-проверка URL.** `POST /api/v2/settings/egress/check` (`scope` + `url`) — разбор URL, DNS и
  сверка по политике **без HTTP-запроса** (эндпоинт сам не становится SSRF-зондом); при прокси честно
  сообщает `addressChecksActive: false` — адрес назначения известен только прокси.
- **Доверие TLS/CA — единый источник.** Секция `security.tls` + env `SYNTH_TLS_*`; приоритет
  env > runtime (UI) > `config.yaml` > defaults. CA-бандл (несколько сертификатов в одном PEM),
  `rejectUnauthorized`, **default mTLS-клиент** и **per-host профили** (`mappings[]`: паттерны `exact`,
  `*.suffix`, `*`, регистронезависимо, первое совпадение — иначе default). Bootstrap-файл
  `{dataDir}/security-tls.json` (0600, читается до подключения к БД), PEM-материалы — в
  `{dataDir}/secrets/tls/` (0600). PostgreSQL использует **тот же** резолвер профиля по хосту, поэтому
  «серт для БД» отдельно не настраивается. TLS-параметры в DSN PostgreSQL **запрещены** — доверие
  задаётся только `storage.postgres.sslmode` и `security.tls`.
- **Runtime-настройки TLS из UI.** API `GET/PUT /api/v2/settings/tls`,
  `PUT/DELETE /api/v2/settings/tls/ca`, `PUT/DELETE /api/v2/settings/tls/client`,
  `POST/PUT/DELETE /api/v2/settings/tls/mappings[/:id]`, `POST /api/v2/settings/tls/validate`. Ответы —
  только метаданные (источники, subject, `hasKey`, `readOnly`): PEM и ключи не возвращаются; параметры
  из config/env — read-only (мутация → 409 `CONFLICT`). Изменения аудируются (`scope:'tls'`),
  применяются **после рестарта** (`restartRequired`).
- **Прокси — часть egress-слоя.** Секция `proxy`: HTTP/HTTPS/SOCKS5, Basic-аутентификация, TLS/mTLS
  **к https-прокси** (отдельно от доверия к цели), `noProxy`, `fromEnv`, `fallbackDirect`, таймаут.
  Модель **«профили + host-правила»**: `mode: all|selected`, `defaultProfile`, `profiles.<name>` (имя
  неизменяемое), `rules[]` — порядок объявления = приоритет, **первое совпадение**; `noProxy` **всегда
  важнее** правил; `action: direct` — без профиля. Паттерны хостов: `exact`, `.suffix`, `*.suffix`,
  `host:port`, IP-литерал, CIDR, `*`; **CIDR матчится только по IP-литералу цели** (DNS для правил не
  резолвится — иначе маршрут зависел бы от DNS).
- **Fail-closed транспорт.** Недоступный прокси → `EGRESS_PROXY_UNAVAILABLE` (тихого «идём напрямую» нет;
  `fallbackDirect` — только явный opt-in и помечается в журнале как `via:'fallback'`). Ошибка
  аутентификации (`407`/отказ SOCKS5) → `EGRESS_PROXY_AUTH_REQUIRED`/`EGRESS_PROXY_AUTH_FAILED`, даже
  при `fallbackDirect` прямой маршрут запрещён. Битая конфигурация (неизвестная схема, Basic без пароля,
  `ntlm`/`negotiate`) — отказ на старте (`EGRESS_PROXY_CONFIG_INVALID`).
- **Пароли и TLS-материалы профилей — только env или файлы.** Профиль `default` —
  `SYNTH_PROXY_PASSWORD` или `{dataDir}/secrets/proxy-password`; профиль `<name>` —
  `SYNTH_PROXY_<NAME>_PASSWORD` или `{dataDir}/secrets/proxy/<name>.password` (0600); TLS профиля —
  `{dataDir}/secrets/proxy/<name>/{ca.pem,client.crt,client.key}`. Значения write-only: не возвращаются,
  не логируются и не попадают в аудит; при env-пароле мутация из UI → 409 `CONFLICT`. В `config.yaml`
  пароли и userinfo не хранятся.
- **API и UI.** `GET/PUT/DELETE /api/v2/settings/proxy` (профили/правила/режим; статус
  `saved`/`running`/`defaults`, `isOverridden`, `password`, `restartRequired`),
  `PUT/DELETE /api/v2/settings/proxy/password`, `.../profiles/:name/password`,
  `.../profiles/:name/tls/ca`, `.../profiles/:name/tls/client`, `POST /api/v2/settings/proxy/check`
  (коннект к прокси по **saved**-конфигурации) и `POST /api/v2/settings/proxy/test` (target-check:
  `HEAD` без редиректов и тела, политика проверяется **до** запроса; в ответе — маршрут, правило,
  профиль, прокси, `ok`, `httpStatus`, `latencyMs`). Новый админ-раздел **«Сеть»**: «Прокси» (режим,
  таблица профилей, правила с приоритетом, write-only пароль и PEM профиля, target-check, плашка
  «требуется перезапуск») и «Доверенные CA (TLS)».
- **Честные ограничения.** Доменная аутентификация прокси (**NTLM/Negotiate/Kerberos**) в приложении
  **не реализована** — `auth.type` только `basic`; она делегирована промежуточному egress-прокси/шлюзу
  (Squid `login=NEGOTIATE`, `px` для NTLM/PAC) — ADR-099 п. 25. **SOCKS5 — best-effort**: доверие к цели
  через SOCKS не поддерживается (`requestTls` не принимается), `proxy.tls` с `socks5://` несовместим,
  GSSAPI нет — п. 26. Per-host маршрут работает только в HTTP-транспорте: git и stdio-MCP получают один
  прокси через child-env и выбрать прокси per-host не умеют (в `mode: selected` прокси-env им не
  ставится). Runtime-reload прокси/TLS без рестарта — остаток.

### Слой хранения и PostgreSQL (ADR-096/097/098, PROP-032)

- **Доменные порты вместо конкретных классов.** `packages/core/src/storage/ports/*` — порт выражает то,
  что домен реально делает (видимость сессий, поиск, «лёгкие» листинги, уникальность метки,
  append-журналы, резолвинг секрета), а не generic-KV; конфиг-словари (провайдеры, модели, агенты) —
  порт `DocumentRepository<T>`. Точка сборки — `StorageContext` (`createFileStorage`/`createMemoryStorage`
  и асинхронный `buildStorageContext` для БД).
- **Контрактный suite — «паспорт» порта** (`packages/core/src/storage/contract/*`): обязателен для любой
  реализации; эталон семантики — in-memory.
- **PostgreSQL как опциональный backend.** `storage.backend: file | memory | postgres` (env
  `SYNTH_STORAGE_BACKEND`, fail-closed на неизвестном значении). Драйвер — отдельный in-tree пакет
  `@itphx/synth-storage-postgres` (peer-dep core, `pg` — optional dependency), подключаемый **динамическим
  `import()`** только при `postgres`, поэтому standalone и локальный home БД не тянут. Реализованы все
  доменные порты; прогон против живой БД гейтится env `SYNTH_TEST_POSTGRES_DSN` (задача
  `test-postgres` в CI). Параметры — секция `storage.postgres`; пароль — только env
  `SYNTH_POSTGRES_PASSWORD` или файл `{dataDir}/secrets/postgres-password`.
- **Координация в multi-replica.** PG advisory-lock'и (`PgMutex`/`PgLeader`) в `StorageContext.locks` —
  для шедулера и выбора лидера.
- **Деградированный режим (ADR-098).** Недоступность БД → `storage.degradedMode: fallback-file | halt`
  (env `SYNTH_DEGRADED_MODE`). `fallback-file` поднимает сервис на **отдельном** каталоге
  `{dataDir}/fallback` в строго read-only режиме: доступ — только ADMIN, мутации → 503
  `STORAGE_DEGRADED_READONLY`, `/health` → `status: 'degraded'`. Авто-возврата нет — только рестарт.
  Ошибки конфигурации/зависимостей и «схема новее» — **fail-closed** (фоллбек не применяется): опечатка
  в конфиге не должна выглядеть как пустое хранилище.
- **Перенос данных между backend'ами.** `synth storage migrate --to postgres|file` — идемпотентно;
  `--dry-run` показывает счётчики по сущностям, без `--yes` — отказ.

### Обслуживание инстанса (ADR-091/092)

- **Бэкап.** `synth backup --out <dir>` — архив данных с манифестом и контрольными суммами (свой
  потоковый ustar-писатель, без внешних зависимостей); флаги `--with-secrets`, `--with-workspace`,
  `--live` (предупреждение о нетранзакционном срезе), `--encrypt` (AES-256-GCM внешним ключом
  оператора; `.enc` восстанавливается **только** через CLI — ключ серверу недоступен).
- **Восстановление.** `synth restore <archive>` — строгий порядок: манифест → формат → версия схемы →
  контрольные суммы → `--dry-run` → `--yes` → страховочная копия → очистка цели → распаковка.
  Восстановление **возвращает каталог к снимку**; `workspaces/` сохраняется, если его нет в архиве
  (защита от потери рабочих файлов проектов). После restore обязателен `synth doctor`.
- **Диагностика.** `synth doctor [--json]` — data-dir, схема, мастер-ключ, права секретов, целостность
  данных, провайдеры, локи, версия; exit 1 при любом `fail`.
- **Версия схемы и миграции.** `{dataDir}/meta.json` (`schemaVersion`/`instanceVersion`/`migrations`);
  реестр миграций идемпотентен. При старте — guard совместимости (данные новее версии → отказ старта),
  затем **обязательная страховочная копия** и применение миграций под межпроцессным локом. Ручной режим —
  `synth migrate --dry-run` / `--yes` (без `--dry-run` и без `--yes` — отказ).
- **Обновление и откат.** `synth update [--apply] [--to <version>] [--dry-run] [--yes] [--json]` —
  проверка, установка или **откат** пакета. Понижение версии данные назад не мигрирует: откат данных —
  только restore из бэкапа, откат версии — `helm rollback` (K8s) или `synth update --to <prev> --apply`.
- **Удаление.** `synth uninstall [--purge|--purge-db|--dry-run|--yes]` — по умолчанию данные сохраняются;
  `--purge` требует `--yes` и предупреждает об утрате мастер-ключа и страховочных копий, `--purge-db`
  удаляет схему БД при `storage.backend=postgres`.
- **Admin-API и UI.** Раздел **«Обслуживание»** (Настройки, ADMIN) и `/api/v2/maintenance/*`: `status`,
  `doctor`, `migrations` (+ `migrations/apply`), `backups` (создание, скачивание, удаление), `restore`
  (`/restore/validate`, `POST /restore` — **отложенное** восстановление, применяется при следующем старте;
  `DELETE /restore` — отмена) и `audit`. Восстановление из API/UI — офлайн: под живым процессом данные не
  вычищаются.
- **Перезапуск инстанса.** `POST /api/v2/maintenance/restart {confirm:true}` → **202**
  `{status, restartId, mode, startedAt}`; процесс завершается штатно с **exit code 75**, поднимает его
  супервизор. Режимы `SYNTH_RESTART_MODE=disabled|process|supervisor` (по умолчанию `disabled`;
  `synth serve --restart-mode` приоритетнее env); `disabled` → 409 `RESTART_UNSUPPORTED`; повторный вызов
  идемпотентен; аудит `restart.requested`. В multi-replica перезапускается только свой pod — весь
  Deployment перезапускается через `kubectl rollout restart`.
- **Аудит обслуживания.** Порт в слое хранения и журнал `{dataDir}/audit/maintenance.jsonl`:
  `backup.created`, `restore.scheduled|applied`, `migrate.applied`, `update.applied`,
  `rollback.applied`, `restart.requested`, `uninstall.purge`.
- **Портативный перенос проекта.** `synth project export|import` (CLI) и HTTP
  `GET /api/v2/projects/:id/export` + `POST /api/v2/projects/import` — архив
  `<name>.synth-project.tar.gz` с манифестом и sha256, опционально `workspace/**`. Импорт —
  materialization (новый `projectId` и новые id сессий), а не funnel `session.requested`;
  `--merge-into` — импорт в существующий проект. Экспорт и импорт идут через **контекст хранения
  инстанса** (`StorageContext`): на `storage.backend=postgres` видны БД-проекты — раньше экспорт
  отдавал 404 для всех БД-проектов, а импорт уходил в файловое хранилище (split-brain).
  UI-кнопки в разделе проекта — остаток.
- **Секреты в портативном архиве — по умолчанию нет.** Каталог `secrets/`, ключи, credentials и
  API-ключи в архив не попадают; дополнительно при упаковке session-payload'ов **вырезается карта
  обфускации LLM Gateway** (ADR-036) — `obfuscation_map` сессии и `messages[].metadata.secrets`
  сообщений (соответствие «плейсхолдер → реальный секрет»), поэтому участник проекта не вывозит
  чужие секреты. Явный opt-in `--with-secrets` (CLI) / `?withSecrets=true` (HTTP) — только
  `ADMIN`/`LEAD` (в standalone/core — локальный владелец); выдача пишется в аудит обслуживания
  (`export.created`, деталь `withSecrets: true`), а такой архив — **сам секрет**. Импорт карту
  принимает: архив, собранный с opt-in, импортируется корректно.
- **Экспорт сессии: доступ — по чтению, карта — по привилегии.** `GET /api/v2/sessions/:id/export`
  отдаёт объект сессии (camelCase, формат publish/fork не изменён). Право на экспорт = право на
  чтение сессии, а карта обфускации Gateway (`obfuscationMap`, `messages[].metadata.secrets`) —
  отдельная привилегия: **полный экспорт** — владелец сессии (`ownerId ?? userId`), `ADMIN` и
  `AUDITOR` (тот же набор привилегий, что у `GET /api/v2/sessions/:id/secrets`); **прочие читатели**
  (участник проекта `VIEWER`/`EDITOR`, владелец проекта, не владеющий сессией, `LEAD`) — **200 с
  очищенным телом** (карты нет, разговор переносится полностью, очистка — на копии, сохранённая
  сессия не меняется); **нет доступа на чтение сессии** — 403 `FORBIDDEN`.

### Аналитика и отчётность (PROP-102)

- **Суточные роллапы вместо пересчёта истории.** Порт `AnalyticsRollupRepository` (ADR-096) с файловой,
  in-memory и PostgreSQL-реализациями; единица роллапа — **сутки в UTC**. Четыре семейства: `usage`
  (токены и стоимость), `activity` (сессии, сообщения, тулы, ошибки, ходы), `decision` (персистентные
  метрики decision-слоя), `prompt` (проекция `usage` на чтении). Дериваты (`cache_hit_rate`,
  `reasoning_ratio`, `output_tps`, итоги по валютам) считаются **на чтении** и не персистятся.
- **API только на чтение.** `GET /api/v2/analytics/{summary,usage,activity,decision,prompt,export}` —
  период `from`/`to` (`YYYY-MM-DD`, UTC, по умолчанию 30 дней), `groupBy`
  (`day,user,project,model,agent,provider`), фильтры по осям. `export` — `report=usage|activity|decision|prompt`
  и `format=csv|json` (CSV — RFC 4180 + BOM, `Content-Disposition: attachment`); серверного PDF/XLSX нет —
  PDF закрывает печать браузера.
- **RBAC.** `ADMIN`/`LEAD` — сквозной обзор, `AUDITOR` — чтение, обычный `USER` — **только свои строки**
  (`summary` и `decision` → 403).
- **UI.** Отдельное лениво монтируемое окно «Аналитика» (входы — меню пользователя и правая панель):
  вкладки «Расход и стоимость», «Активность», «Decision», «Кэш и эффективность», пресеты
  7д/30д/90д/произвольный, группировка, экспорт CSV/JSON и печать браузера.
- **Бэкфилл.** `synth analytics rebuild [--from <date>] [--dry-run|--yes]` — идемпотентная пересборка
  роллапов из истории сообщений и журнала LLM Gateway; без `--yes` (и без `--dry-run`) — отказ.
- **Retention.** `analytics.retentionDays` (по умолчанию 400), чистка на старте и раз в 6 ч. В роллапах
  нет текста сообщений, содержимого промптов, ключей и PII.
- Остаток: лимиты, квоты и алерты по расходу, часовые роллапы и отдельный scope `analytics:read` — вне
  scope.

### Авторизация доступа к сессиям (security)

- **Единый prefix-guard вместо проверок в обработчиках** (`server/session-access-guard.ts`): guard
  вешается один раз на `/:id` и `/:id/*` вместе с `requireAuth`, поэтому покрывает все `:id`-маршруты —
  включая будущие; вид доступа (`read`/`write`) выводится из HTTP-метода.
  - **Это изменение поведения:** раньше проверка жила вызовом в хендлерах — из 22 core-маршрутов ресурса
    сессии она была в 4, а под-ресурсы `messages`/`queue` не проверялись вовсе, то есть любой
    аутентифицированный пользователь мог читать и изменять чужую сессию. Теперь через одну точку решения
    проходят и `/status`, и `/prompt` (состав системного промпта), и `/stats` (статистика по
    агентам/пользователям), и `messages`, и `queue`.
- **Роли участника проекта.** `VIEWER` читает, `EDITOR`/`OWNER` мутируют (`canReadProject` против
  `canEditProjectContent`); read-уровень доступа **не** расширяет права на изменение.
- **Экспорт — не чтение.** Переносимые артефакты доступаются как выдача секретов: экспорт сессии
  `GET /api/v2/sessions/:id/export` — доступ по праву на чтение, но карта обфускации только у
  владельца сессии, `ADMIN` и `AUDITOR`; портативный архив проекта карту обфускации по умолчанию
  вырезает, а привилегированный `?withSecrets=true` (`ADMIN`/`LEAD`) — сохраняет, с записью в
  аудит обслуживания (`export.created`, деталь `withSecrets: true`).
- **Экспорт сессии: очистка вместо 403.** Гибридный publish/fork переносит сессии проекта
  **токеном пользователя** (`forkProjectToLocal` → `remoteClient.exportSession` по каждой сессии
  проекта): запрет 403 сломал бы перенос проекта для обычного участника. Поэтому читателям сессии
  без привилегии карты отдаётся 200 с очищенным телом — секреты не покидают инстанс, а фича
  работает. `AUDITOR` в полном наборе — тот же набор привилегий, что у
  `GET /api/v2/sessions/:id/secrets` (сама карта является секретом); `LEAD` — не аудит-роль и карту
  через выделенный эндпоинт не читает.
- **Экспорт сессии: доступ решает единый guard, карта — отдельная привилегия.** Маршрут
  `GET /api/v2/sessions/:id/export` зарегистрирован **после** prefix-guard'а
  (`app.use('/:id')`/`app.use('/:id/*')`), поэтому доступ к сессии (403/404) решает он, а второй копии
  правила в обработчике больше нет (инвариант 16). Привилегию карты обфускации решает **свой
  route-level guard** `createSessionExportGuard`: **полный экспорт** — владелец сессии, `ADMIN`,
  `AUDITOR`; **прочие читатели** (участник проекта, `LEAD`) — 200 с очищенным телом; без доступа на
  чтение — 403 `FORBIDDEN`.
- **Вырезание карты обфускации — по всем носителям сообщений.** Очистка payload'а вырезала только
  `session.obfuscationMap` и `session.messages[].metadata.secrets`, но сессия несёт сообщения ещё в
  `pendingMessages[]` и `checkpoints[].messages[]` — карта обфускации продолжала покидать инстанс
  через экспорт сессии и портативный архив проекта. Теперь очистка рекурсивная и copy-on-write:
  `metadata.secrets` вырезается в любом месте payload'а, исходный объект не мутируется, формат
  переноса не меняется.
- **Значения плейсхолдеров секретов — по привилегии, а не по факту чтения.** Реальные значения
  `messages[].metadata.secrets` отдавались обычным чтением сессии любому читателю, включая `VIEWER` участника
  проекта, хотя сама карта обфускации доступна только владельцу сессии, `ADMIN` и `AUDITOR`. Теперь значения
  чистятся для непривилегированных читателей (ключи-плейсхолдеры сохраняются, сохранённая сессия не
  мутируется — правка идёт на копии ответа).
- **Импорт workspace — realpath-контейнмент.** Распаковка `workspace/**` при импорте проекта
  проверяет путь по realpath: пре-существующий симлинк внутри workspace больше не позволяет
  записать наружу; ошибка остаётся `invalid-archive` (400 `VALIDATION_ERROR`).
- **Лимит на распакованный объём при импорте архива проекта.** Загрузка архива была ограничена
  100 МиБ, но содержимое записей буферизовалось целиком — gzip-бомба (100 МиБ на входе → гигабайты
  в памяти) исчерпывала память инстанса. Теперь при импорте проверяются **100 000 записей**,
  **128 МиБ на запись** и **2 ГиБ суммарно**, и проверка идёт **в момент чтения** архива (лимит
  записи — по заголовку tar, до буферизации содержимого); превышение → `invalid-archive`
  (400 `VALIDATION_ERROR`). Экспорт проекта не ограничен (архив пишется потоком на диск);
  восстановление бэкапа инстанса — другой артефакт и этими лимитами не ограничено.
- **Импорт сессии в проект — это запись.** `POST /api/v2/sessions/import` требовал лишь права **чтения**
  целевого проекта, хотя импорт сессии в проект меняет его содержимое: участник с ролью `VIEWER` мог
  импортировать сессию в чужой проект. Теперь требуется уровень изменения (`canEditProjectContent` —
  `EDITOR`/`OWNER`), как и для любой другой мутации проекта (инвариант 21: read-уровень доступа не
  расширяет права на изменение).
- **Матрица IDOR.** `packages/backend/src/routes/session-idor-matrix.test.ts` — негативная и позитивная
  матрица (владелец сессии, участник `VIEWER`/`EDITOR`, владелец проекта, `ADMIN`, `LEAD`, `AUDITOR`,
  чужой `USER`) **плюс** тест-перепись по смонтированному приложению: появление `:id`-маршрута вне
  матрицы роняет тест.
- **Git read-роуты: доступ к проекту на границе.** `POST /api/v2/git/scan`, `GET /api/v2/git/log` и
  `GET /api/v2/git/commit` не проверяли доступ к проекту — в managed любой аутентифицированный
  пользователь читал git-данные чужого проекта по его id. Теперь проверка — граничный guard
  (`projectGuard('read'|'write')`): read требует права **чтения** проекта (owner/участник/`LEAD`/
  `ADMIN`), write — права изменения контента; запрос к несуществующему проекту в managed даёт 403
  вместо 404 (fail-closed, без раскрытия существования).
- **Git-роуты: один идентификатор проекта.** Гвард брал id проекта из **query**, а обработчик — из **тела**,
  поэтому `POST /api/v2/git/scan?project_id=<свой>` с телом `{"projectId": "<чужой>"}` проходил проверку и
  затем читал (а на write-роутах — мутировал) чужой проект. Теперь резолвер один, расхождение query и тела
  даёт 403 (fail-closed), а авторизованный id кладётся в контекст Hono — обработчики берут id только оттуда.
- **Аргументы git-тулов валидируются.** Значения параметров попадали в argv git без проверки и без
  разделителя, поэтому значение от модели могло оказаться флагом (`commit="--output=<path>"` в `git_diff`
  писал произвольный файл правами процесса), а `remote` в `git_push`/`git_pull` не сверялся с реестром
  проекта — дочерний git уходил на произвольный хост мимо адресной политики egress и выталкивал содержимое
  репозитория наружу. Теперь действует allowlist формы значения, явно запрещены опасные опции
  (`--output`, `--exec`, `--upload-pack`, `--force`, `--mirror` и другие — 17 позиций), а `remote` привязан к
  реестру репозиториев проекта (ADR-076).
- **Мутации instance-wide настроек — только ADMIN.** В managed мутации `/api/v2/settings/*` были
  защищены лишь `requireAuth`, то есть любой аутентифицированный пользователь мог менять настройки всего
  инстанса. Гейт ADMIN добавлен одной опцией фабрики и одной строкой при монтировании — на все
  instance-настройки; standalone не меняется (один ключ → ADMIN), чтение остаётся доступно по роли.
- **Пароль прокси в теле настроек — явный отказ.** `auth.password` в `PUT /api/v2/settings/proxy`
  больше не игнорируется молча: `validateProxyConfig` отклоняет его по сырому входу, до разбора
  схемой (и в `auth`, и в `profiles.<name>.auth`), с подсказкой, где задать пароль. Значение пароля
  в текст ошибки не попадает.
- **Прочее:** анонимный запрос к ADMIN-роутам → 401 `UNAUTHORIZED` (403 — только аутентифицированному без
  роли); CSP для SPA в core и nginx; побег из workspace через симлинк закрыт единым realpath-хелпером
  (fail-closed на битый симлинк/цикл), `/api/v2/fs/workspace-root*` в managed → 403; лимит
  `POST /api/v2/fs/upload` (по умолчанию 100 МиБ, настраивается `storage.maxUploadBytes` /
  `SYNTH_MAX_UPLOAD_BYTES`).

### Публичная API-платформа и внешние события — доведены до зрелости (ADR-052/ADR-089)

Контур service-key/webhooks/OpenAPI/SDK, приём внешних событий, привязки/маршруты/ключи и шедулер
**вышли в 0.10.0** — в 0.11.3 они не появляются заново. В этом релизе доведены до зрелости:

- **Перенос ключей на PostgreSQL без перевыпуска.** `synth storage migrate` переносит service-key и
  ключи привязок **с исходными id, префиксом и at-rest хэшем** — выданный ранее токен продолжает
  работать после перехода file → postgres. Раньше миграция пересоздавала секрет, и внешние потребители
  (шлюз, installer-ключ) получали 401.
- **Владелец внешне созданной сессии.** В standalone сессия, материализованная из внешнего события, была
  невидима человеку: не попадала в список, `GET` по id давал 403, WS-события не доходили — резолвер
  внешней идентичности возвращал UUID профиля вместо литерала `local`. Резолвер нормализован; внешний
  идентификатор (`tg:<id>`) остаётся внешним — для routing, привязок и `metadata.principal_id`.
  Legacy-сессии с владельцем-UUID нормализуются **при чтении** (данные не перезаписываются).
- **Уведомление хаба о новых сессиях** — инвариант, а не точечная заплатка: детект события вынесен в
  общий шов `packages/core/src/events/child-session.ts`, им пользуются и managed `EventHub`, и standalone
  `/ws/events`; путь, создающий сессию, публикует `session.created`. Закрыты разрывы: дочерние сессии
  тула `task`, `forkProjectToLocal`, импорт/перенос проекта, resume субагента. В standalone добавлен
  реестр подписок WS — сессия, созданная **после** подключения клиента, больше не остаётся без
  подписчиков («0 subscribers — EVENT LOST»). Подписка строго по владельцу (нет владельца —
  fail-closed).
- **Публичный контракт:** из него удалено мёртвое поле `Session.engine` (`'synth'|'opencode'|'cline'`) —
  логики по нему нет (адаптеры движков — PROP-050). **Ломающее изменение** для потребителей OpenAPI/SDK:
  ответы `GET /sessions*`, `GET /sessions/:id/messages` и тела создания/обновления сессии больше не
  содержат `engine`; данные существующих сессий читаются как есть, миграция не требуется.

### Offline-дистрибуция (PROP-101)

- **Portable-архивы для закрытого контура** (`scripts/offline/`): приложение + pinned Node 22 + ripgrep +
  launcher'ы + установщики. Linux x64, macOS Intel/ARM, Windows x64 (per-user, без admin rights).
  Нативные пакеты (`.deb`/`.rpm`/`.msi`/`.pkg`) не выпускаются.
- **Сборка:** `node scripts/offline-bundle.mjs [--platform <name>|all] [--out <dir>] [--skip-build]
  [--source-date-epoch <s>]` — детерминированная упаковка, `manifest.json` (версии Synth/Node/ripgrep,
  sha256, `gitCommit`) и `SHA256SUMS`. Сборка **без интернета**: через предзаполненный кэш
  (`--node-cache`/`--rg-cache`) или локальные распаковки (`--node-dir`/`--rg-dir`); архивы сверяются с
  официальными SHA256, при несовпадении сборка падает.
- **Установщики:** `install.sh`/`uninstall.sh` (Linux/macOS) и `install.ps1`/`uninstall.ps1` (Windows) —
  конфликт чужого launcher'а приводит к отказу без полуустановки; `systemd` user-unit; offline-доки
  RU/EN в `share/docs`.
- **Установщик проверяет целостность бандла (fail-closed).** Манифест уже нёс sha256 верхнеуровневых
  файлов, но payload (`app/**`) был покрыт лишь счётчиками — подменённый бандл в закрытом контуре ставился и
  исполнялся без сверки. Теперь в бандл пишется `files.sha256` — sha256 каждого файла рекурсивно, — а
  `install.sh`/`install.ps1` сверяют всё **до** любых файловых операций и до запуска bundled node, разбирая
  манифест системными средствами (awk / .NET) и не исполняя код проверяемого бандла; несовпадение — отказ.
  Значение `synthVersion` из манифеста валидируется по строгому шаблону до любых ФС-операций (неранее оно
  попадало в `rm -rf` / `Remove-Item -Recurse -Force`, и значение `../../etc` удаляло `/etc`).
- **Multi-arch образы:** `amd64` (kaniko) + `arm64` (buildx, без QEMU) и best-effort manifest list;
  офлайн-образы `synth`, `synth-backend`, `synth-ui` собираются локально и складываются как `docker save`
  архивы с `SHA256SUMS`.
- **Helm без Keycloak:** пример `charts/synth/examples/values-apikey.yaml` —
  `backend.auth.apiKey.enabled: true` (ключ — только в Secret) и `backend.oidc.enabled: false`;
  несовместимо с OIDC, чарт падает на рендере.

### Надёжность и исправления

- **Egress-прокси на Node 22:** `EgressDispatcher` безусловно объявлял new-style handler
  (`onRequestStart`), а `fetch` в Node 22 (undici 6.x) отдаёт legacy-handler (`onHeaders`) — ответ
  терялся и запрос висел. Обёртка стала style-aware, одноразовый dispatcher освобождается через
  `destroy()`; добавлены регрессионные тесты на legacy-контракт (на Node 26 этот путь был слеп).
- **FileMutex:** добавлен owner-токен — `release`/`touch` срабатывают только для своего лока,
  stale-takeover перезаписывает токен; `ScheduleStore` продлевает лок heartbeat'ом на время долгой мутации.
- **«Стоп» больше не теряется.** Запрос остановки, попавший в окно между постановкой сообщения в
  обработку (Phase 1 пишет сессию) и созданием контроллера отмены, уходил в пустоту: `abort()`
  вызывался у ещё не созданного контроллера, и LLM-вызов уходил до конца, хотя пользователь уже
  нажал «Стоп». Теперь остановка перепроверяется непосредственно перед вызовом модели, сам вызов
  не запускается вовсе, а `stream.cancelled` публикуется ровно один раз. Найдено первым живым
  прогоном CI на релизе, закреплено детерминированным регрессионным тестом.
- **Правки ядра:** `qa_pass`/`qa_reason` больше не теряются при персистентности; permission субагента не
  теряется в режиме контекста `none`; read-modify-write сессии — под `SessionManager.withLock`; ответ
  micro-first больше не затирается устаревшим снапшотом.
- **Docker:** права на `packages/backend/dist` в образе не зависят от umask/ACL (`chmod a+rX`) — иначе под
  непривилегированным uid был EACCES.
- **Зависимости:** MCP SDK 1.32.1 и simple-git 4.0.2 — закрытие critical-замечания аудита.
- **CI:** рекурсивные задачи pnpm 12 (разрешён намеренный цикл workspace `core ↔ storage-postgres`),
  драйвер хранилища собирается **до** тестов core (тесты деградации динамически импортируют его),
  контрактный suite PostgreSQL вынесен в отдельную задачу `test-postgres`. Ожидание появления версии
  в npm-реестре больше не может зависнуть намертво: у запроса есть таймаут и общий бюджет ожидания.
- **Внутренний аудит безопасности перед релизом** — обязательный гейт `security-gate` в `release.yaml`:
  сборка не проходит без содержательной записи аудита релизуемой версии
  (`docs/security/releases/<version>.json`, обязательные `command`+`result`, fail-closed); secret-scan
  дерева и истории (15 правил, allowlist `.gitleaks.toml`); ратчет зависимостей (в обычном CI
  `pnpm audit` остаётся report-only, блокирует только релизный гейт). Документы:
  `docs/security/README.md`, `docs/security/AUDIT-CHECKLIST.md`.
- **Гейт читает результат тестов по JSON-отчёту, а не по текстовой сводке, и печатает вывод упавшей
  команды:** разбор человекочитаемой сводки vitest зависел от её формата и остановил релизный прогон
  при зелёных тестах. Теперь счётчики берутся из машинного отчёта (`numPassedTests`/`numFailedTests`),
  нечитаемый отчёт — fail-closed, а провал читается из лога джобы без локального воспроизведения.

### Ограничения и открытые пункты

- **Offline-архивы образов и multi-arch (arm64) в 0.11.3 не опубликованы.** Их сборка требует
  Docker-демон (buildx и проверка запуском контейнера), а раннер сборки релизов работает в контейнере
  без `/var/run/docker.sock`. Опубликованы: npm-пакеты, amd64-образы в `gitverse.ru` и `ghcr.io`,
  Helm-чарт и portable-бандлы (архивы для установки без сети). Публикация arm64 и offline-архивов
  перенесена в 0.12.0 — сборка переносится на раннер с Docker-демоном либо на kaniko.
- **SSRF/TOCTOU (PROP-100) — не реализовано.** Адресная проверка и установка соединения разделены во
  времени: проверенный адрес не «закрепляется» за соединением, поэтому остаётся окно DNS-rebinding.
  Пиннинг адреса — отдельное предложение и в 0.11.3 не входит.
- **Доменная аутентификация прокси** (NTLM/Negotiate/Kerberos) делегирована промежуточному
  egress-прокси/шлюзу; в приложении поддерживается только Basic.
- **SOCKS5** — best-effort: без доверия к цели (CA/mTLS) и без `proxy.tls`.
- **Runtime-reload прокси/TLS** без рестарта не поддерживается: настройки сохраняются, но применяются при
  следующем старте (`restartRequired`).
- **Per-host маршрут прокси** работает только в HTTP-транспорте; git и stdio-MCP получают один прокси
  через child-env. Дочерние процессы git не проходят и через адресную политику egress: `remote` привязан к
  реестру репозиториев проекта (произвольный URL выбрать нельзя), но per-host маршрутизация к дочернему git
  не применяется, а адрес его соединения политикой не проверяется.
- **Политика protected-paths не распространяется на HTTP-роуты файлов.** Запрет путей администратора
  действует на тулы агента (`write_file`, `execute_shell`) и на маршруты `/api/v2/fs/workspace-root*`, но не на
  основные файловые маршруты `/api/v2/fs/*`: путь внутри workspace, запрещённый политикой, всё ещё отдаётся
  через `GET /api/v2/fs/read` и `GET /api/v2/fs/download`. Исправление — применить deny-проверку в единой
  точке резолва пути FS-роутов; план — в 0.12.0.
- **Вывод `execute_shell` не фильтруется.** Команды чтения окружения (`env`, `printenv`) считаются
  read-only, поэтому проходят в режиме `plan`, а их вывод — значения `SYNTH_API_KEY`,
  `SYNTH_PROXY_PASSWORD`, `SYNTH_SECRET_KEY` и других переменных инстанса — попадает в контекст модели без
  фильтрации. Исправление — считать env-дампы чувствительными и добавить скруббер известных секретов в вывод
  тула; план — в 0.12.0.
- **Денylist shell-команд совпадает по форме.** Правило `deniedCommandPrefixes` сопоставляет токены префикса
  буквально, поэтому правило на `rm -rf /` не покрывает `rm -fr /` или `rm --recursive --force /` — совпадает
  ровно одно написание. Исправление — нормализовать форму команды перед сопоставлением (флаги в любом
  порядке, длинные опции) либо опираться на классификацию мутирующих команд и protected-paths; план — в
  0.12.0.
- **Реестр агентов инстанса — per-process:** определения читаются при старте процесса, поэтому в
  multi-replica развёртывании реплика видит только свой реестр (изменения, сделанные через API,
  применяются в обработавшем их процессе).
- **`Session.engine` удалён из публичного контракта** — намеренное ломающее изменение для OpenAPI/SDK
  (детали выше).
- **Аналитика:** лимиты, квоты и алерты по расходу не входят; серверного PDF/XLSX нет (PDF — печать
  браузера); `decision`-роллапы не пересобираются бэкфиллом (нет истории метрик).
- **Хранилище:** онлайн-срез бэкапа нетранзакционен (`--live` — с предупреждением); инкрементальный бэкап
  и PITR — остаток.

### Как обновиться

- **npm** (7 пакетов): `npm i -g @itphx/synth@0.11.3` — CLI-обёртка подтягивает `@itphx/synth-core`,
  `@itphx/synth-shared` и `@itphx/synth-ui`; отдельно публикуются `@itphx/synth-backend`,
  `@itphx/synth-sdk` и `@itphx/synth-storage-postgres`.
- **Docker:** образы с версионным тегом `0.11.3` (amd64/arm64) —
  `gitverse.ru/itphx/synth:0.11.3`, `gitverse.ru/itphx/synth-backend:0.11.3`,
  `gitverse.ru/itphx/synth-ui:0.11.3` и те же три образа в `ghcr.io/itphx/`.
- **Helm:** чарт `synth` версии `0.11.3` (`helm upgrade synth <репозиторий>/synth --version 0.11.3`).
- **Перед обновлением** — бэкап (`synth backup`): миграция при старте может изменить данные необратимо.
  Откат данных — только restore из бэкапа; откат версии — `helm rollback` или `synth update --to <prev>
  --apply`.
- **Проверка после обновления:** `synth doctor`, `GET /health` и `GET /ready` (деградация хранилища
  оставляет `/ready` = 200).
