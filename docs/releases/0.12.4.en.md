## 0.12.4 (2026-10-28)

**Cumulative release notes for the 0.12.x wave (0.12.0–0.12.4), not a single patch delta.** 468 commits
after v0.11.3 (1,305 files, +250,050 / −6,424 lines) close five large areas: **extensibility** (the plugin
layer, memory, pipelines, extension packs), **autonomous agent work** (background runs, mid-turn questions,
steering, git worktrees), **multimodal attachments and instance state in SQL**, the **tool execution
environment** (executor, flavor images, all-in-one) and the **gateway core**. Within the wave, the plugin
layer, memory and pipelines, background runs and questions, worktrees and the executor, and finally
attachments and the blob store landed in sequence. Version 0.12.3 was also published to npm; it has no
separate notes and is covered by this document.

### Plugin layer (ADR-090)

- **Extension API v1 is complete** — phases Ф0–Ф7 and debts Д1–Д3. The `synth.pack` manifest
  (`kind: "plugin"`), the `PluginHost` loader (resolve → integrity → semver gate → trust/scan → mode policy
  → import → facade → disposers → audit) and bundle-only distribution: a plugin arrives as one bundle and
  does not pull host dependencies.
- **Three extension points:** `promptBlocks` (system prompt blocks, composed by `SystemPromptComposer`),
  `llmFilters` (`pre_request` / `post_response` / `embedding` phases) and `tools` (namespace
  `plugin_<ns>_<tool>`, visible to the permission layer). Declared `provides` are checked against actual
  registrations at activation — “declared but not registered” does not pass.
- **Two execution modes:** `inline` (code inside the core process) and `out-of-process` (a separate
  process, an HTTP/1.1 + JSON wire protocol modelled on the ADR-077 executor, a token file). The mode is
  selected in the manifest, so heavy or untrusted code can live outside the process boundary.
- **Trust model:** levels `builtin` → `verified` → `trusted` → `community`, an instance trust floor
  (`trusted` by default) and a static bundle scan. Only a plugin with an effective trust ≥ `trusted` has
  veto power (`deny`/`redact`); for `community` the verdict is downgraded to `allow` and written to the
  journal. A `caution` verdict means quarantine plus an ADMIN approval bound to the bundle **content hash**
  and valid for **24 hours**; the approval is checked both at install and at activation.
- **Install and lifecycle:** sources are a local directory/`.tgz`, an npm package and an https archive URL;
  `update` from the lock entry’s source and `rollback` to the previous step; removal is idempotent. CLI —
  `synth plugin scan|install|update|rollback|approve|enable|disable|remove|list`; HTTP — `/api/v2/plugins*`
  (install, approve, enable/disable, rollback, update, token) with an RBAC matrix; the action journal is an
  append-only `GET /api/v2/plugins/audit` (`{dataDir}/audit/plugins.jsonl`, in PostgreSQL the `plugin_audit`
  table).
- **UI and operations:** the admin section “Plugins” (version, mode, trust, scan verdict, content hash,
  activity, journal) and the CLI. Instance policy — `plugins.executionEnabled`, `trustFloor`, `scan`,
  `runtimeInstall`, `deployDir`/`deployTrust`, `managedReadonly`; changes take effect **after a restart**.
  In managed mode installation is deploy-time and runtime installation is denied by default.
- **Hybrid:** the server publishes the policy (`/auth/oidc-meta`, `GET /api/v2/settings/plugins`). Level 1
  is a cooperative allow-list (a local core does not activate a plugin outside the list, but keeps working
  when the server is unreachable); level 2 is a server-scoped token bound to `plugin_id` (scope
  `plugins:invoke`, header `X-Synth-Plugin-Id`); level 3 (client attestation) is outside v1.
- Documentation: [docs/PLUGINS.md](../PLUGINS.md) and the EN mirror [docs/en/PLUGINS.md](../en/PLUGINS.md),
  HTTP — [docs/API_V2.md](../API_V2.md) §5.36, configuration — [docs/CONFIGURATION.md](../CONFIGURATION.md).

### Memory (ADR-107, the implemented core of PROP-047)

- **Memory is a plugin, not a core subsystem.** The core provides the domain ports
  `MemoryFactRepository`/`MemoryIndexRepository` (facts with versions and provenance, indexes with
  generations, a fingerprint and chunks; file/memory/PostgreSQL, migrations `017`–`020`), scoped access
  `facade.memory` (the host enforces the `plugin:<name>` namespace), `facade.embed` **only** through
  `GatewayProvider.embed`, `facade.getSettings` and `facade.security`. The memory logic lives in the
  `@itphx/synth-plugin-memory` plugin (private, deploy-time and dev).
- **Vanilla RAG in the plugin:** a markdown-aware chunker (1,200 characters / 200 overlap), embeddings in
  batches of up to 32 texts, an atomic generation switch, a fingerprint of `model + dimension + chunker
  version` (a model change marks the index `stale` even at the same dimension), hybrid keyword (BM25-lite)
  + cosine search merged with RRF (`k = 60`), and evidence with a path, line range and score. Without an
  embedding model the index is not built and recall degrades to keyword.
- **Index scope:** `project` (the default — visible only to its project) and `instance` (a shared instance
  corpus). An instance `files` index uses the workspace of the specified project as its corpus and
  deliberately exposes it to all users (an ADMIN action, with a warning in the UI); a `facts` index covers
  all active instance facts (capped at 1,000). Recall and `memory_search` merge project and instance
  results, deduplicating by `indexId:chunkId`.
- **Portal in the core:** `GET /api/v2/memory/{status,facts,facts/:id,indexes}`, `POST /memory/indexes`,
  `POST /memory/indexes/:id/rebuild`, `DELETE /memory/indexes/:id`, `POST /memory/consolidate`,
  `GET /memory/graph`. Reads — `requireAuth` (core) / ADMIN (managed); project operations are checked **at
  the boundary** (`read`/`write`; `VIEWER` reads only). Index mutations go through the plugin’s admin tool;
  no active plugin → `409 MEMORY_PROVIDER_UNAVAILABLE`, no ports → `503 MEMORY_UNAVAILABLE`.
- **CLI `synth memory`** is a thin portal client: `status`, `list`, `index`, `rebuild`, `drop` (options
  `--scope project|instance`, `--wait`, `--timeout`, `--json`; `drop` without `--yes` is refused).
  Connection — `--url`/`--token`/config/`{dataDir}/secrets/api-key`.
- **Consolidation and graph:** fact deduplication by embeddings, an entity graph without an LLM, and an SVG
  visualisation in the memory admin section. Built-in pipeline templates: `builtin:memory-consolidation`
  (session → facts), `builtin:memory-consolidate-facts` (duplicate facts), `builtin:memory-reindex` (all
  project indexes).
- **Observability and UI:** the “Memory” tab in the right panel (`GET /sessions/:id/memory` — aggregates
  without texts), a `memory.guide` block in the system prompt (only when memory is available), a per-project
  memory toggle, `synth_memory_*` metrics and the “Synth — Memory” Grafana dashboard.
- **Secrets:** secret files and directories are not indexed (the policy lives in the core and the plugin asks
  `facade.security`); there is **no** obfuscation during indexing — chunks go to the embedding provider as
  they are. Local embeddings (Ollama) are recommended. Design — [docs/MEMORY.md](../MEMORY.md).

### Pipelines (ADR-100/101)

- **Two contours.** An extension pack `synth.pack` (`provides`: mcp/skills/agents/pipelines) is installed in
  one operation via `POST /api/v2/packs` with ADMIN approval; the service-key scope is `automation:install`.
  The legacy “declaration + accounting” contour remains functional and lists definitions/runs. The new
  engine is ADR-101.
- **Run engine** (`engine/pipelines/`): a `PipelineSpec` graph, `agent`/`script`/`tool`/`human` nodes,
  transition conditions (a structured DSL, fail-soft), step retries and timeouts, a transition limit, a HITL
  pause `awaiting_human` with `resume`, cancellation via `AbortSignal`, and an append-only run journal with
  secret sanitisation. A run uses only a **published** version; a pipeline has at most one active run at a
  time.
- **Versions:** a draft is edited without a version bump; `publish` creates an immutable published version
  and the next draft version; re-publishing without changes is idempotent.
- **HTTP and permissions:** `/api/v2/projects/:id/pipelines*`, `/api/v2/pipeline-runs/:runId*` (header,
  journal, HITL `resume`, `cancel`), `/api/v2/pipeline-templates*` (list and instantiate). Reading requires
  project read access (`VIEWER` can read), writing requires permission to change project content; checks
  live at the boundary; a service key needs scope `automation:install` plus `allowedProjects`.
- **Visual editor:** its own IR is `PipelineSpec`, not the React Flow format (the `specToFlow`/`flowToSpec`
  adapter is lossless); node palette, inspector, condition editor, edges, a “Visual / JSON” switch and a
  “Validate” button (`validatePipelineSpec`). React Flow attribution is kept (licence).
- **Templates:** instance templates plus legacy pack definitions are converted on the fly at instantiation
  (`agent` steps → nodes; `loop` is not converted → `409 PIPELINE_TEMPLATE_UNSUPPORTED` with a list of
  problems). `installedBy` provenance is preserved.
- **Schedule target `pipeline`:** `ScheduleTarget = {mode:'pipeline', projectId, pipelineId, version?,
  payload?}` — the scheduler starts a run **directly** (no session is created, no event is published to the
  Router), the Job gets a `runId`, and the pipeline must be published. `payload` is static.
- **Run artifacts and attachments:** artifact bytes live in the blob store
  (`artifacts/<runId>/<name>`, tracked by `blob_refs`), metadata in the run header;
  `GET /api/v2/pipeline-runs/:runId/artifacts/:name` serves the object with `ETag`/`304` and
  `Content-Disposition: attachment`. A run accepts `attachments[]` (links validated before the start,
  hydration identical to sessions, `ownerKind: 'pipeline-run'`).
- **Tools and skills:** 12 `pipeline_*` and 6 `schedule_*` tools (capability `pipeline`/`schedule`),
  mutations are forbidden in plan mode, `pipeline_run_resume` is an `approve` action (ADR-106); built-in
  skills `synth-pipelines` (`/pipelines`) and `synth-schedules` (`/schedules`).
- **UI:** the “Pipelines” tab in the left panel, pipeline and run center tabs, HITL “Approve”/“Reject”
  buttons, live progress via `pipeline.run.*` events without a separate transport. Design —
  [docs/PIPELINES.md](../PIPELINES.md), API — [docs/API_V2.md](../API_V2.md) §5.35.

### Background runs and user questions (ADR-111/112/113)

- **Background subagents:** `task({background: true})` returns immediately; the run has its own
  `AbortController`, `streamId` and cancellation, the child is marked busy, depth is 1 and limits apply.
  Completion reaches the parent as exactly one notification (`child.completed|failed|cancelled` + a message
  and an auto-turn); the terminal transition is idempotent. `task({task_id})` continues the child. After a
  restart unfinished records are marked `orphaned` — background runs are not resumed.
- **Background processes:** `execute_shell({background: true})` creates a record in the shared registry
  (`{dataDir}/processes/registry.json`, PostgreSQL `021`/`022`), the log goes to the blob store, with a
  `maxLogBytes` limit and `SIGTERM` → `SIGKILL` after 5 s. The `background.enabled` gate applies; events are
  `process.started`, `process.exited`, `process.stopped`, `process.detached`.
- **Detaching a running call (detach):** `POST /api/v2/sessions/:id/background` moves a foreground `task` or
  `execute_shell` call into the background; the move is **one-way**, and `process.detached` is published to
  the session channel. The parent’s “Stop” does not stop the detached run — it has its own Stop. In the UI —
  the “Send to background” button, and `ctrl+b` for all blocking runs of the active session.
- **User question:** the `question` tool (1–5 questions, up to 8 options, a free answer ≤ 1,000 characters,
  an optional `timeout` ≥ 5 min; no timeout by default) pauses the turn until answered. The record is
  persistent (`questions.json`/PostgreSQL `021`); unfinished questions are marked `interrupted` on restart;
  HTTP — `GET/POST /sessions/:id/questions[/:qid/answer|cancel]`, events `user_question.*`. The tool is
  denied to subagents and allowed in plan mode.
- **Registry and UI:** a single `GET /api/v2/processes` (processes and background subagents) behind a
  boundary guard; the “Processes” tab in the right panel shows statuses, stop/delete, a log with
  auto-refresh, opening the child session, and notifications on start and terminal transition. The question
  dock sits above the composer with collapsing, segments, a “question → answer” review step and a countdown.

### Worktrees and steering (ADR-114/104)

- **Git worktrees:** each session can work in its own working directory with shared history. The root is
  `{workspacesRoot}/.worktrees/<projectId>/<slug>`, and a `WorktreeRecord` lives in the
  `WorktreeRepository` port (three backends, no new migration). The binding is an additive
  `Session.worktree`; directory resolution order is worktree → `project.workspace` → default, and subagents
  inherit the parent’s binding. A missing directory is fail-closed, not a silent fallback.
- **Tools and API:** `git_worktree_list|create|remove|prune` (capability `git_read`/`git_write`; mutations
  are forbidden in plan mode), `GET/POST /api/v2/projects/:id/worktrees`, `DELETE .../:wid`,
  `POST .../prune`, binding via `PATCH /api/v2/sessions/:id {worktreeId}`. The `worktree.updated` event
  invalidates the Files tree; `.worktrees` is hidden from the tree and search.
- **Lifecycle:** deleting a “dirty” worktree is a two-step confirmation (`forceRequired`), a bound session
  gives 409, `prune` only removes records without a directory, a sweep of orphaned records runs at start,
  and an optional `project.worktreeSetupScript` runs through `ExecutionPort`.
- **UI:** the worktree inventory in the right panel (“Project” and “Session” tabs), a working-directory
  selector, a secondary-worktree indicator and hiding `.worktrees`. Design — [docs/WORKTREES.md](../WORKTREES.md).
- **Steering:** the send mode is the `mode` field (`queue`/`steer`/`interrupt`) in `POST /prompt` and the WS
  `send_message`; `steer` weaves input into the current turn at a step boundary, `interrupt` cancels
  generation without ending the turn. Ordering is `interrupt` before `steer`, FIFO within a class; the
  injection limit is 5 (`429 STEER_LIMIT_EXCEEDED`). It also works for a child/background subagent session
  (the shared `engine/steering/apply.ts`). In hybrid mode `mode` reaches the remote side and the response
  carries `mode_applied`. Unapplied injections are dropped at the end of the turn/on Stop (`steer.dropped`).
  In the UI — an icon “Intervene” toggle and intervention/interruption markers.

### External access and Authority (ADR-105/106)

- **External access (OAuth connectors):** the `ExternalCredential` entity with an expiry and status
  (`active`/`expired`/`revoked`/`error`), a port (file/memory/PostgreSQL, migration `012`), an OAuth client
  with PKCE/device flow/refresh with CAS/revoke through `egressFetch`, encryption at rest (`enc:v1:` in
  `secrets/oauth/`). Secret headers do not follow redirects to another host; a plaintext secret in the MCP
  registry is forbidden (`400 MCP_SECRET_HEADER_FORBIDDEN`) with migration to an access. The provider
  catalog is `oauth.providers`.
- **MCP binding:** the access token is injected into the transport dynamically, with exactly one refresh per
  request on `401`. HTTP — `/api/v2/oauth/credentials*` (issue, list, metadata, refresh, revoke, bind to a
  connector); the operation journal is append-only `{dataDir}/audit/credentials.jsonl` (not a public API).
  Master-key rotation (`synth secrets rotate`) covers external access and webhook signing secrets; backup
  and project export never carry tokens. UI — the “Accesses” section.
- **Authority layer:** permissions are reduced to one model — the turn principal (`Turn.principal`), session
  participants (`Session.participants`), a session ceiling and a restriction on `PATCH mode`, and
  `permission.asked` approvals bound to the principal and the turn. The resolver went through shadow mode
  and is now enforced by the permission layer; decisions are visible in metrics. Content:
  `provides.authority` at pack install, `pending_approval` “on the merits” (a summary of roles/actions/
  targets), activation in the instance policy with a trust floor, PostgreSQL ports. UI — the “Authority”
  section (read-only). Remainder — flavor roles (PROP-082). Design — [docs/AUTHORITY.md](../AUTHORITY.md),
  [docs/EXTERNAL_ACCESS.md](../EXTERNAL_ACCESS.md).

### Multimodal attachments and instance state (ADR-115/116)

- **The content model is extended additively:** `PartType` plus `image`/`audio`/`video`/`file`; a media part
  carries a **reference** (`blobPath`, `sha256`, `mime`, `size`, `name?`) while `content` carries a
  placeholder (`[image: name.png]`), so string derivatives (DB, export, search) never lose the fact that an
  attachment exists. The LLM call contract gains `LLMMessage.attachments`.
- **Blob store:** originals are content-addressed at `{dataDir}/blobs/attachments/<sha2>/<sha256>`, with
  deduplication, a name sidecar, reference tracking in `blob_refs` (migration `024`) and GC by references
  plus `attachments.gcDays`. The DB and the message carry only a reference. Metadata (EXIF/IPTC/XMP) is
  stripped **only at the provider boundary**; API delivery and workspace materialisation return the original.
- **HTTP:** upload into a session and delivery with `Range`/`206`/`416`, `ETag`/`304`, `HEAD`; staging
  upload **outside a session** (`POST /api/v2/attachments`, `GET/HEAD /api/v2/attachments/:sha256` — for
  gateways and pipelines); `attachments: string[]` in `POST /prompt` becomes media parts; outbound —
  `stream.done.attachments` and delivery by sha. The Gateway neither obfuscates nor logs base64 — only a
  `{mime,name,sizeBytes}` summary.
- **Hydration: native → aux text → drop.** Modalities come from the provider catalog. If the model accepts
  the modality, the attachment goes as is; if not, an aux model of the family from
  `attachments.modalityModels` (`image`/`pdf`/`audio`/`video`) produces text; if there is no processing, the
  attachment is materialised into `<workspace>/attachments/` with an `[ATTACHMENTS NOT DELIVERED]` block.
  Silent loss is forbidden; the session model never changes.
- **Audio and video:** audio formats follow a provider predicate (OpenAI wav/mp3, RouterAI plus ogg/opus,
  Anthropic protocol — only wav and only RouterAI); when an aux audio model is configured, audio always goes
  through it. Video is native on RouterAI (`video_url`), otherwise frames via `ffmpeg`; for a model with
  `video` but without `audio`, the track is extracted and transcribed by an aux model
  (`[video-audio: <name>]`). “Audio-in-video” (an MP4 with a black frame) was removed — it burned tokens
  without benefit.
- **Media from tools and other contours:** `ToolResult.attachments` + `web_fetch({include_media})`, injected
  into the **current** turn; MCP attachments (executor protocol 5); external event attachments
  (`attachments[]`, an explicit `dedupKey` is required); pipeline run attachments. Tools:
  `attach_workspace_file` (workspace file → attachment), `save_attachment` (attachment → workspace file),
  `send_attachment` (file → reply attachment, `stream.done.attachments`).
- **UI:** button/drag-and-drop/paste in the composer, file preparation (HEIC→JPEG, office→text+images), chips
  and a gallery, feed rendering (image grid, `audio`/`video` with `controls`, files as chips), a modality
  gate from the catalog. Runtime settings — `/api/v2/settings/attachments` (limits, allowlist,
  `modalityModels`, `workspaceFallback`, `gcDays`).
- **Instance state in SQL (ADR-116):** four ports moved to PostgreSQL — `packs`, legacy `pipelines`,
  `skills` (metadata; content in the blob store) and `contextFiles` (the user part; image system prompts stay
  on the filesystem). Migrations `024`–`027`: `blob_refs`, `packs`/`pipelines`, `instance_skills`,
  `context_files`. `blobs` stays **file-based by design**: bytes on the volume, only references in the DB;
  attachments remain readable when storage is degraded.
- **Transfer and chart:** `synth storage migrate` moves the new ports both ways (`blobs` — never); the
  PostgreSQL driver no longer assembles a file context — the core runtime import is narrowed to
  `FileBlobStore` and `ContextConfig`. The chart gains an optional separate blob volume (`backend.blobs.*`);
  with `replicaCount > 1` it requires `ReadWriteMany` (otherwise rendering fails). Portable project
  export/import (format 2) moves attachment bytes and `blob_refs`.

### Executor and deployment topologies (ADR-077)

- **The `ExecutionPort`:** `inline` and `remote` modes, the `execution.mode` switch, a dynamic `import()` of
  `@itphx/synth-executor`, and a fail-closed startup check (there is no silent fallback to local execution).
  Control-plane git operations go through the port; `simple-git` was removed from the core.
- **The executor protocol is now 5:** 2 — MCP endpoints, 3 — background processes, 4 — call secrets
  (`secrets[]`, SSH keys; an older executor → fail-closed `ESECRETS`), 5 — MCP result attachments
  (`features.mcpAttachments`). Compatibility is negotiated via the `protocol` field in `GET /capabilities`
  and additive `features`; an executor ≤ 4 returns a text result without crashing.
- **MCP in the executor:** stdio servers are hosted by the executor, tools and calls go over HTTP
  (`GET /mcp/servers`, `GET /mcp/tools`, `POST /mcp/call`); the control plane receives them through
  `ExecutorMcpSource`. Tool availability is determined by the pool (`requires`, `probe()`); Playwright browser
  tools were verified in a container.
- **Remote background processes:** `BackgroundExecService`, `POST /exec/spawn`, status/logs/stop; the client
  polls state and journal, and `stop` respects the signal. Stopping kills the **process group**, not just the
  shell (see “Reliability”).
- **Observability:** `synth_executor_*` metrics on both sides, the executor’s own `/metrics`, pool scraping;
  `synth_executor_commands_total` means different things on the control plane and on the executor — do not sum
  them.
- **Deployment:** a Helm pool (`execution.*`/`executor.*`), a shared RWX workspace volume, a trust token from
  a Secret/file, an optional `NetworkPolicy`; compose profiles `all-in-one` and `split`; flavor images
  `slim`/`core`/`dev`/`devops`/`browser`/`full` and a multi-stage all-in-one. Details —
  [docs/EXECUTION.md](../EXECUTION.md).

### Reliability and fixes

- **Executor and background work.** `stop` and timeouts now kill the **process group** (`kill(-pid)`), not
  just the shell: previously a child of `sh -c` survived the stop, held the pipes and kept the record in
  `running`. Reading the journal right after a process closes no longer loses the tail (a race between the
  write-chain snapshot and the last append). PostgreSQL stores `processId`, `timeoutMs: 0` (no timeout) is
  accepted, the `background.enabled` gate and the `process.stopped` event are aligned, completion produces
  exactly one notification, and a background refusal or a free-form question answer leaves no side effects.
- **Attachments and media.** The video transcript goes through a temporary file instead of a full buffer;
  “audio-in-video” was removed; `video/` is allowlisted and frames are extracted from MP4; Ollama receives
  `images[]`; `attach_workspace_file` injects the attachment into the current turn; Telegram audio is
  media-only without JSON, with an aux model and transport formats; PDF — a `file` block for OpenAI-type
  providers and `pdf` in Anthropic-type modalities; modalities come from the provider catalog rather than a
  coarse prefix; the composer keeps the attachment marker and a retry returns attachments; “Reasoning” is
  counted the same way in the stream and in the final message.
- **Events and context.** A Telegram message without text produces a marker, not JSON; disabling a user reply
  disables its whole turn (not just the text).
- **Memory.** The secret-exclusion policy lives in the core, not in the plugin bundle (the extension scanner
  no longer blocks the plugin for containing a list of secret file names); the index fingerprint uses the
  host’s actual embedding model, so a model change marks the index `stale` even at the same dimension.
- **Plugins.** Install approval is honoured at activation too; a relative `identifier` no longer makes a
  plugin managed; the deploy-plugin path is not set via ENV in the image; the contract suite no longer ends up
  in the production bundle; live filter budgets and `promptBlockMaxChars` work.
- **MCP and egress.** The MCP network policy fail-open for a single IP rule is fixed; `egressFetch` no longer
  drops response headers (HTTP-MCP did not work with any server); secret headers do not follow redirects to
  another host.
- **Pipelines, worktrees, agents.** Creating a pipeline from the UI no longer returns 400 “Invalid pipeline
  body”; switching tabs no longer shows stale state; run artifacts are wired in managed mode; worktree tools
  return the id, the event carries the action, and the prune schema and the `PATCH` race are fixed; the agent
  registry sees runtime agents with `storage.backend=postgres`.
- **Localisation.** Engine and notification strings for the new subsystems were added to `shared/i18n`
  (questions, background work, attachments), and the EN translations of the API/CONFIGURATION sections and
  the question docs are in sync.
- **CI and release.** npm publication is fail-closed while the visibility check is a separate non-blocking
  step; the release no longer depends on the CI artifact quota (the release page and the GitHub mirror are
  built without them); `docker-cleanup` no longer deletes the version being published (`GV_KEEP_TAGS`); CI
  builds the `core` flavor of both images, with the full matrix on release. Three red tests in the first run
  turned out to depend on the runner environment (git identity, argv form of the kill path, the React caret)
  and were fixed in the tests without weakening the checks.

### Known limitations and open items

- **The hybrid mode does not transfer attachment bytes.** `remote/transfer.ts` (publish/fork) moves sessions
  and messages, but not blob objects: media parts on the remote side keep an unresolved `blobPath`. ADR-115
  remainder.
- **Multi-replica is not fully supported.** Instance state for the four ports is now in SQL (ADR-116), cron
  leadership and client affinity work, but backend auth sessions live in process memory, the queue has no
  claim semantics (a replica crash leaves it stuck until `resume`), and rate limits and the event bus are
  in-process. PROP-104/105 are still needed, not just a shared volume.
- **Memory has prerequisites:** `plugins.executionEnabled: true` and configured embeddings
  (`plugins.embeddingProvider`/`embeddingModel`). Without a model the index is not built and recall is
  keyword-only. An instance `files` index exposes the workspace to all users — an ADMIN action.
- **`@itphx/synth-gateway-core` is not published to npm** — publication is blocked by the token’s rights on
  the `@itphx` scope; consumers use a local link. HA via leader election is a remainder.
- **Pipelines:** no chained rollback/exit strategy, no monitoring dashboard and no separate artifact store
  (artifacts live in the shared blob store; retention is not implemented); legacy `loop` steps are not
  converted; the run-attachment form in the UI is a remainder.
- **Plugins:** facade services (`memory`/`embed`/`getSettings`) are available only to `inline` plugins;
  parity with `out-of-process` requires a v2 wire protocol. Client attestation (level 3) is outside v1.
- **Attachments:** there is no server-side ASR/OCR/sharp preprocessing (only external `ffmpeg` for
  audio/video); attachment drafts do not survive a session switch; video is native only on RouterAI, others
  get frames; `transcript` and aux-call cost in session counters are remainders.
- **Analytics:** no spending limits, quotas or alerts; no server-side PDF/XLSX (PDF means browser printing).
- **Worktrees:** the shared `.git` (refs, hooks, stash, config), ignored files are not copied into a new
  worktree, and there is no automatic deletion when a session is archived.
- **Executor:** quotas, workspace-v2 and the topology-switch runbook are ADR-077 steps 10–12; the executor’s
  background-process registry is in memory (surviving a restart requires external state).
- **Release artifacts:** flavor images in the private Gitea registry and arm64 images in `gitverse.ru` were
  not published in this run because of the registry quota; see “Artifacts”.

### How to update

- **npm (8 packages):** `npm i -g @itphx/synth@0.12.4` — the wrapper pulls in `@itphx/synth-core`,
  `@itphx/synth-shared` and `@itphx/synth-ui`; `@itphx/synth-backend`, `@itphx/synth-sdk`,
  `@itphx/synth-storage-postgres` and `@itphx/synth-executor` are published separately.
- **Docker:** `ghcr.io/itphx/synth{,-backend,-ui}:0.12.4` — multi-arch (`amd64`+`arm64`);
  `gitverse.ru/itphx/synth{,-backend,-ui}:0.12.4` — `amd64`. Flavor images (`slim`/`dev`/`devops`/
  `browser`/`full`, executor images) are published to the private Gitea registry by a separate release job;
  in this run it failed due to the quota — the test environment runs 0.12.4 from a local build.
- **Helm:** chart `synth` 0.12.4 (`helm upgrade synth <repository>/synth --version 0.12.4`).
- **Before updating** — take a backup (`synth backup`): migrations `024`–`027` run at startup and change the
  data schema. Rolling data back means restoring from a backup; rolling the version back means `helm rollback`
  or `synth update --to <prev> --apply`.
- **After updating:** `synth doctor`, `GET /health`, `GET /ready`. For memory, enable
  `plugins.executionEnabled`, configure the embedding model, restart the instance and check
  `synth memory status`. For plugins, review `plugins.trustFloor`/`runtimeInstall`/`deployTrust` — policy
  changes take effect after a restart.
