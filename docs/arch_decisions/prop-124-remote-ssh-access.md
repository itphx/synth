# PROP-124: Удалённый SSH-доступ агента — два режима работы с ключами (`tools` / `agent`)

> **Статус:** 🧩 Предложение
> **Дата:** 2026-11-05
> **Решение до:** 2026-12-01
> **Связано:** [ADR-076](./adr-076-git-repo-registry-ssh.md) (реестр SSH-ключей, шифрование at-rest), [ADR-077](./adr-077-runtime-toolchain.md) (порт исполнения, секреты вызова), [ADR-078](./adr-078-runtime-dependency-availability.md) (доступность внешних программ), [ADR-099](./adr-099-egress-tls-trust.md) (egress/TLS), [ADR-105](./adr-105-external-credentials.md) (модель «секрет → транспорт»), [ADR-113](./adr-113-background-processes.md) (фоновые процессы), [ADR-075](./adr-075-project-workspace-provisioning.md) (workspace), [ADR-114](./adr-114-git-worktrees.md) (worktrees).

## Контекст

Настроенные SSH-ключи Synth сегодня работают только для git: `reveal()` → `ExecSecret{kind:'ssh-key'}`
→ `createSshEnv()` материализует ключ в tmp (`0700`/`0600`) и отдаёт **`GIT_SSH_COMMAND`**. Эту
переменную понимает только git; `ssh`, `scp`, `sftp`, `rsync` её игнорируют.

Нужны оба сценария:

1. **Адресные операции** — агент сам собирает argv (`ssh_exec`/`ssh_copy`/`ssh_tunnel`), хост известен
   заранее, политика хостов/портов проверяется до запуска.
2. **Существующие проекты пользователя** — Ansible (и любые скрипты) должны работать как есть: свой
   `ansible.cfg`, свои роли, свой `hosts`, свой venv. Ограничивать их отдельным тулом с генерируемым
   инвентарём — искусственно: это то же, что запрещать python. Защита от несанкционированных
   подключений живёт **на стороне хоста** (`sshd` + `authorized_keys`: `from=`, `restrict`,
   `permitopen=`, `command=`), и она сильнее любого нашего списка.

Поэтому решение — **не один способ, а два режима**, выбор между ними делает администратор инстанса.
Оба опираются на один и тот же реестр ключей и один шов раскрытия секрета.

## Решение

### 0. Режим инстанса

`ssh.mode: 'tools' | 'agent'` — конфиг (`ssh.mode`), env `SYNTH_SSH_MODE`, runtime-настройка (UI),
приоритет по ADR-023; применяется без рестарта, изменение пишется в аудит `scope:'ssh'`.
Дефолт — **`tools`** (fail-closed: без явного выбора ключ не попадает в окружение команд).

| | `tools` | `agent` |
|---|---|---|
| Как ключ попадает к потребителю | argv тулов (`-i` на время вызова) | эфемерный `ssh-agent` на время вызова (`SSH_AUTH_SOCK`) |
| Политика хостов/портов на ключе | **обязательна**, проверяется до запуска | **не применяется** (и не настраивается — см. ниже) |
| `execute_shell` | ключа не видит | ключ виден всем дочерним процессам вызова |
| Ansible и существующие проекты | не работают (нет ssh-доступа из shell) | работают как есть |
| Адресные тулы | доступны | недоступны (`unavailable(policy)`) — чтобы не было двух толкований |

### 1. Модель ключа (расширение ADR-076)

`usages: Array<'git' | 'ssh'>` (дефолт при чтении — `['git']`), `agentIds: string[]` — **обязательная
привязка для ssh** (в обоих режимах). `allowHosts: string[]` и `allowPorts: number[]` существуют
**только для режима `tools`**; в режиме `agent` поля не показываются в форме ключа, вместо них —
пояснение: «в режиме ssh-агента ключ доступен командам на время вызова; фильтрация по хостам не
применяется — ограничивайте доступ на стороне хоста (`authorized_keys`)». Значения, сохранённые
раньше, не удаляются и снова действуют при переключении в `tools`.

`agentIds` — единственный ACL ключа в режиме `agent`: ключ без привязки к роли не используется.

### 2. Механизм `agent` (эфемерный ssh-agent на вызов)

`createSshEnv({agent:true})` — одна общая функция для inline и remote (executor вызывает её через
динамический `import('@itphx/synth-core')`, дублирования нет):

1. `mkdtemp('synth-ssh-')` `0700`, ключ `0600`;
2. `ssh-agent -a <dir>/agent.sock` (сокет `0600`, peer-uid проверяется самим агентом);
3. `ssh-add <key>` — с passphrase через существующий `SSH_ASKPASS`/`SSH_ASKPASS_REQUIRE=force`;
4. **`unlink` ключа и askpass-скрипта** — приватный ключ остаётся только в памяти агента и
   недоступен для чтения процессам вызова (строго лучше текущего git-пути, где файл живёт весь вызов);
5. env команды: `SSH_AUTH_SOCK` (+ `SSH_AGENT_PID`);
6. `cleanup`: kill агента + `rm -rf` каталога; в фоне — при `process_stop`; sweep осиротевших
   каталогов/процессов — **по живости pid**, а не по возрасту (иначе длинный прогон теряет ключ).

Git-путь не меняется: `purpose:'git'` по-прежнему получает ключ файлом и `GIT_SSH_COMMAND`
(`IdentitiesOnly=yes` несовместим с agent-идентичностями, поэтому в agent-режиме переменная не ставится).

### 3. Единый гейт

`resolveSshKey({keyId?, agentRole, purpose, host?, port?})` — один шов на все пути раскрытия:
`ssh.mode` → `usages` → `agentIds` → (только `tools`) `hostMatchesRule(host, allowHosts)` →
(только `tools`) порт из `allowPorts` (пусто = 22). Матчер хостов переиспользуется
(`engine/mcp/network-policy.ts`: exact, `*.suffix` — только поддомены, CIDR — только по IP-литералу,
`*` не разрешает ничего).

### 4. Адресные тулы (режим `tools`)

`ssh_exec` (`{host, user?, port?, key_id?, argv[], timeout_ms?, background?}`; argv собираем сами,
локального shell нет — исключены `-o ProxyCommand`, `-F`, `-o LocalCommand`), `ssh_copy` (sftp/rsync,
`local` внутри workspace), `ssh_tunnel` (`-L`/`-R`/`-D`; цель — только из `allowPorts`, слушающий
сокет — `127.0.0.1`). В режиме `agent` эти тулы недоступны с причиной `policy`.

### 5. Capability и образы

`ssh`/`scp`/`sftp`/`rsync` — в `EXTRA_TOOLCHAIN_BINARIES` + `TOOL_RUNTIME_DEP` (в
`EXECUTION_BASE_CAPABILITIES` не добавлять: в slim их нет); `rsync` — в hard deps образов, кроме `slim`.
`ansible-core` в поставку **не входит**: как обычный python-пакет, ставится в venv проекта.

### 6. Известные хосты

`{dataDir}/ssh/known_hosts` на инстансе (переживает рестарт, попадает в бэкап с `--with-secrets`);
дефолт — `accept-new`, опциональный pin на ключ (только `tools`).

### 7. Фон

Протокол 6: `secrets[]` в `POST /exec/spawn` + `features.secretsSpawn`; для agent-режима —
`features.sshAgent` (нет признака → адрес не выбирается, тихого фоллбека нет). TTL нет по решению
владельца: агент живёт до `process_stop`/выхода процесса.

### 8. Аудит

`{ts, keyId, purpose, mode, tool, sessionId, outcome}` без материала; хост пишется только в режиме
`tools` (в `agent` он неизвестен — фиксируем факт выдачи ключа вызову, а не цель).

### 9. Permissions

Новая группа `ssh` и запись в `authority/actions.ts`; в plan-режиме адресные тулы — отказ целиком.
В `agent`-режиме ключ выдаётся только вызову `execute_shell`, разрешённому permission-слоем
(`act`/`yolo`), в plan — ключ не выдаётся.

### 10. UI

Раздел «Агенты» → «SSH-ключи»: переключатель режима (ADMIN), список ключей. В `tools` — поля
`allowHosts`/`allowPorts` (`ListField` chips, как в правилах прокси). В `agent` — те же поля скрыты,
вместо них пояснение; у ключа видно, привязан ли он к агенту.

## Решения владельца

| Вопрос | Решение |
|---|---|
| Типы использования ключа | `git` \| `ssh` (два значения) |
| **Способ работы с ssh-ключами** | **два режима на инстанс: `tools` / `agent`, выбирает администратор** |
| **Фильтрация хостов в `agent`** | **не применяется; поля настройки скрыты с пояснением** |
| Порты | Список на ключе (только `tools`), пусто = 22 |
| `agentIds` | Обязательная привязка для ssh |
| Передача файлов | `rsync` в образы (+ sftp/scp) |
| TTL фоновых сеансов | Нет TTL, только ручной стоп |
| Туннели `-L/-R/-D` | Только `tools`, с allowlist портов |
| Ansible | Отдельного тула/инвентаря нет; работает через shell в режиме `agent` |

## Что осознанно не делаем

- **Тул-обёртка над Ansible** (генерация инвентаря и конфига) — ломает существующие проекты и не
  даёт реальной границы (плейбук исполняет произвольный код на control node).
- **Ключи в Secret пода / долгоживущий агент** — ключ живёт дольше вызова, виден всем сессиям.
- **Agent forwarding** как поддерживаемый сценарий, **SOCKS `-D` без правил** (открытый вопрос).
- **Гейт по хостам в `agent`-режиме** — неисполним по конструкции; вместо ложной границы — честное
  пояснение и ограничение на стороне хоста.

## Ограничения режима `agent` (называем прямо)

- **Нет адресной фильтрации**: пока вызов жив, процесс может подключиться к любому хосту, которому
  доверяет ключ. Реальная граница — `authorized_keys` (`from=`, `restrict`, `permitopen=`, `command=`).
- **`ssh -A`** возможен: агент можно форвардить на сторонний хост и использовать оттуда, пока вызов жив.
- **Prompt injection**: инструкция из репозитория может отправить данные на доверенный ключу хост.
  Митигации — ключ только на вызов, аудит, привязка к агенту.
- **Ключ не читается процессами** — это плюс агента: подписывает только он, приватного материала в
  файловой системе вызова нет.
- **Фон без TTL** — ключ в памяти исполнителя до `process_stop`; рестарт пода снимает и процесс, и ключ.

## Открытые вопросы

1. `-D` (SOCKS) в режиме `tools`: запретить или фильтровать по портам назначения.
2. Применять ли обязательную привязку `agentIds` и к git.
3. `known_hosts`: `accept-new` + файл инстанса или обязательный pin.
4. Переключение режима: live (предлагается) или `restartRequired`.

## Альтернативы

| Вариант | Почему не выбран |
|---|---|
| Только адресные тулы | Не позволяют использовать существующие Ansible/скрипты; ограничение ради ограничения |
| Только эфемерный агент (без режима) | Лишает возможности строгой адресной политики там, где она нужна; нельзя выбрать политику инстанса |
| Долгоживущий агент на поде | Ключ живёт до рестарта, виден всем сессиям, отзыв не работает; нужен sidecar и `executor.extraEnv` |
| `-i`/`-F`/подмена `HOME`/обёртка в `PATH` | Нет env для конфига; обёртка ломается на абсолютных путях, `env -i`, вложенных shell; `HOME` ломает git/npm |
| Свой ssh-agent-сервер с форвардом подписи | Максимальная изоляция, но новый бинарный протокол — отдельное решение, не первый шаг |

## Этапы

| Этап | Содержание | Критерий |
|---|---|---|
| Ф1 | `ssh.mode` (config/env/runtime/audit) + модель ключа + UI (переключатель, скрытие полей в `agent`) | миграция чтения, 400 на невалидных правилах, режим виден в UI |
| Ф2 | **agent-механизм**: `createSshEnv({agent:true})`, unlink, cleanup, sweep по живости | спайк на живом хосте: key с passphrase, `ansible-playbook` из venv проекта, отмена и `SIGSTOP`-сценарии не оставляют агента |
| Ф3 | Единый гейт + матрица доступа (режим/usage/agentIds/хост/порт) | тесты падают при обходе гейта |
| Ф4 | Адресные тулы (`ssh_exec`/`ssh_copy`/`ssh_tunnel`) + capability + permissions | работают inline и remote, в `agent` — `unavailable(policy)` |
| Ф5 | Протокол 6: `secrets[]` в spawn, `features.sshAgent`, `features.secretsSpawn` | старый исполнитель не выбирается, ключ не теряется на длинном прогоне |
| Ф6 | Аудит + `known_hosts` + документация (ADR-076/077/078, API_V2, TOOLS, EXECUTION) | записи аудита, `pnpm adr:check` зелёный |

## Тесты

- **agent**: ключ с passphrase без tty; удаление key/askpass после `ssh-add`; повторные соединения;
  cleanup при успехе, ошибке, таймауте, отмене; sweep не убивает живой фон и убирает осиротевший.
- **ansible (smoke)**: `ansible-playbook` из venv проекта в `execute_shell` на живом хосте.
- **гейт**: матрица «режим × usage × agentIds × хост × порт» (позитив и негатив).
- **протокол**: `features.sshAgent`/`secretsSpawn`, отсутствие тихого фоллбека.
