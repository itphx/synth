# ADR-091: Бэкап, восстановление и диагностика инстанса — свой контур `backup`/`restore`/`doctor`

> **Статус:** ⚠️ Частично — MVP реализован (`synth backup`/`restore`/`doctor`); admin-API/UI добавлены (`/api/v2/maintenance`, раздел «Обслуживание»); шифрование архива (`--encrypt`) реализовано; портативный экспорт/импорт проекта (`synth project export|import`) реализован (ядро + CLI); остаток — онлайн-консистентность/PITR.
> **Дата:** 2026-10-16
> **Связано:** [ADR-005](./adr-005-json-storage.md), [PROP-032](./prop-032-history-storage-postgresql.md), [ADR-036](./adr-036-llm-gateway.md), [ADR-076](./adr-076-git-repo-registry-ssh.md), [ADR-079](./adr-079-local-home-independent-instances.md), [PROP-055](./prop-055-instance-exchange.md), [PROP-048](./prop-048-self-help-skills-admin-mcp.md), [ADR-092](./adr-092-instance-lifecycle-maintenance.md); процедуры — [docs/MAINTENANCE.md](../MAINTENANCE.md).

## Контекст

Восстановление после сбоя держалось на ручном копировании каталога данных и нигде не было описано: не было команды, манифеста и версии архива, правила, что архив с `secrets/` — сам секрет (без `master.key` зашифрованные SSH-ключи невосстановимы). Файловое хранилище ([ADR-005](./adr-005-json-storage.md)) атомарно на уровне файла, но сквозной транзакции между сущностями нет — архив с работающего сервиса даёт несогласованный срез.

## Решение

Ввести контур жизненного цикла данных инстанса:

1. **`synth backup`** — архив каталога данных (`$SYNTH_DATA_DIR`) в `tar.gz`, записанный **своим потоковым ustar-писателем без внешних зависимостей**; внутри — `manifest.json` (tool/formatVersion, `schemaVersion` из `meta.json`, `instanceVersion`, время, флаги, исключения, записи с sha256) и `contentChecksum`. Имя `synth-backup-<instanceVersion>-<YYYYMMDD-HHmmss>.tar.gz`, права `0600`. Флаги: `--out`, `--with-secrets`, `--with-workspace`, `--live` (предупреждение о нетранзакционном срезе), `--encrypt` (шифрование внешним ключом оператора → `<archive>.tar.gz.enc`, AES-256-GCM, + плейнтекст-sidecar `*.enc.meta.json` со сводкой без путей/хешей; ключ — `--key-file` > env `SYNTH_BACKUP_KEY_FILE` > env `SYNTH_BACKUP_KEY`, 32 байта base64/hex — **не** мастер-ключ инстанса и **не** попадает в вывод/аудит). Исключаются `backups/`, `tmp/`, `logs/`, `*.lock`, `workspaces/` (без флага — поэтому рабочие файлы проектов в бэкап по умолчанию **не** входят), `secrets/` (без флага).
2. **`synth restore <archive>`** — строгий порядок: манифест → формат → `schemaVersion` (`>` текущей → отказ) → контрольные суммы → `--dry-run` → `--yes` (без него отказ) → страховочная копия → очистка цели → распаковка. Зашифрованный архив (`.tar.gz.enc`) восстанавливается **только через CLI** и требует внешний ключ (`--key-file`/env): он потоково расшифровывается во временный файл `{dataDir}/tmp/…` (удаляется даже при ошибке), затем идёт обычный путь; API/UI такой архив не восстановит (ключ серверу недоступен). Правило: **restore возвращает каталог к снимку** — удаляются все элементы верхнего уровня, которых нет в архиве, кроме `backups/`, поэтому лишние и повреждённые файлы не переживают восстановление; страховочная копия создаётся автоматически (`{dataDir}/backups/synth-pre-restore-<stamp>.tar.gz`, `--no-safety-copy` отключает с предупреждением). **`workspaces/` — исключение:** если архив его **не** содержит (бэкап без `--with-workspace`), каталог при очистке **сохраняется** (иначе потеряли бы рабочие файлы проектов, восстановить которые из архива нечем); если архив снят с `--with-workspace`, `workspaces/` заменяется архивным — обычная семантика снимка. После restore **обязателен `synth doctor`**.
3. **`synth doctor`** — health инстанса (`--json`): `data-dir` (write-доступ пробным файлом), `schema`, `master-key`, `secrets-permissions`, `data-integrity`, `providers`, `locks`, `version`; exit 1 при любом `fail`. Read-only, кроме пробного файла.
4. **`{dataDir}/backups/`** — единый каталог страховочных копий (`pre-restore`/`pre-migrate`), исключённый из архивов бэкапа. Архив с секретами — секрет сам по себе.
5. **admin-API и UI (`/api/v2/maintenance`, раздел «Обслуживание»)** — тот же контур без CLI: `createMaintenanceRoutes` (status/doctor/migrations/backups/restore; managed — только `ADMIN`, core — `requireAuth`; скачивание архива — `application/gzip`). Восстановление из API/UI — **офлайн**: `POST /restore` не выполняется сразу, а планируется и применяется при следующем старте (`applyPendingRestore`); под живым процессом данные не вычищаются.
6. **`synth project export|import` — портативный перенос проекта между инстансами (этап 2).** Экспорт — самодостаточный архив `<name>.synth-project.tar.gz`: `manifest.json` (tool `synth-project-export`/`formatVersion`, проект, число сессий, записи с `sha256`), `project.json` (`serializeProject`) и `sessions/<id>.json` (переносимый payload `buildSessionExport`) по каждой **локальной** сессии проекта (сессии `origin: remote` пропускаются с предупреждением — они принадлежат другому инстансу); опционально `workspace/**` (`--with-workspace`). **По умолчанию секретов в архиве нет** — каталог `secrets/`, ключи, credentials, токены, API-ключи не попадают (проверяется тестом), и при упаковке session-payload'ов **вырезается карта обфускации LLM Gateway** ([ADR-036](./adr-036-llm-gateway.md)): `obfuscation_map` на уровне сессии и `metadata.secrets` — **рекурсивно, в любом месте payload'а**, то есть по всем носителям сообщений сессии (`messages[]`, `pendingMessages[]`, `checkpoints[].messages[]`) (соответствие «плейсхолдер → реальный секрет») — тест на отсутствие секретов покрывает и её. Явный opt-in — `--with-secrets` (CLI) / `?withSecrets=true` (HTTP) — доступен **только** `ADMIN`/`LEAD` (в standalone/core — локальному владельцу), для остальных флаг недоступен; выдача такого архива фиксируется в аудите обслуживания (`export.created`, деталь `withSecrets: true`), а сам архив — **секрет** (он несёт реальные секреты других участников проекта). Импорт карту принимает, если она в архиве есть, — архив, собранный с привилегированным opt-in, импортируется корректно. Экспорт **сессии** (`GET /api/v2/sessions/:id/export`) отдаёт объект сессии (camelCase, формат publish/fork не изменён) и **делит доступ на две части**: право на экспорт = право на чтение сессии (его решает **единый** prefix-guard сессий — маршрут зарегистрирован ПОД ним, проверок доступа в обработчике нет, инвариант 16), а карта обфускации — отдельная привилегия, которую решает **свой route-level guard** (`createSessionExportGuard`). **Полный экспорт** (карта и `messages[].metadata.secrets` включены) — владелец сессии (`ownerId ?? userId`), `ADMIN` и `AUDITOR` (тот же набор привилегий, что у `GET /api/v2/sessions/:id/secrets`); **прочие читатели сессии** (участник проекта `VIEWER`/`EDITOR`, владелец проекта, не владеющий сессией, `LEAD`) — 200 с **очищенным** телом (карты нет, разговор переносится полностью, очистка — на копии, сохранённая сессия не меняется); **нет доступа на чтение** — 403 `FORBIDDEN`. Именно очистка, а не запрет: гибридный publish/fork переносит сессии проекта **токеном пользователя** (`forkProjectToLocal` → `remoteClient.exportSession` по каждой сессии) — 403 сломал бы перенос проекта для обычного участника, а очищенный экспорт остаётся валидным payload'ом переноса (`POST /api/v2/sessions/import` его принимает). Импорт — **materialization**, а не `session.requested` (ADR-089, инвариант 15): `SessionManager.createSession` создаёт **новый** `projectId` и **новые** id сессий (`--merge-into <projectId>` — импорт сессий в существующий проект); переносятся `title`/`icon`/`color`/`settings`/`messages` (в порядке)/`todos`/план проекта/описание, `status` сессии сбрасывается в безопасное (`idle`, без `blocked`/`currentStream`/`cancelRequested`), ссылки `parentId`/`references`/`session_reference` переписываются на новые id; по каждой материализованной сессии публикуется `session.created` (инвариант 18). `--dry-run` — валидация архива (манифест/формат/чек-суммы) и план без записи; без `--dry-run` и без `--yes` — отказ. Импорт `workspace/**` — с проверкой **realpath-контейнмента** (пре-существующий симлинк внутри workspace больше не позволяет записать наружу; ошибка — `invalid-archive`). Импорт ограничен и **распакованным** объёмом архива (защита от archive-«бомб»): `DEFAULT_PROJECT_IMPORT_LIMITS` — 100 000 записей, 128 МиБ на одну запись, 2 ГиБ суммарно (`projects/portable.ts`); лимит записи сверяется по заголовку tar **до** буферизации содержимого, суммарный — по сумме объявленных размеров, число записей — по счётчику, т.е. проверка идёт **в момент чтения** и превышение обрывает разбор; превышение — `invalid-archive` (HTTP 400 `VALIDATION_ERROR`), переопределение лимитов — `ImportProjectOptions.limits`. Экспорт при этом **не** ограничен (архив пишется потоком на диск) — асимметрия намеренная; путь restore бэкапа инстанса — **другой артефакт** со своей политикой размеров и этими лимитами **не** ограничен (лимит для него выводится из манифеста бэкапа — отдельная задача). Реализация — `projects/portable.ts` (ядро) + CLI `synth`/`core`. HTTP-роуты — следующая волна.

Процедуры (setup → verify → backup → restore → verify → migrate), флаги и коды выхода — [docs/MAINTENANCE.md](../MAINTENANCE.md).

## Альтернативы

- **Системный `tar`/`gzip` через `child_process`** — отклонён: нет на Windows и в минимальных образах, внешняя зависимость в рантайме.
- **Готовая библиотека архивации** — отклонена: новая зависимость ради простого ustar-формата и контроля путей (отвергаем абсолютные и `..`).
- **Бэкапить только БД** — преждевременно: файлового уровня ещё нет (БД — следующий шаг, [PROP-032](./prop-032-history-storage-postgresql.md)).

## Последствия

- (+) Восстановление после сбоя — воспроизводимая проверяемая процедура, а не ручное копирование; архив самодостаточен (манифест + контрольные суммы).
- (+) Ноль новых зависимостей; `doctor` даёт машинно-читаемый health (`--json`, exit-код) и обязателен после restore.
- (−) Онлайн-срез нетранзакционен (best-effort, `--live`); прод-подход — снапшот ФС (PVC/LVM/ZFS).
- (−) Restore деструктивен по цели (возврат к снимку) — отсюда обязательная страховочная копия и подтверждение `--yes`; `workspaces/` при этом сохраняется, если его нет в архиве (защита от потери рабочих файлов проектов).
- (−) Портативный архив проекта по умолчанию **не** переносит чужие секреты (карта обфускации вырезается при упаковке), но при `--with-secrets`/`?withSecrets=true` — несёт их: такой архив **сам секрет**, выдаётся только `ADMIN`/`LEAD` (в standalone/core — локальному владельцу) и фиксируется в аудите обслуживания.
- (−) В экспорте сессии карта обфускации — **привилегия, отличная от права чтения**: полный экспорт (карта включена) — владелец сессии, `ADMIN` и `AUDITOR`; остальным читателям — 200 с очищенным телом (иначе перенос проекта в гибриде сломался бы), без доступа на чтение — 403.

## Остаток

- `workspaces/` по умолчанию не входит в бэкап (исключение по объёму): при восстановлении он **сохраняется**, поэтому полный откат рабочих файлов проектов даёт только архив с `--with-workspace`; вкладывать рабочие каталоги автоматически — не решено;
- онлайн-консистентный/инкрементальный бэкап и PITR — после [PROP-032](./prop-032-history-storage-postgresql.md);
- UI-кнопки портативного экспорта/импорта проекта в разделе проекта (HTTP-роуты `/api/v2/projects/:id/export|import` готовы);
- руководства портала `docs.synth.itphx.ru`; автоматизация ops-скиллами ([PROP-048](./prop-048-self-help-skills-admin-mcp.md)).

- 2026-10-20 — второй раунд независимого аудита релиза 0.11.3: в §6 добавлены **лимиты распакованного объёма** импорта портативного архива (`DEFAULT_PROJECT_IMPORT_LIMITS`: 100 000 записей / 128 МиБ на запись / 2 ГиБ суммарно; проверка — в момент чтения, лимит записи сверяется по заголовку tar ДО буферизации содержимого; превышение → `invalid-archive`, HTTP 400) и явно зафиксирована асимметрия «экспорт не ограничен (потоковая запись на диск), импорт ограничен»; путь restore бэкапа инстанса — **другой артефакт**, этими лимитами **не** ограничен (лимит для него выводится из манифеста бэкапа — отдельная задача). Также уточнено правило вырезания карты обфускации: `metadata.secrets` вырезается **рекурсивно, во всех носителях сообщений сессии** (`messages[]`, `pendingMessages[]`, `checkpoints[].messages[]`), а не только в `messages[]`; и уточнено, что доступ к сессии при экспорте решает единый prefix-guard (маршрут зарегистрирован ПОД ним, инвариант 16), а карта обфускации — отдельный route-level guard `createSessionExportGuard`.
