## Решение

Добавить тулу `task` режим **`background: true`**: дочерняя сессия запускается **асинхронно**, родительский ход **не блокируется**; по завершении (успех/ошибка/отмена) родитель **уведомляется**. Повторить модель OpenCode:

- foreground (как сейчас) — родитель ждёт результат;
- `background: true` — тул возвращает `{ childSessionId, status: 'running' }` сразу, а по завершении ребёнка родитель получает уведомление;
- продолжение той же дочерней сессии — по её `childSessionId` (аналог `sessionID` в OpenCode);
- **глубина вложенности — 1** (как в OpenCode): саб-агент не может породить фонового саб-агента.

MVP: `background` у `task` + уведомление о завершении + список/открытие/отмена дочерних сессий в UI. Автопродолжение родительского хода (реакция на уведомление без участия человека) — второй этап.

## Контекст

Сейчас `task`-тул (`packages/core/src/engine/tools/task.ts`) **синхронный**: создаёт дочернюю сессию и прогоняет её цикл внутри родительского хода — родитель ждёт. Есть частичный механизм `startSubagentResume` (`task-resume.ts`) для возобновления **прерванных** детей, но инициировать их фоново и продолжать родителя, пока дети работают, нельзя: длинные задачи саб-агентов блокируют основную сессию.

Модель OpenCode (источник для повторения): `subagent` с `background: true` возвращает управление сразу, уведомляет родителя о завершении и позволяет продолжить ребёнка по `sessionID`; вложенность ограничена (depth 1).

## Детали

### Модель

- **Запуск.** `task({ prompt, agent, background: true, contextMode })`:
  1. создаёт дочернюю сессию существующим путём (`fork`/`createSession` по режиму контекста, AD-026) — это **materialization**, не прямой request (инвариант 15);
  2. регистрирует фоновый прогон в супервизоре (см. PROP-097: тот же реестр — для детей тип `subagent`);
  3. немедленно возвращает `tool_result { childSessionId, status: 'running' }`.
- **Уведомление родителя.** По завершении: событие `child.completed|failed|cancelled` (EventHub) + **инъекция в родительскую сессию** системного сообщения-уведомления (`metadata.subagent`, `childSessionId`, статус, краткое резюме/ошибка). Это делает результат видимым и в истории, и в UI (по аналогии с `Notice` для планировщика).
- **Продолжение ребёнка.** `task` с переданным `childSessionId` (или отдельный `task_resume`) продолжает диалог того же ребёнка — как `startSubagentResume`, но доступно и для живых фоновых детей.
- **Статус/наблюдаемость.** Дочерняя сессия — полноценная `Session` (владелец, видимость по AD-089), поэтому переживает реконнект/рестарт; незавершённые после падения процесса помечаются `interrupted` и возобновляемы существующим resume.

### Ограничения и контроль

- **Параллелизм:** лимит одновременных фоновых детей на родителя и на инстанс (`N`), сверх лимита — `ask`/отказ либо очередь.
- **Глубина 1:** саб-агент не запускает фоновых саб-агентов.
- **Ресурсы:** общий бюджет токенов/времени, наследование модели/провайдера от родителя (как сейчас); расход отражается в статистике (ADR-070).
- **Отмена:** отмена ребёнка — через надёжный «Стоп» (`POST /sessions/:id/abort`, персистентный флаг ADR-089); отменённый ребёнок уведомляет родителя.
- **Права:** `background` не обходит permission-слой — capabilities агента и правила `task` сохраняются.

### UI

- Индикатор активных фоновых детей у родительской сессии (бейдж/секция), открытие дочерней сессии в таб, отмена.
- Панель «Процессы» (PROP-097) показывает и детей-сабагентов, и шелл-процессы в одном реестре.

## Этапы

1. **MVP:** `background` у `task` + супервизор + уведомление родителя + отмена + UI-индикатор. ~2–3 дня.
2. Продолжение живого ребёнка по id из UI/тула; лимиты и очередь. ~1–2 дня.
3. Автопродолжение хода родителя по уведомлению (реакция без человека) + политики. ~2 дня.

## Открытые вопросы

1. Уведомление родителя — только историей (человек/родитель реагирует в следующем ходе) или автозапуск хода родителя? (по умолчанию — безопаснее «только уведомление»).
2. Лимит одновременных детей — на сессию, на проект или на инстанс?
3. Как фоновые дети ведут себя в **гибриде** (ребёнок локально, родитель на сервере) и в managed (executor, ADR-077)?
4. Нужны ли приоритеты/пул воркеров для фоновых прогонов (иначе N детей = N параллельных LLM-вызовов)?
