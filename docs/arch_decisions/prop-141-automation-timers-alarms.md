# PROP-141: Автоматизация проекта — таймеры, будильники и секундные таймауты инструментов

> **Статус:** 🧩 Предложение — ввести таймеры и будильники как вид автоматизации проекта, переработать панель «Шедулер» в «Автоматизация» и перевести таймауты инструментов на секунды с пределом по режиму исполнения
> **Решение до:** 2026-11-30
> **Дата:** 2026-11-17
> **Обсуждено:** 2026-11-17 — владелец принял 15 решений опросником: жёсткие секунды, потолок fg 10 мин / bg сутки, `web_fetch` 600 с, отдельная сущность `Timer`, гибридная доставка со steering, иконка только в дереве сессий, повтор daily/every/once, TZ явным параметром, точность ~1 с, удаление вместе с сессией, лимиты 50/500/10 с/30 дней, вкладка «Автоматизация», редактор-модалка, 2 тула с `action`, **никаких инстансных автоматизаций — всё привязано к проекту**. ## Контекст

1. **Ожидание внутри хода — единственный способ «подождать».** Агент, которому нужно вернуться к задаче позже, запускает `sleep` в `execute_shell`; при фоне это не блокирует ход, но занимает процесс и слот, при foreground — блокирует сессию. Встроенного «разбуди меня через N» нет.
2. **Расписание не заменяет будильник.** `Schedule` всегда несёт свой `prompt` — текст задания, который инъецируется в сессию. Для «напомни/проснись и реши по контексту» собственное сообщение вредно: агент должен сам понять, зачем был будильник, по комментарию и истории.
3. **Таймауты инструментов измеряются в миллисекундах** и упираются в 600 000 мс (10 минут). Секунды есть только у `web_fetch`; `question` уже допускает сутки, но в мс. Долгая операция (сборка, обучение, ожидание внешнего события) невыразима.
4. **Правая панель «Шедулер» — чужеродная.** Один `GET` при монтировании, без скоупа и фильтров, инлайн-редактор вверху панели, самодельные пустое состояние и строка счётчика, кнопки 40 px. Панель «Процессы» уже задаёт эталон (секции, счётчики, фильтры, тумблер «Весь проект», polling + live-события, карточки).
5. **Инстансных автоматизаций быть не должно.** Сейчас `Schedule.target` допускает цели без проекта (`ephemeral` без `project`, `bound`/`queue` без явного проекта), а `GET /schedules` отдаёт все расписания инстанса любому аутентифицированному. Как только в панели появятся таймеры сессий, это станет утечкой чужих данных.

## Проблема

Нужен механизм отложенного возврата к работе, который:

1. переживает рестарт и не блокирует ход и сессию;
2. не требует собственного текста задания — несёт только комментарий, смысл восстанавливает агент;
3. умеет одноразовый и повторяющийся режим с точностью порядка секунды;
4. доставляется в сессию **как завершение фонового процесса** (вклинивание в текущий ход обязательно);
5. виден в интерфейсе: иконка в дереве сессий и карточки в правой панели, унифицированные с расписаниями;
6. не смешивает данные разных проектов и уважает роли проекта;
7. а также — позволяет инструментам работать дольше 10 минут там, где это осмысленно (фон), и не позволяет «подвесить» сессию на сутки.

## Часть A. Таймауты инструментов в секундах

### Правило

- Входной параметр всех тулов — `timeout` (секунды, целое). Внутри: `timeoutMs = timeout * 1000` — на границе, как уже сделано в `web_fetch`. Порты, executor-протокол (`ExecRequest.timeoutMs`), конфиг-дефолты остаются в миллисекундах.
- Предел зависит от **режима исполнения**, а не от тула: foreground ≤ 600 с, background ≤ 86 400 с. `0` («без лимита») убирается: у фонового процесса лимит — сутки, у синхронного — 10 минут.
- `question` — исключение: это ожидание человека, а не исполнение; предел остаётся 86 400 с (минимум 300 с), но в секундах.
- `web_fetch` — отдельный потолок 600 с (осознанный сетевой предохранитель), дефолт 30.

| Тул | Параметр | Дефолт | fg | bg |
|---|---|---|---|---|
| `execute_shell` | `timeout` | 120 | ≤ 600 | ≤ 86 400 (дефолт 86 400) |
| `git_*` (11 тулов) | `timeout` | 30 / 120 / 300 | ≤ 600 | — |
| `browser_navigate/wait/screenshot` | `timeout` | из конфига (120) | ≤ 600 | — |
| `terminal_run` | `timeout` | 30 | ≤ 600 | ≤ 86 400 |
| `sandbox_exec` | `timeout` | 120 | ≤ 600 | — |
| `ssh_exec` / `ssh_copy` | `timeout` | 120 | ≤ 600 | `ssh_exec` фон ≤ 86 400 |
| `ssh_tunnel` | `timeout` | 86 400 | — | ≤ 86 400 |
| `question` | `timeout` | нет | 300…86 400 | — |
| `web_fetch` | `timeout` | 30 | 1…600 | — |
| декларация скрипта `.synth/scripts/*.md` | `timeout` | нет | ≤ 600 | ≤ 86 400 |

Дополнительно:

- **Исполнитель.** `SYNTH_EXECUTOR_MAX_TIMEOUT_MS` (сейчас 600 000) поднимается до 86 400 000 в default/Helm/compose; core начинает **читать** `/capabilities.limits` и предупреждать при расхождении потолков (сейчас не читает — рассинхрон тихий).
- **Метки и сообщения.** `metadata.timeoutMs` → секунды (`metadata.timeout`), i18n-ключи `tool.shell_timeout`, `git.timeout`, `git.clone_timeout`, `terminal.tool.run_timeout` — в секундах; `timeout_ms=` в терминале заменяется на `timeout=`.
- **Промпт.** В описаниях `execute_shell`/`terminal_run`/`ssh_*` прямо сказано: для ожидания использовать `timer`, а не `sleep`; `sleep` в foreground ограничен 10 минутами.
- **Совместимость.** SDK и MCP-фасад тул-таймаутов не передают; единственный внешний контракт — executor-протокол, он остаётся в мс. Значения вида `120000` после перехода означают 120 000 с и будут отвергнуты валидацией (`> 86400`) — это осознанно: лучше явная ошибка, чем тихий 33-часовой таймаут.

## Часть B. Таймеры и будильники

### Модель

Отдельная сущность, один тип на два вида:

```ts
type TimerKind = 'timer' | 'alarm';
type TimerRepeat =
  | { mode: 'once' }                                   // одноразовый
  | { mode: 'daily'; time: 'HH:MM'; timezone: string } // ежедневно
  | { mode: 'every'; everySec: number };               // каждые N секунд

interface Timer {
  id: string;                 // tmr_<uuid>
  kind: TimerKind;
  name?: string;
  comment: string;            // ≤ 500 символов — единственный «смысл» срабатывания
  projectId: string;          // обязателен (нет инстансных автоматизаций)
  sessionId: string;          // обязателен: сообщение уходит в конкретную сессию
  ownerId: string;
  repeat: TimerRepeat;
  status: 'active' | 'paused' | 'fired' | 'cancelled';
  firesAt: string;            // ближайшее срабатывание, ISO-8601
  createdAt: string;
  updatedAt: string;
  firedAt?: string;
  lastError?: string;
}
```

- **Таймер** — относительный: `delaySec` (10…2 592 000), `firesAt = now + delay`.
- **Будильник** — абсолютный: `at` (ISO) либо `time` + `timezone`; `repeat` — `once`/`daily`/`every`.
- История срабатываний — append-only `TimerFiring` (`{ id, timerId, firedAt, scheduledFor, lagMs, outcome, sessionId }`), ретеншн как у Job-истории.
- Хранение — новый доменный порт `TimerRepository` (ADR-096): файл `{dataDir}/timers.json` (атомарная запись, ADR-005), memory, PostgreSQL (миграция `timers` + `timer_firings`). Схема данных инстанса получает версию (ADR-092).
- **Скоуп.** `projectId` и `sessionId` обязательны в контракте и в Zod-схеме. Проект берётся у сессии и хранится денормализованно для выборок и RBAC; смена проекта сессии переносит и автоматизации (или запрещает перенос — см. «Последствия»).

### Движок

- Отдельный `TimerService` (`engine/timers/`), но **без второго тикера**: он переиспользует лидер-выбор `SchedulerService` (`AlwaysLeader`/`FileLeader`/PG advisory-lock) и общий `HookBus`.
- Точность ~1 с: на ближайший `firesAt` ставится единичный `setTimeout` (не `setInterval`), после срабатывания/создания/правки пересоздаётся; страховочный тик раз в 30 с ловит дрейф часов и пропущенные окна. `setTimeout` живёт в control plane и **не заменяет** персистентность.
- **Рестарт.** На старте: `active`-записи читаются из порта, просроченный one-shot срабатывает **один раз** (метаданные `catchup: true`), `daily`/`every` пересчитывают `firesAt` от текущего времени; `fired`/`cancelled` не воскресают.
- **Multi-replica.** Срабатывает только лидер; дедуп по `(timerId, scheduledFor)` — в существующем dedup-хранилище событий, поэтому повторный тик и failover не дают двух сообщений.
- **Удаление сессии** — каскад: `TimerService.onSessionDeleted` переводит записи в `cancelled` и удаляет их (история срабатываний остаётся).

### Доставка (гибрид, вклинивание обязательно)

1. `TimerService._fire` формирует событие `{ source: 'timer', type: 'timer_fired', identity: { principalId: ownerId }, payload: { timerId, kind, comment, scheduledFor, recurring }, dedupKey }` и подаёт его в `EventIngress`.
2. `TimerRuleProvider` (`RouteRuleProvider`) возвращает `decision { kind: 'bound', sessionId, delivery: 'steer' }` — сессия уже известна, эфемерных сессий и пайплайнов у таймеров нет.
3. `deliver()` получает новый режим `steer` и использует `createBackgroundParentNotifier` (`engine/background/notify-parent.ts`): идёт ход → `enqueueSteerMessage`, иначе `enqueueUserMessage`, фоллбек — прямая запись сообщения + `message.added`. Это ровно тот же путь, что у завершения фонового процесса, — «ровно одна копия в истории» и вклинивание на границе шага.
4. `RouteDecision` расширяется аддитивным полем `delivery?: 'enqueue' | 'defer' | 'steer'`; для остальных источников поведение не меняется.

### Сообщение

- `role: USER`, `author: 'Timer'`, конверт в теле:
  `<timer id="…" kind="alarm" repeat="once" fired_at="…">\n{comment}\n</timer>`.
- `metadata`: `type: 'timer_fired'`, `timer_id`, `timer_kind`, `repeat`, `comment`, `scheduled_for`, `fired_at`, `catchup?`.
- Служебность: `isServiceUserMessage` (`packages/core/src/sessions/user-messages.ts`) получает признак `metadata.type === 'timer_fired'`; зеркально — `MessageList.isHumanReply`; `ChatMessage` рендерит `Notice` варианта `timer` (иконка `time`, для будильника — новая `alarm` в реестре `Icon.tsx`). Авто-тайтл сессии такие сообщения игнорирует.
- Тост о срабатывании — не обязателен (Notice + иконка в дереве достаточны); если появится, то по образцу `notify.background.*`.

### Инструменты

Два тула, capability `schedule` (группа «Автоматизации»), доступны и без workspace:

- `timer` — `action: create | list | cancel`; `create`: `delay` (сек), `comment`, `name?`.
- `alarm` — `action: create | list | update | cancel`; `create`/`update`: `at` (ISO) **или** `time` + `timezone`, `repeat` (`once|daily|every`), `comment`, `name?`.
- В описаниях: отличие от расписания (нет своего промпта), отличие от `sleep` (не занимает процесс), требование писать комментарий так, чтобы через сутки было понятно, зачем будильник.

### Права и лимиты

- Чтение — участник проекта (VIEWER+), мутации — EDITOR/OWNER проекта; ADMIN/LEAD — сквозной обзор (ADR-140). Для `:id`-маршрутов — общий prefix-guard по сессии (инвариант 16), плюс проверка проекта.
- Лимиты: ≤ 50 активных на сессию; комментарий ≤ 500; минимальный интервал/повтор ≥ 10 с; one-shot горизонт ≤ 30 дней; `daily` живёт до отключения.
- Аудит `scope: 'timer'` (создание/срабатывание/отмена), метрики `synth_timer_active{kind}`, `synth_timer_firings_total{kind,outcome}`, `synth_timer_lag_seconds` (гистограмма).

### Расписания: привязка к проекту

- `Schedule` получает обязательный `projectId`; `ephemeral`-цель требует `project`; `bound`/`queue` берут проект у сессии; `pipeline` уже его имеет.
- `GET /schedules` начинает фильтровать по `sessionId`/`projectId` и правам. Без этого панель со скоупом невозможна, а чужие расписания остаются видимыми.
- Миграция: проект выводится из цели; если вывести нельзя (легаси `ephemeral` без проекта) — запись остаётся, но помечается `needs_attention` (видна в панели с подсказкой «укажите проект»), не срабатывает.

## Часть C. Панель «Автоматизация»

Эталон — «Процессы» (`ProcessesTab.tsx`): `PanelTab` → фильтры → ошибка → спиннер → секции → карточки.

- **Вкладка**: `scheduler` → `automation` (ключ `rightPanel.tab.automation`, вкладка проектная, доступна без сессии).
- **Секции**: «Расписания», «Таймеры», «Будильники» — `PanelSectionHeader` (заголовок · ICU-счётчик + кнопка «+») и `PanelSectionEmpty`.
- **Фильтры**: чипы `Все | Расписания | Таймеры | Будильники` и `Активные | На паузе | С ошибкой`; справа — `Toggle` «Весь проект» (сессия → проект), только при наличии и сессии, и проекта. Инстансного уровня нет.
- **Данные**: серверная фильтрация по `sessionId`/`projectId`, polling 5 с, live-события `timer.*`/`schedule.*`, тикер 1 с для обратного отсчёта (`formatRemaining`).
- **Карточка** (одна на три вида): иконка вида, имя, бейдж состояния (`running`/`paused`/`error`/`fired` в стиле `STATUS_CLASS`), `dl`: цель (сессия, проект), триггер (`Cron …` / `Через 15 мин` / `Завтра 09:00 · ежедневно`), ближайшее срабатывание, последнее срабатывание, комментарий (усечён), ошибка.
- **Действия**: `Toggle` вкл/выкл (оптимистично, `usePanelSettingSave` с откатом), «Запустить сейчас» (расписания), «Редактировать», «История» (раскрытие, ленивая загрузка), «Удалить». Кнопки — `size="icon"` (32 px, `pointer-coarse:size-10`), как в «Процессах».
- **Редактор** — модалка/поповер: поля по виду автоматизации, валидация на месте, ошибки — в модалке.
- **API**: `GET /api/v2/timers` (страницы-сводки по ADR-118 §4), `POST/PATCH/DELETE /api/v2/timers[/:id]`, `GET /api/v2/timers/:id/firings`; у `/schedules` — фильтры и `projectId`.
- **Переиспользование**: `PanelTab`, `PanelSectionHeader`, `PanelSectionEmpty`, `Button`, `Toggle`, `InfoField`/`InfoSection`, `ExpandableListRow`+`RowBadge`, `FieldTooltip/TextField/TextArea/SelectField/SegmentedControl`, `SessionSelect/ProjectSelect`, `confirm()`, `useNotification`, `formatDateTime/formatDuration/formatRemaining`, `useActiveProject`.
- **Вынести при реализации** (сейчас копипаста в 10+ файлах): общий `Card`, общий `Badge`/`StatusBadge`, `FilterChips`. Без этого три вида карточек снова разъедутся.
- **Иконка в дереве**: `countSessionActivity` + `SessionActivityCounts` получают `timers`/`alarms`, `SessionActivityBadge` — два новых элемента (`leftPanel.activity.timer|alarm`, иконки `time`/`alarm`); данные — `timersStore.loadActive()` (30 с, как процессы) + live-события. DTO сессии не меняется.
- **i18n**: новый namespace `automation.*` для секций/фильтров/карточек/форм таймеров и будильников (~60 ключей на язык); существующие `rightPanel.scheduler.*` переиспользуются для полей расписания, миграция namespace — отдельным шагом, если понадобится.

## Часть D. Перенос сессии между проектами

### Принцип

Перенос меняет «дом» сессии (ADR-040). Всё, что привязано к дому, при переносе либо **завершается**, либо **переезжает осознанно** — молчаливого наследования не бывает. Сейчас правило размазано по трём путям (HTTP `PATCH`, `project_attach`/`project_create`, материализация) и у каждого своё поведение; часть состояния вообще не обрабатывается (`BackgroundRunRecord.projectId`, `TerminalRecord.projectId`), а снятие worktree молчит.

### Привязанное состояние и эффекты

| Класс | Признак | Без согласия | С `move_consent` |
|---|---|---|---|
| Активный ход | `isTurnActive` | **409** | — (согласия нет: только дождаться конца хода) |
| Фоновые процессы | `running` | **409** | `stop`: SIGTERM → 5 с → SIGKILL, статус `cancelled` |
| Саб-агенты | `running` | **409** | `stop`; **всё поддерево** сессий-потомков (включая завершённые) переезжает вместе с родителем, если их `projectId` = старый |
| Терминалы | `running`/`starting` | **409** | `close`, PTY гасится, запись терминала не переезжает |
| Автоматизации | `timer`/`alarm` active; `schedule` enabled с целью `bound`/`queue` | **409** | **все отменяются**: таймеры/будильники `cancel`, расписания `disable` |
| Worktree | `session.worktree` | снимается всегда (как сейчас, ADR-114 §3.4) | — |
| Завершённые прогоны и терминалы | терминальный статус | не блокируют | `projectId` **переатрибутируется** на новый проект |
| Расписания `pipeline`/`ephemeral` | цель не ссылается на сессию | не блокируют | не трогаются |

### Контракт

- `PATCH /api/v2/sessions/:id {project_id}` при блокерах → `409 SESSION_HAS_ATTACHED_STATE` + `details: { active_turn, processes, subagents, terminals, timers, alarms, schedules, worktree }` (counts + компактный список `{id, kind, name}`).
- Повтор с `move_consent: { stop_running: true, cancel_automations: true }`. Флаги явные: нельзя «согласиться на всё» одним `force`.
- **Поддерево** — все потомки переносимой сессии (включая завершённые), у которых `projectId` совпадает со старым; потомки, уже живущие в другом проекте, не трогаются. У перенесённых worktree снимается.
- Порядок эффектов детерминирован: stop processes → stop subagents → close terminals → cancel automations → detach worktree → перенос поддерева сессий → смена `projectId` → переатрибуция записей → событие + Notice + аудит. Любая неудача останова → перенос **не выполняется** (fail-closed), 409/500 с деталями.
- **Согласие даёт только человек.** Агентские `project_attach`/`project_create` при наличии блокеров возвращают ошибку с подсказкой «останови ресурсы и повтори» (остановка — отдельными тулами, видимыми в истории). `service-key` с `move_consent` → `403`; remote-сессия (`remote:` id) не переносится.
- Один шов — `SessionMoveService.moveSession({ sessionId, targetProjectId, actor, consent })` в core; вызывают HTTP-роут, `attachSessionToProject`, `project_create`, импорт/merge. Проверки в обработчиках не дублируются (инвариант 16).

### Уведомление

- **До переноса** — UI ловит 409 и показывает `ConfirmDialog` со списком последствий: «3 фоновых процесса будут остановлены, 1 саб-агент остановлен, 2 терминала закрыты, 1 будильник отменён, worktree отвязан».
- **После переноса** — служебное сообщение `Notice` в сессии (`metadata.type: 'session_moved'`) с тем же списком фактических эффектов; `session.moved` получает `effects[]` (инвариант 27 — второй клиент рисует то же), остальным клиентам — тост; аудит `scope:'session'`, `action:'move'`. Для агентского пути Notice формирует тот же сервис, effects возвращаются в metadata тула (сейчас там только `worktree_detached`).

### Почему не «перенести всё за собой»

`cwd` живого процесса и PTY изменить нельзя: перенос записи не переносит точку исполнения, поэтому участники нового проекта получили бы доступ к файлам старого workspace через лог процесса или терминал. Плюс владелец автоматизации может не быть участником нового проекта — это была бы тихая передача прав.

### Риски

- Перенос становится «тяжёлой» операцией: диалог должен быть коротким и перечислять только counts, без простыни.
- Переатрибуция истории меняет отчёты по проектам — осознанно: история следует за сессией.
- Перенесённое поддерево саб-агентов меняет проект у записей, созданных в старом проекте; ссылки родитель↔ребёнок остаются валидными, но старый проект теряет эти сессии из своего обзора.

## Последствия и риски

1. **Фоновый shell с дефолтом суток.** Долгоживущий dev-сервер умрёт через сутки. Это осознанно: фон перезапускаем, а «вечный» процесс без присмотра дороже. Если понадобится дольше — отдельное решение (не в этой итерации).
2. **Изменение смысла `timeout`.** Значения `> 86400` теперь ошибка валидации. Модели это не вредит, но сохранённые пользовательские сниппеты/инструкции могут содержать старые мс — нужно упомянуть в описаниях и в `docs/TOOLS.md`.
3. **Кламп исполнителя.** Без поднятия `SYNTH_EXECUTOR_MAX_TIMEOUT_MS` сутки тихо превращаются в 10 минут; тест на согласованность `/capabilities.limits` обязателен.
4. **Изменение `deliver()`** — самый рискованный шов: он обслуживает все источники событий. Требуются тесты на неизменность поведения `enqueue`/`defer` и отдельная матрица для `steer`.
5. **Миграция расписаний.** Легаси `ephemeral` без проекта нельзя вывести автоматически; такие записи не должны ни срабатывать, ни исчезать молча — `needs_attention` + подсказка в панели.
6. **Часовые пояса и DST.** `daily` считается в TZ параметра; переход на летнее время может дать сдвиг/дубль — фиксируем поведение тестом (первое вхождение после перехода).
7. **Панель и i18n.** Переименование вкладки и новые ~60 ключей затрагивают тесты `RightPanel.tabs`, `SchedulerTab`, `ProcessesTab`; менять их нужно вместе с разметкой, а не после.
8. **Объём.** Оценка: этап 1 — 0,5–1 день; этапы 2–4 — 2–3 дня; этап 5 — 1 день; этап 5.1 — 1–1,5 дня; этап 6 — 0,5 дня; этап 7 — 2–3 дня; этап 8 — 1 день. Итого ~8–10 рабочих дней одного разработчика.

## Решения, подтверждённые владельцем (2026-11-17)

1. **RBAC автоматизаций в managed** — расширяем: EDITOR/OWNER проекта управляют своими автоматизациями, ADMIN/LEAD — любыми; прежнее `requireAdmin` на все мутации снимается.
2. **SDK/OpenAPI для `/timers`** — вне итерации: внутренний API + service-key scopes, SDK отдельной задачей.
3. **Перенос сессии** — модель из Части D принята: блок по умолчанию, отмена автоматизаций, перенос дочерних сессий, переатрибуция истории, Notice.
