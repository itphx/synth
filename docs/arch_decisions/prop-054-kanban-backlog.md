# PROP-054: Kanban-доска, backlog, управление проектами

> **Статус:** 🧩 Предложение — Kanban-доска поверх `project.plan` + глобальный backlog, assignee/WIP-лимиты
> **Решение до:** 2026-11-14
> **Дата:** 2026-09-16
> **Обновлено:** 2026-11-07 — согласован дизайн правой панели, модальной доски и точечного API
> (см. «Дополнение 2026-11-07»).
> **Источник:** перенесено из `AD-DRAFTS.md` (D9, идея 9 + Roadmap «Kanban/Backlog», Obsidian `Фичи.md`).
> **Связано:** [ADR-039](./adr-039-plan-in-project.md), [ADR-033](./adr-033-session-branching-merge.md),
> [ADR-044](./adr-044-mobile-adaptive-ui-pwa.md), [PROP-065](./prop-065-ui-docs-plan-todo.md),
> [ADR-051](./adr-051-scheduler-pipelines.md), [ADR-040](./adr-040-sessions-without-project.md).

**Решение:** сделать **интерактивную Kanban-доску** поверх `project.plan` и **глобальный backlog вне проекта**:

- доска с drag & drop и inline-edit колонок/карточек (на базе `project.plan`);
- backlog — задачи вне конкретного проекта, с приоритизацией (**urgency/importance** или **MoSCoW**);
- назначение на агентов (**assignee**), **WIP-лимиты**, **fast-add**;
- превращение задачи в запрос к агенту.

> **Дополнено 2026-11-07:** ближайший инкремент — не backlog/assignee, а рабочая правая панель,
> модальная доска, ручной журнал и точечный API плана/ToDo/журнала; см. «Дополнение 2026-11-07».

## Контекст

### Что уже есть

- Модель `project.plan` (колонки, зависимости, приоритеты) + инструменты `plan_*`/`todo_*` (ADR-039).
- UI-блок плана — **read-only**: `packages/ui/src/components/panels/ProjectTab.tsx` (`ProjectPlanBlock`
  только рендерит колонки/карточки).
- Роут плана: core-фабрика `packages/core/src/server/routes/projects.ts` принимает `plan` как
  `z.unknown()` (`planFieldSchema`) и **пишет** его в проект; backend монтирует core-фабрику.
- В прототипе t11 `.cline/kanban` пуст (`~/dev/aic/t11/.cline/kanban`).

> **Поправка к черновику (устарело):** в D9 сказано, что backend принимает `plan` как `z.unknown()`
> (`packages/backend/src/routes/projects.ts:18`), а core-роут плана **не пишет** (0 вхождений). На момент
> переноса в код это **не так**: схема `planFieldSchema = z.unknown()` и запись `plan` живут в **core**-фабрике
> (`packages/core/src/server/routes/projects.ts`), а backend — тонкая обёртка. Фактическое состояние — ниже.

### Проблема

Агент умеет вести план/ToDo, но человек не может управлять ими из UI: доска read-only, нет backlog вне проекта,
нет назначения на агентов/WIP-лимитов. Планирование и приоритизация остаются «в голове» пользователя и в
промптах агента, а не в интерфейсе.

## Детали

### Интерактивная доска

- Drag & drop карточек между колонками, inline-edit, fast-add; синхронизация с `project.plan` через API/WS
  (`plan.approved`, `todos.updated`).
- Правки отражаются в модели плана, которую видит агент ([ADR-039](./adr-039-plan-in-project.md)).

### Backlog

- Глобальный backlog вне проекта (или per-user — открытый вопрос): задачи без привязки к проекту/сессии.
- Приоритизация: **urgency/importance** или **MoSCoW**; WIP-лимиты колонок.

### Назначение и запуск

- **Assignee** (агент/пользователь); превращение карточки в запрос к агенту (запуск сессии/промпта).
- Связь с шедулером ([ADR-051](./adr-051-scheduler-pipelines.md)) — запуск задачи по расписанию/событию.

### Модель данных

- Расширять `project.plan` или вводить отдельную сущность `Task`? (открытый вопрос).
- Хранение — JSON/FileStore (ADR-005) до PostgreSQL (ADR-097).

### Мобильный UI

- На тач-устройствах DnD отключён ([ADR-044](./adr-044-mobile-adaptive-ui-pwa.md)) — нужна touch-альтернатива
  (кнопки/меню перемещения).

## Дополнение 2026-11-07 — правая панель, модальная доска и API

> Согласовано с владельцем 2026-11-07 по результатам разбора dev-инстанса. Основание — текущее
> состояние UI: план обрезан (`max-h-48`), колонки идут вертикально, третий пункт скрыт; ToDo и план
> выглядят по-разному; журнал — read-only в конце вкладки; HTTP-правок ToDo нет, план пишется целиком
> через `PUT /projects/:id` (`z.unknown()`). Реализация не начата.

### Принятые решения

1. **Места не меняем, вид унифицируем.** План и журнал остаются во вкладке «Проект» правой панели,
   ToDo — во вкладке «Сессия». Обе используют общий набор компонентов (`TaskRow`/`TaskGroup`) и общий
   словарь статусов/приоритетов.
2. **Компактные списки + модальное рабочее окно.** В панели — компактные группы с раскрытием
   отдельного пункта; полная kanban-доска, подробный журнал, статистика и редактирование — в отдельном
   модальном окне (`~90vw × 90vh`).
3. **Журнал — ручной.** Записи создают модель (`project_log_write`) и пользователь; CRUD из UI и
   инструментов. Авто-лента событий в этом инкременте не делается.
4. **Полноценный API сразу.** Точечные endpoint'ы по пунктам/колонкам/записям журнала, zod-валидация,
   версионирование плана, события в существующей шине. UI-правка не пишет план целиком через
   `PUT /projects/:id`.
5. **Точечные инструменты не дублируем.** Для плана уже есть `plan_write` с `create_item/update_item/
   move_item/delete_item/set_dependencies/add_column`, для ToDo — `todo_add/update/delete`. Дополняем
   недостающее: операции с колонками и порядком, правка/удаление записей журнала.

### Правая панель: план (вкладка «Проект»)

- Заголовок секции: «План проекта» + сводка (`N пунктов · M в работе`) + кнопка «Доска» (модальное окно).
- Группы по колонкам: имя, счётчик, WIP (`3/5`), collapse; пустые группы свёрнуты; «+ пункт» в группе.
- Свёрнутый пункт: статус-контрол (колонка), заголовок (до 2 строк), приоритет, маркеры описания/
  тегов/зависимостей; действия по hover/focus — изменить, переместить, удалить.
- Раскрытый пункт: описание, теги, зависимости, id, `createdAt/updatedAt`, те же действия.
- Убрать фиксированный `max-h-48` и вложенный скролл: в панели показывать первые N пунктов группы
  (например, 5) и «показать ещё»; полный список — в модальном окне.
- Пустой план: кнопка «Создать план» с дефолтными колонками (Бэклог/К выполнению/В работе/Готово).
- Дубликаты колонок не мигрируются автоматически; пользователь переименовывает/удаляет их через
  новые операции (при удалении — перенос пунктов в выбранную колонку).

### Правая панель: ToDo (вкладка «Сессия»)

- Тот же `TaskRow`: статус, заголовок, приоритет, связь с пунктом плана (`planItemId` → название +
  переход), действия.
- Группировка по статусам (`pending/in_progress/completed/cancelled`) со счётчиками; выполненные и
  отменённые свёрнуты по умолчанию; «очистить выполненные».
- Добавление пункта из панели; reorder — в модальном окне; в панели — меню «переместить».
- Раскрытый пункт: id, связь с планом, действия.

### Модальное окно

Открывается из плана, ToDo или журнала; секции:

1. **Доска** — колонки плана горизонтально, drag & drop карточек и колонок, inline-edit, fast-add,
   индикатор WIP. На тач-устройствах DnD отключён ([ADR-044](./adr-044-mobile-adaptive-ui-pwa.md)) —
   перемещение через меню.
2. **Журнал** — полный список с пагинацией, фильтрами (автор, сессия, дата), добавление/правка/удаление.
   В панели — последние 3–5 записей и «все записи».
3. **Статистика** — план: по колонкам/приоритетам, WIP, прогресс; ToDo: по статусам/приоритетам;
   журнал: записи по дням/авторам/сессиям. Метрик по срокам нет — в модели плана нет due date.

### Модель и API

**Схемы.** Добавить zod-схемы в `packages/shared` для `ProjectPlan`, `PlanColumn`, `PlanItem`,
`PlanDependency`, `TodoItem`, `ProjectLogEntry` (известные поля; неизвестные — `passthrough` при
чтении для совместимости, в телах мутаций — strict). `planFieldSchema = z.unknown()` заменить на
`ProjectPlanSchema.nullable()`.

**План (проект)** — все мутации требуют `canEditProjectContent`:

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/v2/projects/:id/plan` | план целиком (для модального окна) |
| POST | `/api/v2/projects/:id/plan/items` | создать пункт |
| PATCH | `/api/v2/projects/:id/plan/items/:itemId` | изменить поля пункта |
| PATCH | `/api/v2/projects/:id/plan/items/:itemId/move` | переместить/переупорядочить (`columnId`, `beforeItemId`/`afterItemId`) |
| DELETE | `/api/v2/projects/:id/plan/items/:itemId` | удалить пункт |
| POST | `/api/v2/projects/:id/plan/columns` | создать колонку |
| PATCH | `/api/v2/projects/:id/plan/columns/:columnId` | переименовать/WIP |
| DELETE | `/api/v2/projects/:id/plan/columns/:columnId` | удалить (`moveItemsTo`) |
| PUT | `/api/v2/projects/:id/plan/columns/order` | порядок колонок |

- `plan.version` — оптимистичная блокировка для `move`, `delete column`, `columns/order`; при
  несовпадении — `409 PLAN_VERSION_CONFLICT` и актуальный план в теле. Для одиночных field-правок
  версия не требуется (операция применяется к текущему пункту под локом хранилища).
- После `move`/`order` сервер нормализует `order` в колонках (`0..n-1`).

**ToDo (сессия)** — мутации требуют write-доступа к сессии (тот же prefix-guard):

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/v2/sessions/:id/todos` | создать пункт |
| PATCH | `/api/v2/sessions/:id/todos/:todoId` | изменить/сменить статус/приоритет/связь |
| DELETE | `/api/v2/sessions/:id/todos/:todoId` | удалить пункт |
| PUT | `/api/v2/sessions/:id/todos/order` | порядок (`ids`) |
| POST | `/api/v2/sessions/:id/todos/clear` | очистить (`statuses`) |

- Отдельной версии ToDo не вводим: операции атомарны под `SessionManager.withLock`. `order` принимает
  только id существующих пунктов; отсутствующие/неизвестные id игнорируются, новые пункты дописываются
  в конец — воскрешения удалённых нет.

**Журнал (проект)**:

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/v2/projects/:id/log?limit&offset` | страница журнала |
| POST | `/api/v2/projects/:id/log` | добавить запись |
| PATCH | `/api/v2/projects/:id/log/:entryId` | изменить текст |
| DELETE | `/api/v2/projects/:id/log/:entryId` | удалить запись |

- `ProjectLogEntry` дополняется аддитивными `updatedAt`/`updatedBy` (кто и когда правил); `author` —
  `userId` для пользовательских записей, роль агента для записей модели; `sessionId` сохраняется.
- Деталь проекта (`GET /projects/:id`) пока продолжает отдавать `log`; при росте журнала — убрать
  из детали и оставить только страницу (отдельный шаг).

**Права и ошибки.**

- План/журнал: чтение — `canReadProject`, мутации — `canEditProjectContent` (owner/editor/LEAD/ADMIN);
  VIEWER — только чтение.
- ToDo: чтение — read-доступ к сессии, мутации — write-доступ к сессии (действующая матрица
  owner/участник проекта/LEAD/ADMIN).
- Коды: `400 VALIDATION_ERROR`, `403 PROJECT_FORBIDDEN`/`SESSION_FORBIDDEN`, `404 NOT_FOUND`,
  `409 PLAN_VERSION_CONFLICT`.

### События и синхронизация

- План: `plan.updated` публикуется в каналы **всех сессий проекта** (не только текущей) с
  `{project_id, version}`; публикация — после успешной мутации (HTTP и tool).
- Журнал: `project.updated` в каналы всех сессий проекта (по инварианту 27); `project_log_write`
  сейчас не публикует событие — исправить.
- ToDo: `todos.updated` в канал сессии, payload с актуальным списком (как сейчас).
- UI: на `plan.updated` и `project.updated` — перечитывать **деталь** проекта
  (`useProjectsStore.getProject(projectId)`), а не `loadProjects()`: список — сводки без `plan`/`log`,
  и текущая реализация может обнулить открытую панель. Требование: деталь открытого проекта не
  затирается загрузкой списка (разделить summary/detail или перечитывать деталь после списка).
- Все правки из UI публикуют те же события, что и инструменты; новых каналов нет (ADR-024).

### Доменные сервисы и инструменты

- Мутаторы вынести из `packages/core/src/engine/tools/{plan,todo,project-manage}.ts` в доменные
  сервисы (`plan-service`, `todo-service`, `project-log-service`); их вызывают и инструменты, и
  HTTP-роуты. Инвариант 1 («состояние меняется только инструментами `plan_*`/`todo_*`») уточнить в
  ADR-039: единый доменный мутатор, а не дублирование логики в роутах.
- `plan_write`: добавить `update_column`, `delete_column` (с `moveItemsTo`), `reorder_columns`;
  `move_item` расширить `beforeItemId`/`afterItemId` (упорядочивание без ручного `order`).
- `todo_*`: добавить `todo_reorder`, `todo_clear` (completed/cancelled).
- `project_log_*`: добавить `project_log_update`, `project_log_delete`; `project_log_write` — append.
- Ответы инструментов — компактные (id + краткий итог), полный markdown — только для `plan_read`/
  `project_log_read`.

### Не входит в этот инкремент

- Глобальный backlog, assignee, отдельная сущность `Task`, WIP-enforcement, запуск задачи в сессию/
  по расписанию — остаются в исходном видении PROP-054.
- Авто-лента событий в журнале (поверх ручного).
- Поиск/RAG по журналу и документации (PROP-065).

### Порядок реализации

1. Shared-схемы, доменные сервисы, HTTP API, инструменты; тесты RBAC/409/событий.
2. UI: общий `TaskRow`/`TaskGroup`, компактные списки, inline-edit, раскрытие, создание/удаление,
   журнал в панели.
3. Модальное окно: доска (DnD + touch-альтернатива), журнал с пагинацией/фильтрами, статистика.
4. Реалтайм-фиксы, `docs/API_V2.md`, `docs/TOOLS.md`, `packages/ui/AGENTS.md`, визуальная проверка.

### Критерии готовности

- План и ToDo в панели читаются без обрезки: все пункты доступны (полный список — в модальном окне),
  пустые группы не занимают место.
- Пользователь с правами создаёт/правит/перемещает/удаляет пункты плана, колонки, ToDo и записи
  журнала; изменения видны агенту в следующем ходе (`plan_updated`/`todos_updated`).
- Правки из другого клиента/модели приходят без перезагрузки и не затирают открытую панель.
- Негативная матрица: VIEWER не мутирует план/журнал; пользователь без write-доступа к сессии не
  мутирует ToDo; 409 при устаревшей версии колонок/порядка.
- `pnpm typecheck`, `pnpm lint`, `pnpm test` зелёные; визуальная проверка в dev.

## Статус реализации в коде

**Не реализовано (проверено 2026-11-07 на dev-инстансе и по коду).**

- `ProjectPlanBlock` (`packages/ui/src/components/panels/ProjectTab.tsx`) — read-only; `max-h-48`,
  вертикальные колонки, пустые колонки занимают место; третий пункт в «Тестовом проекте 2» скрыт
  внутренним скроллом.
- `SessionTodosBlock` (`packages/ui/src/components/panels/SessionSettingsTab.tsx`) — read-only;
  длинные тексты занимают много места, нет группировки/редактирования/связи с планом.
- `ProjectLogBlock` — read-only, сырые ISO-таймстемпы, без автора/сессии, в конце вкладки.
- HTTP: план — только `PUT /projects/:id` с `planFieldSchema = z.unknown()`; точечных endpoint'ов нет;
  записи ToDo по HTTP нет.
- События: `plan_write` публикует `plan.updated` только в текущую сессию; UI обновляет сессию, а не
  проект; `project_log_write` не публикует событие; `project.updated` обрабатывается через
  `loadProjects()` (сводки без `plan`/`log`).
- Инструменты: точечные действия плана/ToDo есть; нет операций с колонками/порядком и правки/удаления
  журнала.

> Исходная проверка (grep по `packages/**`) подтверждала read-only план; уточнение 2026-11-07 добавило
> состояние ToDo/журнала, HTTP и событий. Пути/строки из черновика (`backend/src/routes/projects.ts:18`)
> устарели — логика плана перенесена в core-фабрику.

## Открытые вопросы

- Backlog — глобальный или per-user? (не входит в текущий инкремент)
- Отдельная сущность `Task` для backlog/assignee — нужна ли? (в текущем инкременте остаёмся на
  `project.plan`)
- WIP-лимиты — только индикатор или жёсткий запрет перемещения? (в текущем инкременте — индикатор)
- Достаточно ли write-доступа к сессии для правки ToDo участником проекта, или только владелец/EDITOR?
- Нужна ли авто-лента событий поверх ручного журнала? (отложено)
- Выносить ли `log` из детали проекта в отдельную страницу сразу или после роста журнала? (в текущем
  инкременте деталь сохраняет `log`, модальное окно читает страницу)
