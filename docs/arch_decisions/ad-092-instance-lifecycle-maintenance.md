# AD-092: Обслуживание инстанса — обновление, миграции, откат и удаление

> **Статус:** ⏳ Не реализовано (проект)
> **Дата:** 2026-10-15
> **Парные документы:**
> - [AD-005](./ad-005-json-storage.md) «JSON-файлы как хранилище» — данные, которые мигрируют и бэкапятся;
> - [AD-032](./ad-032-history-storage-postgresql.md) «PostgreSQL» — будущий источник формальных миграций схемы;
> - [AD-091](./ad-091-backup-restore-transfer.md) «Бэкап, восстановление и перенос данных» — страховка перед необратимыми шагами и механизм отката данных;
> - [AD-038](./ad-038-npm-packages.md) «Публикуемые npm-пакеты» — поставка версий и версионирование;
> - [AD-076](./ad-076-git-repo-registry-ssh.md) — `synth secrets rotate` как образец безопасной one-shot команды.

## Решение

Замкнуть жизненный цикл инстанса: **обновление → миграция → (при неудаче) откат → удаление**. Четыре части:

1. **Версионирование данных и миграции.** Ввести глобальный `meta.json` (`{dataDir}/meta.json`) с `schemaVersion` и журналом применённых миграций. Миграции — идемпотентная цепочка, применяется на старте (и/или `synth migrate`), **с обязательной страховочной копией перед записью**; неизвестная старшая версия → отказ старта с понятной ошибкой.
2. **Обновление и откат.** `synth update` получает `--to <version>` (в т.ч. откат на предыдущую) и не тянет `latest` вслепую; документируется `helm rollback` и порядок «откат версии + восстановление данных из бэкапа».
3. **Удаление (uninstall/cleanup).** Явный сценарий удаления инстанса: CLI `synth uninstall` (по умолчанию — **данные сохраняются**, `--purge` удаляет), плюс helm-инструкция (`helm uninstall`, `keepOnUninstall`, удаление PVC/секретов/образов/namespace).
4. **Runbook эксплуатации.** Доковая страница: порядок обновления, миграции, откат, удаление, что делать при несовместимости версий.

## Контекст

Аудит отметил отсутствие эксплуатационного контура: нет ни команд backup/restore, ни миграций, ни плана rollback, ни удаления за собой. По факту:

- **Обновление — только «вперёд».** `synth update --apply` (`packages/core/src/main.ts`) ставит `@itphx/synth@latest`; параметра версии и отката нет. `latest` в реестре GitVerse **не публикуется** (см. `docs/PUBLISHING.md`), то есть команда апеллирует к тегу, которого может не быть.
- **Нет глобальной версии схемы данных.** Есть точечные `schemaVersion` у отдельных стораджей (`event-binding-store.ts`, `route-rule-store.ts`) и маркер-миграция `session-scope-snapshots-v1` (`packages/core/src/storage/migrations.ts`, гвард — запись в runtime settings). Общего механизма «версия → набор миграций → журнал» нет; `{dataDir}` в целом не версионирован.
- **PVC по умолчанию теряется при uninstall.** В Helm-чарте `backend.persistence.keepOnUninstall: false` по умолчанию (`charts/synth/values.yaml`), т.е. `helm uninstall` удаляет PVC с данными. Это не задокументировано как риск.
- **Откат не описан.** Ни `helm rollback`, ни downgrade пакета, ни согласование отката версии с откатом данных.
- **Удаление за собой не описано.** Нет инструкции по очистке PVC, секретов, образов, namespace; нет осознанного «оставить/удалить данные».

## Детали

### Версия схемы данных и миграции

- `{dataDir}/meta.json`:
  ```json
  { "schemaVersion": 3, "instanceVersion": "0.10.0", "migrations": ["session-scope-snapshots-v1", "…"] }
  ```
- Реестр миграций в коде: `id → fn(deps)`; применение по порядку, идемпотентно, под маркером (`settingsStore`/`meta.json`).
- Порядок старта: `meta.schemaVersion` == ожидаемый → старт; `<` → **снапшот `{dataDir}`** → миграции → запись `meta.json`; `>` → **отказ** («данные новее версии; обновите Synth»).
- Команды: `synth migrate --dry-run` (показать план), `synth migrate` (применить; `--yes` обязателен для записи).
- Существующие точечные миграции переводятся на общий реестр.

### Обновление и откат

| Операция | Команда | Замечание |
|---|---|---|
| Проверить | `synth update` | как сейчас (показать current/latest) |
| Обновить | `synth update --apply [--to <version>]` | без `--to` — последняя **стабильная из известных**, не слепой `latest` |
| Откат (standalone, npm) | `synth update --to <prev> --apply` | downgrade пакета |
| Откат (K8s) | `helm rollback <release> <revision>` | + при необходимости restore данных из бэкапа ([AD-091](./ad-091-backup-restore-transfer.md)) |
| Совместимость | — | правило: **понижение версии не мигрирует данные назад**; откат данных = только restore из бэкапа |

- Документируется правило: перед обновлением — бэкап ([AD-091](./ad-091-backup-restore-transfer.md)); после обновления миграция может изменить данные необратимо.
- Версии пиннуются явным тегом (никакого `latest`).

### Удаление и очистка

- CLI `synth uninstall [--purge] [--dry-run] [--yes]`:
  - по умолчанию — **не удаляет** `{dataDir}` (печатает, что осталось и где);
  - `--purge` — удаляет каталог данных (требует `--yes`);
  - для локального home ([AD-079](./ad-079-local-home-independent-instances.md)) — учитывать `config.yaml`/`profiles.json`/`credentials.json`.
- Helm/Managed-инструкция:
  - `helm uninstall synth -n synth` — при `keepOnUninstall: false` **удалит PVC**; предупредить и рекомендовать `true` там, где данные нужны;
  - очистка PVC, Secret (`synth-secrets`, signing-ключи), образов, namespace;
  - чек-лист «что удаляется / что остаётся».
- Аудит событий: `maintenance.migrate`, `maintenance.rollback`, `uninstall.purge`.

## Безопасность

- Миграция/откат/purge — привилегированные операции: подтверждение (`--yes`), `--dry-run`, страховочная копия перед изменяющими шагами.
- Никаких секретов в логах; при purge — предупреждение об утрате данных и о мастер-ключе (без него зашифрованные SSH-ключи невосстановимы).
- Не ломать идемпотентность существующих миграций (маркер не сбрасывается).

## Объём MVP и этапы

1. **MVP:** `meta.json` + реестр миграций + миграция существующих точечных на общий механизм; `synth migrate --dry-run|--yes`; `synth uninstall [--purge]`. ~3–4 дня.
2. `synth update --to <version>` (обновление и откат) + документация `helm rollback`. ~1–2 дня.
3. Runbook в портале: обновление/миграции/откат/удаление + чек-лист очистки. ~1 день.

## Открытые вопросы

1. Где хранить «ожидаемую» схему — в `meta.json` или в самом пакете (константа), а `meta.json` только фиксирует фактическую?
2. Снапшот перед миграцией: полный ([AD-091](./ad-091-backup-restore-transfer.md)) или только затрагиваемые файлы?
3. Политика понижения: разрешать ли автоматический откат данных при мажорном апгрейде (сейчас — нет)?
4. `synth uninstall` для managed-гибрида: должен ли он отзывать серверный binding/токены?
