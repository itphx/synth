# PROP-127: Параллельное исполнение инструментов в шаге — паритет с opencode

> **Статус:** 🧩 Предложение
> **Дата:** 2026-11-07
> **Решение до:** 2026-12-06
> **Связано:** [ADR-026](./adr-026-subagent-context-modes.md), [ADR-029](./adr-029-granular-permissions.md), [ADR-030](./adr-030-hooks-agent-events.md), [ADR-111](./adr-111-background-subagent-sessions.md), [ADR-117](./adr-117-provider-compatibility.md), [ADR-118](./adr-118-message-stream-v2.md), [ADR-096](./adr-096-storage-layer.md), [PROP-058](./prop-058-service-agents-council.md)

## Контекст (что есть сейчас)

**Synth исполняет вызовы инструментов одного шага строго последовательно.** В трёх местах тела цикла
идут обычным `for` с `await` на каждом вызове:

| Место | Цикл | Что это |
|---|---|---|
| `packages/core/src/engine/orchestrator.ts:5166` | `for (const tc of toolCalls)` | основная сессия |
| `packages/core/src/engine/tools/task/run-cycle.ts:1561` | `for (const tc of toolCalls)` | цикл саб-агента (`task`) |
| `packages/core/src/engine/pipelines/executors/agent-step.ts:368` | `for (const plan of planning.plans)` | агентский шаг пайплайна |

**Наблюдаемое следствие.** Если модель в одном шаге вызывает `task` несколько раз **без**
`background: true`, сабагенты выполняются друг за другом, а не одновременно: тул `task` без фонового
режима уходит в `runDetachableSubagent` (`packages/core/src/engine/tools/task/detachable.ts:75`), который
ждёт завершения прогона ребёнка, а цикл оркестратора ждёт завершения этого тула. Время шага растёт
линейно по числу вызовов.

Фоновый режим (`background: true`, `packages/core/src/engine/tools/task/tool.ts:979`) уже работает как
`void runSubagent(...)` — fire-and-forget, поэтому такие прогоны **перекрываются**. Но результат
приходит отдельным уведомлением, а не ответом в текущем шаге: модель не получает выход ребёнка в том же
сообщении.

**В opencode — параллельно.** `refs/opencode/packages/core/src/session/runner/step.ts:110-135`: каждое
событие `tool-call`, пришедшее в поток провайдера, порождает отдельный файбер (`Effect.forkScoped`),
поэтому вызовы одного assistant-сообщения выполняются одновременно. Свойства, которые важны для
порта:

| Свойство | opencode | Ссылка |
|---|---|---|
| Результат привязан к `id` вызова, а не к позиции | `publisher.toolExecution(event.id, …)` | `step.ts:133` |
| Порядок в истории = порядок вызовов модели, не порядок завершения | слот в `message.content` заводится на `tool.input.started`, результат дописывается по id | `message-updater.ts:305-362` |
| `tool_use`/`tool_result` в пары — порядок 1:1 | `to-llm-message.ts:210-221` | — |
| Permission `ask` проверяется **внутри** файбера: подтверждений может быть несколько одновременно | `permission.ts:248-280` | — |
| Отказ по одному `ask` каскадирует на весь пакет ожидающих | `permission.ts:315-328` | — |
| Ошибка одного вызова не роняет остальные | `classifyToolExits` (`step.ts:306-330`) | — |
| Ограничения на число одновременных вызовов нет | — | — |
| Шаги не перекрываются: шаг ждёт завершения всех файберов | `Fiber.awaitAll` (`step.ts:153`) | — |

**Что мешает просто перенести схему.** Тело цикла в Synth — не «вызвать тул и вернуть результат», а
конвейер с общим состоянием, рассчитанным на последовательность:

| Общее состояние | Где | Чем ломается при параллели |
|---|---|---|
| `currentMessages.push({role:'tool', …})` | `orchestrator.ts:6054` | Порядок tool-сообщений в LLM-запросе обязан совпадать с порядком `tool_calls` ([ADR-117](./adr-117-provider-compatibility.md)): OpenAI-совместимые API требуют по одному `tool`-сообщению на каждый `tool_call`, Anthropic — подряд идущие `tool_result` в одном user-сообщении (`providers/anthropic.ts:735`). Порядок завершения вместо порядка вызовов → `400`. |
| `allToolCalls.push(…)` | `orchestrator.ts:6040` | Порядок попадает в `metadata.tool_results` и в `_injectToolAttachments`. |
| `doomLoopTracker` (Map) | `orchestrator.ts:4282` | Инкремент счётчика одинаковых вызовов — гонка. |
| `denyRepeatKey` / `denyRepeatCount` | `orchestrator.ts:4347` | Смысл «N одинаковых отказов **подряд**» — по определению последователен. |
| `effectivePermissionConfig` / `permissionEvaluator` | `orchestrator.ts:5459` | Пересоздаются при «Разрешить в сессии» — переприсваивание общего состояния посреди батча. |
| `sessionMode` / `planApproved` / `modeChangePending` | `orchestrator.ts:5934` | `plan_enter`/`plan_exit` меняют режим — следующий вызов в батче обязан видеть новый режим. |
| `tools` / `workingDir` / `allowedRoots` / `workspaceReady` | `orchestrator.ts:5969` | `project_create`/`project_attach`/`project_workspace_set` пересобирают инструменты и периметр — следующий вызов обязан их видеть. |
| `this._lazyInstructions` (реестр per-session) | `engine/context/lazy-instructions.ts:196` | Общий `_loaded`/`_claims` — гонка на первой догрузке. |
| `classify_conversation`, `todo_write` | `orchestrator.ts:5918`, `engine/tools/todo.ts:263` | `withLock` + `saveSession` — полная перезапись сессии; при параллельной точечной дозаписи другого вызова возможна потеря записи. |

**Следствие для хранилища.** `SessionManager.withLock` — взаимоисключающий мьютекс на сессию, но **не
реентерабельный**: вложенный `withLock` той же сессии ведёт к дедлоку (`sessions/manager.ts:125-139`).
При этом `appendMessage` (точечная дозапись, `sessions/manager.ts:708`) берёт **другой** лок — файловый
(`storage/file-store.ts:671`), а `saveSession` — файловый же, но переписывает файл целиком. Параллельная
комбинация «точечная дозапись + полная перезапись» в одном батче — источник потери сообщений.

## Решения владельца (основа предложения)

| № | Вопрос | Решение |
|---|---|---|
| 1 | Объём параллелизации | **Полный паритет с opencode**: параллельное исполнение всех вызовов одного шага — в основной сессии, в цикле саб-агента и в агентском шаге пайплайна. |
| 2 | Одновременные подтверждения прав | **Параллельно**, как в opencode: несколько `ask` в одном шаге висят одновременно; отказ по одному каскадирует на весь пакет. |
| 3 | Форма документа | Сначала **PROP** (этот документ), не ADR — решение не принято, реализация впереди. |

## Предлагаемое решение

### 1. Ключевая идея: разделить цикл на фазы, параллелизовать только исполнение

Тело цикла делится на три фазы. Общее состояние, зависящее от порядка, живёт в последовательных
фазах; параллельной остаётся только фаза исполнения — ровно то, что делает opencode, где файбер
охватывает только `executeTool`.

```
Фаза A — ПЛАНИРОВАНИЕ (последовательно, порядок вызовов модели)
  для каждого вызова: разбор аргументов → resolve toolDef → MCP-скоуп →
  pre_tool_use хук → проверка прав → doom/deny-учёт → решение «execute | deny | error»
  результат: массив планов в порядке вызовов модели

Фаза B — ИСПОЛНЕНИЕ (параллельно)
  для всех планов вида «execute» — executeToolDef одновременно
  каждый вызов — в своей промис-цепочке; результат пишется в слот по индексу вызова
  ошибка вызова не влияет на остальные

Фаза C — ФИКСАЦИЯ (последовательно, порядок вызовов модели)
  для каждого вызова в порядке модели: IPI-обёртка → lazy-инструкции →
  публикация tool_call.result → персист результата → currentMessages.push →
  allToolCalls.push → переходы режима/проекта → post_tool_use хук
```

**Инварианты, которые сохраняются.**

1. **Порядок в истории — порядок вызовов модели.** Результат каждого вызова кладётся в слот по его
   индексу в `toolCalls`; в `currentMessages` tool-сообщения добавляются на фазе C в том же порядке.
   Провайдерский контракт (один `tool`-сообщение на `tool_call`, подряд идущие `tool_result` в одном
   user-сообщении) сохраняется.
2. **Общее состояние остаётся последовательным.** `doomLoopTracker`, `denyRepeat*`, `hadDeny`,
   `roleBlocked*`, пересоздание `permissionEvaluator` — всё на фазе A, до запуска фазы B.
3. **Смена режима и проекта видна следующему вызову.** `plan_enter`/`plan_exit` и `project_*` меняют
   `sessionMode`/`planApproved`/`tools`/`workingDir`. Это означает, что их эффект должен быть виден
   вызовам, идущим после них, — а значит, такие вызовы образуют **барьер**: батч делится на группы,
   и группа, содержащая смену режима/проекта, завершается раньше, чем начнётся следующая.
   Точный порядок вызовов модели при этом сохраняется: `plan_exit` остаётся раньше `write_file` в том же
   assistant-сообщении.
4. **Ошибка изолирована.** Исключение тула — результат тула (`tool.exec_error`), а не падение хода.
   Поведение совпадает с текущим (`orchestrator.ts:5543-5558`).
5. **Отмена прерывает весь батч.** Сигнал отмены хода (`toolAbortController.signal`) общий для всех
   параллельных вызовов; незавершённые вызовы получают отменённый результат, как сейчас.
6. **Шаги не перекрываются.** Шаг ждёт завершения всех вызовов перед следующим LLM-вызовом — как в
   opencode (`Fiber.awaitAll`).

### 2. Где именно параллелизуется

| Цикл | Что меняется |
|---|---|
| `orchestrator.ts:5166` | Основная сессия — основной объём работы. |
| `run-cycle.ts:1561` | Цикл саб-агента: параллельно становятся и несколько `task` внутри саб-агента. |
| `agent-step.ts:368` | Агентский шаг пайплайна: уже спланирован батч (`planning.plans`), нужна только параллельная фаза исполнения. |

### 3. Что это даёт для сабагентов

- Несколько `task` **без** фонового режима в одном шаге → дети выполняются одновременно, ответы
  собираются в порядке вызовов модели и уходят в LLM-контекст как парные `tool_result`.
- Несколько `task` **с** `background: true` → поведение не меняется (уже fire-and-forget).
- Сабагент, внутри которого вызывается несколько `task` → то же самое на уровне `run-cycle.ts`.

### 4. Подтверждения прав: несколько одновременных `ask`

`PermissionApprovalManager` (`engine/permission/approval.ts:156`) уже адресует ожидание по
`approval_id`, а идентификатор уникален на вызов (`approval_${tcId}`, `orchestrator.ts:5431`), —
механизм допускает несколько висящих подтверждений. Нужно:

- публиковать `permission.asked` для всех `ask`-вызовов батча;
- отмену («Стоп») снимать **все** ожидания сессии, а не текущее;
- отказ по одному подтверждению каскадировать на весь пакет ожидающих (паритет с opencode,
  `permission.ts:315-328`): остальные ожидания разрешаются отказом, вызовы получают
  `tool_result` с причиной отказа, ход продолжается по обычным правилам (deny не останавливает ход —
  [ADR-029](./adr-029-granular-permissions.md)).

**UI.** `PermissionRequestBar` (`packages/ui/src/components/chat/PermissionRequestBar.tsx:36`) уже
показывает очередь: текущий запрос — `requests[0]`, остальные — за счётчиком `waitingCount`. Значит,
UI к параллельным подтверждениям готов; нужно лишь проверить, что очередь корректно снимается при
ответе на любой из них.

### 5. Хранилище: точечная дозапись вместо полной перезаписи

Пункт 3 инвариантов требует, чтобы `todo_write` и `classify_conversation` не переписывали сессию
целиком, пока батч пишет точечные дозаписи. Варианты (выбор — при реализации):

- перевести мутации сессии на порт точечного обновления (`updateMessage`/`appendMessage` уже есть,
  `sessions/manager.ts:708`, `:766`), как это уже сделано для сообщений;
- либо ввести отдельную персист-операцию «обновить поле сессии» (`settings`/`todos`/`planApproved`),
  не переписывающую историю.

Полная перезапись файла сессии во время параллельного батча исключается — это потеря сообщений.

### 6. События и наблюдаемость

Публикуемые события не меняются: `tool_call.started` / `tool_call.result` / `step.tools.started` /
`step.tools.finished` ([ADR-118](./adr-118-message-stream-v2.md)). Меняется их **взаимный порядок**:
сейчас `started`/`result` идут строго чередуясь по одному вызову, при параллелизации `started` для
всех вызовов батча предшествует `result` для любого из них. `step.tools.started`/`finished` уже
несут `callIds` в порядке вызовов модели — он сохраняется.

Следствие для UI: карточки инструментов в ленте перестают появляться строго по очереди — они
появятся по мере завершения. Это соответствует opencode и не ломает контракт UI (карточка
привязана к `call_id`).

## Не цели

- Параллелизация *шагов* (несколько LLM-вызовов одновременно) — не входит; шаги остаются
  последовательными, как в opencode.
- Параллелизация разных сессий/ходов — уже обеспечивается очередью (`queue/processor.ts`).
- Параллельные `ask` **в разных сессиях** — уже работает (у каждой сессии своё ожидание).
- Новые инструменты или новые права — не входят.
- Смена поведения фонового режима `task` — не входит.

## Открытые вопросы

- **Барьер смены режима/проекта.** Предлагается делить батч на группы: группа со сменой
  `sessionMode`/`planApproved`/`tools`/`workingDir` завершается до старта следующей. Альтернатива —
  выполнять такие вызовы всегда последними в своём батче (меняет порядок вызовов модели — хуже).
  Нужно решить, чем именно делить: по факту наличия таких вызовов в батче или по более общему
  правилу «вызовы, меняющие состояние сессии, образуют барьер».
- **Предел одновременных вызовов.** opencode ограничения не имеет. Для Synth предлагается стартовать
  без предела (паритет), но рассмотреть предел (например, 8) как защиту от лавины вызовов от
  провайдера — отдельно от паритета.
- **Сохранение порядка `tool_call.started`/`result` в шине.** Возможен вариант с буферизацией
  `result` до завершения батча (порядок строго по модели) вместо публикации по мере завершения
  (живее, но порядок завершения). Требуется выбор.
- **Где живёт фазовая разбивка.** Вынести общий планировщик батча в отдельный модуль ядра (например
  `engine/tools/tool-batch.ts`) или реализовать три фазы на месте в каждом из трёх циклов. Общий
  модуль убирает дублирование, но требует вынести наружу большой объём общего состояния.
