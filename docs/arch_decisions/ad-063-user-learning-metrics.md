# AD-063: Обучение пользователя и метрики

> **Статус:** 🧩 Предложение (vision) — Обучение пользователя и метрики: Pre-PR Understanding Check, анализ сессий, дашборд без рейтингов
> **Дата:** 2026-09-16
> **Источник:** перенесено из `AD-DRAFTS.md` (D18, «Обучение пользователя и метрики», Roadmap Фаза 3/4;
> Obsidian `User-Skills-Learning-Metrics.md`, `Fear-of-Replacement.md`).
> **Связано:** [AD-057](./ad-057-loop-engine.md), [AD-059](./ad-059-pipeline-automation.md),
> [AD-047](./ad-047-memory-gbrain.md), [AD-054](./ad-054-kanban-backlog.md),
> [AD-036](./ad-036-llm-gateway.md), [AD-083](./ad-083-instance-customization-branding.md).

**Решение:** встроить в Synth **развитие пользователя, а не только ускорение кодинга** —
без «токенмаксинга» и без рейтингов разработчиков:

- **Pre-PR Understanding Check** — агент проверяет, что разработчик понимает сделанные изменения
  (вопросы по диффу/решению), прежде чем предлагать PR.
- **Анализ сессий** — частые ошибки, неиспользуемые фичи, повторяющиеся паттерны работы.
- **Персональные рекомендации** и контекстные подсказки.
- **Интерактивный онбординг** (смыкается с приветственным окном
  [AD-083](./ad-083-instance-customization-branding.md)).
- **Дашборд метрик** — понимание/успешность/переделки/покрытие автоматизацией/свежесть контекста/
  срабатывание guardrail'ов; **тренды по команде, без рейтингов отдельных разработчиков**.

## Контекст

Roadmap Фаза 3/4 фиксирует разворот от «скорость написания кода» к «осознанной работе и обучению».
Идея — измерять не количество сгенерированного кода и не «принятые токены», а качество и понимание.

В Synth сегодня **нет ни механизмов обучения, ни сбора метрик**:

- нет Pre-PR understanding check;
- нет анализа сессий пользователя и персональных рекомендаций;
- нет онбординга как продуктового механизма (приветственное окно — в
  [AD-083](./ad-083-instance-customization-branding.md));
- нет дашборда метрик.

Есть инфраструктура, на которую это можно опереть:
- аудит LLM-вызовов JSONL ([AD-036](./ad-036-llm-gateway.md));
- `DebugCollector` (`packages/core/src/debug.ts`) — технический слой метрик (микро-слой, промпт);
- память/индексы ([AD-047](./ad-047-memory-gbrain.md)) — для анализа истории;
- loops/pipelines ([AD-057](./ad-057-loop-engine.md), [AD-059](./ad-059-pipeline-automation.md)) —
  источники данных о прогонах;
- задачи/backlog ([AD-054](./ad-054-kanban-backlog.md)) — привязка метрик к задачам.

**Метрики без токенмаксинга.** Заявленный набор: understanding score, loop success rate,
rework rate, automation coverage, context freshness, guardrail hit rate. Явный антипаттерн —
рейтинги отдельных разработчиков и оптимизация «ради метрик».

## Детали

### 1. Pre-PR Understanding Check

Перед созданием PR агент задаёт разработчику несколько вопросов по существу изменений
(почему так, какие альтернативы, какие риски) и на основе ответов формирует сигнал
`understanding score`. Цель — обучение и осознанность, **не блокирующий аудит**.

Возможные точки встраивания: git-flow ([AD-076](./ad-076-git-repo-registry-ssh.md)), pipelines
([AD-059](./ad-059-pipeline-automation.md)), скиллы ([AD-046](./ad-046-skills-and-slash-commands.md)).

### 2. Анализ сессий

Периодический разбор истории сессий ([AD-005](./ad-005-json-storage.md) → [AD-032](./ad-032-history-storage-postgresql.md),
память [AD-047](./ad-047-memory-gbrain.md)): частые ошибки, повторяющиеся запросы, неиспользуемые
возможности. Учитывать приватность: анализ — для самого пользователя.

### 3. Рекомендации и подсказки

Персональные рекомендации (что изучить, какие фичи попробовать) и контекстные подсказки в UI.
Формат — не «оценка», а подсказка/навигация.

### 4. Онбординг

Интерактивный онбординг нового пользователя (тур по интерфейсу, первые задачи). Согласуется с
приветственным окном [AD-083](./ad-083-instance-customization-branding.md).

### 5. Дашборд метрик

Агрегаты и тренды по команде. Хранение — JSON/`FileStore` ([AD-005](./ad-005-json-storage.md)) до
[AD-032](./ad-032-history-storage-postgresql.md). UI — раздел статистики; на мобильных (AD-044) —
упрощённый вид.

### 6. Антипаттерны (жёстко)

- **Никаких рейтингов разработчиков** и соревновательных метрик.
- Никакого «токенмаксинга» — метрики количества не являются целью.
- Метрики — инструмент самонаблюдения, а не контроля.

## Статус реализации в коде

**Не реализовано, кода нет.** Проверено по репозиторию (`packages/**`, без `dist/`/`node_modules/`):

- Идентификаторы `understandingScore`, `learningMetrics`, `prePrUnderstanding`, `reworkRate`,
  `sessionAnalysis` — 0 вхождений.
- Pre-PR check — только в Roadmap Фаза 4.
- Метрики — лишь `DebugCollector` (`packages/core/src/debug.ts`, технический слой) и аудит
  [AD-036](./ad-036-llm-gateway.md); продуктового дашборда и агрегатов нет.
- Онбординг как продуктовый механизм отсутствует (приветственное окно — в проекте
  [AD-083](./ad-083-instance-customization-branding.md)).

## Открытые вопросы

- Где хранить агрегаты метрик — JSON/`FileStore` или PostgreSQL ([AD-032](./ad-032-history-storage-postgresql.md))?
- Как на уровне дизайна не скатиться к «метрикам ради метрик»?
- Приватность: персональные рекомендации видны только пользователю? Тренды — кому?
- Достаточно ли эвристик/`DebugCollector` или нужен отдельный аналитический слой?
- Как соотносится с аудитом [AD-036](./ad-036-llm-gateway.md) (тоже хранит историю вызовов)?
- Как учитывать данные loops/pipelines, которые ещё не реализованы
  ([AD-057](./ad-057-loop-engine.md)/[AD-059](./ad-059-pipeline-automation.md))?
