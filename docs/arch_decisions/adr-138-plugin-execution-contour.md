# ADR-138: Контур исполнения плагинных инструментов — capability → пул, `ctx.runtime`

> **Статус:** ⚠️ Частично — реализовано: capability-гейт, `ctx.runtime` в `inline`, out-of-process
> runtime по проводу v2 (host-side loopback-прокси, invocation binding), шлюзы вне контура.
> Остаток: SDK для `ctx.runtime`, plugin-runtime внутри исполнителя (как альтернатива).
> **Дата:** 2026-11-13
> **Источник:** PROP-138 (файл удалён после принятия).
> **Связано:** [ADR-090](./adr-090-extension-api.md) (extension API), [ADR-086](./adr-086-extensibility-plugins-editions.md)
> (плагины), [ADR-135](./adr-135-execution-contour.md) (контур исполнения), [ADR-137](./adr-137-executor-isolation.md)
> (изоляция); спецификация — [docs/PLUGINS.md](../PLUGINS.md) §5.2.1, каталог тулов — [docs/TOOLS.md](../TOOLS.md).

## Контекст

Плагинный тул с файловыми/git/shell-capability исполнялся в процессе control plane и получал
`node:fs`/`child_process`: в split-топологии это означало доступ к ФС **control plane**, а не к
рабочему каталогу сессии на исполнителе. Прямой доступ плагина к ФС control plane как поддерживаемый
путь недопустим: он обходил и контур исполнения (ADR-135), и permission-слой/аудит.

## Решение

1. **Capability тула определяет контур.**

   | Capability | Контур |
   |---|---|
   | `file_read`, `file_write`, `shell`, `search`, `git_read`, `git_write` | пул сессии — через узкий runtime-интерфейс |
   | `web`, `memory`, `user` | control plane |

   Плагинный тул **не получает** прямого доступа к ФС control plane как поддерживаемого пути;
   использование `node:fs`/`child_process` — неподдерживаемый путь, сканер и ревью помечают его явно.
   В managed такой путь запрещён; предупреждение при загрузке и работа по старому пути — только
   `inline`/standalone.
2. **`ctx.runtime` — инжектируемый хостом узкий объект, привязанный к пулу сессии:** `exec(argv)` (без
   shell), `fs.read/write/list/stat/realpath`, `git` (через существующие операции). `ctx.extra` и
   `ctx.dataDir` по-прежнему **не передаются**.
3. **Capability-гейт.** Runtime выдаётся **только** тулу, у которого объявлена файловая/shell-capability
   (пересечение с контуром). Тул без неё runtime не видит — иначе граница «capability → контур»
   обходится объявлением.
4. **Out-of-process — wire protocol v2.** Хост поднимает **свой** loopback-прокси runtime'а и отдаёт
   плагину `SYNTH_RUNTIME_URL` + отдельный `SYNTH_RUNTIME_TOKEN` (не `SYNTH_PLUGIN_TOKEN`). Запросы:
   `POST /runtime/exec`, `POST /runtime/fs/{read,write,stat,readdir,realpath}`; тело — JSON, ответ — JSON.
   **Invocation binding:** хост регистрирует invocation на время вызова точки `tools` и снимает сразу
   после; `invocation_id` приходит в `context.invocationId`; незарегистрированный id → `404
   unknown_invocation`. Плагин не может исполнить команду «в чужом» вызове и не остаётся с привязкой
   после конца вызова. Плагин **не ходит** к исполнителю напрямую: единственная точка — хост, он же
   применяет permission-слой и аудит. Семантика inline и wire v2 совпадает (`argv` без shell,
   `if_exists: fail` не поддерживается, те же коды ошибок и лимиты); расхождение контуров запрещено.
   Плагин v1 работает как раньше — runtime по проводу ему не выдаётся (`404 unknown_invocation`).
5. **Шлюзы — вне контура исполнителя.** Мессенджер-шлюзы остаются отдельными деплойментами
   (HTTP-сервисы): приём/доставка сообщений и API, без ФС агента. Перенос шлюзов в пул не
   предусмотрен — иначе они получили бы доступ к файлам проекта.
6. **Совместимость.** Встроенные и MCP-тулы не меняются. Существующие плагины с ФС-capability
   переводятся на `ctx.runtime`; прямая работа с `node:fs` в managed запрещена.

## Альтернативы

- **Дать плагинам `ctx.dataDir`/`ctx.extra`** — отклонено: это порты хранилища и контекст ядра,
  плагин обошёл бы permission-слой и аудит.
- **Плагин ходит к исполнителю напрямую** — отклонено: адрес/токен пула утёк бы в плагин, проверка
  прав и аудит остались бы в обход.
- **Plugin-runtime внутри исполнителя** — отдельное решение (остаток): требует доставки кода плагина
  в пул и своего жизненного цикла.
- **Перенести шлюзы в контур** — отклонено: у шлюзов нет файловых операций, а доступ к ФС проекта им
  не нужен.

## Последствия

- **Плюсы:** плагинные тулы идут тем же контуром, что встроенные (изоляция и аудит едины); capability
  честно описывает, что тулу нужно; wire v2 не расширяет доверенную поверхность (только DTO runtime'а).
- **Минусы:** out-of-process плагинам нужен прокси и токен, а хосту — реестр invocation'ов; часть
  сервисов фасада (`facade.memory`/`embed`/`getSettings`) по проводу недоступна — такие плагины
  остаются `inline`; миграция существующих плагинов на `ctx.runtime` обязательна.
- **Остаток:** SDK для `ctx.runtime` (типы/клиент для авторов плагинов), plugin-runtime внутри
  исполнителя (альтернативный контур, отдельное решение).
