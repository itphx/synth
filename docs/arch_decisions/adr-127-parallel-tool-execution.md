# ADR-127: Параллельное исполнение инструментов в шаге — паритет с opencode

> **Статус:** ✅ Реализовано
> **Источник:** PROP-127
> **Дата:** 2026-11-07
> **Связано:** [ADR-026](./adr-026-subagent-context-modes.md), [ADR-029](./adr-029-granular-permissions.md), [ADR-030](./adr-030-hooks-agent-events.md), [ADR-096](./adr-096-storage-layer.md), [ADR-106](./adr-106-authority-layer.md), [ADR-111](./adr-111-background-subagent-sessions.md), [ADR-117](./adr-117-provider-compatibility.md), [ADR-118](./adr-118-message-stream-v2.md), [PROP-058](./prop-058-service-agents-council.md)

## Контекст

**Synth исполнял вызовы инструментов одного шага строго последовательно.** В трёх местах тела цикла
идут обычным `for` с `await` на каждом вызове:

| Место | Цикл | Что это |
|---|---|---|
| `packages/core/src/engine/orchestrator.ts` | `for (const tc of toolCalls)` | основная сессия |
| `packages/core/src/engine/tools/task/run-cycle.ts` | `for (const tc of toolCalls)` | цикл саб-агента (`task`) |
| `packages/core/src/engine/pipelines/executors/agent-step.ts` | `for (const plan of planning.plans)` | агентский шаг пайплайна |

**Наблюдаемое следствие.** Если модель в одном шаге вызывает `task` несколько раз **без**
`background: true`, сабагенты выполнялись друг за другом: тул `task` без фонового режима уходит в
`runDetachableSubagent` и ждёт завершения прогона ребёнка, а цикл оркестратора ждёт завершения
этого тула. Время шага росло линейно по числу вызовов. Фоновый режим (`background: true`) уже был
fire-and-forget, поэтому такие прогоны перекрывались, но результат приходил отдельным уведомлением,
а не ответом в текущем шаге.

**В opencode — параллельно.** `refs/opencode/packages/core/src/session/runner/step.ts`: каждое
событие `tool-call`, пришедшее в поток провайдера, порождает отдельный файбер, поэтому вызовы
одного assistant-сообщения выполняются одновременно. Свойства, взятые как образец: результат
привязан к `id` вызова; порядок в истории = порядок вызовов модели, а не порядок завершения;
permission `ask` проверяется внутри файбера (параллельные подтверждения); отказ по одному `ask`
каскадирует на весь пакет ожидающих; ошибка одного вызова не роняет остальные; шаги не перекрываются.

**Что мешало просто перенести схему.** Тело цикла в Synth — не «вызвать тул и вернуть результат», а
конвейер с общим состоянием, рассчитанным на последовательность: порядок `tool`-сообщений в
LLM-запросе (провайдерский контракт требует по одному `tool`-сообщению на каждый `tool_call`),
`doomLoopTracker`, «N одинаковых отказов **подряд**», пересоздание `permissionEvaluator` при
«Разрешить в сессии», `sessionMode`/`planApproved` (смена режима), `tools`/`workingDir`/`allowedRoots`
(смена проекта), реестр ленивых инструкций.

## Решение

### 1. Ключевая идея: разделить цикл на фазы, параллелизовать только исполнение

Общее состояние, зависящее от порядка, живёт в последовательных фазах; параллельной остаётся только
фаза исполнения — ровно то, что делает opencode, где файбер охватывает только исполнение тула.

```
Фаза A — ПОДГОТОВКА (последовательно, порядок вызовов модели)
  разбор аргументов → resolve toolDef → MCP-скоуп → pre_tool_use хук →
  проверка прав → doom/deny-учёт → ожидание подтверждения (ask) → план вызова

Фаза B — ИСПОЛНЕНИЕ (параллельно)
  все планы вида «execute» стартуют одновременно; результат кладётся в слот
  по индексу вызова; ошибка вызова не влияет на остальные

Фаза C — ФИКСАЦИЯ (последовательно, порядок вызовов модели)
  IPI-обёртка → lazy-инструкции → публикация tool_call.result → персист результата →
  currentMessages.push → allToolCalls.push → переходы режима/проекта → post_tool_use хук
```

### 2. Общий примитив

`packages/core/src/engine/tools/tool-batch.ts` — `runToolBatch(items, options?)`: конкурентный старт
всех исполнителей, слоты результатов по **исходной** позиции вызова, изоляция ошибок (сбой одного
вызова не роняет батч, батч не отклоняется целиком), `settleOrder` — порядок завершения отдельно от
порядка вызовов. Примитив используют все три цикла; дублирования нет.

### 3. Барьеры смены состояния

Вызовы, меняющие состояние, от которого зависят следующие вызовы того же сообщения, образуют
**барьер**: `plan_enter`/`plan_exit` (режим и `planApproved`), `project_create`/`project_attach`/
`project_workspace_set` (рабочий каталог, периметр, состав тулов). Батч делится на сегменты, мутирующий
вызов завершает свой сегмент, сегменты обрабатываются строго по порядку (подготовка → исполнение →
фиксация). Эффект мутирующего вызова виден следующим вызовам — как в последовательном цикле.

В цикле саб-агента барьер иной: `deriveSubagentPermission` безусловно запрещает `question`/`plan_enter`/
`plan_exit`/`task`, поэтому эти вызовы не исполняются и барьером быть не могут; состояние режима и
рабочего каталога ребёнка снимается один раз до цикла.

В шаге пайплайна барьеров нет: права и режим решены для всей партии до исполнения, а меняющие
состояние тулы в шаге пайплайна и не работают (у вызова тула нет `extra`).

### 4. Подтверждения прав: несколько одновременных `ask` + каскад отказа

`PermissionApprovalManager` (`engine/permission/approval.ts`) получил пакетный API:
`prepareWaiters`/`prepareWaiter` готовят ожидания, `publishWaiters` публикуют все `permission.asked`
разом (несколько подтверждений висят **одновременно**), `waitForDecision` остаётся тонкой обёрткой
для одиночных случаев.

**Каскад отказа** (паритет с opencode): отказ по любому подтверждению гасит остальные ожидания той же
сессии — ход не ждёт ответов на вопросы, на которые пользователь уже отказал. Каскад живёт в
менеджере (`_cascadeDeny`), а не в производителях ответа: ответы пользователя приходят через HTTP и
WS и не менялись. Серверный отказ (ответ с `reason`, например `already_consumed`) каскада **не**
запускает — каскадится только отказ пользователя.

**Одноразовость реестра (ADR-106 Ф3) сохранена.** Каскадное подтверждение списывается
(`ApprovalRegistry.consume`), поэтому поздний ответ на погашенное подтверждение — отказ
(`already_consumed`), одобрение уже невозможно.

**Переоценка после гранта.** «Разрешить в сессии» (`once: false`) пересобирает
`permissionEvaluator`, а ожидающие подтверждения переоцениваются по новым правилам (паритет с веткой
`always` в opencode): покрытый новым правилом соседний запрос одобряется без нового вопроса
пользователю. Переоценка идёт с **тем же** контекстом Authority, что и исходная проверка: без этого
guard пересчитал бы потолок хода без роли участника (участник `viewer` потерял бы read-only потолок,
ADR-106 Ф4) и оси агента — и вызов, который слой требует подтвердить, одобрялся бы грантом соседа без
нового вопроса пользователю.

### 5. Хранилище

Трёхфазный цикл исключает потерю сообщений: все перезаписи сессии (тулы вида `todo_write`) happen в
фазе исполнения под per-session локом с свежей загрузкой, все точечные дозаписи результатов
(`appendMessage`) — в фазе фиксации, а фазы не пересекаются. Правки слоя хранения не потребовались;
закрыт регресс-тест на смешение точечной дозаписи и полной перезаписи в одном батче.

## Ограничения

- **Параллелизуются вызовы, не шаги.** Несколько LLM-вызовов одновременно не входят: шаги остаются
  последовательными, как в opencode.
- **Предела на число одновременных вызовов нет** — паритет с opencode.
- **`task` без фонового режима** блокирует вызов до завершения ребёнка; несколько таких вызовов в
  одном шаге теперь идут одновременно, но каждый по-прежнему ждёт своего ребёнка.
- **Карточки инструментов в UI** перестают появляться строго по очереди: `tool_call.started` для всех
  вызовов батча предшествует `result` любого из них. Контракт UI не ломается — карточка привязана к
  `call_id`.
- **Слой Authority к проверке прав ребёнка (саб-агента) не подключён** — это прежнее поведение
  (`childEvaluator` без `authorityGate`), в рамках ADR-127 не менялось.
- **Предел параллелизма и пул вызовов** — отдельная задача (в opencode ограничения нет).

## Альтернативы

- **A. Параллелизовать только «безопасные» вызовы** (чтение) — отклонено: не даёт выигрыша в целевом
  сценарии (несколько `task`).
- **B. Параллелизовать шаги** — отклонено: меняет контракт провайдеров и семантику очереди.
- **C. Оставить цикл последовательным, распараллелить только на уровне opencode-совместимого
  планировщика** — отклонено: общий планировщик требует вынести наружу большой объём общего
  состояния, а трёхфазная разбивка локальна для каждого цикла.
- **D. Параллельные `ask` — по одному** (без каскада) — отклонено владельцем: ход «зависал» бы до
  ask-таймаута на вопросы, на которые пользователь уже отказал.

## Последствия

- Шаг с несколькими вызовами (в т.ч. несколькими `task` без фонового режима) выполняется за время
  самого долгого вызова, а не за сумму.
- Порядок в истории, в `metadata.tool_results` и в LLM-запросе — **порядок вызовов модели**; провайдеры
  получают парные `tool_result` в том же порядке.
- Подтверждения прав в UI: очередь уже была (`requests[0]` + счётчик ожидающих); добавлена обработка
  `permission.replied` — карточка снимается и для запросов, на которые пользователь не отвечал
  (каскад/авто-одобрение).
- Ошибка одного вызова не роняет остальные и не прерывает шаг — как раньше.
- Регресс-тесты: конкурентность (на настоящем барьере, без тайминговых допущений), порядок в истории
  при обратном порядке завершения, изоляция ошибок, барьер смены режима, отмена, одновременные
  подтверждения, каскад отказа, одноразовость реестра, переоценка после гранта (в т.ч. недопущение
  авто-одобрения вызова, который требует подтвердить слой Authority).
