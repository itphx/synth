# PROP-142: Управление сабагентом на ходу и автовосстановление прерванных прогонов

> **Статус:** 🧩 Предложение — тул `task` доставляет сообщение идущему сабагенту, продолжение передаёт новые указания (со сменой модели/провайдера), рестарт автоматически возобновляет прерванные ходы — включая дочерние сессии и фоновые прогоны.
> **Решение до:** 2026-12-15
> **Дата:** 2026-11-17
> **Связано:** [ADR-026](./adr-026-subagent-context-modes.md) (режимы контекста саб-агента), [ADR-104](./adr-104-mid-turn-steering.md) (вмешательство в ход), [ADR-111](./adr-111-background-subagent-sessions.md) (фоновые прогоны и реестр), [ADR-113](./adr-113-background-processes.md) (фоновые процессы), [ADR-118](./adr-118-message-stream-v2.md) (поток сообщений), [ADR-039](./adr-039-plan-in-project.md) (план/todo), [ADR-089](./adr-089-external-events-automation.md) (события и владелец), [ADR-092](./adr-092-instance-lifecycle-maintenance.md) (жизненный цикл инстанса, п. 7), [ADR-096](./adr-096-storage-layer.md) (порты слоя хранения), [ADR-095](./adr-095-god-object-decomposition.md) (швы без дублей)

## Контекст

Сегодня сабагент управляется асимметрично:

- **Запуск и продолжение** — только тулом `task` (`background: true` — фоновый прогон, `task_id` — продолжение). Продолжение возможно **только для свободного** ребёнка: `child.status.blocked || child.currentStream` → ошибка `task.resume_child_busy` (`engine/tools/task/tool.ts`).
- **Идущий прогон** — снаружи, только клиентским контрактом: `POST /api/v2/sessions/:id/prompt` с `mode: 'steer' | 'interrupt'` (ADR-104). Инъекция ложится в `steerInbox` **дочерней** сессии и применяется на границе шага в её цикле (`engine/tools/task/run-cycle.ts` → `applyChildSteerInjections`). Тула, которым агент-родитель мог бы это сделать, нет; в UI вкладка саб-агента read-only, а композер с 2026-10-30 всегда отправляет `queue`.
- **Продолжение не передаёт ввод**: `task({task_id, prompt, subagent_type})` требует `prompt` и `subagent_type`, но `continueChildSession` их не использует — в историю ребёнка добавляется только синтетический маркер `task.resume_marker` («Resume the interrupted task. Continue from where you stopped.»). Сменить агента/модель ребёнка при продолжении нельзя.
- **Скрытая третья семантика**: `POST /prompt` в **дочернюю** сессию в режиме `queue` поднимает обычный `QueueProcessor` (`enqueueUserMessage` → `createProcessor`). Прогон идёт **как у обычной сессии**: без цикла саб-агента, без его лимитов и шаг-механики, без уведомления родителю и без записи в реестр фоновых прогонов. Со стороны API это выглядит как «сообщение сабагенту», по факту — другой контур исполнения.
- **Рестарт**: обычные сессии восстанавливаются — `SessionManager.recoverInterruptedSessions()` (отсрочка 60 с), INFO-блок `restart_resumed` и `resumeMessage` в новый процессор; очереди без активного хода автозапускаются, кроме `queueStopped` (`server/app/deps.ts`, `backend/app/deps.ts`). Но:
  - дочерние сессии **явно пропускаются** (`s.sessionOrigin === 'subagent' → continue`, «решение за родителем»);
  - фоновые прогоны переводятся в `orphaned` (`BackgroundRunService.recoverOnStart`) — без попытки возобновления и без уведомления родителю (он узнаёт о незавершённости только из реестра);
  - **бюджета попыток нет**: каждый старт возобновляет ход заново — серия падений даёт цикл «рестарт → возобновление → падение» с расходом LLM.

## Проблема

1. **Агент не может управлять своим сабагентом на ходу.** Единственный способ — человек или внешний клиент через HTTP/шлюз; из тулов доступны только «создать», «продолжить свободного» и «остановить».
2. **Продолжение — не «новое указание», а «продолжай как было».** Модель-родитель не может уточнить задачу после остановки/успешного завершения, хотя параметры для этого уже объявлены в схеме тула.
3. **Неоднозначная доставка в дочернюю сессию.** `steer`, `queue` и «обычный ход сессии» дают три разных поведения в зависимости от того, идёт ли прогон и какой путь вызван; ни одно из них не описано как контракт «сообщение сабагенту».
4. **Рестарт теряет работу сабагентов.** Дочерние ходы не возобновляются, фоновые прогоны становятся `orphaned`, родитель не получает уведомления; в длинных многошаговых задачах это потеря уже оплаченной работы.
5. **Нет предохранителя восстановления.** Автопродолжение после рестарта не ограничено по числу попыток, а решение «восстанавливать или нет» не видно в конфигурации.

## Предложение (гипотеза)

### 1. Доставка сообщения в сессию сабагента — часть контракта тула `task`

`task({ task_id, prompt, delivery?: 'steer' | 'queue', background?: boolean })` — два ортогональных параметра: `delivery` отвечает на «как доставить в идущий прогон», `background` — на «ждать ли результата».

| Состояние ребёнка | `background` не задан | `background: true` |
|---|---|---|
| свободен | синхронное продолжение в текущем ходе родителя (`<task_result>`), как сейчас | фоновый прогон продолжения: запись в реестре, `{status:'running'}`, итог — уведомлением |
| занят фоновым/отделённым прогоном | `delivery` (см. ниже): `steer` (default) / `queue`; тул сразу возвращает `{status}` | то же; `background` не нужен (доставка и так не блокирует) и игнорируется |

- **`delivery` имеет смысл только для фонового (detached) прогона.** Блокирующий ребёнок исполняется внутри вызова тула — родитель в этот момент не работает и отправлять ему нечего, поэтому «занят» на практике = идёт фоновый/отделённый прогон (или resume-прогон из UI).
- **`steer` (default)** → `enqueueSteerMessage` в `steerInbox` ребёнка, применение на границе шага его цикла (механика ADR-104 уже реализована); лимит инъекций и `steer.dropped` — как у основной сессии.
- **`queue`** → `pendingMessages` ребёнка; после текущего прогона дочерняя сессия **сама** делает один проход продолжения (дренаж очереди в финализации `run-cycle`), потому что у ребёнка нет кнопки «возобновить очередь»: молча оставленное сообщение — это зависший ввод. Страховка — бюджет проходов на прогон (один проход на пачку, без накопления) и `background.maxRunsPerSession`.
- Тул **не блокирует** ход родителя при доставке в занятого ребёнка: возвращает `{ status: 'steered' | 'queued', child_session_id, pending_count }`; итог работы ребёнка приходит обычным уведомлением (ADR-111 п. 3). Блокирующее присоединение к идущему прогону в этой итерации не поддерживается.
- Ограничения: только **свой** ребёнок (`parentId`), только режим `subagent` у его агента. Права — по граничному guard'у `:id`-маршрутов (инвариант 16, ADR-089): владелец сессии, участник проекта с правом изменения (`OWNER`/`EDITOR`), `LEAD`, `ADMIN`; `VIEWER` — 403. Саб-агенту `task` по-прежнему `deny` (см. «Границы»).

Тот же контракт на HTTP: `POST /api/v2/sessions/:id/prompt` для дочерней сессии получает **явную** семантику вместо скрытой третьей: `queue`/`steer` доставляются через цикл саб-агента (у idle — старт прогона продолжения), а не через `QueueProcessor` обычной сессии. Ответ — существующий `202 {messageId, mode, position}`.

### 2. Продолжение передаёт новые указания и может сменить модель/провайдера

- `prompt` обязателен только для новой задачи; при `task_id` — опционален. Если задан — в историю ребёнка пишется **обычное user-сообщение** (`metadata.continuation: true`, `stream_id`), а не только маркер. Маркер `task.resume_marker` остаётся лишь для путей без текста (HTTP-resume, автовосстановление).
- `model`/`provider` при `task_id` — переключение пары в `child.settings` с проверкой каталога (тот же резолвер, что у создания). Не заданы — остаются текущие.
- `subagent_type` при `task_id` **не переключает агента**: история, системный промпт, права и лимиты ребёнка принадлежат одному агенту, смешение системных промптов в одной истории — источник необъяснимых ошибок. Для continuation параметр становится необязательным; если задан и **не совпадает** с текущим агентом ребёнка — ошибка с объяснением (тихое игнорирование недопустимо), совпадает — принимается. Другой агент — только новым `task` (новый ребёнок).
- HTTP `POST /api/v2/sessions/:id/resume-subagent` получает необязательное тело `{prompt?, model?, provider?}`; реализация — та же (`resume-target.ts` + `runSubagentResume`), без второго свода правил.

### 3. Автовосстановление прерванных ходов после рестарта

База уже есть: durable-маркер хода (`currentStream.owner`), `recoverInterruptedSessions`, INFO-блок `restart_resumed`, механика `resumeMessage`. Добавляется:

1. **Сабагенты.** Убрать исключение `sessionOrigin === 'subagent'`. Восстановление дочерней сессии идёт **не** через `QueueProcessor`, а по resume-пути саб-агента (`runSubagentResume`): маркер продолжения, цикл ребёнка, итог в родителя (`subagent_resumed_result`). Если родителя нет или он архивный — терминализация + запись в реестре (уведомлять некого), без «осиротевшего» хода.
2. **Фоновые прогоны — по виду работы.** `subagent` → попытка возобновления дочерней сессии и продолжение **той же** записи реестра (`status: running`, `metadata.resumed_from`, счётчик попыток); `process` → возобновить нельзя (процесс мёртв вместе с исполнителем) → терминальный `orphaned` + **гарантированное** USER-сообщение владельцу в контекст (`metadata.type = 'background_run_lost'`) и обновление записи реестра (`summary`) вместо молчаливой пометки.
3. **Бюджет попыток и crash-loop.** Durable счётчик на **ход** (инкремент на каждый авто-резюм, сброс терминальным статусом) плюс детект crash-loop по меткам попыток: N рестартов за M минут. Превышение любого условия → терминализация (`failed`/`orphaned`), USER-сообщение владельцу («восстановление прекращено: …») и обновление записи реестра. Конфигурация: `recovery.autoResume` (default `true`), `recovery.maxAttempts` (default `3`), `recovery.crashLoop.windowMinutes` (default `10`), `recovery.crashLoop.maxRestarts` (default `3`); env — `SYNTH_RECOVERY_*`.
4. **Одиночный владелец.** Автовосстановление включается только когда инстанс уверен, что он единственный владелец данных. При нескольких репликах нужен claim/lease (это предмет [PROP-105](./prop-105-multi-replica-coordination.md)); до него — `fail-closed`: авто-резюм выключен, поведение деградирует до сегодняшнего (`orphaned` + снятие маркеров).
5. **Контракт побочных эффектов.** Восстановление возобновляет **ход**, но не откатывает уже выполненные инструменты: они могут выполниться повторно (at-least-once). Это тот же контракт, что уже зафиксирован для рестарта (ADR-092 п. 7); он явно попадает в документацию восстановления.
6. **Наблюдаемость.** Существующие события `subagent.resume.started|finished` переиспользуются; добавляются `execution.recovered` (аддитивно) и счётчик `synth_session_resume_total{kind,outcome}` (имена и лейблы — по контракту ADR-094).
7. **Ручной повтор после терминализации.** `POST /api/v2/sessions/:id/recovery/retry` — write-доступ по граничному guard'у `:id`-маршрутов; сбрасывает счётчик попыток и запускает восстановление (для дочерней сессии — resume-путём саб-агента). Идемпотентно: повтор во время активного хода → `409`; состояния «нет чего восстанавливать» → `200 {status:'nothing_to_resume'}`.

### 4. UI — минимум для паритета

- Вкладка саб-агента: «Продолжить» для **остановленного** прогона (сейчас только для recoverable-ошибки провайдера) и явный индикатор «прерван рестартом».
- Композер дочерней сессии становится активным **без нового переключателя режима**: пока прогон идёт — отправка `steer`, иначе — `queue` (сообщение начнёт ход). Это не переоткрывает решение ADR-104 об удалении `SteerModeSwitch`, а выводит режим из состояния.
- «Процессы»: восстановленный прогон показывается со статусом «возобновлён»; потерянный — с причиной (`interrupted by restart`) и ссылкой на уведомление.
- Карточка саб-агента и «Процессы»: кнопка «Повторить восстановление» после терминализации по бюджету — сбрасывает счётчик (через `POST /sessions/:id/recovery/retry`) и запускает восстановление.

## Границы (что сознательно не входит)

- **Вложенные сабагенты** — не включаются: `task` у саб-агента остаётся `deny` (`engine/permission/derive.ts`). Поле `agents.subagentDepth` сохраняется как **резерв на будущее**: вложенность выключена правилом `deny`, и документация/UI должны это прямо говорить («резерв; вложенность отключена»), а не обещать «при лимите 1 саб-агент может запустить саб-агента». Включение — отдельным решением: тогда снимается `deny`, появляется тест на глубину и проверка `question`/`task` в промпте ребёнка.
- **Вопрос пользователю от сабагента** — остаётся `deny`: ребёнок возвращает вопрос в итоге, а не открывает интерактивное ожидание.
- **Присоединение к идущему прогону** (blocking join: «дождаться результата уже идущего сабагента из тула») — не входит: требуется waiter-реестр у фоновых прогонов; сегодня результат приходит уведомлением.
- **Откат эффектов инструментов** при восстановлении — не входит.
- **Мультиреплика** — не входит (см. п. 3.4).
- **Фоновые процессы после рестарта** — не возобновляются (только честное уведомление); LLM-циклы возобновляются.

## Принятые решения по открытым вопросам (2026-11-18)

| # | Вопрос | Решение |
|---|---|---|
| 1 | `delivery: 'queue'` для занятого ребёнка | **Авто-продолжение после прогона**: сообщение ждёт в `pendingMessages` и запускает ровно один проход продолжения; страховка — бюджет проходов на прогон и `background.maxRunsPerSession` |
| 2 | Что можно менять при продолжении | **Только модель и провайдер.** Агент фиксируется при создании ребёнка; `subagent_type` при `task_id` необязателен и при несовпадении даёт ошибку |
| 3 | Бюджет восстановления | **Попытки на ход + детект crash-loop** (N рестартов за M минут); `recovery.maxAttempts`, `recovery.crashLoop.*` |
| 4 | Невосстановимый прогон | **USER-сообщение в контекст владельца + обновление записи реестра** — видят и модель, и UI |
| 5 | Права доставки | **Как у прочих `:id`-маршрутов**: владелец, `OWNER`/`EDITOR` проекта, `LEAD`, `ADMIN`; `VIEWER` — 403; из тула — только свой ребёнок |
| 6 | Ручной триггер | **Нужен**: кнопка в карточке/«Процессах» + `POST /api/v2/sessions/:id/recovery/retry` (write-права, сбрасывает счётчик) |
| 7 | `agents.subagentDepth` при `task: deny` | **Резерв на будущее**: поле и проверка глубины остаются, документация и UI прямо говорят, что вложенность отключена правилом; включение — отдельным решением |
| 8 | Матрица `delivery`/`background` | **Два ортогональных параметра**: `delivery` (`steer` default / `queue`) — только для фонового/отделённого прогона, `background: true` — «продолжить и не ждать» для свободного ребёнка (сегодня флаг при `task_id` молча игнорируется) |

### Остаточные технические вопросы (решаются на реализации, блокирующими не являются)

1. Бюджет проходов продолжения: предлагается 1 проход на пачку очереди без накопления; нужен ли счётчик на прогон — по итогам нагрузочных тестов.
2. Идемпотентность USER-уведомлений о потере прогона при повторных рестартах: дедуп по `background_run_id` (повторная доставка не должна давать второе сообщение).
3. Форма ключей `recovery.*` в runtime-настройках UI: live-применение или `restartRequired` (по умолчанию — `restartRequired`, как у остальных process-глобальных настроек).

## Альтернативы (отклонены предварительно)

- **Оставить ручной resume** — не решает ни управление на ходу, ни потерю работы при рестарте.
- **Отдельный тул `subagent_message`** — лишняя сущность: `task({task_id})` уже означает «продолжение», доставка — его параметр.
- **Новый канал/очередь для сообщений сабагенту** — противоречит ADR-104/ADR-118: `steerInbox` и `pendingMessages` уже есть, новых каналов не заводим.
- **Смена агента при продолжении** — отклонено: история, системный промпт и права ребёнка должны принадлежать одному агенту; другой агент — только новым `task` (новый ребёнок).
- **Блокирующий join к идущему прогону** — нужен реестр ожидающих; отложено (возвращает «эффект свободной руки» и блокировку родителя).
- **Восстановление «переигрыванием журнала» всего дерева прогонов** — избыточно: durable-маркер хода + реестр фоновых прогонов дают тот же результат дешевле.
