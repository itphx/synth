# PROP-125: Серверные MCP-серверы в локальных сессиях гибрида — режимы relay и tools

> **Статус:** 🧩 Предложение
> **Дата:** 2026-11-06
> **Решение до:** 2026-12-06
> **Связано:** [ADR-042](./adr-042-hybrid-mode.md), [ADR-043](./adr-043-unified-identity-login.md), [ADR-045](./adr-045-hybrid-server-profiles.md), [ADR-052](./adr-052-public-api-platform.md), [ADR-071](./adr-071-mcp-servers-prompt.md), [ADR-077](./adr-077-runtime-toolchain.md), [ADR-099](./adr-099-egress-tls-trust.md), [ADR-105](./adr-105-external-credentials.md), [ADR-115](./adr-115-multimodal-input.md)

## Контекст (что есть сейчас)

**Локальные сессии в гибриде исполняет локальный core, но MCP-серверы он видит только свои.**
`McpManager` получает `config.mcpServers` локального инстанса
(`packages/core/src/server/app/deps.ts:468-469`, `mcpManager.setConfig(config.mcpServers ?? {})`)
и больше ничего: серверный реестр MCP локальному core недоступен — `/api/v2/mcp` **не** входит
в `REMOTE_PROXY_PREFIXES` (`packages/core/src/server/proxy.ts:28-41`), а реестр живёт только
в backend (`packages/backend/src/routes/mcp-registry.ts`, монтаж — `backend/src/app/mount-routes.ts:955`).
Итог: локальная сессия в гибриде не видит ни одного MCP-сервера, настроенного на сервере, хотя
LLM для неё уже централизован через серверный прокси (`docs/HYBRID.md` §3). Панельные `:id`-маршруты
сессии в гибриде уже origin-aware (`docs/HYBRID.md` §2.1), но локальная сессия остаётся локальной —
слепой прокси `/api/v2/mcp` тут не помогает: у локального мира просто нет серверного реестра.

**Удалённые (`remote:`) сессии** исполняются на сервере и видят серверные MCP-серверы; их скоуп —
трёхуровневый: системный мастер `enabled` → проектный hard-gate `project.mcp.enabled` →
сессионный снимок/opt-out (`mcpDefaultOn`/`mcpDisabledServers`), см.
`packages/core/src/engine/mcp/scope.ts:63-111` и материализацию снимка в
`packages/core/src/sessions/manager.ts:267-298`.

**Готовый шов «MCP живёт не в этом процессе» уже есть** — executor B2 (ADR-077):

- `ExecutorMcpSource` (discovery: TTL 120 с, retry 15 с) и `ExecutorMcpClient implements McpClientLike`
  (`packages/core/src/engine/mcp/executor-mcp-source.ts`, `executor-mcp-client.ts`);
- `McpClientLike` — единственная точка замены транспорта (`engine/mcp/client.ts:94-107`):
  `connect/tools/callTool/isConnected/name/instructions`;
- runtime-записи в `McpManager` — не персистятся, не редактируются, коллизия имён решается
  в пользу локального сервера (`manager.ts:87-200`);
- контракт исполнителя: `GET /mcp/servers`, `GET /mcp/tools`, `POST /mcp/call` →
  `{content, isError, attachments?}` (протокол 5, base64-вложения; `docs/EXECUTION.md:341-344`).

**Секреты серверных коннекторов не переносимы на клиент.** `auth.kind='credential'` — это id записи
`ExternalCredentialStore` сервера; plaintext-заголовки запрещены (`MCP_SECRET_HEADER_FORBIDDEN`).
Приватные адреса K3s/CA/mTLS/прокси из локальной сети недостижимы (ADR-099). Прямой egress
локального core к MCP-URL — новый SSRF-вектор с машины пользователя.

**stdio в managed разрешён** ровно как «серверная зона»: создание — только ADMIN (installer-scope
`addons:install` проверку stdio **не** ослабляет), исполняется на хосте backend, сетевая политика
(ADR-071 §2.3.1) к stdio не применяется (`packages/backend/src/routes/mcp-registry.ts`,
`checkNetwork`).

## Решения владельца (основа предложения)

| № | Вопрос | Решение |
|---|---|---|
| 1 | Включённость серверных MCP в локальных сессиях | **Точно такая же, как в удалённых**: system `enabled` → `project.mcp.enabled` → сессионный снимок `mcpDefaultOn`/`mcpDisabledServers`; сид новых проектов — из `enabledByDefault`. Никаких исключений «system-level в обход проекта» (в отличие от executor-серверов) |
| 2 | stdio-серверы | **Разрешены** как в managed: создаёт только ADMIN, исполняются на сервере, сетевая политика к ним не применяется. Для локальных сессий новых ограничений нет |
| 3 | Скоуп | **Как в удалённых сессиях** (п. 1), без особой модели для локального мира |
| 4 | Недоступность backend/сервера | **Показывать ошибку с причиной** (панель и `mcp.status` промпта), а не молча убирать серверы |
| 5 | Аудит/квоты/approval | **Не вводим** — существующих механизмов достаточно |
| 6 | Режимы транспорта | **Нужны оба**: (a) protocol relay — полноценный MCP через backend (streaming, `instructions`, `_meta`, будущие elicitation); (b) tool-level proxy — `servers/tools/call` (простой, надёжный, без стриминга) |
| 7 | Существующие локальные проекты | При первом подключении серверные `enabledByDefault` **добавляются** в `project.mcp` существующих проектов (идемпотентно, маркер `remoteSeeded`), чтобы попасть в новые сессии; сессионные снимки `mcpDefaultOn` не переписываются |
| 8 | Неудачный relay | **Всегда** деградировать в `tools` с причиной в статусе (в т.ч. при явном `remoteMode: 'relay'`), без отказа |
| 9 | Авторизация вызовов | Интерактив — `requireAuth` (Bearer гибрида); service-key — scope `mcp:invoke` (семейство `mcp:*`) |
| 10 | Видимость в UI | **Все** записи реестра (как `GET /registry`): `instance` + `user` любого автора |

## Предлагаемое решение

### 0. Режим на запись реестра

Аддитивное поле `remoteMode?: 'auto' | 'relay' | 'tools'` в записи MCP-реестра, по умолчанию `auto`:

| `remoteMode` | Фактический транспорт локальной сессии |
|---|---|
| `relay` | полноценный MCP-клиент на `/api/v2/mcp/relay/:name` (Streamable HTTP) |
| `tools` | `BackendMcpClient` поверх `/remote/{servers,tools,call}` |
| `auto` | `relay` для `http`/`sse`, `tools` для `stdio` |

Неудачный handshake relay — **всегда деградация в `tools`** (в том числе при явном
`remoteMode: 'relay'`) с причиной в статусе, без падения сервера и без «тихого» исчезновения.
Смена режима — без рестарта (запись реестра), действует на следующем подключении/обновлении состава.

### 1. Контракт backend (backend-only)

Все маршруты — `requireAuth` (интерактивный пользователь гибрида), версия контракта видна в
`GET /api/v2/meta` аддитивным признаком `features.remoteMcp` (сейчас `instanceCapabilities` —
`packages/core/src/server/routes/meta.ts:36-56`). Секреты и URL с креденшелами в ответы/ошибки
не попадают (редактирование — как в `mcp-registry`).

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/v2/mcp/remote/servers` | `[{name, type, origin, trust, enabled, enabledByDefault, status, toolCount, error?, instructions?}]` — без секретов; `enabled` — системный мастер |
| `GET` | `/api/v2/mcp/remote/tools?server=…` | схемы инструментов `{name, description, inputSchema}` + `instructions` сервера |
| `POST` | `/api/v2/mcp/remote/call` | `{server, tool, arguments?, meta?}` → `{content, isError, attachments?}` |
| `GET/POST/DELETE` | `/api/v2/mcp/relay/:name` | MCP Streamable HTTP endpoint релея (см. ниже) |

- **Шейп вызова — тот же, что протокол исполнителя 5** (`docs/EXECUTION.md:341-344`): один формат
  результата на два «MCP вне процесса», а не третий. Таймауты/лимиты — как у `McpManager`:
  connect 60 с, вызов 120 с, текст 30 000 симв., вложения 25 МиБ/файл и 20 МиБ/вызов (ADR-115).
- **relay.** Backend поднимает MCP-сервер (`@modelcontextprotocol/sdk`, серверные транспорты) и
  мостит его к своему MCP-клиенту реального сервера — любого транспорта (http/sse/stdio), —
  ретранслируя `tools/list`, `tools/call`, `notifications/progress` и `instructions`. Нужны маппинг
  сессий relay ↔ MCP-сессий и идемпотентное закрытие по `DELETE`/disconnect. Фабрика релея живёт
  в core (экспорт), монтирует её **только backend** — на локальном инстансе маршрута нет.
- **Авторизация (решение 9).** Интерактивный пользователь — `requireAuth` (Bearer гибрида);
  для service-key — scope `mcp:invoke` (добавить `mcp` в `SERVICE_SCOPE_FAMILIES` и `mcp:invoke`
  в каталог `SERVICE_SCOPES`, `packages/shared/src/types/service-keys.ts:17-60`;
  wildcard-семейство `mcp:*`, глобального `*` по-прежнему нет). Новых approval/квот нет (решение 5).

### 2. Интеграция в локальный core

**Источник состава — `RemoteMcpSource`** (по образцу `ExecutorMcpSource`): discovery с TTL 120 с,
retry 15 с на неудачу, refresh **до** расчёта скоупа в `orchestrator/phases/process-setup.ts`
(рядом с `refreshExecutorServers`), снятие записей на `disconnectRemote`
(`server/app/hybrid-remote.ts`, `applyConnected`/`disconnectRemote`).

**Два клиента — обе ветки одного `McpClientLike`:**

- **relay** — обычный `McpClient` с `StreamableHTTPClientTransport` на `/api/v2/mcp/relay/:name`,
  Bearer гибрида, TLS — существующий egress (ADR-099/инвариант 22, новых агентов не заводим);
- **tools** — `BackendMcpClient implements McpClientLike` (по образцу `ExecutorMcpClient`):
  `servers`/`tools`/`call`, base64-вложения → `McpManager` → `AttachmentService` (тот же путь, что
  у executor, ADR-115).

**`McpManager` — третий вид runtime-записей:** `kind: 'executor' | 'remote'` (вместо одного
`_executorServers`), `origin: 'instance'`, системный мастер — из ответа сервера. Коллизия имён —
локальный сервер выигрывает (как сейчас), remote пропускается с предупреждением. Записи
**не** персистятся и не редактируются пользователем.

**Скоуп — без флага-исключения.** Серверные записи проходят проектный гейт и сессионный слой;
`executor: true` (обход `project.mcp.enabled`, `scope.ts:36-43,77-85`) для них **не** ставится.
`remote`-пометка нужна только UI/статистике (источник), а не резолверу.

**Сид проектов.** `getProjectSeeds` (`server/app/mount-routes.ts:256-267`) объединяет локальные
`enabledByDefault` и серверные `enabledByDefault` из последнего синка. Backend недоступен —
только локальные дефолты (серверные добавляются при следующем успешном коннекте).

**Существующие локальные проекты (решение 7).** При первом успешном подключении (и при появлении
новых серверных дефолтов) серверные `enabledByDefault` объединяются в `project.mcp.enabled` и
`project.mcp.defaultOn` всех существующих локальных проектов — чтобы серверы попали в новые сессии.
Операция **идемпотентна**: в `ProjectMcpSettings` аддитивно хранится `remoteSeeded: string[]` —
имена серверных дефолтов, уже применённых к проекту; повторный коннект **не** возвращает сервер,
который пользователь затем выключил. Изменение публикует `project.updated` (инвариант 27).
Сессионные снимки `mcpDefaultOn` существующих сессий не переписываются (паритет с удалённым миром,
где снимок тоже создаётся при создании сессии).

**Панель проекта.** `knownServers` ответа `GET /projects/:id/mcp` (`server/routes/projects.ts:376-405`)
должен включать серверные имена (сейчас строится из `mcpManager.getConfig()`), иначе тумблеры
проекта не увидят серверные записи; `PUT` валидирует по объединённому списку.

**Оффлайн и ошибки (решение 4).** Серверы **остаются** в выдаче `GET /sessions/:id/mcp` со
`status: 'error'` и `reason` (backend offline / сервер упал / handshake relay). Тулы при этом не
попадают ни в промпт, ни в `ToolRegistry` — заведомо недоступное не предлагаем; после реконнекта
состав восстанавливается. В `mcp.status` промпта — ошибка с причиной, а не пустой список
(слои `mcp.servers`/`mcp.tools`/`mcp.status` — `docs/TOOLS.md`).

### 3. Совместимость

- Старый backend без `features.remoteMcp` — фича выключена **молча** (fail-closed, без шума в UI).
- Контракт версионируется аддитивно, по образцу `protocol` исполнителя; `features.remoteMcp`
  читается как признак, а не как обязательное поле.
- `McpClientLike` расширяется аддитивно (`instructions`/`meta` уже в поверхности; для relay ничего
  не ломаем). `McpServerEffective` получает аддитивное `source`.
- Старые локальные проекты получают серверные дефолты при первом успешном коннекте (идемпотентно,
  маркер `remoteSeeded` — §2); сессионные снимки существующих сессий не меняются.

### 4. UI

- `McpServerEffective` (`packages/shared/src/types/mcp.ts:196-222`) — аддитивное
  `source: 'local' | 'server'` (в дополнение к `origin`).
- «Проект» — группировка/бейдж «серверный» в списке известных серверов; «Сессия» — статус и
  причина ошибки; «Статистика» — колонка источника (если таблица MCP есть). Доступный список
  серверных записей — **все** записи реестра (`instance` + `user` любого автора), как `GET /registry`
  (решение 10); фильтрации по автору в UI нет.
- Новых настроек в UI нет: режим задаётся в реестре MCP (админ-раздел/API backend).

### 5. Безопасность

- Локальный core **не ходит к upstream MCP** и **не видит секретов**; сеть/TLS/SSRF/политика —
  на сервере (ADR-099, ADR-071 §2.3.1). Идентичность — Bearer гибрида (ADR-043).
- Инвариант 3 (LLM через `GatewayProvider`) не затрагивается: MCP — не LLM.
- Аудит вызовов остаётся существующим (`scope:'mcp'` в egress-журнале), новых квот и approval нет
  (решение 5).

### 6. Тесты (план)

- Контрактный шейп `servers`/`tools`/`call` — по образцу `executor-mcp-client.test.ts`.
- relay: установление сессии, стриминг/progress, идемпотентное закрытие по `DELETE`/disconnect.
- Коллизии имён: локальный сервер выигрывает, remote пропускается с предупреждением.
- Скоуп-паритет с удалёнными сессиями: project gate, сессионный opt-out, `enabledByDefault`;
  отдельный тест, что remote-записи **не** получают executor-обход проекта.
- Авто-сид существующих проектов: первый коннект добавляет серверные дефолты в `project.mcp`,
  повторный — идемпотентен, выключенный пользователем сервер не возвращается (`remoteSeeded`);
  публикуется `project.updated`, сессионные снимки не меняются.
- Оффлайн: `status:'error'` + `reason`, тулы отсутствуют в промпте и `ToolRegistry`, восстановление.
- Матрица авторизации новых `:name`-маршрутов (инвариант 17) — негативная и положительная.
- Отсутствие секретов и URL с креденшелами в текстах ошибок.

### 7. Этапы и объём

| Этап | Содержание | Оценка |
|---|---|---|
| 1 | Контракт backend + `tools`-режим (backend + core: source/client/manager/scope/seeds; `remoteSeeded` в `ProjectMcpSettings` — shared) | 2–4 дня |
| 2 | `relay`: серверный MCP + мост, `remoteMode`, деградация `relay → tools` | 2 дня |
| 3 | UI (бейджи/статусы/источник) + документация (HYBRID/API_V2/EXECUTION/TOOLS) | 1 день UI + 0.5–1 день доки |

Ориентир, не обязательство: 4–6 дней core+backend, 1 день UI, 0.5–1 день доки.

## Альтернативы

| Вариант | Вердикт и обоснование |
|---|---|
| **A. Синхронизация конфигурации серверных MCP в локальный core** | Секреты (`credentialId` живёт на сервере) не переносятся; SSRF с клиента; недостижимые приватные адреса/CA/mTLS/прокси; устаревший конфиг и необходимость опроса реестра |
| **D. Прямое подключение локального core к MCP-URL с выдачей токенов** | Утечка секретов на клиент (ADR-105, инвариант 13); SSRF с ноутбука; невоспроизводимая сеть. Отклонён |
| **B. Relay протокола** | **Принят** (решение 6а) — полноценный MCP, streaming/`instructions`/`_meta`/будущие elicitation; дороже |
| **C. Tool-level proxy** | **Принят** (решение 6б) — простой, надёжный, без стриминга; контракт уже есть (протокол исполнителя 5) |

**Когда какой.** По умолчанию `auto`: `relay` для `http`/`sse` (нужны стриминг и полная семантика),
`tools` для `stdio` (транспорт не потоковый для клиента по конструкции). Если relay не поднялся —
деградация в `tools`, а не отказ.

**Что осознанно не делаем:** не синхронизируем конфиг/секреты на клиент, не вводим прямой egress
локального core к MCP, не добавляем новых approval/квот, не заводим отдельный UI-переключатель
режима (он в реестре).

## Последствия и риски

**Плюсы:** паритет локальных и удалённых сессий по MCP; секреты и сеть не покидают сервер; один путь
вызова/регистрации тулов (`McpClientLike` + `McpManager`), без второго permission-контура.

**Риски:**

- relay сложнее, чем tools: SSE/таймауты/отмена, маппинг сессий и корректное закрытие;
- двойной хоп задержки (клиент → backend → MCP), особенно заметен на relay;
- в `tools`-режиме нет streaming/progress/elicitation — деградация по конструкции;
- при офлайне список серверов устаревает (последний снимок), тулы недоступны до реконнекта;
- коллизии имён между локальным и серверным реестром (решается приоритетом локального, но требует
  явного предупреждения, чтобы не терять серверные тулы молча).
