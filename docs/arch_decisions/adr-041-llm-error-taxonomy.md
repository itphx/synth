# ADR-041: Единая таксономия ошибок LLM + контракт локализации строк движка

> **Статус:** ✅ Реализовано
> **Источник:** перенесено из AGENTS.md
> **Дополнение (2026-11-19):** класс `empty_completion` (пустой completion провайдера) и правило «повторы считает цикл саб-агента, провайдер только сигнализирует» — см. раздел «Пустой финальный ответ модели» ниже. **Обрезанный ответ** (`finish_reason: length`) — не ошибка провайдера, а исход шага `output_limit` с продолжением — см. раздел «Обрезанный ответ — не ошибка провайдера» ниже.

**Решение:** (1) классификация/«recoverable» ошибок LLM-провайдеров — одна точка истины в `packages/core/src/engine/llm-error.ts`, используемая и основной сессией, и саб-агентом; (2) локализованные строки движка — по месту потребления, с контрактом ключей в `@itphx/synth-shared` и автопроверкой синхронизации core↔ui.

**Контекст:** классификация ошибок была реализована в трёх местах (`llm-error.ts`, `orchestrator._isRecoverable`, `processor._isRecoverable`) с расходящимися списками — одна и та же ошибка получала разные вердикты «можно ретраить» в основной сессии и в саб-агенте. Локализация движковых системных сообщений не имела автопроверки: изменение en-шаблона (ключ/параметр) молча рассинхронизировало ru-словарь UI.

**(1) Таксономия ошибок.** `classifyLlmError` + `isLlmErrorRecoverable(error, errMsg?, errorType?)` — единый источник. Приоритеты: `ContextLengthExceededError` (по классу, а не по тексту) → unrecoverable; переданный `errorType` из `UNRECOVERABLE_TYPES` → unrecoverable; иначе по объединённому `UNRECOVERABLE_PATTERNS`. `orchestrator._handleLlmFailure` и `processor._isRecoverable` делегируют сюда; инлайновые списки удалены. Политика ретрая (3 попытки, задержки 5/15/30с) вынесена в константы `LLM_MAX_ATTEMPTS`/`LLM_RETRY_DELAYS_MS` — единые для основной сессии и саб-агента (`task.ts` — реэкспорт-алиасы, внешние импорты не сломаны).

**(2) Локализация.** Схема «LLM = один язык / UI = локализация» сохранена. Хранение по месту потребления:
- **en-шаблоны** (LLM-канал, источник истины) — `packages/core/src/engine/system-messages.ts` (текст в core, не перемещён).
- **ru-переводы** (потребитель — UI; движок их сам не эмитит) — `packages/ui/src/lib/i18n/messages/ru.ts` (как было).
- **контракт** — `packages/shared/src/i18n/index.ts`: `ENGINE_MESSAGE_KEYS` (201 ключ, `as const`), `ENGINE_MESSAGE_PARAMS` (канонические `{param}`-имена на ключ), `extractParams`, тип `EngineMessageKey`; реэкспорт `MessageI18n`.
- **промпты-файлы** (роли/режимы/саб-агенты, LLM-facing, большие markdown) — остаются `.md`-локализуемыми в `core/prompts/` (отдельная механика серверного резолва по языку; осознанно не объединяется со словарём).

**Автопроверка синхронизации (устраняет рассинхрон core↔ui):**
- core `system-messages.ts` типизирован `as const satisfies Record<SystemMessageKey, string>` → TS не допускает «осиротевших»/«лишних» ключей; `SystemMessageKey = EngineMessageKey`.
- тест core: ключи `SYSTEM_MESSAGES` set-равны `ENGINE_MESSAGE_KEYS`; `extractParams(en)` ≡ `ENGINE_MESSAGE_PARAMS[key]`.
- тест ui: каждый `ENGINE_MESSAGE_KEYS` присутствует в `ru.ts` и `extractParams(ru)` ≡ `ENGINE_MESSAGE_PARAMS[key]`; en-локаль может не содержать движковые ключи (деградация на en-`content`).

**Расширение локалей (целевое).** Механизм добавления новых локалей — **контент-пак** `packType: i18n`
(единый манифест `synth.pack`, [PROP-068](./prop-068-skills-agents-registry.md)); сейчас en-шаблоны живут в core,
ru-переводы — в ui, механизма пакетов локалей нет.

**Переопределяет/заменяет:** ничего из прежних AD не отменяет. **Расширяет:** ADR-036 (gateway) — общая точка классификации ошибок; ADR-039/ADR-040 — i18n движковых сообщений.

**Почему не переносим весь каталог в shared:** ru-переводы потребляет только UI, en-шаблоны — только движок; перенос текста заставил бы переписывать словарную загрузку UI и размыл бы границы пакетов. В shared — только контракт (словник как контракт/тип/утилита), что соответствует роли пакета «контракты, без логики».

## Пустой финальный ответ модели — класс `empty_completion` (2026-11-19)

Дополнение к п. (1) «Таксономия ошибок»: у провайдеров появился класс
**пустого ответа** — стрим закрылся корректно (`finish_reason` пришёл), но не
принёс ни текста, ни вызовов инструментов, ни reasoning. Раньше такой ответ
выглядел успехом: ретрай не срабатывал, вызывающая сторона получала пустой финал
без диагностики, а саб-агент превращал его в плейсхолдер `task.empty_response`
со статусом `completed`.

1. **Провайдер только сигнализирует.** `OpenAIProvider` (и путь совместимости)
   бросает `ProviderError` с текстом `empty_completion`, когда ответ пуст по
   всем трём каналам (текст, `tool_calls`, reasoning с `reasoning_tokens`).
   Ответ только с `tool_calls`, только с reasoning-блоками или с расходом
   `reasoning_tokens` **пустым не считается** — это легитимные ответы (бюджет
   ушёл в размышления; диагностика — на уровне цикла, как у
   `session.output_limit`).
2. **Повторы считает цикл, а не провайдер.** `classifyLlmError` даёт тип
   `empty_completion`, `isLlmErrorRecoverable` — `true`; при этом
   retry-цикл саб-агента (`engine/tools/task/run-cycle.ts`) для этого типа
   **не тратит** провайдерную попытку (иначе один и тот же класс повторялся бы
   3×3 раза). Попытки пустого финала считает сам цикл — свой счётчик
   `SUBAGENT_EMPTY_RESPONSE_MAX_ATTEMPTS` (= `LLM_MAX_ATTEMPTS`).
3. **Повтор — с диагностикой.** Перед повтором в историю ребёнка кладётся
   служебное сообщение `metadata.type='empty_response_notice'`
   (`role:'user'`, автор `System`, ключи `task.empty_retry_empty` /
   `task.empty_retry_truncated`): причина (`max_tokens` или молчание модели),
   фактический расход и что именно изменить (сократить вывод, разбить работу
   на части, читать файлы частями). Свой ход оно не открывает
   (`sessions/user-messages.ts`), в результат родителя не попадает.
4. **Исчерпание попыток — провал, а не успех.** Финальное
   assistant-сообщение ребёнка получает статус `error`, в историю пишется
   durable-причина остановки `empty`
   ([PROP-143](./prop-143-stop-reason-history.md)), родителю уходит `<status>error</status>` + `isError: true`.
   `max_tokens`/`length` различаются текстом: `task.output_limit` (лимит вывода,
   `limit`/`reasoning`) против `task.empty_response`.
5. **Повтор не расходует шаг агента.** `iteration` не растёт (`stepIndex` — тот
   же), как у сжатия на границе шага (ADR-128); успешный повтор оставляет в
   метаданных результата `empty_retries` и причину последней пустой попытки.

## Обрезанный ответ — не ошибка провайдера, а исход шага `output_limit` (2026-11-19)

Раньше `finish_reason: length` (`max_tokens`) обрабатывался как «объяснение постфактум»:
ответ считался финальным, а модель/пользователь получали текст `session.output_limit`. Это
смешивало два разных класса: «провайдер не ответил» (ошибка, ретрай) и «ответ не уложился в
бюджет вывода» (не ошибка — работа не закончена).

1. **Разделение классов.** `empty_completion` — провайдер вернул ноль содержимого, лечится
   **ретраем** (см. выше). `output_limit` — контент есть, но он срезан лимитом вывода, лечится
   **продолжением**: ход не финализируется, в историю и в следующий вызов кладётся сервисное
   сообщение `metadata.type='output_limit_notice'`, срезанный фрагмент сохраняется как
   assistant-сообщение (`status: 'limit'`, `output_limit_attempt: N`). В цикле саб-агента
   фрагмент возвращается в контекст как assistant-префикс — иначе модель пишет ответ заново и
   упирается в тот же лимит.
2. **Текст инструкции — системный контекстный файл.** `prompts/system/OUTPUT_LIMIT.{lang}.md`
   (раздел «Контекст → Системные», плейсхолдеры `{attempt}/{max}/{limit}/{reasoning}`), а не
   i18n-ключ: прецедент — шаблон `ATTACHMENTS_DROPPED` (ADR-115). Это шаблон сообщения модели,
   а не постоянный блок промпта; геттер — `ContextFileRepository.getOutputLimitNotice`,
   правка без пересборки кода.
3. **Предел продолжений.** `MAX_OUTPUT_LIMIT_CONTINUATIONS = 2` (`MAX_OUTPUT_LIMIT_STREAK = 3`
   подряд обрезанных ответов) — паритет с opencode, где три подряд `finish: length` дают
   `StepFailedError`. Дальше — исход `output_limit`: `session.output_limit_exhausted`, статус
   сообщения `limit`, durable-запись `reason: 'output_limit'` (PROP-143); в сабагенте —
   `isError: true` и `<partial_output>` (собранный текст не теряется).
4. **Лимит вывода — политика, а не константа.** Дефолт `llm.maxTokens` поднят до 32768
   (паритет с opencode `OUTPUT_TOKEN_FALLBACK`), плюс адаптивное ужатие под остаток окна
   (`min(base, max(1024, window·(1−headroom) − вход))`, потолок 256000, `headroom` 1% / 0 для
   компактизации) — `engine/orchestrator/max-output.ts`. Причина исходного инцидента — 8192
   вывода при окне 1 000 000 и reasoning-модели: весь бюджет уходил в размышления.
5. **Обрезанный tool-call** — свой класс `tool.input_incomplete`: аргументы не разобраны из-за
   лимита → вызов не исполняется, модели возвращается «разбей payload на меньшие вызовы и
   повтори с полными аргументами» (а не ошибка схемы аргументов).
6. **Стоимость шага.** Продолжение (как и ретрай пустого ответа) не расходует шаг агента:
   лимит считает отдельный счётчик, `stepIndex` при этом растёт — индекс шага должен оставаться
   уникальным для адресации в UI.
