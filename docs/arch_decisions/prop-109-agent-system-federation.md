# PROP-109: Централизация внешних агентных систем (федерация)

> **Статус:** 🧩 Предложение — внешняя агентная система как управляемый peer: реестр, права, маршрутизация задач, единый журнал
> **Решение до:** 2027-01-31
> **Дата:** 2026-10-24
> **Источник:** 2026-10-24 (обсуждение приоритетов: «управление разрозненными агентными системами, которые уже
> есть у заказчика; цель та же — централизация»)
> **Связано:** [ADR-052](./adr-052-public-api-platform.md), [ADR-087](./adr-087-gateways.md),
> [ADR-089](./adr-089-external-events-automation.md), [ADR-099](./adr-099-egress-tls-trust.md),
> [ADR-105](./adr-105-external-credentials.md), [ADR-106](./adr-106-authority-layer.md),
> [PROP-050](./prop-050-external-engines-runner.md), [PROP-055](./prop-055-instance-exchange.md),
> [PROP-056](./prop-056-synth-mcp-server.md).

**Решение:** ввести класс «внешняя агентная система» (`AgentSystem`) — зарегистрированный **peer**, которым
Synth управляет из одной точки: знает его возможности, вызывает по задаче, получает результат и события,
применяет к вызову свои полномочия и ведёт общий журнал. Внутреннее устройство peer'а нам неизвестно и не
копируется: интеграция идёт по контракту, а не по нашей архитектуре.

Мотив — не «запустить наш движок у заказчика», а обратное: у заказчика уже есть работающие агентные системы
(ассистенты, боты, автоматизации, самописные оркестраторы), и централизация означает **единую точку входа,
прав, наблюдаемости и маршрутизации задач** поверх них, а не их замену.

## Что это не (границы класса)

Класс легко перепутать с четырьмя соседними механизмами; различие фиксируется здесь, чтобы реализация не
расползлась:

| Механизм | Направление | Чем отличается |
|---|---|---|
| Шлюз ([ADR-087](./adr-087-gateways.md), [ADR-103](./adr-103-gateway-core-channel-contract.md)) | человек ↔ Synth | канал к **человеку** в мессенджере; peer'ом не является и задач не исполняет |
| Runner ([PROP-050](./prop-050-external-engines-runner.md)) | Synth → чужой движок | исполняет **наш ход** внутри нашего цикла; это один из видов подключения peer'а, а не весь класс |
| Обмен инстансами ([PROP-055](./prop-055-instance-exchange.md)) | Synth ↔ Synth | частный случай федерации: peer — такой же инстанс Synth с известным контрактом |
| MCP-сервер Synth ([PROP-056](./prop-056-synth-mcp-server.md)) | внешний агент → Synth | обратное направление: мы отдаём свои возможности наружу |

Отсюда следствие: **PROP-050 переводится в `🧊 Icebox`** и пересматривается как `kind: runner-engine` внутри
этого предложения — отдельного решения о «Runner как продукте» не требуется.

## Модель

### Сущность `AgentSystem`

Минимальный набор полей (уточняется при принятии):

| Поле | Смысл |
|---|---|
| `id`, `name`, `kind` | идентификатор и способ подключения: `remote-http` (свой API), `remote-mcp` (MCP-клиент), `event-source` (система сама присылает события), `runner-engine` (opencode/cline как движок) |
| `endpoint`, `tlsProfile` | адрес и профиль доверия — только через egress-слой ([ADR-099](./adr-099-egress-tls-trust.md)), без собственных HTTP-агентов |
| `auth` | как мы аутентифицируемся в peer'е: статический секрет, OAuth-коннектор ([ADR-105](./adr-105-external-credentials.md)), mTLS |
| `capabilities` | что peer умеет: виды задач, инструменты, ограничения (длительность, объём, стоимость) |
| `health` | состояние и последняя успешная связь (для UI и метрик) |
| `scope` | в каких проектах/сессиях система доступна (проекция, как `allowedProjects` у service-key, [ADR-052](./adr-052-public-api-platform.md)) |
| `owner` | кто отвечает за регистрацию и секреты |

### Права

Вызов внешней системы — **действие** в смысле authority-слоя ([ADR-106](./adr-106-authority-layer.md)) с
целью `agent-system:<id>`; нет гранта — нет вызова. Правила:

- полномочия вызывающего (пользователя или агента) не расширяются тем, что задача ушла наружу;
- ответ peer'а — **данные, а не инструкции**: он не получает наш тул-сет по умолчанию и не может через ответ
  инициировать действия от нашего имени (иначе централизация превращается в обход permission-слоя);
- идентичность внешнего пользователя маппится на principal по правилам [ADR-089](./adr-089-external-events-automation.md)
  (`resolveEffectiveRoles`), роли только сужаются;
- каждый вызов и его результат — в журнале (аудит), включая отказ по правам.

### Вызов и стрим

Задача формулируется в терминах сессии: пользователь (или пайплайн) ставит задачу, маршрутизатор выбирает
систему по `capabilities` и `scope`, вызов уходит наружу, ответ и промежуточные события возвращаются в сессию
как сообщения/ход. Требования:

- стрим ответа — через существующий транспорт ([ADR-024](./adr-024-eventhub-transport.md)), новых каналов не
  заводим; внешний протокол стрима адаптируется на границе;
- идемпотентность: повторный вызов по тому же `turn` не должен дублировать работу peer'а (ключ идемпотентности
  в запросе);
- таймауты и отмена: отмена хода в Synth должна доноситься до peer'а, иначе получаем «работу-призрак»;
- деградация: недоступный peer — это ошибка хода с внятной причиной, а не тихий фоллбек на локальный движок.

### Журнал и наблюдаемость

Единый журнал вызовов (кто, какая система, какая задача, результат, длительность, стоимость) + метрики
`synth_agent_system_*` (вызовы, ошибки, длительность) в контракте [ADR-094](./adr-094-observability-metrics.md).
Без этого «централизация» недоказуема: заказчику нужен один экран, а не пять.

## Этапы

| Этап | Содержание | Критерий |
|---|---|---|
| Ф0 | Модель, порт хранения, реестр, `GET /api/v2/agent-systems`, health, UI-список (read-only) | система регистрируется и видна, вызовов нет |
| Ф1 | Вызов `remote-http`/`remote-mcp` с журналом и правами, без стрима | задача уходит и возвращает результат, аудит полный |
| Ф2 | Стрим ответа в сессию, отмена, идемпотентность | ход в UI неотличим от локального по наблюдаемости |
| Ф3 | `event-source`, маршрутизация задач по `capabilities`, квоты и лимиты | задача маршрутизируется без ручного выбора системы |
| Ф4 | `runner-engine` (пересмотр PROP-050), федерация с другими инстансами (PROP-055) | — |

Ф0–Ф1 — минимум, дающий ценность; дальше по спросу. Реализация — **после 0.12.4**, в горизонт текущей
трёхэтапной нарезки не входит.

## Открытые вопросы

1. **Единица централизации** — сессия (человек разговаривает с системой) или проект (задачи распределяются
   между системами автоматически)? От ответа зависит, где живёт маршрутизатор.
2. **Представление peer'а в UI** — участник сессии, инструмент или отдельная сущность со своим экраном?
3. **Граница «данные vs инструкции»** — нужен ли отдельный фильтр вывода peer'а (по образцу `llmFilters`
   [ADR-090](./adr-090-extension-api.md)) перед попаданием в контекст.
4. **Air-gapped** — как регистрировать и обновлять описания систем без внешней сети (оффлайн-манифест).
5. **Кто владелец прав при машина-к-машине** — service-key инстанса или отдельная «системная» идентичность.

## Последствия

- Новые контракты в `shared` (`AgentSystem`, capability-схемы), новый доменный порт хранения, новые роуты и
  UI-раздел — то есть это правка ядра, а не расширение.
- Появляется риск «второго permission-слоя»: все проверки обязаны идти через authority/permission-слой
  (инварианты 5 и 17), дублирующих проверок в обработчиках быть не должно.
- Класс несовместим с мультирепликой «по факту»: реестр систем и журнал должны лежать в общем хранилище
  ([PROP-106](./prop-106-file-ports-to-sql.md)), иначе федерация разъедется между репликами.
