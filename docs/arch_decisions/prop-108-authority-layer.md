## Решение

Предлагается ввести **Authority-слой** — единую доменно-нейтральную модель полномочий, в которой право
выражается не «какой инструмент разрешён», а **грантом «действие × цель»**:

- **Действие** — доменный глагол (`read`, `write`, `execute`, `publish`, `approve`, `sign`, `delegate`),
  а не имя тула: `write_file` и `git_commit` — разные способы одного действия над разными целями.
- **Цель** — типизированный ресурс (`project:<id>`, `path:<относительный путь>`, `session:<id>`,
  `mcp:<server>/<tool>`, `external:<connector>/<resource>`), а **не** текст команды или промпта.
- **Роль** — именованный набор грантов, который **поставляется контентом** (пакет `synth.pack`,
  flavor-дистрибутив, каталог), а не зашивается в код ядра.
- **Принципал** — тот, от чьего имени исполняется **ход**: пользователь, агент, service-key, шедулер или
  внешний источник. Права считаются для принципала хода, а не «для сессии вообще».
- **Потолок (ceiling)** — максимум, который может быть активен: пересечение прав пользователя, агента,
  сессии, пакета и политики инстанса. Делегирование только сужает.

Состав слоя — пять частей:

| # | Часть | Суть | Ядро работы |
|---|---|---|---|
| 1 | **Модель** | `Principal`, `Action`, `Target`, `Role`, `Grant`, `Ceiling`, `Turn`, `Approval` — схемы в `@itphx/synth-shared` | `shared/src/types/authority.ts` |
| 2 | **Резолвер** | `effective = grants(user) ∩ grants(agent) ∩ ceiling(session) ∩ ceiling(pack) ∩ policy(instance)`; нет гранта — нет права | `engine/authority/resolve.ts` |
| 3 | **Точка решения** | один guard на все входы (tool_call, HTTP, WS, пайплайн, событие) — не проверки в обработчиках | `engine/authority/guard.ts` + `server/authority-guard.ts` |
| 4 | **Подтверждения** | `Approval` привязан к `(principal, turn, action, target, digest)`, одноразовый, отвечает только носитель гранта | `engine/permission/approval.ts` (переработка) |
| 5 | **Контент и доставка** | `provides.authority` в `synth.pack`, flavor-дистрибутивы, каталог ролей; установка — с одобрением ADMIN | `routes/packs.ts`, `shared/src/types/pack.ts`, [PROP-068](./prop-068-skills-agents-registry.md) |

Ключевая гипотеза: **сегодняшние пять осей (глобальные роли, проектные роли, capability агента,
permission-правила сессии, capability пакета) — это пять разных языков об одном и том же.** Пока они
не сведены к одной модели, доменный вопрос («может ли этот сотрудник подписать этот документ») невыразим,
а многопользовательская сессия небезопасна по построению.

## Контекст

### Четыре вопроса, на которые сегодня нет ответа

1. **Кто действует?** У сессии один `userId`/`ownerId` и нет списка участников; `Message.author` —
   display-строка. В проектной сессии пишут несколько человек, но «принципал хода» нигде не зафиксирован.
2. **Что именно разрешено?** `PermissionConfig.rules` говорит «тул `write_file` — allow», но не говорит
   «запись в `contracts/**` — да, в `secrets/**` — нет» в терминах домена; файловые glob'ы — единственное
   приближение, и только для файловых тулов.
3. **Кто подтверждает?** `permission.asked` не несёт принципала, а `permission.replied` принимается по
   `approval_id`; в backend проверяется только **видимость на чтение** — то есть участник проекта с ролью
   `VIEWER` может подтвердить мутирующий инструмент.
4. **Чем ограничен контент?** Пакет уже приносит агента с `capabilities` (группы тулов) и пайплайн с
   собственным `mode`; `capabilities` кастуются без проверки по перечислению, а `provides` — `.passthrough()`.
   То есть контент уже сегодня влияет на права — без модели, без одобрения по существу и без аудита решений.

## Модель

### Сущности

| Сущность | Смысл | Ключевые поля (набросок) |
|---|---|---|
| `Principal` | От чьего имени исполняется ход | `kind: 'user'\|'agent'\|'service'\|'scheduler'\|'event'`, `id`, `roles[]` |
| `Action` | Доменный глагол | `id` (`read`/`write`/`execute`/`publish`/`approve`/`sign`/`delegate`), `mutating: boolean` |
| `Target` | Типизированный ресурс | `kind` (`project`/`path`/`session`/`mcp`/`external`), `ref`, `scope?` |
| `Grant` | Разрешение | `action`, `targetPattern`, `effect: 'allow'\|'ask'\|'deny'`, `constraints?` (`once`, `ttl`, `maxCount`) |
| `Role` | Именованный набор грантов | `id`, `displayName`, `grants: Grant[]`, `domain` |
| `Ceiling` | Верхняя граница активных прав | `grants: Grant[]`, `source` (`user`/`session`/`pack`/`instance`) |
| `Turn` | Единица исполнения | `id`, `sessionId`, `principal`, `ceiling`, `startedAt` |
| `Approval` | Запрос подтверждения | `id`, `turnId`, `principal`, `action`, `target`, `digest`, `once`, `expiresAt` |

### Резолвинг и решение

```ts
// effective — не «объединение», а пересечение: каждая ось может только сузить.
effective(turn) = grants(turn.principal) ∩ grants(agentOf(turn))
                  ∩ ceiling(session) ∩ ceiling(pack) ∩ policy(instance)

decide(turn, action, target):
  if !known(action) || !resolved(target)  -> deny('unknown')    // fail-closed
  if any(deny matches)                    -> deny('explicit')
  if none(allow matches)                  -> deny('no_grant')   // нет гранта — нет права
  if any(ask matches) || requireConfirm   -> ask(Approval{turn, action, target, digest})
  return allow

approve(approval, principal):
  require approval.turn === currentTurn
  require covers(principal, approval.action, approval.target)  // носитель гранта, не «любой читатель»
  consume(approval)                                            // одноразово; повтор → deny
```

### Инварианты модели

1. **Нет гранта — нет права.** `allow` не выводится из отсутствия запрета; неизвестное действие/цель — `deny`.
2. **Грант — всегда «действие × цель».** Цель — типизированный ресурс; текст команды, промпт и имя тула целью не являются.
3. **Права только сужаются.** Агент ≤ пользователь, саб-агент ≤ родитель, ход ≤ сессия, пакет ≤ политика инстанса; ни один слой не «добавляет» право, которого нет выше.
4. **Принципал фиксируется при приёме ввода**, а не при исполнении: очередь, steering и повторный запуск не меняют автора хода.
5. **Подтверждение привязано** к `(principal, turn, action, target, digest)`, одноразово и отвечается только носителем гранта; «кто-то из читателей сессии» — не ответ.
6. **Контент не выдаёт права сам себе**: `provides.authority` объявляет роли, но активируется политикой инстанса и одобрением ADMIN.
7. **Одно место решения.** Проверки — в authority-guard (граница + движок), не в обработчиках и не в промпте.
8. **Аудит каждого решения** — `principal`/`action`/`target`/`effect`, без секретов и без сырых путей.

## Точки принуждения

| Уровень | Где | Что проверяет | Почему именно здесь |
|---|---|---|---|
| **1. Граница ресурса** | `session-access-guard`, `requirePermission`, `requireScope`, проектные роли, `isSessionVisible` | Можно ли вообще обратиться к сессии/проекту и в каком виде (`read`/`write`) | Единственная точка для `:id`-маршрутов (инвариант 16); не размазывается по хендлерам |
| **2. Право на действие** | `PermissionEvaluator` (availability → rules → shell-policy → protected paths → `yolo`) | Можно ли этому принципалу в этом ходу выполнить это действие над этой целью | Здесь уже собираются все оси; сюда встаёт резолвер `effective` |
| **3. Фактическая достижимость** | `ExecutionPort` (`inline`/`remote`), `egress-guard`, MCP network-policy, workspace containment, `pipelines/permissions.ts` | Дойдёт ли действие до ресурса физически (и не шире ли оно объявленного) | Право без достижимости — ложь; достижимость без права — дыра |
| **4. Поставка контента** | установка `synth.pack` (`needsApproval`), `AgentDefinition.capabilities`, `spec.mode` пайплайна, flavor-образ | Что вообще может быть объявлено в этом инстансе | Контент — источник ролей; ограничивать его надо на входе, а не в момент исполнения |

### Почему парсинг shell-команды — эвристика, а не граница

Shell-guard сам фиксирует предел: токенизация shlex-подобная, без полного резолва динамики; `$()`,
`${...}`, glob дают `source: 'unknown'` и fail-closed в `ask`
(`packages/core/src/engine/security/shell-guard.ts:1-23`). Этого достаточно как **сетки безопасности**
(дешёвый барьер против случайного `rm -rf`), но недостаточно как **модели прав**:

- интерпретаторы (`bash -c`, `python -c`, `node -e`), heredoc, base64 и загрузка по сети обходят любой разбор текста;
- одна и та же цель достижима разными командами (`cat`, `less`, `python -c open(...)`), а один и тот же текст — разными целями (симлинк, `cwd`, переменная);
- «неизвестная динамика» неотличима от «враждебной» — остаётся только `ask`, то есть человек в цикле.

Поэтому в Authority-слое `execute_shell` получает грант на **действие + рабочую область** (`execute` ×
`workspace:<project>`), а не на разобранную строку; тонкая настройка остаётся в shell-policy как
дополнительный слой, но не как источник истины.

## Многопользовательская сессия

Сегодня сессия — «один владелец + один режим + один permission-конфиг». В проектной сессии это ломается
в трёх местах.

**Turn principal.** Ход открывается вводом (сообщение, событие, расписание) и несёт принципала:
`user:<id>`, `agent:<id>`, `service:<keyId>`, `scheduler`, `event:<source>`. Принципал фиксируется **при
постановке в очередь**, а не при исполнении: иначе сообщение из `pendingMessages` исполнится «от текущего».

**Ceiling хода.** `effective` считается один раз на ход: права инициатора ∩ права агента ∩ потолок сессии
∩ потолок пакета ∩ политика инстанса. Сообщение другого участника **не поднимает** потолок уже начатого
хода; оно либо становится новым ходом, либо (при steering) пересчитывает потолок с записью в журнал.

**Подтверждения.** `Approval` адресуется носителям гранта, а не «подписчикам канала»: ответ принимается,
только если у ответившего есть покрывающий грант на `(action, target)`. `once` — одноразовый; повторный
ответ на тот же `approval_id` — `deny`. `yolo` не снимает `ask`, если потолок сессии его требует.

**Асинхронные ходы.** Очередь исполняет ходы последовательно, но принципал у каждого свой; фоновые сессии
саб-агентов ([PROP-096](./prop-096-background-subagent-sessions.md)) наследуют потолок родителя, а не
пользователя «по умолчанию». Steering ([PROP-098](./prop-098-mid-turn-steering.md)) — единственный законный
способ сменить ввод посреди хода; он несёт принципала и либо сохраняет потолок, либо понижает его.

**Три сегодняшние дыры** (все подтверждены кодом):

1. **Подтверждение без принципала.** `permission.asked` не содержит, кто спрашивает; `permission.replied`
   принимается по `approval_id` (`approval.ts:84,94-102`). В core WS-путь публикует ответ без проверки
   видимости (`ws-events.ts:392-405`), в backend — только read-видимость (`listen.ts:193-201,276-291`):
   `VIEWER` участник проекта может подтвердить мутирующий инструмент.
2. **Режим — на сессию, а не на ход.** `PATCH /sessions/:id` ставит `mode` (`sessions.ts:505,594`), `yolo`
   автоматически подтверждает все `ask` (`evaluator.ts:171-180`) — один участник с write-доступом снимает
   подтверждения для всех, включая тех, кто в этом ходу не участвовал.
3. **Нет участников и атрибуции.** `Session` хранит одного `userId`/`ownerId` (`session.ts:239-240`),
   `Message.author` — display-строка (`message.ts:66`). Нельзя ни ограничить права конкретного участника,
   ни посчитать лимиты, ни ответить на вопрос «кто это сделал» в аудите.

## Доменная нейтральность и доставка контентом

Модель не знает предметной области: «действия», «цели» и «роли» — данные. Проверка — на трёх примерах.

| Домен | Действия | Цели | Роли (поставляются контентом) | Чего не хватает сегодня |
|---|---|---|---|---|
| **Разработка ПО** | `read`, `write`, `execute`, `commit`, `publish` | `path:src/**`, `path:.git`, `mcp:git/*`, `external:registry/*` | `developer`, `reviewer`, `release-manager` | `reviewer` невыразим: нет действия `approve` над целью `change:<id>` |
| **Клинические процессы** | `read`, `write`, `sign`, `approve`, `delegate` | `record:<patientId>`, `document:<id>`, `external:registry/*` | `clinician`, `nurse`, `registrar` | `sign` и `delegate` отсутствуют; «цель — запись пациента» невыразима путём/тулом |
| **Финансы и закупки** | `read`, `approve`, `execute`, `publish` | `invoice:<id>`, `payment:<id>`, `report:<period>` | `accountant`, `controller`, `treasurer` | Нет лимитов/условий (`maxAmount`) и разделения «создал ≠ утвердил» |

Фрагмент контента (набросок, не контракт):

```jsonc
// synth.pack → provides.authority
{
  "roles": [
    { "id": "clinician", "domain": "clinic",
      "grants": [
        { "action": "read",  "target": "record:*" },
        { "action": "write", "target": "record:*", "constraints": { "requireConfirm": true } },
        { "action": "sign",  "target": "document:*" }
      ] }
  ],
  "actions": [{ "id": "sign", "mutating": true, "requires": ["write"] }],
  "targets": [{ "kind": "record", "resolver": "clinic:patient-record" }],
  "agents":  [{ "id": "clinic-assistant", "roles": ["clinician"], "ceiling": ["read"] }]
}
```

Правила безопасности контента:

- **Декларация, не код.** `provides.authority` описывает роли/действия/цели; исполняемой логики резолва
  в пакете нет — резолверы целей регистрирует ядро (или плагин — после [PROP-090](./prop-090-extension-api.md)).
- **Пересечение, не дарование.** Пакет не может выйти за политику инстанса: `effective` всегда пересекает
  `ceiling(pack)` с `policy(instance)`; «пакет выдал себе `sign`» невозможно по построению.
- **Одобрение по существу.** Пакет с непустым `provides.authority` попадает в `pending_approval` — как и
  пакет с `capabilities`/пайплайнами/расписаниями (`packs.ts:740-752`); ADMIN видит **какие** роли и
  действия приносит пакет, а не только факт «есть capabilities».
- **Trust-floor.** `community`-пакет объявляет роли и целевые шаблоны, но гранты на мутирующие действия
  активируются только при trust ≥ `trusted` (модель доверия — [PROP-068](./prop-068-skills-agents-registry.md)).
- **Валидация, а не каст.** Сегодня `capabilities` агента кастуются без проверки по перечислению
  (`packs.ts:626`); для `authority` — строгая схема: неизвестное действие/цель/роль → отказ установки.
- **Flavor-дистрибутив.** Доменные роли едут не в ядре, а во flavor'ах ([PROP-082](./prop-082-full-images-deployment.md)):
  `slim` — без доменных ролей, `core` — базовые `developer`/`reviewer`, `devops`/`browser` — свои,
  отраслевые — с `provides.authority` и профильными агентами; ядро остаётся нейтральным.
- **Каталог.** Роли, действия и цели — такие же объекты каталога, как скиллы и агенты; распространение,
  подписи и install-policy — [PROP-068](./prop-068-skills-agents-registry.md), отдельной сущности не заводим.

## Совместимость и миграция

| Что | Сейчас | После | Ломает? |
|---|---|---|---|
| `PermissionConfig.rules` (ADR-029) | allow/deny/ask по тулу/группе/glob | остаётся; компилируется в гранты «действие × цель» при чтении | нет |
| `ToolCapability` (11 групп) | грубая ось доступности | остаётся как **отображение** действий на группы тулов | нет |
| `AgentDefinition.capabilities` | объявление прав агента | читается как `roles`/гранты; при отсутствии роли — выводится из capability | нет |
| Проектные роли `OWNER`/`EDITOR`/`VIEWER` | доступ к проекту | остаются; становятся целями `project:<id>` (чтение/изменение содержимого) | нет |
| `service-key` scopes (ADR-052) | точечный гейт | остаются; маппинг scope → действие | нет |
| `packType: 'policies'` | пустой тип без контракта | уточняется до `provides.authority` (старый `packType` сохраняется) | нет |
| `Session.mode` | сессионный переключатель | остаётся, но трактуется как **потолок**; `PATCH` ограничивается | поведение — да |
| `permission.asked`/`replied` | без принципала | + `principal`, `turn_id`, `digest` (аддитивные поля) | нет |
| `Message.author` | display-строка | + `principal` (аддитивно); `author` остаётся для UI | нет |

**Миграция — двойное чтение, без переписывания данных.** Ф0–Ф1: старые правила и `capabilities` читаются
как раньше, authority-резолвер работает в режиме **shadow** (решение считается и пишется в журнал, но не
применяется). Расхождение shadow-решения с текущим — дефект миграции, а не повод «подкрутить» политику.
Ф2+: применение по доменам, начиная с файловых/исполнительных действий; неизвестное действие — `deny`
(а не «пропустить»).

## Этапы

**Ф0 — контракты.** Схемы `authority.ts` в `@itphx/synth-shared`; `provides.authority` (строгая схема);
аддитивные поля `permission.asked`/`replied`; порт политики (`AuthorityPolicyRepository`, ADR-096) — **без
принуждения**. Критерий: схема валидирует три доменных примера выше, `pnpm typecheck` зелёный.

**Ф1 — резолвер + shadow.** `effective`, пересечение осей, журнал решений, метрики `synth_authority_*`
(лейблы `action`/`effect`/`source`, без `user_id`/`session_id`). Критерий: shadow-решения совпадают с
текущими, кроме перечисленных расхождений.

**Ф2 — принуждение в движке.** Authority-guard в `PermissionEvaluator`; `yolo` ограничен потолком; `deny`
для неизвестных действий. Критерий: ни один тул не исполняется без гранта; тест «новый тул без маппинга →
`deny`».

**Ф3 — границы и подтверждения.** `Approval` с принципалом/ходом/digest; ответ только носителем гранта;
WS-путь (core и backend) проверяет покрытие, а не видимость. Критерий: `VIEWER` не подтверждает мутацию;
повторный ответ — `deny`.

**Ф4 — многопользовательские сессии.** `Turn.principal` в очереди и steering; `Session.participants` (или
эквивалент) и потолок сессии; ограничение `PATCH mode`. Критерий: два участника получают разные решения на
одно действие; смена режима не поднимает потолок другому.

**Ф5 — контент и дистрибуция.** `provides.authority` в установке пакета, `pending_approval` по существу,
flavor-роли, каталог (PROP-068), UI-раздел «Полномочия» (read-only для не-ADMIN). Критерий: доменный пакет
ставится, роли видны, права не выходят за политику инстанса.

## Альтернативы

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| **A. Оставить как есть** | `PermissionConfig` + `capabilities` + роли | ноль работ, совместимость | пять осей, нет принципала, домен невыразим, дыры §5 остаются |
| **B. Внешний policy-engine** (OPA/Casbin) | вынести решение в отдельный сервис/библиотеку | зрелые языки политик, аудит из коробки | новая зависимость и сетевая точка отказа, оффлайн-инстанс, дублирование моделей |
| **C. OAuth-подобные scopes на сессию** | выдать сессии набор scope'ов | привычно, просто в UI | scope выдаётся клиенту, а не ходу; нет целей и условий; утечка при шаринге сессии |
| **D. Capability-токен на ход** | подписанный набор грантов, передаваемый исполнителю | сильная изоляция, проверяемо на исполнителе | сложнее подтверждения и UI; без модели прав превращается в «ещё один JWT» |

Предлагается **A как основа** (сохраняем совместимость и данные), **D как транспорт** (потолок хода
передаётся исполнителю и не пересчитывается там), **B — позже** как адаптер резолвера, если появится
внешний запрос (editions/enterprise).

Отклонённые варианты:

- **Жёсткие роли в коде** (`if role === 'clinician'`) — домен протекает в ядро, каждый клиент требует релиза.
- **Проверка прав в промпте** («тебе запрещено…») — не граница безопасности; модель можно уговорить.
- **Парсинг shell как граница** — см. §4: интерпретаторы и динамика обходят текстовый разбор.
- **Пакет выдаёт себе права** (`provides.authority` без пересечения с политикой) — контент становится
  привилегированным кодом без доверия.

## Открытые вопросы

1. **Гранулярность цели** — `path:` (относительный путь), `resource:<type>/<id>` или оба? Кто резолвит `external:*` — ядро или коннектор ([PROP-107](./prop-107-oauth-credential-layer.md))?
2. **Где живёт политика инстанса** — `config.yaml` (секция `security.authority`), runtime-настройки (UI) или порт хранилища (ADR-096)? Нужен ли отдельный журнал изменений политики?
3. **Принципал нечеловеческих входов** — как выражается потолок для `scheduler`, `event:<source>`, `service:<keyId>`; наследуют ли они права владельца привязки (ADR-089) или имеют собственные роли?
4. **Подтверждения** — кто вправе подтвердить: любой носитель гранта, только инициатор, только `approve`-роль? Нужны ли TTL, эскалация и делегирование подтверждения?
5. **Участники сессии** — вводить `Session.participants` или вычислять из проекта? Как совместить с видимостью ADR-089 и не сломать standalone?
6. **Совместимость capability** — сохранять ли 11 групп `ToolCapability` как публичный контракт навсегда или объявить их производными от действий (и когда можно ломать)?
7. **Контент** — `provides.authority` как новый ключ или расширение `packType:'policies'`? Нужна ли подпись ролей и отдельный trust-уровень для «приносит права»?
8. **Аудит и метрики** — отдельный журнал решений (`audit/authority.jsonl`) или расширение `SECURITY_AUDIT_SCOPES` (breaking change `shared`)? Какие метрики допустимы без `user_id`/`session_id` (ADR-094)?

## Предлагаемые инварианты для AGENTS.md

26. **Права — «действие × цель» через Authority-слой.** Нет гранта — нет права; цель — типизированный ресурс, а не текст команды, имя тула или промпт; неизвестное действие/цель — `deny` (fail-closed).
27. **Права только сужаются.** Ход ≤ сессия ≤ пользователь; агент ≤ пользователь; саб-агент ≤ родитель; пакет ≤ политика инстанса. Принципал хода фиксируется при приёме ввода; подтверждение привязано к `(principal, turn, action, target, digest)` и одноразово — ответ «читателя сессии» не считается.
28. **Доменные роли/действия/цели/агенты — контент.** Поставляются `provides.authority` в `synth.pack` и flavor-дистрибутивом, а не кодом ядра; установка — с одобрением ADMIN и trust-floor (PROP-068); контент не расширяет права инстанса.
