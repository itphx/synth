# PROP-140: Класс исполнителей MCP — пулы, хостящие MCP-серверы

> **Статус:** 🧩 Предложение — отдельный класс пулов `mcp` для MCP-серверов (включая сторонние образы) с discovery инструментов через короткоживущий probe-под
> **Решение до:** 2026-12-15
> **Дата:** 2026-11-13
> **Обсуждено:** 2026-11-13 — владелец предложил класс MCP для образов вроде GitHub MCP; требуется дополнительное исследование транспорта и discovery.
> **Связано:** [ADR-135](./adr-135-execution-contour.md) (контур исполнения, пулы/профили/классы), [ADR-136](./adr-136-shell-trust.md) (доверие к исполнению), [ADR-070](./adr-070-system-prompt-composer.md) (промпт и тулы), [ADR-071](./adr-071-mcp-servers-prompt.md) (MCP в промпте), [ADR-090](./adr-090-extension-api.md) (плагины/тулы), [ADR-105](./adr-105-external-credentials.md) (внешние доступы), [ADR-115](./adr-115-multimodal-input.md) (вложения MCP-результатов)

## Контекст

Сейчас MCP-серверы живут **внутри исполнителя**: профиль пула задаёт
`mcpServers: [{ name, command, args, env }]`, исполнитель поднимает их как stdio-процессы и
отдаёт `/mcp/servers`, `/mcp/tools`, `/mcp/call`. Браузерный класс — частный случай этого
механизма (пул на проект, встроенные `browser_*` ходят в `playwright-mcp`).

Профили уже позволяют задавать **кастомный образ** и **кастомные MCP-серверы**, но:

- MCP-серверы и агентский toolchain живут в одном образе — нельзя взять готовый сторонний образ
  MCP-сервера (например, GitHub MCP) без сборки обёртки;
- discovery инструментов MCP возможен **только запуском сервера** — статически из образа схемы
  тулов не достать;
- нет отдельного класса пула, который было бы естественно масштабировать/изолировать по проектам
  для MCP-сценариев (креды, сессии, лимиты).

## Проблема

Нужен способ подключать MCP-серверы как **отдельный класс исполнителей** (`mcp`), в том числе
поставляемые в виде Docker-образов, и при этом:

1. знать схемы инструментов **до** первого вызова агента (они попадают в реестр тулов/промпт);
2. не держать постоянный пул «на всякий случай» (стоимость простоя);
3. не смешивать креды/сессии MCP между проектами;
4. не ломать существующий контракт `profile.mcpServers` и браузерный класс.

## Варианты

### A. MCP-класс как пул-хост MCP-серверов (executor + `mcpServers`)

Профиль класса `mcp` — обычный образ исполнителя с `mcpServers` (как сейчас у browser, но без
привязки к браузеру). Пул поднимается по требованию, исполнитель хостит серверы, core регистрирует
их тулы. Работает существующим кодом; сторонние серверы — через образ-обёртку (executor + бинарь).

**Плюсы:** минимум новых сущностей, переиспользует протокол `/mcp/*`, аудит и токены пула.
**Минусы:** готовые сторонние образы напрямую не подходят.

### B. Произвольные MCP-образы (sidecar/HTTP)

Профиль описывает **контейнеры** пула (`containers: [{ image, command, args, env, transport: http|sse }]`).
MCP-серверы общаются с исполнителем по сети (stdio между контейнерами пода напрямую не пробросить).

**Плюсы:** можно брать готовые образы (GitHub MCP и т.п.), если у них есть HTTP/SSE-режим.
**Минусы:** смена модели пода и протокола, транспорт, health-check, сетевые политики; stdio-only
образы всё равно требуют обёртки или моста.

### C. Внешний MCP-сервер (URL)

Подключение к уже развёрнутому MCP-серверу по HTTP/SSE (без пула). Не решает «образы», но полезно
для централизованных MCP.

## Предложение (гипотеза для исследования)

1. **Класс `mcp`** в профилях (`class: mcp`; допускается комбинация с `exec`? — открытый вопрос).
   Профиль описывает образ исполнителя и `mcpServers`; пул — **проектный** (креды/сессии не текут
   между проектами), по требованию.
2. **Discovery — probe-под.** При сохранении профиля (кнопка «Обновить инструменты») или при первом
   использовании backend просит provisioner поднять короткоживущий под профиля, дождаться `/health`,
   забрать `/mcp/servers` + `/mcp/tools`, сохранить схемы и метаданные (версия/хеш/время) в
   runtime-настройках профиля, под удалить. TTL/refresh — вручную и при смене образа.
3. **Реестр и вызовы.** Инструменты регистрируются как `profile_server_tool` в существующем
   `McpManager`/реестре (имена не конфликтуют со встроенными), вызовы маршрутизируются в пул профиля;
   в промпт попадают только схемы (без секретов), объём ограничивается как у MCP сейчас.
4. **Секреты** — только env из Secret/файлов (инвариант 13); MCP-серверы пула не логируются.
5. **Warm-кэш** образов — использовать существующий/планируемый механизм прогрева (DaemonSet),
   чтобы probe не платил за pull каждый раз.

## Открытые вопросы (что исследовать)

1. **Транспорт сторонних образов.** Какие MCP-серверы (GitHub и др.) умеют HTTP/SSE из коробки;
   насколько реально требование «HTTP-only» для класса `mcp`; нужен ли stdio-мост (socat/прокси) и
   где он живёт.
2. **Sidecar-модель.** Готовы ли мы менять pod spec (несколько контейнеров), как это влияет на
   read-only rootfs, токены пула, сетевые классы и NetworkPolicy.
3. **Discovery.** Где хранить схемы (runtime-настройки профиля vs отдельный кэш), как версионировать,
   что делать при недоступном сервере (fail-closed/последний удачный кэш), лимиты размера схем.
4. **Изоляция.** Проектный пул для MCP: стоимость (под на проект), TTL/idle, шаринг между сессиями
   проекта; можно ли instance-пул для нечувствительных серверов.
5. **Права/доверие.** Кто может создавать MCP-профили (ADMIN), как аудировать вызовы, что считать
   внешним доступом (ADR-105), как ограничивать набор серверов проектом/агентом.
6. **Совместимость.** Не ломает ли `class: mcp` текущие `browserProfiles`/`class: browser|both`;
   нужен ли `mcp` в `allowedProfiles`/потолках и как он сочетается с exec-классом.
7. **UI.** Один профиль — один класс или мультикласс; как показывать инструменты и их обновление;
   как отключать отдельные серверы профиля.

## Альтернативы (отклонены предварительно)

- **Оставить только `mcpServers` в exec-профиле** — не даёт готовых сторонних образов и отдельного
  масштабирования/изоляции; остаётся базой для варианта A.
- **Discovery «на лету» в первом ходе** — схемы нужны до формирования промпта/реестра; первый ход
  окажется без инструментов либо с задержкой.
- **Постоянный MCP-пул на инстанс** — простой, но платный по ресурсам и смешивает креды проектов.
