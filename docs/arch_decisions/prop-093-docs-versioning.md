# PROP-093: Версионирование документации

> **Статус:** 🧩 Предложение — Версионирование документации портала: версионные подкаталоги + селектор или `mike`
> **Решение до:** 2026-11-14
> **Дата:** 2026-10-15
> **Парные документы:**
> - [ADR-038](./adr-038-npm-packages.md) «Монорепо как набор публикуемых npm-пакетов» — релизный цикл, к которому привязывается версия документации;
> - скилл `synth-docs` — процесс ведения документации (портал `synth-docs` + dev-доки `synth/docs`);
> - [PROP-092](./prop-092-instance-lifecycle-maintenance.md) — обновление/откат версий, с которыми должны согласовываться версии доков.

## Решение

Ввести **версионирование пользовательского портала** `docs.synth.itphx.ru` в такт с релизами платформы, с двумя поддержанными вариантами:

- **Вариант A (MVP, под текущий деплой).** При сборке портала формировать **версионные подкаталоги** `site/<version>/` для каждой поддерживаемой git-метки `synth-docs`, алиас `site/latest/` → актуальная версия; в шапке — селектор версий (override Material `alternate`/custom); в образ (`nginx:alpine`) кладётся конкатенация версий.
- **Вариант B (когда появится GitHub-зеркало/Pages).** Перейти на **`mike`** (стандарт MkDocs Material): `mike deploy <version> latest`, встроенный селектор, хранение версий в ветке.

**Предпосылки:** (1) тегировать репозиторий `synth-docs` в такт с релизами кода; (2) определить политику хранения (сколько версий держим); (3) EN-страницы включаются (`build: true`) после перевода и версионируются вместе.

Dev-документация в `synth/docs` (AD, ARCHITECTURE, DEVELOPMENT…) уже версионируется git-тегами основного репозитория и в этот AD не входит.

## Контекст

- Портал — **отдельный репозиторий** `synth-docs` (MkDocs Material, плагин `i18n`; EN сейчас `build: false`). Сборка: `mkdocs build --strict` в multi-stage Docker → раздача `site/` через `nginx:alpine`; раскатка Helm/Fleet (1 реплика, ingress). **Версий нет** — всегда публикуется текущий `main`.
- Классический `mike` рассчитан на раздачу версий из git-ветки (gh-pages), а у нас nginx-образ → нужен либо переход на Pages (вариант B), либо генерация версионных подкаталогов в образ (вариант A).
- Пользователь читает доки про конкретную версию, а платформа обновляется и откатывается ([PROP-092](./prop-092-instance-lifecycle-maintenance.md)) — без версий доки «уезжают» от установленного инстанса.
- При GitHub-зеркале (отдельная задача) публичный портал логично поднять на Pages, что снимает ограничение `mike` и делает вариант B предпочтительным в перспективе.

## Детали

### Схема URL и алиасы

| URL | Содержимое |
|---|---|
| `/` → `/latest/` | редирект на актуальную версию |
| `/latest/…` | алиас последней стабильной версии |
| `/<version>/…` (напр. `/0.10/`) | документация конкретной версии |
| поиск | scoped на текущую версию (`search` плагин per-instance) |

- Канонические ссылки (`<link rel="canonical">`) указывают на версионный URL; баннер-переключатель — существующий `alternate` Material, переиспользуемый под версии.

### Сборка и публикация (вариант A)

1. На релиз кода — тег в `synth-docs` (`v<version>`), соответствующий версии платформы.
2. Скрипт сборки: для каждой хранимой метки — checkout → `mkdocs build --strict` → копирование в `dist/<version>/`; `dist/latest` → последняя.
3. Docker-образ отдаёт `dist/` через nginx; `scripts/build-push.sh` пинит тег образа (как сейчас).
4. Селектор версий — небольшой override-шаблон с JSON-списком доступных версий; редирект `/` → `/latest/` в nginx.
5. `robots.txt`/`sitemap.xml` — генерировать по версиям; устаревшие версии — `noindex`, если не хотим дубли в поиске.

### Совместимость с i18n

- Версии и языки — ортогональны: `/<version>/<locale>/`. Плагин `i18n` уже строит `build/`-структуру по локалям; версии добавляются уровнем выше.
- До перевода EN: версионные подкаталоги содержат RU, `/en/` включается позже.

## Объём MVP и этапы

1. **MVP (вариант A):** скрипт сборки по меткам + раздача версионных подкаталогов + селектор + редирект `/`→`/latest/`. ~1–2 дня.
2. Тегирование `synth-docs` в релизном процессе + политика хранения (например, 3 последних минора). ~0.5 дня.
3. (Опц.) Вариант B на `mike` — при переходе портала на GitHub Pages. ~1–2 дня.
