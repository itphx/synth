## Контекст

Модель контента сообщения — текстовая: `PartType = 'text' | 'tool_use' | 'tool_result' | 'reasoning' |
'session_reference'` (`packages/shared/src/types/message.ts:19`), `Part = { id, type, data: unknown }`.
Провайдеры получают `LLMMessage.content: string` (`packages/core/src/providers/base.ts:151-154`), поэтому
картинку, голос или документ передать нельзя. При этом:

- ввод с телефона (камера/микрофон, ADR-044) и вложения из мессенджеров (ADR-087/ADR-089) — востребованные
  сценарии; шлюзы уже **приносят метаданные** вложения (`kind`/`fileId`/`fileName`), но не байты;
- vision/audio/pdf-модальности у провайдеров есть, а в Synth нет ни контракта, ни хранилища, ни UI;
- blob-подложка уже существует и работает (логи фоновых процессов через порт `BlobStore`), но у неё один
  потребитель и нет учёта ссылок.

Дополнительно: `content` — производное строковое поле (`buildContentFromParts`,
`packages/shared/src/utils/index.ts:194`) и источник для PG-маппинга
(`packages/storage-postgres/src/ports/sessions-mapping.ts`), экспорта, легаси-сообщений и поиска. Любая
новая часть обязана давать в `content` осмысленный плейсхолдер, иначе вложение «испаряется» без ошибки.

## Решение

1. **Расширить `Part`** типами `image`/`audio`/`video`/`file`; данные части — ссылка на blob + метаданные
   (`blobPath`, `mime`, `size`, `sha256`, `name?`, `width?`, `height?`, `durationMs?`, `transcript?`).
   Текстовые части не меняются — обратная совместимость. Медиа-часть обязана давать в `content`
   плейсхолдер (`[image: name.png]`), чтобы строковые производные не теряли факт вложения.
2. **Байты — на томе через порт `BlobStore`**, content-addressed (`attachments/<sha2>/<sha256>`);
   в БД байты не пишутся (обоснование и `blob_refs` — [ADR-116](./adr-116-instance-state-and-blob-ports.md)).
3. **Контракт LLM-вызова расширяется аддитивно:** `LLMMessage.attachments?: LLMAttachment[]` рядом с
   `content: string` (а не `content` как массив частей). Причина: guard, обфускация, фильтры,
   `estimateTokens`, debug и маппинг истории остаются текстовыми; провайдер сам собирает массив частей
   запроса. Порядок — текст, затем вложения.
4. **Провайдеры** маппят вложения в свои форматы: OpenAI (`image_url`, `input_audio`), Anthropic
   (`image`, `document`), Gemini (inline). Вложение, модальность которого модель **точно** не принимает
   (модальности известны из конфига модели), не отправляется: модель получает плейсхолдер + системную
   пометку, пользователь — предупреждение (i18n-ключ), не 500. Если модальности модели **неизвестны**,
   вложение отправляется как есть — тихая потеря запрещена (см. §«Модальности входа модели»).
5. **Gateway** (инвариант 3) остаётся единственным путём: обфускация/guard/payload-лог работают **только**
   с текстом (`content`, `systemPrompt`, сериализованный `tools`); бинарь не сканируется и не логируется —
   в журнал попадают только ссылки `{blobPath, sha256, size, mime}`. Обфускация на медиа не
   распространяется: это фиксируется как известное ограничение, OCR-инъекции — новый вектор (ADR-036).
6. **HTTP-контур** (core, монтируется backend'ом):
   - `POST /api/v2/sessions/:id/attachments` — multipart, один файл за запрос; MIME определяется по
     содержимому (не по заявленному), размер и количество — по лимитам; ответ `{id, blobPath, sha256, mime, size}`;
   - `GET /api/v2/sessions/:id/attachments/:partId` — байты с проверкой доступа (session prefix-guard, read),
     `Content-Type`, `Content-Length`, `ETag = sha256`, `Content-Disposition: inline` (с санитайзом),
     `Cache-Control: private`; большие файлы — потоком с поддержкой `Range`;
   - `POST /api/v2/sessions/:id/prompt` получает аддитивное `attachments?: string[]` (id вложений) →
     сообщение с частями `[text, image, …]`.
7. **Конфиг** — секция `attachments` (`maxBytesPerFile`, `maxFilesPerMessage`, `maxBytesPerSession`,
   `allowedMimePrefixes`, `gcDays`), приоритет CLI > env > config.yaml > defaults (ADR-023).
8. **UI — по образцу OpenChamber** (эталонный код: `tmp/refs/openchamber/packages/ui/src`). Копируем
   поведение и структуру, а не код; отличия — из-за серверного хранения (см. §«UI»).

## Модель контента

```ts
export type PartType = 'text' | 'tool_use' | 'tool_result' | 'reasoning' | 'session_reference'
  | 'image' | 'audio' | 'video' | 'file';

export interface MediaPartData {
  blobPath: string;   // 'attachments/ab/<sha256>'
  sha256: string;
  mime: string;
  size: number;
  name?: string;
  width?: number;
  height?: number;
  durationMs?: number;
  /** Текстовая расшифровка (ASR/OCR/извлечение из документа) — подставляется в контекст вместо байтов. */
  transcript?: string;
}
```

`messages.parts` в PostgreSQL — `jsonb` (`packages/storage-postgres/src/migrations/001-init.ts:82`), поэтому
новые виды частей схемы БД **не требуют**; требуется только приём новых типов в
`serializePart`/`deserializePart`.

## Хранение

- Порт `BlobStore` (`packages/core/src/storage/ports/blob-store.ts`) расширяется двумя аддитивными
  методами: `stat(path)` (размер/mtime для ответа и `Range`) и `readStream(path, {start?, end?})`
  (раздача без чтения в память). `read()` остаётся для мелких объектов и тестов.
- Content type в порт не переезжает: он живёт в метаданных домена (часть сообщения, запись артефакта).
- Учёт ссылок — `blob_refs` (порт; миграция `024_blob_refs`, первая из релизной серии): ссылка пишется при появлении сообщения и снимается
  при его удалении; объект удаляется, когда ссылок не осталось (плюс sweep сирот).
- Раздача идёт через API, а не прямой ссылкой на файл: доступ проверяется на границе
  (`server/session-access-guard.ts`, инвариант 16).

### Отброшенное вложение не теряется: материализация в workspace

**Решение 2026-10-27.** Если вложение **не уходит** провайдеру (модель не принимает модальность —
`reason: modality`; превышен суммарный лимит base64 — `limit`; объект недоступен — `unavailable`),
байты всё равно сохраняются в рабочем каталоге проекта, а модели сообщается путь:

- Материализация — `packages/core/src/engine/attachments/materialize.ts`
  (`materializeAttachment`): `<workspace>/attachments/<name>`, имя санитайзится (последний сегмент
  пути, без `..`/управляющих символов/кавычек, пусто → `attachment-<sha8>` от содержимого),
  публикация атомарная (`tmp` в том же каталоге → `link`/`copyFile` с `COPYFILE_EXCL`), существующий
  файл **не перезаписывается**; совпадающее содержимое дедуплицируется (тот же путь, копий нет),
  иначе суффикс `-2`, `-3`, … . Возвращается путь **относительно workspace** (`attachments/<name>`);
  ошибки (нет workspace/прав, объект не прочитан) → `null` — ход не падает.
- Модель видит блок `[ATTACHMENTS NOT DELIVERED]` (один на сообщение, добавляется к `content`
  LLM-сообщения; сохранённая история сессии не меняется): список `- {name} ({mime}) — {reason}`
  и `; path: <путь>` у материализованных. Файл доступен инструментам (`read_file`/`glob`/shell) —
  модель может прочитать его, обработать иначе или честно сказать пользователю, что формат не поддержан.
- Шаблон блока — системный контекстный файл `packages/core/prompts/system/ATTACHMENTS_DROPPED.{ru,en}.md`
  (плейсхолдер `{items}`; загрузка — `ContextConfig.getAttachmentsDroppedTemplate(language)`, override —
  `{userDataDir}/user/system/ATTACHMENTS_DROPPED.{lang}.md`). Файла нет/он пуст — короткая техническая
  строка на английском (канал LLM, ADR-041).
- Workspace не готов (нет `project.workspace`/worktree) — материализация не выполняется, путь модели
  не сообщается (блок остаётся со списком причин).
- Уборка `attachments/` в workspace не автоматизирована: каталог живёт как обычные файлы проекта
  (удаляется вместе с проектом/чистится пользователем). Предотвращения дублей между ходами —
  дедуп по содержимому при том же имени; имена не «уникализируются» идентификатором сообщения.

### Повторная привязка файла из workspace

**Решение 2026-10-27.** Материализованный файл (`<workspace>/attachments/<name>`) доступен агенту, но
**медиа-файл повторно прочитать нечем**: `read_file` читает только UTF-8 (`engine/tools/fs-read.ts`), а
`ToolResult` умеет отдавать лишь строку — медиа-блоков в результатах тулов нет. Круг замыкает тул
`attach_workspace_file` (`packages/core/src/engine/tools/attach-workspace-file.ts`): файл с диска
загружается в сервис вложений и доставляется в сессию **обычным user-сообщением** с медиа-частью,
поэтому следующий ход получает вложение штатной гидратацией — тот же путь, что у загруженного из UI.

- **Что делает.** `attach_workspace_file(path, name?)` → `AttachmentService.upload` (байты + имя) →
  `AttachmentService.buildMediaPart` (тип части по MIME, sidecar-метаданные) → сообщение `role: user`
  с медиа-частью, `content` = текст + плейсхолдер (`appendMediaPlaceholders`),
  `metadata.source: 'workspace-attachment'` → `deliverUserMessage` (очередь + автоход; тот же
  нотификатор, что у фоновых прогонов). В результате тула — `blob_path`/`mime`/`size`/`message_id`.
- **Границы.** Только внутри рабочего каталога: абсолютный путь, `..` за пределы workspace и побег
  через симлинк отклоняются (`path-utils`, тем же результатом `permission.external_directory_default`);
  путь объявлен в `TOOL_PATH_PARAMS`, поэтому file-паттерны правил (`read`/`external_directory`)
  действуют и здесь. Capability — `file_read` (группы `read`/`file_read`): доступность как у
  read-тулов, в plan-режиме тул не блокируется (файлы проекта он не меняет).
- **Лимиты и allowlist — общие**, второй политики нет: размер проверяется по `stat` **до** чтения
  файла (`attachments.maxBytesPerFile`), MIME/модальности/белый список/SVG-запрет — в
  `AttachmentService.upload` (единственная точка записи байтов); выключенные вложения
  (`attachments.enabled: false`) — отказ до чтения.
- **Доставка обязательна.** Нет `deliverUserMessage` (контекст без очереди) — честный отказ
  `attach.tool.delivery_unavailable`, а не «тихий» успех: файл загружен, но модель его не увидит.
  Ссылка на объект пишется в `blob_refs` (`ownerKind: 'message'`) — иначе GC счёл бы объект сиротой
  по TTL; сбой учёта ссылки привязку не отменяет (best-effort).
- **Text-only модель.** Вложение сохраняется как обычно, а гидратация отбрасывает его по модальности:
  модель получает штатный блок `[ATTACHMENTS NOT DELIVERED]` с путём в workspace (§«Отброшенное
  вложение не теряется») — то есть честное «не доставлено», а не молчаливую потерю.

### Сохранение вложения в workspace

**Решение 2026-10-27.** Доставленное вложение живёт **только** в blob-хранилище: в сообщении лежит
ссылка (`MediaPartData.blobPath`), байтов там нет. Материализация (§«Отброшенное вложение не
теряется») касается лишь **отброшенных** файлов, агенту же нужен и доставленный оригинал — например,
чтобы прогнать его через shell (`pdftotext`, `ffprobe`), положить в репозиторий или обработать
скриптом. Тул `save_attachment` (`packages/core/src/engine/tools/save-attachment.ts`) выгружает
вложение текущей сессии в рабочий каталог:

- **Поиск — только в текущей сессии.** Источник — `messages[].parts[]` сессии `ctx.sessionId`
  (`ctx.extra.sessionManager.getSession`); медиа-части (`image`/`audio`/`video`/`file`) с валидным
  `data {blobPath, sha256, mime, size, name?}`. Селектор: `sha256` — точное совпадение;
  `name` — по имени файла (совпадений больше одного → **ошибка** `attach.tool.ambiguous` со списком
  `name (sha8, messageId)` и подсказкой передать `sha256`, а не «первое попавшееся»); ничего не
  задано — **последнее** медиа-вложение сессии. Нет вложений — `attach.tool.no_attachment`, нет
  совпадений — `attach.tool.not_found`.
- **Только объекты вложений.** `blobPath` обязан быть из `attachments/` (проверка в туле и в
  `AttachmentService.resolve`/`read`): логи процессов, артефакты и прочие blob'ы через этот контур
  не выгружаются — иначе тул стал бы универсальным читателем хранилища.
- **Куда.** `path` — относительный путь в workspace (по умолчанию `attachments/<name|sha8>`; имя
  санитайзится общей функцией `sanitizeAttachmentName`). Родительские каталоги создаются;
  containment — как у `attach_workspace_file` (`path-utils`: абсолютный путь, `..` и побег через
  симлинк → отказ), путь объявлен в `TOOL_PATH_PARAMS`, поэтому file-паттерны правил действуют.
- **Без перезаписи.** Байты пишутся потоком во временный файл `.tmp-<uuid>` того же каталога и
  публикуются **без перезаписи** (`link`, fallback `copyFile` с `COPYFILE_EXCL` — `rename` молча
  заменил бы существующий файл); занятое имя → `attach.tool.exists` с подсказкой указать другой
  `path`, временный файл убирается в любом исходе. Лимитов размера нет (файл уже принят
  `attachments.*`), проверяется только непустота объекта.
- **Права.** Capability `file_write` (это запись в workspace), группа записи — plan-режим тул
  блокирует (ADR-025/ADR-029). Результат — `{content: attach.tool.saved, metadata: {path, blob_path,
  sha256, mime, size}}`; ошибки — ключи `attach.tool.*` (ADR-041).

### Отправка файла в ответе (`send_attachment`)

**Решение 2026-10-27.** Обратное направление к `save_attachment`: файл из workspace уходит
**получателю ответа** — во внешний канал (Telegram/VK) он попадает как вложение ответа, потому что
шлюз раздаёт только `stream.done.attachments`. Тул `send_attachment`
(`packages/core/src/engine/tools/send-attachment.ts`):

- **Файл из workspace.** `path` — относительный путь; containment как у `attach_workspace_file`
  (`path-utils`: абсолютный путь, `..` и побег через симлинк → отказ), путь объявлен в
  `TOOL_PATH_PARAMS`, поэтому file-паттерны правил действуют. Capability `file_read`, группа `read`:
  workspace не мутируется, plan-режим тул не блокирует.
- **Проверки до чтения.** `attachments.enabled`, `stat` (файл существует, это файл, `0 < size ≤
  attachments.maxBytesPerFile`); MIME/модальность/белый список — в `AttachmentService.upload`
  (единственная точка записи байтов). `name` — имя для получателя (по умолчанию `basename`).
- **Не отправка, а очередь.** Часть (`image|audio|video|file` по MIME) складывается в
  **коллектор хода** (`ctx.extra.outboundAttachments`, создаётся в `_processMessage`), а к
  сообщению её добавляет финализация: `saveAssistantMessage` собирает `parts` = текст **+**
  накопленные медиа-части, поэтому они попадают и в историю, и в `stream.done.attachments`
  (через `collectOutboundAttachments`). После сохранения — `blobRefs.add({ownerKind:'message',
  ownerId: <id сообщения>})` (best-effort): иначе GC удалил бы объект по TTL.
- **Один ход, никаких «полуотправок».** Части живут ровно один ход: ошибка/отмена до финального
  сохранения ничего не отправляет (объект остаётся в blob без ссылки и вычищается pruner'ом),
  промежуточные tool-chain сообщения вложений не несут.
- **Ошибки** — ключи `attach.tool.*` (ADR-041): `not_found`, `not_a_file`, `too_large`, `disabled`,
  `unrecognized` (MIME не распознан/запрещён, пустой файл), `deps_unavailable` (нет сервиса
  вложений или коллектора — «тихий» успех недопустим); успех — `attach.tool.queued` с `metadata
  {path, blob_path, mime, size, name}`.

### Медиа из инструментов (`ToolResult.attachments`)

**Решение 2026-10-27.** Инструмент, который получил медиа (первый — `web_fetch` с
`include_media`), **не** возвращает байты в `content` (это строка: бинарь превратился бы в мусор
в контексте) и **не** пишет их сам: объект кладётся в blob через `AttachmentService`, а в
результате тула появляется аддитивное поле `ToolResult.attachments: ToolAttachmentRef[]`
(`{blobPath, sha256, mime, size, name?}`, `packages/shared/src/types/tools.ts`). Оркестратор
вставляет ссылки в **текущий** ход, поэтому модель видит вложение уже на следующей итерации Tool
Use, а не на следующем ходу.

**MCP-инструменты (протокол исполнителя 5).** Инструмент с MCP-стороны тоже приносит медиа:
`McpClient` (stdio) и `ExecutorMcpClient` (remote, ответ `POST /mcp/call`) раскладывают `content`
на текст и нетекстовые блоки (`image`/`audio`/`resource.blob`) в `McpToolResult.attachments`
(base64 без `data:`-префикса; транспортные капы — 25 МиБ на файл и 20 МиБ на вызов, при `isError`
не собираются), а `McpManager` грузит байты через `AttachmentService.upload` и отдаёт
`ToolResult.attachments` ссылками (дедуп по `blobPath`). Дальше действует **штатный шов**
`ChatOrchestrator._injectToolAttachments` — тот же, что у `web_fetch`: блобы пишет только control
plane, исполнитель их не знает. Исполнитель протокола ≤ 4 поля `attachments` не отдаёт — результат
остаётся текстовым, вызов не падает ([ADR-077](./adr-077-runtime-toolchain.md) п. 9).

- **Шов и проверка ссылок.** Тул отдаёт **ссылку**, не байты. Оркестратор валидирует каждую
  ссылку (`isToolAttachmentRefValid`): `blobPath` строго под `attachments/` (`isAttachmentPath`,
  без `..`), `sha256` — ровно 64 hex, `mime` непустой, `size > 0`, `name?` — строка. Невалидная
  ссылка отбрасывается с предупреждением (`ATTACHMENTS`), текст результата тула модель всё равно
  получает. Это граница недоверия: MCP-сервер/плагин/веб-контент не могут подсунуть модели
  произвольный объект (лог процесса, артефакт, чужое вложение).
- **Порядок сообщений.** `ChatOrchestrator._injectToolAttachments` вызывается на границе
  итерации Tool Use: **после** того как все результаты итерации попали в `currentMessages`
  (накопленные `allToolCalls` с полем `iteration`), и **до** следующего LLM-вызова. В запросе
  порядок строго `assistant(tool_use) → tool(tool_result) → user(media)`. Anthropic собирает
  `tool_result` итерации в **одно** user-сообщение (буфер в `_formatMessages`), поэтому
  media-реплика идёт отдельным сообщением строго после буфера — пары `tool_use`/`tool_result`
  не рвутся (`orchestrator-tool-attachments.test.ts`, кейс «Anthropic: media-реплика идёт после
  user(tool_result)»).
- **История и живые события.** На каждое принятое вложение создаётся отдельное сообщение:
  `role: user`, `author: 'Tool'`, `content` из плейсхолдеров (`appendMediaPlaceholders` →
  `[image: name]`), `metadata {source: 'tool-attachment', tool, call_id}`. Оно персистится
  (`SessionManager.addMessage`) и публикуется в канал сессии (`message.added` +
  `session.updated`): чат показывает вложение сразу, без перезагрузки. В `blob_refs` добавляется
  ссылка `{ownerKind: 'message', ownerId}` (best-effort) — иначе GC счёл бы объект сиротой.
- **Гидратация — тот же шов, что у истории.** Ссылка маппится в LLM-сообщение
  (`sessionMessagesToLlm`) и гидрируется `hydrateAttachments` оркестратора: модальности модели
  хода (`ModelConfig.modalities`), `attachments.modalityModels`/`derive` для text-only моделей,
  материализация в workspace и блок `[ATTACHMENTS NOT DELIVERED]` — ровно те же правила, что для
  пользовательских вложений. Байты модели сессии не уходят, если она модальность не принимает:
  в диалог попадает производный текст aux-модели (`derive`). Ошибка чтения/гидратации ход не
  роняет: модель видит хотя бы плейсхолдер, в лог — предупреждение.
- **Бюджет хода.** Не более `MAX_TOOL_ATTACHMENTS_PER_TURN = 4` вложений за **ход** (не за тул) и
  суммарно не более `attachments.maxBytesPerMessage`; не задано — `DEFAULT_TOOL_ATTACHMENT_MAX_BYTES`
  (20 МиБ — как общий предел base64-вложений запроса). Порядок — порядок результатов итерации;
  дубли по `blobPath` схлопываются (один объект из двух тулов — одно вложение); лишнее и
  превышающее бюджет отбрасывается с логом (модель всё равно видит текст результата). Предел
  защищает контекст: один `web_fetch` по десяти URL не должен раздувать промпт.
- **`isError` и отказы.** Результат с `isError: true` вложений не даёт (результат не считается
  доставленным). Отмена, ask-deny и ролевой отказ следующую итерацию не запускают — инъекции нет.
- **Безопасность.** SSRF — на туле: `web_fetch` ходит через `fetchWithEgressGuard`/`egressFetch`
  (ADR-099), т.е. медиа скачивается только с разрешённого адреса. Размер ограничен **до** чтения
  (`content-length`) и потоковым капом (`attachments.maxBytesPerFile`), затем повторно проверяется
  `AttachmentService` (размер, MIME по сигнатуре, модальности, allowlist, запрет SVG). IPI: текст
  результата тула идёт по обычной матрице доверия (`applyPolicy`/обёртка контента), а **байты
  вложения не сканируются и не обфусцируются** — как и пользовательские вложения (§«Провайдеры и
  gateway»); имя файла санитайзится при материализации.
- **Assistant-медиа в контекст не идёт.** Гидратация собирает вложения только из `role: user`;
  медиа в assistant — исходящее (`stream.done.attachments`, `send_attachment`) и провайдеру не
  отправляется (OpenAI такие части отвергает). Media-реплика тула — `user`, поэтому проходит
  штатно.

## Модальности входа модели

**Решение 2026-10-27: единственный источник истины — каталог провайдера при синхронизации моделей.**

- `POST /api/v2/models/fetch` забирает каталог провайдера (`architecture.input_modalities` и
  `architecture.modality`, одинаково у OpenAI- и Anthropic-совместимых эндпоинтов) и пишет результат в
  `ModelConfig.modalities` (парсер — `parseArchitectureModalities`, `packages/core/src/providers/base.ts`).
- Ручной override — `POST /api/v2/models` (`modalities: ['text','image',…]`, `null` — сброс). Он же
  остаётся способом задать модальности там, где каталог их не сообщает.
- Захардкоженный справочник модальностей (`KNOWN_MODEL_MODALITIES` / `resolveModelModalities` /
  `DEFAULT_MODEL_MODALITIES` / `MODALITY_KEYS_BY_LENGTH` в `packages/shared/src/model-metadata.ts`)
  **удалён**: актуализировать его некому, а поиск по «самому длинному префиксу» давал неверные ответы —
  vision-модель без ключа в справочнике выглядела текстовой, и её вложения молча терялись.
  Тип `AttachmentModality` оставлен (конфиг модели, схемы, провайдеры).
- `GET /api/v2/models` отдаёт `modalities` **только если они заданы**; отсутствие поля в JSON и есть
  «модальности неизвестны» (фоллбэка `['text']` нет).
- Гидратация (`packages/core/src/engine/attachments/hydrate.ts`) при неизвестных модальностях
  **не фильтрует**: вложение уходит провайдеру как есть, а ошибку непринятого типа возвращает провайдер и
  видит пользователь. Тихая потеря вложения недопустима — это и был баг, из-за которого справочник удалён.
- UI предупреждает о несовместимом вложении только при **известных** модальностях (`models[].modalities`
  есть и не пуст); поля нет — гейт не применяется, отправка не блокируется.

## Модели обработки по модальностям (aux-модели)

**Зачем.** Модель сессии может не принимать модальность (текстовая модель и картинка). Прежде
единственным исходом было «вложение отброшено с путём в workspace» (§«Отброшенное вложение не
теряется»). Владелец может назначить модель **обработки** для семейства: вложение обрабатывается
ею, а в диалог попадает **текстовый результат** — модель сессии остаётся прежней.

**Подход — по образцу Hermes Agent** (`tmp/refs/hermes-agent-main`: `website/docs/user-guide/configuring-models.md`
§Auxiliary, `agent/image_routing.py`, `tools/vision_tools.py`): основная модель не подменяется; если она
не принимает модальность, изображение уходит aux-модели, а в контекст инжектится текстовое описание;
aux-модели задаются конфигом `auxiliary.<task>.{provider,model,fallback_chain}`.

Отличия решения в Synth:

- **`auto`-значений нет.** У Hermes `auxiliary.vision.provider: auto` означает «основная модель»;
  в Synth нативная поддержка уже определяется по `ModelConfig.modalities` модели сессии, поэтому
  отдельный «auto» дублировал бы её и путал приоритет. Нативный путь **всегда приоритетнее**:
  aux-модель вызывается только когда модель сессии модальность не принимает.
- **Модель сессии не меняется** — ни при обработке, ни при ошибке aux-модели. Диалог, история,
  стоимость и prompt-cache остаются привязаны к модели сессии; aux-вызов — отдельный вызов через
  `GatewayProvider` (ADR-036), его расход виден в метриках/аналитике как отдельный вызов.
- **Нет `fallback_chain`.** Резервная цепочка — это ещё один слой политики; на первом этапе хватает
  одной пары `provider`+`model` на семейство (как у модели по умолчанию инстанса). Понадобится —
  отдельное решение, а не «тихое» расширение конфига.
- **Нет записи = обработка не настроена.** Молчаливого фоллбека на «какую-нибудь» модель нет:
  поведение прежнее — вложение, которое модель сессии не принимает, отбрасывается и
  материализуется в workspace с путём в блоке `[ATTACHMENTS NOT DELIVERED]`.

**Конфиг и API.**

- `attachments.modalityModels` — `Partial<Record<'image'|'pdf'|'audio'|'video', {provider, model}>>`
  (секция `attachments`, env-оверрайдов нет — слишком дробно: только `config.yaml` и runtime);
- runtime-настройки — `GET/PUT/DELETE /api/v2/settings/attachments` (`docs/API_V2.md` §5.21):
  патч `modalityModels` мёржится **по семействам** (runtime дополняет config, перекрывает одну
  модальность, не трогая остальные), `null` (или `{}`) снимает запись семейства, отсутствие ключа
  оставляет базу. `GET` отдаёт `saved` — сохранённый runtime-патч как есть, `defaults` — базу без
  runtime/env. Резолвер (`resolveAttachmentsSettings`) нормализует результат: в эффективных
  настройках `modalityModels` всегда объект (возможно пустой), ключи — в каноническом порядке
  `image|pdf|audio|video`.
- Приоритет источников общий для секции: `SYNTH_ATTACHMENTS_*` (env) > runtime > `config.yaml` >
  defaults. Применяется **сразу** (`restartRequired: false`), как и остальные поля секции.

**Валидация — до записи.** `PUT /settings/attachments` проверяет каждую ссылку по каталогу:
провайдер существует, модель `<provider>/<model>` существует, модальности модели **известны**
(`ModelConfig.modalities` не пусто) и содержат нужное семейство. Иначе `400 VALIDATION_ERROR` с
причиной: какое семейство, какая модель и какие модальности у неё заявлены; для неизвестных
модальностей — просьба выполнить `POST /api/v2/models/fetch` (без этого настройка бесполезна: нельзя
понять, принимает ли модель семейство). Частичных сохранений нет. Значения из `config.yaml`
резолвером **не** валидируются по каталогу (мусор отбрасывается при нормализации) — каталог может
измениться позже, и конфиг не должен из-за этого «ломать» старт.

**Агент видит каталог — тул `list_models`.** Прежде каталог моделей агенту не был виден вообще: он
знал только пару своей сессии, поэтому не мог ни предложить пользователю модель под вложение, ни
выбрать модель саб-агенту (`task({provider, model})` это умеет, но кандидатов взять неоткуда). Тул
(`engine/tools/list-models.ts`, capability `models`, группа правил `read`, в plan-режиме разрешён, к
рабочему каталогу проекта не привязан) отдаёт каталог инстанса (`provider/model` + модальности),
**текущую** пару (настройки сессии — `extra.parentSessionSettings`) и **`defaultFor`** — семейства,
где модель назначена в `attachments.modalityModels`. Без аргументов ответ компактный (текущая модель
+ назначенные aux-модели, без дампа каталога — у routerai 578 моделей); фильтры `modality` (только
модели с **известной** модальностью; модели без `modalities` пропускаются и считаются в хвосте) и
`provider`; `limit` 1..50 (по умолчанию 20). Каталог приходит через `extra.listModels`
(`modelStore.list()`) — пробрасывают обе сборки (`core/server/app/deps.ts`, `backend/app/deps.ts`).

**Реализация (этап 2) — сервис обработки.**

Порядок для вложения, которое модель сессии не принимает: **нативный путь** (модель заявляет
модальность — вложение уходит как есть) → **aux-текст** (назначена модель обработки семейства —
вложение обрабатывается ею, в диалог идёт текст) → **отброс** (обработки нет/не удалась —
вложение отбрасывается и материализуется в workspace, §«Отброшенное вложение не теряется»).

- **Сервис.** `deriveModalityText(input, deps)` (`packages/core/src/engine/attachments/derive.ts`):
  вход — семейство `image|pdf|audio|video`, MIME, имя, `blobPath`, готовая часть
  (`AttachmentService.buildMediaPart`), `provider`/`model` модели обработки, язык;
  зависимости — `chat(parts, prompt)` (aux-вызов через `GatewayProvider`, ADR-036),
  `blobs` (кэш/производные объекты), `hasFfmpeg()`, необязательные `runFfmpeg`/`blobsRead`/
  `promptTemplate`/`log`. Результат — `{ok:true, text, cached}` либо
  `{ok:false, reason:'no_ffmpeg'|'unsupported'|'failed'}`; **исключения не бросаются**:
  сбой aux-модели/`ffmpeg`/чтения объекта — `failed` + запись в лог, вызывающий идёт обычным
  путём отброса.
- **Что уходит aux-модели.** `image` и `pdf` — часть как есть; `audio` — `wav`/`mp3` как есть,
  остальные контейнеры (`ogg`/`m4a`/`flac`/…) транскодируются `ffmpeg` в `wav` 16 кГц mono
  (многие провайдеры принимают только wav/mp3); `video` — **только через кадры**: `ffmpeg`
  извлекает до 5 кадров JPEG (равномерно по длительности, если она известна из
  `part.data.durationMs`; иначе `fps=1`, не более пяти), кадры уходят image-частями, промпт просит
  описать содержимое по кадрам. Видео-входа у провайдеров практически нет, поэтому «отправить
  видеофайл как есть» не используется.
- **Производные объекты.** Транскод и кадры пишутся в blob-хранилище
  (`attachments/.derived/<ключ>.wav|<ключ>-<i>.jpg`): `MediaPartData` **не** несёт base64
  (часть всегда ссылается на объект, ADR-115/ADR-116), поэтому aux-вызов читает их тем же путём,
  что и обычные вложения.
- **Кэш результата.** Ключ — `sha256(blobPath + "|" + provider + "/" + model + "|" + family)` (hex);
  файл — `attachments/.derived/<ключ>.json` формата `{version:1, text, at}`. Перед вызовом кэш
  читается (`cached:true` — aux-модель не вызывается), после успеха — пишется. Битый файл, чужая
  версия и пустой текст — пересчёт; ошибки чтения/записи кэша только логируются и обработку не ломают.
  Кэш общий для объекта (content-addressed путь) и модели обработки, поэтому смена модели семейства
  даёт новый ключ, а повторная отправка того же файла — попадание.
- **Промпт.** `prompts/system/MEDIA_DERIVE.{ru,en}.md` (плейсхолдеры `{modality}`, `{name}`),
  загрузчик — `ContextConfig.getMediaDeriveTemplate(language)` (override
  `{dataDir}/user/system/MEDIA_DERIVE.<lang>.md`, затем встроенный, иначе пустая строка → короткая
  техническая инструкция на английском, канал LLM). Шаблон задаёт разные требования по модальностям:
  описание + весь видимый текст (image), извлечение текста с сохранением структуры (pdf), дословная
  транскрипция с разметкой говорящих (audio), описание по кадрам (video).
- **`ffmpeg` — внешняя зависимость (ADR-078).** В словаре `RuntimeDependency`
  (`engine/tools/runtime-deps.ts`) добавлен `ffmpeg` (отдельный список `MEDIA_RUNTIME_DEPENDENCIES`:
  это не требование встроенного тула, поэтому снимок `RuntimeDeps`/permission-слой не меняются).
  Доступность — `isFfmpegAvailable(execution?)`: проба через **порт** исполнения (ADR-077; в
  split-режиме — по составу пула), кэш по экземпляру порта на 60 с, fail-open, ошибка пробы → `false`.
  `ffprobe` не нужен: длительность берётся из метаданных части. Нет `ffmpeg` → `no_ffmpeg`
  (вложение идёт обычным путём отброса).
- **Модель сессии не меняется** ни при обработке, ни при её ошибке: aux — отдельный вызов,
  история/prompt-cache/стоимость диалога остаются на модели сессии.

**Проводка (native → aux → drop).** Обработка встроена в гидратацию
(`engine/attachments/hydrate.ts`), то есть выполняется ровно перед сборкой запроса к модели сессии:

- для вложения, модальность которого **не входит** в модальности модели сессии (`HydrateOptions.modalities`,
  источник — `ModelConfig.modalities`), вызывается переданный гидратации `derive(...)` — колбэк
  оркестратора (`_buildAttachmentDerive`), который резолвит модель обработки семейства из live-настроек
  `attachments.modalityModels`, поднимает её провайдера (`ProviderFactory` + `toCoreProviderConfig`),
  оборачивает в `GatewayProvider` (ADR-036) и вызывает `deriveModalityText`; в колбэк уходят blob-порт
  (кэш/производные объекты), `isFfmpegAvailable(executionPort)` (проба через порт, ADR-077) и шаблон
  `MEDIA_DERIVE` из `ContextConfig`. Модальности модели **неизвестны** — `derive` не вызывается
  (сравнивать не с чем, поведение прежнее: вложение уходит как есть);
- **успех** (непустой текст) — вложение модели сессии **не отправляется**, а к `content` LLM-сообщения
  дописываются блоки в порядке частей: `\n\n[<family>: <name>]\n<текст>`, без имени — `[<family>]`
  (`[image: plan.png]`, `[pdf]`, `[audio: voice.ogg]`, `[video]`). Текст — как есть, без экранирования
  (это уже результат модели обработки); в `debug` сообщения — счётчик `attachmentsDerived`. Кэш
  результата (см. выше) делает повторную отправку того же файла бесплатной — aux-модель не вызывается;
- **ошибка/пустой ответ** — прежний путь: `reason: 'modality'` + материализация в workspace (ход не
  падает, ошибка только в лог);
- **модель сессии не меняется** ни в одном из исходов: aux-вызов не подменяет провайдера/сессию,
  история/prompt-cache/стоимость диалога остаются привязаны к её модели;
- **учёт стоимости** — aux-вызов пишется в аналитику (`AnalyticsRecorder.recordUsage`) отдельным бакетом
  по осям **aux-модели** (`provider`/`model`) со своим `requests`/стоимостью, поэтому в отчётах он
  виден отдельно и не приписывается модели сессии; счётчики сессии (`Session.inputTokens`/…) и
  `usage` сообщения не трогаются (это не токены её ответа).

**Блок «вложения не доставлены»** (`prompts/system/ATTACHMENTS_DROPPED.{ru,en}.md`) теперь сообщает
модели не только список и причины, но и контекст: `Текущая модель: {model} (принимает: {modalities})`
(`{model}` — `provider/model` модели сессии, `{modalities}` — её модальности через запятую; не заданы —
`—`). В инструкции — что делать, если формат не поддержан: предложить пользователю модель с нужной
модальностью (список — тул `list_models`) или приложить файл из workspace тулом
`attach_workspace_file`. Старые шаблоны без плейсхолдеров работают как раньше (подставляется только
`{items}`).

**Остаток этапа 2.** Заполнение `MediaPartData.transcript` результатом обработки, перенос стоимости
aux-вызова в счётчики сессии/`metadata.usage` сообщения (сейчас — только отдельная запись аналитики),
гибрид (удалённая модель обработки) и равномерные кадры при неизвестной длительности (`ffprobe`).


## API и лимиты

- Загрузка — multipart (`@hono/node-server` уже используется для `/fs/upload`); лимит — из конфига,
  превышение → `413 PAYLOAD_TOO_LARGE`, неизвестный/запрещённый MIME → `415 UNSUPPORTED_MEDIA_TYPE`.
- Имя файла — санитайз (без `..`, без управляющих символов); в `blobPath` имя **не** используется
  (content-addressed), оно живёт только в метаданных части.
- Выдача — потоком; `HEAD` поддерживается (размер и `ETag` без тела).
- Доступ: чужой пользователь → 403, нет объекта → 404 (без утечки существования).

Что берём как есть (поведение):

1. **Модель элемента композера**: `{id, mimeType, filename, size, previewUrl, source, groupId?}`;
   `groupId` склеивает элементы, извлечённые из одного документа (удаление любого — удаляет группу).
2. **Чипы в композере** (`AttachedFilesList`): изображения — превью 64×64, клик открывает галерею
   (перелистывание, клавиатура, `aria-label`), кнопка удаления поверх; прочие файлы — чип с иконкой типа,

3. **Кнопка «прикрепить»** (`ComposerAttachmentControls`): меню (локальные файлы + будущие провайдеры
   контекста), скрытый `<input type="file" multiple accept={ATTACHMENT_ACCEPT}>`; на телефоне — bottom sheet
   (мобильный адаптив ADR-044).
4. **Drag&drop**: чистые хелперы `hasDraggedFiles` / `collectDroppedFiles` / `collectDroppedFileUris`
   (в референсе — поддержка браузерных `File`, VS Code-путей и внутреннего дерева файлов) + оверлей
   «бросить сюда»; повторный дроп дубликатов не создаёт.

   (в референсе — markdown-ссылка на выделение; у нас — через `@`-упоминания файлов проекта).
6. **Клиентская подготовка** (`attachment-files.ts`): определение MIME по содержимому, HEIC→JPEG,
   документы (docx/pptx/xlsx/odt/odp/ods) распаковываются на клиенте в текст + встроенные изображения с
   квотами референса (архив ≤ 20 МБ, распаковано ≤ 100 МБ, запись ≤ 25 МБ, XML ≤ 8 МБ, ≤ 5000 записей,
   ≤ 50 изображений, ≤ 20 МБ/изображение и ≤ 40 МБ суммарно, текст ≤ 500 000 символов), тяжёлый
   paste-текст предлагается приложить файлом.
7. **Гейт модальностей**: `getAttachmentInputModality(mime)` → `text|image|pdf|audio|video`;
   `getUnsupportedAttachmentInputs(files, model.modalities.input)`; проверка при добавлении и при смене
   модели/появлении метаданных; предупреждение — тост с перечнем модальностей и имён файлов; блокировка
   отправки несовместимого набора.
8. **Отображение в сообщении** (`MessageFilesDisplay`): компактные чипы/миниатюры, клик — попап:
   текст-подобные файлы показываются как текст (`decodeDataUrlText`), изображения — галерея, остальные —
   скачивание. Это заменяет нам рендер вложений из `content`.
9. **Мелочи, которые в референсе сделаны и которые легко потерять**: дедуп по `name+size`, три попытки
   подготовки при коллизии имён, сохранение набора вложений при переключении черновика/сессии
   (`attachmentDrafts`), «вложения восстанавливаются» при неудачной отправке, `aria-label` на всех
   действиях, ленивая загрузка превью.

Чем отличаемся из-за серверного хранения:

| Референс (OpenChamber) | Synth |
|---|---|
| байты остаются в браузере (`dataUrl`) и уходят провайдеру в промпте | файл **загружается** на `POST /sessions/:id/attachments`, в сообщение попадает `blobPath` |
| сразу готово к отправке | состояние `uploading → ready → error`; чип с прогрессом, повтор при ошибке |
| `file://` и server-path как «вложение» | `blobPath` + API-URL для превью (`/api/v2/sessions/:id/attachments/:partId`) |
| документы распаковываются и уходят текстом | так же: извлечённый текст — отдельная `text`-часть/`transcript`, байты документа — `file`-часть |
| модель-гейт по `modalities.input` приходит с сервера OpenCode | модальности — поле конфига модели (`ModelConfig.modalities`: каталог провайдера при синхронизации / ручной override), отдаётся в `GET /models`, когда задано; нет — гейт не применяется |

Что **не** берём из референса: вкладки-гости, трекеры/issues/PR как вложения, VS Code-интеграцию,
`file://`-пути (у нас — workspace и `@`-упоминания), dictation-режим (голосовой ввод — отдельная задача
после 0.13).

## Лимиты и безопасность

- MIME — по сигнатуре содержимого; `image/svg+xml` запрещён (XSS), HTML-файлы отдаются только как
  `attachment`/`text`-просмотр.
- **Приватность: оригиналы хранятся, метаданные срезаются на отправке** — детали в §«Приватность».
- Обфускация секретов на бинарь **не работает** — фиксируется в ADR-036 и в UI-подсказке.
- Аудит загрузок/выдач — через существующий контур безопасности (без новых журналов).
- Метрики — `synth_attachments_*` (см. ADR-094: имена и лейблы — контракт).

## Приватность

В blob-хранилище (`{dataDir}/blobs`, доступ только серверный — прямой ссылки наружу нет) лежат
**оригинальные** байты: `upload` их не меняет, `sha256`/`size`/дедуп считаются по сырым. Очистка
метаданных (`stripMetadata`: JPEG — `APP1`/`APP2`/EXIF/IPTC/XMP, PNG — `eXIf`/`tEXt`/`iTXt`/`zTXt`/
`tIME`) выполняется **только на границе отправки провайдеру** — в гидратации вложений
(`engine/attachments/hydrate.ts`, `deps.read` → `LLMAttachment.base64`) и в aux-вызове оркестратора
(`_buildAttachmentDerive`). Скачивание через API (`GET /sessions/:id/attachments/:partId`),
материализация в workspace и staging-объекты хранят/отдают оригинал.

Намеренная асимметрия: очистка на записи теряла бы данные пользователя безвозвратно, а провайдеру
метаданные не нужны. Битая или недописанная структура не «чистится наполовину» — возвращается как есть.

## Границы (вне объёма)

- **Видео-ввод** нативно (кадры/аудио-дорожка) — отдельная задача; в 0.13 видео принимается как `file`.
- **ASR/OCR/sharp** — предобработка на сервере не входит (новые зависимости — инвариант 12);
  текстовые расшифровки приходят от клиента (документы) или от провайдера. Исключение — внешний
  `ffmpeg`: это не npm-зависимость, а опциональная программа окружения (транскод аудио и кадры видео
  в сервисе обработки, §«Модели обработки по модальностям»); нет программы — вложение идёт обычным
  путём отброса.
- Смена физического backend'а blob-хранилища — не входит (см. ADR-116: байты на томе).

**Остаток:**

- гибрид (`remote/transfer.ts`, publish/fork) байты вложений не переносит — медиа-части на удалённой
  стороне остаются с неразрешённым `blobPath`;
- черновики вложений не переживают переключение сессии (`attachmentDrafts` из §«UI»);
- предобработка вне объёма: ASR/OCR (извлечение кадров и конвертация аудио — только через внешний
  `ffmpeg` в сервисе обработки, `derive.ts`); видео без `ffmpeg` не обрабатывается;
- уборка `<workspace>/attachments/` не автоматизирована — каталог живёт как обычные файлы проекта;
- `transcript` заполняется только тем, что пришло с клиента/провайдера.

## Открытые вопросы

Решено при реализации: вложения в промпте — `attachments: string[]` (blob-пути); квота сессии считается
по сумме `size` медиа-частей истории; оригиналы хранятся в blob, а EXIF/метаданные срезаются на
границе отправки провайдеру (при загрузке не теряются). Остаются:

1. Где считать стоимость медиа: в `usage` провайдера (если он её отдаёт) или оценкой по размеру?
2. `transcript` для аудио без серверного ASR — только то, что пришло с клиента/провайдера?
3. Как переносить байты вложений в гибриде (publish/fork, `remote/transfer`)?

## История

- 2026-10-27 — принято как ADR-115 из [PROP-085](./prop-085-multimodal-input.md). Зафиксировано: байты на
  томе через `BlobStore` (не в БД), `blob_refs` для дедупа и GC, аддитивное `attachments` в LLM-контракте,
  UI по образцу OpenChamber (`tmp/refs/openchamber`), видео/ASR/OCR — вне объёма.
- 2026-10-27 — **этап 2: обработка медиа.** Добавлены сервис `deriveModalityText` (aux-модель →
  текст, модель сессии не меняется), промпты `MEDIA_DERIVE.{ru,en}.md` и загрузчик
  `getMediaDeriveTemplate`, детект `ffmpeg` (`isFfmpegAvailable`, ADR-078), кэш результатов в blob
  (`attachments/.derived`). Ограничения: аудио только wav/mp3 или через `ffmpeg`; видео — только
  кадрами; без `ffmpeg` — обычный отброс вложения; проводка в оркестратор — следующий шаг.
- 2026-10-27 — **уточнение по модальностям** (по факту бага «вложение теряется молча»): захардкоженный
  справочник (`KNOWN_MODEL_MODALITIES`/`resolveModelModalities`/`DEFAULT_MODEL_MODALITIES`) удалён;
  единственный источник истины — каталог провайдера при синхронизации моделей → `ModelConfig.modalities`
  (+ ручной override). `GET /api/v2/models` отдаёт `modalities` только при заданном значении; неизвестные
  модальности → вложения **не** фильтруются (ошибку непринятого типа возвращает провайдер).
- 2026-10-27 — **отброшенное вложение сохраняется в workspace** (решение владельца): при `modality`/`limit`/
  `unavailable` файл материализуется в `<workspace>/attachments/<name>` (атомарно, дедуп по содержимому,
  существующее не перезаписывается) и модели сообщается путь в блоке `[ATTACHMENTS NOT DELIVERED]`;
  шаблон блока — системные промпты `packages/core/prompts/system/ATTACHMENTS_DROPPED.{ru,en}.md`
  (плейсхолдер `{items}`, override `{userDataDir}/user/system/`), нет шаблона — техническая строка на
  английском. Захардкоженные русские строки из `hydrate.ts` убраны. Без workspace — без пути.
- 2026-10-27 — **повторная привязка файла из workspace** (`attach_workspace_file`): материализованный
  файл нельзя прочитать через `read_file` (UTF-8), а `ToolResult` не несёт медиа — поэтому тул
  загружает файл в сервис вложений и доставляет его **user-сообщением** через очередь
  (`deliverUserMessage`), и следующий ход получает вложение штатной гидратацией. Границы: только
  workspace (абсолютный путь/`..`/симлинк — отказ), лимиты и allowlist — общие `attachments.*`
  (размер по `stat` до чтения), запись `blob_refs` для нового сообщения; text-only модель получает
  обычный блок `[ATTACHMENTS NOT DELIVERED]`. Шаблон блока обновлён: текстовые файлы — `read_file`,
  PDF/изображения/аудио/видео — `attach_workspace_file` либо shell-обработка (`pdftotext`, OCR,
  `ffprobe`), неподдержанный формат — сообщить пользователю.
- 2026-10-27 — **сохранение вложения в workspace** (`save_attachment`): доставленное вложение
  доступно агенту только по ссылке в blob, поэтому тул ищет медиа-часть в **текущей сессии**
  (`sha256` / `name` / последнее), читает объект через `AttachmentService` и кладёт файл в workspace
  (по умолчанию `attachments/<name|sha8>`). Неоднозначное имя — ошибка со списком `name (sha8,
  messageId)` и подсказкой `sha256`; containment как у `attach_workspace_file`; публикация без
  перезаписи (`link`/`COPYFILE_EXCL`), занятое имя → `attach.tool.exists`. Группа записи (plan-режим
  блокирует), capability `file_write`.
- 2026-10-27 — **модели обработки по модальностям** (этап 1: конфиг + API, по образцу Hermes Agent):
  `attachments.modalityModels` (`provider`+`model` на семейство), runtime-патч с `null` для снятия
  записи, валидация по каталогу до записи; модель сессии не меняется, нативный путь приоритетнее,
  нет записи — прежнее поведение (отбрасывание с путём). Обработка медиа — следующий этап.
- 2026-10-27 — **проводка обработки в гидратацию** (native → aux → drop): `HydrateOptions.derive`
  (колбэк оркестратора строит aux-провайдера из live-настроек `modalityModels`, обёртывает
  `GatewayProvider`, читает части через `AttachmentService`/blob-порт, `ffmpeg` — проба через
  `ExecutionPort`); успех — текст в `content` LLM-сообщения блоками `[<family>: <name>]`, вложения
  не отправляются, `debug.attachmentsDerived`; ошибка — прежний отброс с материализацией. Блок
  `[ATTACHMENTS NOT DELIVERED]` получил `{model}`/`{modalities}` и подсказку про `list_models`/
  `attach_workspace_file`; расход aux-вызова — отдельная запись аналитики по осям aux-модели.
  Остаток: `transcript`, стоимость в счётчиках сессии, гибрид, кадры при неизвестной длительности.
