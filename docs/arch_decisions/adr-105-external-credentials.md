# ADR-105: Внешние доступы — единый слой доступа к внешним сервисам (OAuth-коннекторы)

> **Статус:** ⚠️ Частично — Ф0–Ф3 реализованы (контракты `ExternalCredential`/`ExternalCredentialRepository`,
> шифрование at-rest `enc:v1:`, маскирование, file/memory/PostgreSQL-реализации с миграцией `012`, контрактный
> suite, поле `auth` в схеме MCP-сервера; OAuth-клиент — PKCE/refresh/revoke через `egressFetch`,
> host-binding секретных заголовков; Ф3 — подстановка access-токена в MCP-транспорт с refresh по `401`,
> запрет plaintext-заголовков и миграция записей реестра, каталог `oauth.providers`, право привязки доступа
> к коннектору на границе); остаток — Ф4 (API/UI «Доступы», журнал credential-операций, ротация мастер-ключа,
> бэкап и перенос).

## Контекст

Креды MCP-сервера лежали **открытым текстом**: `headers`/`env` в `mcpServerConfigSchema` — свободные
словари, а запись реестра сериализуется целиком. Токен можно было положить в `config.yaml` или реестр, и он
попадал в бэкап, логи и выдачу реестра. Пользовательского OAuth не было вовсе: подключить внешний сервис
«по коду авторизации» было нечем (OAuth-клиент в ядре жил только для логина в гибриде). Два прецедента
секретов в коде показывают, что одной модели «ключа» мало: `service-key`/`binding-key` **хешируются**
(секрет только проверяется), а signing-секрет вебхуков и OAuth-токен нужны **в исходном виде** — их
подставляет транспорт. OAuth-токен вдобавок имеет срок, статус и отзыв: это ресурс с временем жизни.

## Решение

Выделить в Synth **слой внешних доступов** — сущность `ExternalCredential` (`packages/shared/src/types/external-credentials.ts`):

- **Доступ — ресурс с временем жизни**: статус `active | expired | revoked | error`, срок `expiresAt`,
  отзыв `revokedAt` (необратимый: обновление токенов отозванный доступ не «оживляет»).
- **At-rest — шифрование мастер-ключом**, формат `enc:v1:` (AES-256-GCM, `security/crypto.ts`); хеш
  неприменим — токен нужен в исходном виде, чтобы подставить его в заголовок. Хранение —
  `{dataDir}/secrets/oauth/` (каталог `0700`, файл `0600`): обычный бэкап без `--with-secrets`
  исключает только `secrets/`, поэтому токены не должны лежать в обычном JSON.
- **Запись — только через порт** `ExternalCredentialRepository` (ADR-096): реализации file/memory/
  PostgreSQL (миграция `012`) и контрактный suite.
- **Наружу — только метаданные** (`ExternalCredentialMeta`) с маской секрета (`mask:<16 hex>`); значение
  токена не отдаётся никогда. `reveal()` — единственный путь к расшифрованному токену, и только для
  подстановки в транспорт: **токен подставляет транспорт, агент и модель его не видят**.
- **Коннектор ссылается на доступ по id**: `auth: { kind: 'credential', credentialId }` в
  `mcpServerConfigSchema` — сам токен в реестре/конфиге не лежит.
- **Владелец — часть записи**: `owner.kind` = `user | instance | local`; доступ может быть инстансным
  (выдал `ADMIN`/`LEAD`) и не принадлежать ни одному пользователю.
- **OAuth-клиент**: Authorization Code + PKCE (S256, RFC 7636), refresh (RFC 6749 §6) с single-flight
  и CAS по `refreshEnc`, revoke (RFC 7009, best-effort); `invalid_grant` → `status:'error'` — нужна
  явная переавторизация, молчаливый отказ коннектора недопустим. Сеть — **только** `egressFetch`
  (ADR-099); `client_secret` — env `SYNTH_OAUTH_<PROVIDER>_CLIENT_SECRET` или файл
  `{dataDir}/secrets/oauth/<provider>.client_secret` (`0600`), в конфиге его нет.
- **Host-binding секретных заголовков**: `bindSecretHeaders` в `engine/net/egress-guard.ts` — при
  редиректе на другой origin `authorization`/`proxy-authorization`/`x-api-key`/`cookie` не пересылаются.
- **Токен подставляет транспорт** (Ф3): коннектор с `auth: { kind: 'credential' }` получает
  `Authorization: Bearer <token>` в **каждом** HTTP-запросе из порта доступов (`reveal()`); значение токена
  не попадает в конфиг/реестр, логи и тексты ошибок. Ответ `401` обновляет токен (refresh) и повторяет
  запрос — **ровно один refresh на запрос**.
- **Plaintext-секрет в коннекторе запрещён** (Ф3): `authorization`/`proxy-authorization`/`x-api-key`/`cookie`
  в `headers` — 400 `MCP_SECRET_HEADER_FORBIDDEN` (API реестра и `probe`); существующие записи реестра
  переводятся на новую схему явной миграцией (одноразовая, идемпотентная).
- **Право привязки — на границе** (Ф3): привязка доступа к коннектору выдаёт коннектору право действовать
  от имени доступа, поэтому проверяется guard'ом (инвариант 16): свой доступ — его владелец; инстансный —
  `ADMIN`/`LEAD`; проектный — участник проекта с правом изменения содержимого; нет доступа — 404, нет права —
  403.
- **Каталог OAuth-провайдеров** (Ф3): `oauth.providers` в конфиге — описания провайдеров (данные), из них
  строится клиент для refresh; `client_secret` — только env/файл.

## Альтернативы

- **Хешировать секрет** (как service-key/binding-key) — отклонено: токен нужен в исходном виде для
  подстановки в заголовок; хеш подстановку делает невозможной.
- **Держать `Authorization` в `headers` конфига/реестра MCP** — отклонено: это и есть дыра (секрет в
  конфиге, бэкапе и логах). Запрет таких заголовков при записи реестра — **реализовано** (Ф3, 400
  `MCP_SECRET_HEADER_FORBIDDEN` + миграция записей).
- **Внешний secret-manager** (Vault, AWS Secrets Manager) — отклонено на этом этапе: своя криптография
  не дублируется (шифрование только core-хелперами), а self-host-инстанс не должен зависеть от внешнего
  сервиса; точка подключения остаётся — порт хранилища.
- **Отдельный OAuth-сервис вне ядра** — отклонено: доступ — часть реестра инстанса, он обязан жить в
  слое хранения (ADR-096) и проходить тот же цикл бэкапа/переноса.

## Последствия

- **Плюсы:** секреты внешних сервисов не лежат в конфиге и не уезжают в бэкап по умолчанию; у доступа
  явный жизненный цикл (срок, статус, отзыв, переавторизация); агент токен не видит.
- **Минусы:** ещё один порт хранилища и ещё один секрет в `secrets/`; выдача и ротация требуют отдельного
  API/UI (Ф4) — до этого доступ заводится только кодом.
- **Остаток (Ф4):** API/UI «Доступы», журнал credential-операций, ротация мастер-ключа, правила бэкапа и
  переноса.
