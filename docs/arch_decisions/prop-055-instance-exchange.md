# PROP-055: Обмен между инстансами Synth

> **Статус:** 🧩 Предложение (vision) — Обмен между инстансами Synth: идемпотентный upsert/дельта-синхронизация, peer-auth, live-сессии
> **Дата:** 2026-10-08
> **Источник:** перенесено из `AD-DRAFTS.md` (D10; черновик 2026-09-16); Roadmap, идея 10.
> **Связано:** [ADR-042](./adr-042-hybrid-mode.md), [ADR-043](./adr-043-unified-identity-login.md),
> [ADR-045](./adr-045-hybrid-server-profiles.md), [ADR-033](./adr-033-session-branching-merge.md),
> [PROP-032](./prop-032-history-storage-postgresql.md), [PROP-047](./prop-047-memory-gbrain.md),
> [ADR-052](./adr-052-public-api-platform.md), [PROP-073](./prop-073-client-integrity-hybrid.md),
> [PROP-081](./prop-081-hybrid-policy-leak-protection.md).

**Решение:** обмен данными между **равноправными инстансами** Synth (а не только между клиентом и
центральным хабом): идемпотентный upsert и дельта-синхронизация сущностей, peer-auth, обмен «памятью»
и live-сессии. Гибрид ([ADR-042](./adr-042-hybrid-mode.md)) — это связка «локальный core → сервер»
(агрегация миров и проксирование); здесь добавляется второй режим — **инстанс ↔ инстанс**
(два standalone-core, два сервера или гибридный узел и узел), с явным протоколом синхронизации поверх
API v2.

## Контекст

Сегодня модель распространения данных Synth — **однонаправленная**:

- Гибрид ([ADR-042](./adr-042-hybrid-mode.md)): локальный `synth serve` агрегирует локальный и удалённый
  миры; удалённые сессии исполняются сервером; id удалённых сущностей — `remote:<uuid>`, маршрутизация по
  `origin` (инвариант №7 корневого `AGENTS.md`).
- Профили и credentials ([ADR-045](./adr-045-hybrid-server-profiles.md),
  [ADR-043](./adr-043-unified-identity-login.md)): один локальный core подключается к любому серверу на
  лету; credentials — единый мульти-серверный файл.
- Перенос между мирами — `publish` (локально → сервер) и `fork` (сервер → локально)
  (`packages/core/src/remote/transfer.ts`): проект + сессии (история) + файлы, через backend
  `GET /sessions/:id/export` и `POST /sessions/import`. Импорт **создаёт новую сессию**
  (перевыпуск id; вложенные ссылки `parentId`/`references` переписываются по mapping).

Чего нет: **двустороннего** обмена, дельта-синхронизации (сейчас — полный перенос), авторизации
инстанс↔инстанс и обмена памятью. Запросы на такой сценарий: несколько команд/площадок, у каждой свой
инстанс, нужно делиться сессиями/проектами/памятью без выгрузки в общий hub.

## Детали

### 1. Идемпотентный upsert

Синхронизация опирается на **стабильные идентификаторы** сущностей и идемпотентную операцию
`upsert`, а не на «создать заново». Это прямое развитие текущего `import` (который всегда создаёт
новую сущность) в режим «слияние по id». Основа — существующая логическая модель ветвления/слияния
([ADR-033](./adr-033-session-branching-merge.md)).

- Сущности: проекты, сессии, сообщения, план/ToDo, скиллы проекта.
- Конфликты разрешаются по метке версии (`updatedAt` и/или монотонный `seq`) и правилу владельца/приоритета.
- Для неизменяемых частей (сообщения) — append-only семантика; для изменяемых (проект, настройки) —
  last-write-wins с фиксацией источника.

### 2. Дельта-синхронизация

Вместо полного экспорта — обмен **дельтой** по курсору (watermark/`since`): приёмник запрашивает
изменения с последней известной позиции, отправитель отдаёт пачку и новый курсор. Требует:

- курсора по каждой синхронизируемой сущности/потоку;
- хранения состояния синхронизации на обоих инстансах (JSON до [PROP-032](./prop-032-history-storage-postgresql.md));
- идемпотентности повторов (at-least-once доставка).

### 3. Peer-auth

Пользовательские токены/сессии ([ADR-043](./adr-043-unified-identity-login.md)) не подходят для
машино-машинного доверия. Нужен отдельный слой **сервисных токенов инстанс↔инстанс**:

- выпуск/отзыв сервисного токена на инстансе-приёмнике;
- скоупы (какие сущности/проекты можно синхронизировать);
- проверка на стороне сервера (клиент недоверенный — ср. [PROP-073](./prop-073-client-integrity-hybrid.md));
- аудит обмена как отдельный тип события.

### 4. Обмен «памятью»

Целевой потребитель — память Synth ([PROP-047](./prop-047-memory-gbrain.md)): синхронизация индексов,
графов и артефактов памяти между инстансами (в т.ч. «company brain» нескольких площадок). Требования к
формату и направлению (push/pull/bidirectional) определяются в PROP-047; здесь фиксируется **канал** и
**протокол** обмена.

### 5. Live-сессии

Наблюдение за сессией другого инстанса в реальном времени (события через мост, по аналогии с
`RemoteEventBridge`, [ADR-042](./adr-042-hybrid-mode.md)). Отличается от статического обмена историей:
поток событий между инстансами, а не пакетный экспорт.

### 6. Протокол

Базовый протокол — **поверх API v2** ([ADR-017](./adr-017-api-v2-hono.md)): новые эндпоинты
синхронизации (pull/push/status), обслуживаемые core-фабриками с RBAC/guard'ами (по образцу
переиспользуемых роутов). Связанные политики — гибридный контроль утечек
([PROP-081](./prop-081-hybrid-policy-leak-protection.md)); платформенный контур — публичная API-платформа
([ADR-052](./adr-052-public-api-platform.md)).

## Статус реализации в коде

**Не реализовано.** Проверено по репозиторию (grep по `packages/**`, исключая `dist/` и `node_modules/`):

- Есть **однонаправленный** гибрид: `packages/core/src/remote/` (`client.ts`, `connection.ts`,
  `event-bridge.ts`, `transfer.ts`, `aggregate.ts`, `credentials.ts`, `session.ts`, `device-flow.ts`),
  `packages/core/src/providers/remote.ts` (`RemoteProvider`), `packages/core/src/profiles.ts`,
  `packages/core/src/server/connection-watcher.ts`.
- Перенос: `transfer.ts` (`syncProjectToRemote` / `forkProjectToLocal`), backend
  `GET /sessions/:id/export` и `POST /sessions/import` (`packages/backend/src/routes/sessions.ts`).
- Событийный мост: `RemoteEventBridge` (`packages/core/src/remote/event-bridge.ts`).
- **Нет**: идемпотентного upsert по id (import всегда создаёт новую сессию), дельта-курсоров,
  сервисных токенов инстанс↔инстанс, обмена памятью, live-сессий между инстансами.

### Требует перепроверки: карта обфускации на приёмнике

Черновик фиксирует риск: `obfuscationMap` **уезжает вместе с историей** при переносе. В коде это
видно — `packages/core/src/remote/transfer.ts` присваивает `session.obfuscationMap` из
`exportData.obfuscation_map ?? exportData.obfuscationMap`, а карта хранится в `Session.obfuscationMap` и
сериализуется в `FileStore` как `obfuscation_map`
(`packages/core/src/storage/file-store.ts`). Карта обфускации — **секрет**
([ADR-036](./adr-036-llm-gateway.md)). Перед реализацией обмена нужно проверить: (а) корректно ли
де-обфусцируются плейсхолдеры на приёмнике; (б) не происходит ли утечка секретов между инстансами
вместе с картой; (в) как это согласуется с политиками
[PROP-081](./prop-081-hybrid-policy-leak-protection.md) и [PROP-073](./prop-073-client-integrity-hybrid.md).

## Открытые вопросы

- Протокол peer-to-peer — только поверх API v2 или отдельный sync-канал?
- Дельта-синхронизация сообщений (seq/`updatedAt`) — стратегия разрешения конфликтов?
- Авторизация инстанс↔инстанс (сервисные токены) — формат, ротация, отзыв?
- Обмен памятью — кто владеет схемой и как совместить с гибридом
  ([PROP-047](./prop-047-memory-gbrain.md))?
- Переносить ли карту обфускации вообще (и как безопасно)?
- Как обмен соотносится с soft-delete ([PROP-074](./prop-074-soft-delete-retention.md))?
