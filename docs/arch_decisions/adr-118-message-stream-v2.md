## Контекст и проблема

У Synth нет модели «ход». Есть плоский список сообщений сессии и поток дельт поверх него. Отсюда шесть наблюдаемых дефектов:

1. **Приём сообщения во время хода держит HTTP-запрос открытым.** `POST /api/v2/sessions/:id/prompt`
   при идущем ходе отвечает `200 text/event-stream` и висит до `stream.done`
   (`packages/core/src/server/routes/sessions.ts`). Контракт приёма и контракт наблюдения за ходом
   склеены в один ответ: подтверждения приёма у клиента нет, а отмена соединения обрывает и его.
2. **Приём инъекции не публикуется.** `mode: 'steer'` (`packages/core/src/queue/processor.ts`,
   `enqueueSteerMessage`) не публикует событие о приёме — только `steer.dropped` при отказе по
   лимиту. В ленте сообщение появляется лишь по `message.injected` в момент применения
   ([ADR-104](./adr-104-mid-turn-steering.md)), то есть разница между «принято» и «применено» не видна.
3. **Порядок в ленте — это порядок записи, а не порядок отправки.** Инъекция персистится внутри
   хода (`packages/core/src/engine/steering/apply.ts`, `packages/core/src/engine/orchestrator.ts`,
   `_applySteerInjections`) и получает `seq` раньше финального assistant-сообщения. UI рисует
   массив в порядке прихода (`packages/ui/src/stores/chatStore.ts`, `GET /:id/messages` отдаёт
   `session.messages` как есть — `packages/core/src/server/routes/sessions.ts`), поэтому вставленная
   реплика пользователя оказывается «внутри» ответа агента.
4. **Стрим и финал — разные объекты в UI.** `streamingBySession` и `messagesBySession`
   (`packages/ui/src/stores/chatStore.ts`) — два параллельных массива; «финал» — это отдельный
   объект, а не тот же, что стримился.
5. **Перезагрузка страницы теряет начало хода.** Assistant-сообщение персистится в финальной фазе
   (`packages/core/src/engine/orchestrator/phases/process-finalize.ts`), а события шины не
   буферизуются: при отсутствии подписчиков событие теряется
   (`packages/core/src/events/bus.ts` — `EVENT LOST`). После reload клиент до финала видит пустоту.
6. **`message.queued` утекает содержимое.** Событие уходит в канал сессии с полным текстом сообщения
   и автором (`packages/core/src/queue/processor.ts`).

Дополнительно: позиция сообщения в истории (`seq`) — **не** идентичность сообщения. Идентификатор
(`Message.id`) выделяется при приёме, а позиция присваивается при записи в историю; в PostgreSQL
`seq` нормализуется позиционно по массиву (`packages/storage-postgres/src/ports/sessions.ts`), а
уникальность `(session_id, seq)` закреплена в схеме
(`packages/storage-postgres/src/migrations/001-init.ts`). Мутации сообщений адресуются **индексом**
(`packages/core/src/server/routes/messages.ts`, `packages/core/src/remote/client.ts`), то есть
индекс — единственный ключ, который клиент знает о сообщении.

Итог: нельзя ни надёжно подтвердить приём, ни упорядочить вставку, ни досоставить начало хода,
ни обратиться к сообщению устойчивым ключом.

## Решение

1. **Ход = последовательность шагов.** Вводится явная модель:

   | Сущность | Идентификатор | Поля | Смысл |
   |---|---|---|---|
   | `Turn` | `turnId` | статус, автор, границы | ход целиком: от реплики пользователя до терминального статуса |
   | `Step` | `stepIndex` (в ходе) | `messageId`, `usage`, `promptMeta` | шаг = **один вызов LLM** = одно assistant-сообщение |
   | `Part` | `partId` | `text` / `reasoning` / `tool` | части сообщения ([ADR-115](./adr-115-multimodal-input.md)); идентификаторы детерминированные: `msg:text:ordinal` для текста, `callId` для вызова инструмента |

   Визуально сегменты одного хода склеиваются в один блок (заголовок — только у первого сегмента);
   вставленное сообщение пользователя сегменты разделяет.
2. **Порядок — отдельное поле.** Новое поле `Message.ord` — монотонный счётчик сессии; выдаётся при
   материализации записи в историю и **никогда не перенумеровывается**. Существующий `seq` остаётся
   **позиционным**: он хранит порядок, `UNIQUE (session_id, seq)` в PostgreSQL и совместимость с
   текущими реализациями сохраняются. Идентификатор сообщения (`Message.id`) выделяется при приёме
   (стабильный ключ), позиция — при материализации. Альтернатива «сделать `seq` монотонным»
   отклонена (см. «Альтернативы»).
3. **Контракт приёма.** `POST /api/v2/sessions/:id/prompt` **всегда** отвечает `202
   {messageId, mode, position}`; `text/event-stream` в ответе больше не возвращается. `mode`:
   `queue` (по умолчанию) | `steer` | `interrupt` ([ADR-104](./adr-104-mid-turn-steering.md)).
   `steer` применяется только на границе шага — внутри шага не действует.
4. **События и каналы.** Транспорт прежний — шина сессии и `TransportClient` с фоллбеком на SSE
   ([ADR-024](./adr-024-eventhub-transport.md)); **новых каналов не появляется**.

   | Событие | Кому | Содержимое |
   |---|---|---|
   | `message.accepted` | адресно, по `userId` (новое поле `recipient` в `BusEvent`) | `messageId`, `mode`, `position` |
   | `queue.state` | канал сессии | `pendingCount`, `steerCount` — **без текста и автора** |
   | `message.delivered` | канал сессии | `messageId`, `ord`, `author` |
   | `turn.started` / `turn.finished` | канал сессии | `turnId`, терминальный статус |
   | `step.started` / `step.finished` | канал сессии | `turnId`, `stepIndex`, `messageId`, `usage`, ссылка на `promptMeta` |
   | `step.tools.started` / `step.tools.finished` | канал сессии | `turnId`, `stepIndex`, `messageId`, `callIds` (`string[]`) — **аддитивно**: `step.finished` = «вызов LLM завершён», а эта пара явно говорит UI, что идёт **исполнение инструментов** шага (один раз на шаг с вызовами: до исполнения и после записи `metadata.tool_results`; на шаге без вызовов событий нет; `turn.finished` — после `step.tools.finished`) |
   | `part.delta` / `part.updated` | канал сессии | upsert по `{messageId, partId}` |

   В том же релизе **удаляются** (без dual-emit): `stream.chunk`, `stream.usage`, `stream.done`,
   `stream.interrupted`, `message.added` с усечённым контентом
   (`packages/core/src/engine/orchestrator/persistence.ts`), `message.injected`, `message.queued`.
   Остальные события (`stream.start`/`stream.ended`/`stream.cancelled`/`stream.error`,
   `permission.*`, `question.*`, `tool_call.*`, `child.*`) контрактом не меняются — они вне объёма
   решения.
5. **Единое сообщение вместо двух этапов.** Assistant-сообщение создаётся на `step.started` и живёт
   до `step.finished`; черновик персистится инкрементально (с debounce) со статусом
   `streaming | completed | cancelled | error`. «Финал» — это **смена статуса**, а не замена объекта.
6. **Догон.** На сессию заводится журнал событий (кольцевой буфер); для WS и SSE — догон по
   `Last-Event-ID` / `?since`. При подключении клиент получает **снапшот**: текущий ход, черновик
   и очередь. События, пришедшие после снапшота, воспроизводятся из журнала без разрыва.
7. **Адресация мутаций сообщений — только по `id`.** Поле `index` из контракта мутаций уходит
   (`packages/core/src/server/routes/messages.ts`, `packages/core/src/remote/client.ts`). Это
   **ломающее изменение публичного API** ([ADR-052](./adr-052-public-api-platform.md)).
8. **Версии и гибрид.** Новый эндпоинт `GET /api/v2/meta` отдаёт возможности инстанса:
   `messageModel`, `eventSeq`, `replay`, версия. Несовпадение возможностей клиента и сервера →
   **fail-closed** (отказ подключения), а не тихая деградация. Гибрид требует синхронного
   обновления локального core и удалённого сервера ([ADR-042](./adr-042-hybrid-mode.md)).
9. **Миграция — в один релиз на весь контур.** Локально — построчная и идемпотентная миграция:
   старые ответы разбиваются по `tool_calls[].iteration` / `intermediate_text_blocks[].iteration`
   (признак итерации уже есть в персисте), иначе — один сегмент. PostgreSQL — отдельная
   SQL-миграция (колонки `ord`, `turn_id`, `step_index`) и построчный `UPDATE`; перезаписи сессии
   целиком не делается. **Down-миграций нет**: откат — только через `synth backup` / `restore`
   ([ADR-091](./adr-091-backup-restore-transfer.md)).
10. **Pin.** Семантика не меняется: pinned-сообщение не выкидывается и не суммаризируется
    (`packages/core/src/engine/context/optimizer.ts`). Меняется гранулярность: pin ставится на
    сообщении (сегменте), а кнопка на контейнере хода ставит его **всем** сегментам хода.
    `disabled` / `hidden` определяются через `turnId`, а не через соседство в массиве
    (`packages/core/src/engine/context/disabled-turns.ts` — сегодня граница хода выводится из
    порядка сообщений).
11. **Видимость.** Сообщения в очереди и сообщения-вмешательства **видны другим участникам
    сессии, с автором** — осознанное решение (очередь — часть общего состояния сессии). `steer`
    разрешён владельцу сессии и участникам проекта с правом изменения содержимого
    (роли проекта — [ADR-106](./adr-106-authority-layer.md)).
12. **Совместимость потребителей.** `stream.done.attachments` использовали шлюзы и внешние контуры:
    шлюзы (`synth-gateway-telegram`, VK, MAX), `@itphx/synth-sdk`, публичный OpenAPI и
    webhook-подписки — обновляются **в той же волне**; SDK выпускается как **major**. PWA отдаёт
    закешированный старый UI, поэтому сервер вводит **гейт минимальной версии клиента** (`426`)
    и принудительный апдейт ([ADR-044](./adr-044-mobile-adaptive-ui-pwa.md)).

## Модель данных и событий

Сущности и их носители:

| Сущность | Где | Ключ | Порядок |
|---|---|---|---|
| `Turn` | запись хода; `turn_id` в сообщениях/миграции | `turnId` | границы хода в истории |
| `Step` | одно assistant-сообщение хода | `stepIndex` + `messageId` | `stepIndex` внутри хода |
| `Part` | часть сообщения | `partId` (`msg:text:ordinal`, `callId`) | порядок частей внутри сообщения |
| `Message` | запись истории | `id` (стабильный, выдаётся при приёме) | `ord` — монотонный счётчик сессии; `seq` — позиционный |

Правила доставки событий:

- `message.accepted` — **адресное** событие: доставляется подписчику с `recipient === userId`
  отправителя. В гибриде локальный пользователь один, поэтому подтверждение видно всем локальным
  клиентам — **известное ограничение** (см. «Гибрид и многопользовательский режим»).
- `queue.state` и `message.delivered` идут в **канал сессии**: их видят все участники сессии.
  `queue.state` не несёт ни текста, ни автора — только счётчики.
- `turn.*` / `step.*` / `part.*` идут в **канал сессии**: это состояние работы агента, видимое
  всем участникам.
- События с текстом сообщения в канал сессии не публикуются (устранение утечки `message.queued`).

Удаляемые события и их замена:

| Удаляется | Замена |
|---|---|
| `stream.chunk` | `part.delta` (upsert по `{messageId, partId}`) |
| `stream.usage` | `step.finished` (`usage`, ссылка на `promptMeta`) |
| `stream.done` | `step.finished` + `turn.finished` |
| `stream.interrupted` | `step.finished` со статусом `cancelled` |
| `message.added` (усечённый контент) | `message.delivered` + `part.updated` |
| `message.injected` | `message.accepted` (адресное) + `message.delivered` (канал сессии) |
| `message.queued` | `message.accepted` + `queue.state` |

## Порядок и идемпотентность

- **`ord` — монотонный счётчик сессии.** Выдаётся в момент материализации записи в историю; ранее
  выданные значения **не перенумеровываются** (вставка в середину не сдвигает нумерацию).
- **`seq` — позиционный.** Хранит порядок в массиве истории, нормализуется при записи сессии;
  `UNIQUE (session_id, seq)` в PostgreSQL сохраняется. Связь `seq ↔ ord` — many-to-one: несколько
  сообщений могут иметь один `seq` (legacy) и разные `ord`.
- **Идентификатор — при приёме, позиция — при материализации.** `Message.id` выделяется в момент
  приёма запроса и не меняется; `ord` появляется, когда запись попадает в историю. Поэтому
  подтверждение приёма (`202`) возвращает `messageId`, а `position` — ещё не выданный `ord` (или
  позицию в очереди, если сообщение ещё не материализовано).
- **Tie-break.** Если два сообщения получили `ord` в одном тике (параллельная запись), порядок
  определяется `(ord, id)` — `id` сравнивается лексикографически; выбор `ord` сериализуется
  per-session локом (`StorageContext.locks` — advisory-lock'и PostgreSQL, ADR-097).
- **Идемпотентность доставки.** Клиент дедуплицирует по `ord` для сообщений и по
  `{messageId, partId}` для частей; `part.delta`/`part.updated` — upsert, а не append.
- **Событийная нумерация.** Каждое событие журнала получает монотонный `eventSeq`
  **глобально в пределах инстанса** (сквозной по всем сессионным каналам) — по нему
  работает догон (`Last-Event-ID` / `?since`). Номер глобальный, потому что клиент
  передаёт в `since` максимум по всем сессиям, а сервер отдаёт журнал по всем
  журналам: при per-session нумерации события «хвостовой» сессии (номер ≤ глобального
  максимума) терялись — догон молча пропускал `step.*`/`part.*`/`turn.*` другой
  сессии. Инстансный канал (`pipeline.run.*`) номера не получает и в журнал не
  попадает; `latestEventSeq(sessionId)` отдаёт номер последнего события **этой**
  сессии.

## Гибрид и многопользовательский режим

- **Адресация.** Событие может нести `recipient` (`userId`): доставляется только подписчику этого
  пользователя. `message.accepted` — адресное; остальные события хода — в канал сессии (их видят все
  участники).
- **Права.** Отправка и `steer` — владельцу сессии и участникам проекта с правом изменения
  содержимого (`OWNER`/`EDITOR`/`LEAD`/`ADMIN`; `VIEWER` только читает). Проверка — **на границе**,
  а не в обработчике: префикс-guard сессии (`packages/core/src/server/session-access-guard.ts`), вид
  доступа `read`/`write` выводится из HTTP-метода.
- **Видимость.** Очередь и вмешательства видны другим участникам сессии **с автором** — осознанное
  решение (решение 11). Скрытый «тихий» режим не вводится.
- **Ограничение адресности в гибриде.** Локальный пользователь один, поэтому адресное
  `message.accepted` в standalone/гибрид-клиенте видно всем локальным клиентам. Разделение по
  пользователям работает только на управляемом backend'е с несколькими пользователями.
- **Fail-closed.** Клиент и сервер сверяют возможности (`GET /api/v2/meta`: `messageModel`,
  `eventSeq`, `replay`, версия). Несовпадение → **отказ подключения**, а не деградация: молча
  работать со старым протоколом нельзя — расхождение порядка и догона даёт тихо испорченную ленту.
- **Гибрид требует синхронного обновления** локального core и удалённого сервера: локальный core
  проксирует удалённые сессии, и смешение протоколов v1/v2 в одном инстансе недопустимо.

## Миграция и откат

- **Один релиз на весь контур.** Миграция данных, контракт API, UI и внешние потребители
  выпускаются вместе; промежуточного состояния «сервер v2 — клиент v1» не существует.
- **Локальная миграция** — построчная и идемпотентная: каждое сообщение получает `ord`
  (по порядку истории), `turn_id` и `step_index`. Старые ответы разбиваются по
  `tool_calls[].iteration` / `intermediate_text_blocks[].iteration` (признак итерации уже
  персистится) — иначе сообщение остаётся одним сегментом. Перезапуск миграции безопасен: уже
  разобранные записи не трогаются.
- **PostgreSQL** — отдельная SQL-миграция: колонки `ord`, `turn_id`, `step_index` + построчный
  `UPDATE`. Перезаписи сессии целиком (как это делает `save()`) не делается — переписывается
  построчно.
- **Починка уже записанных ходов (§1, «финал = последний шаг»).** Ходы, созданные до исправления
  «финал = последний шаг», несут в финальном сообщении reasoning всех шагов и
  `metadata.tool_results` всех вызовов, а шаговые сообщения скрыты `metadata.tool_chain`. Их
  чинит отдельная разовая миграция `migrations.message-stream-v2-step-parts`
  (`schemaVersion` 3, `core/storage/migrations.ts` → `planMessageStepPartsCleanup` +
  `migrateMessageStreamV2StepParts`): `tool_results` группируются по `iteration` и переносятся
  в assistant-шаг того же хода с `stepIndex === iteration` (слияние по `id` вызова, дубли не
  плодятся; записи без своего шага остаются на месте), из финала удаляются reasoning-части,
  точно совпадающие с reasoning более ранних шагов (каждое совпадение гасится один раз; поле
  `reasoning` пересчитывается через `\n\n---\n\n`), удаляется
  `metadata.intermediate_text_blocks`, а у шагов с видимым содержимым или вызовами инструментов
  снимается `tool_chain` (иначе после обрезки финала их карточки и размышления пропали бы).
  Только основные сессии (`parentId == null`): отчёт дочерней сессии монолитен по устройству.
  Миграция построчная (`updateMessage`), идемпотентная и только forward — как и основная.
- **Down-миграций нет.** Миграция необратима: откат — только через `synth backup` / `synth restore`
  ([ADR-091](./adr-091-backup-restore-transfer.md), [ADR-092](./adr-092-instance-lifecycle-maintenance.md)).
- **Атомарность `ord`.** Выдача `ord` сериализуется per-session локом
  (`StorageContext.locks`: advisory-lock'и PostgreSQL, ADR-097); для файлового хранилища — лок
  сессии в `SessionManager`. Гонка двух параллельных записей не должна выдать один `ord` двум
  сообщениям.
- **Совместимость старых данных.** Мигрированные сообщения сохраняют `seq` (позиционный) и
  получают `ord`; оба поля видны в API, `seq` остаётся для потребителей, которым он нужен.

## Альтернативы

- **(а) Сделать `seq` монотонным вместо нового поля `ord`.** Отклонено: `seq` позиционный по
  построению — драйвер PostgreSQL нормализует его по порядку массива при записи сессии
  (`packages/storage-postgres/src/ports/sessions.ts`), уникальность `(session_id, seq)` закреплена
  в схеме (`packages/storage-postgres/src/migrations/001-init.ts`), а перенумерация выполняется в
  нескольких местах (ветвление и merge — `packages/core/src/sessions/manager.ts`, пакетная мутация
  сообщений — `packages/core/src/server/routes/messages.ts`, порт экспорта/импорта проекта —
  `packages/core/src/projects/portable.ts`, перенос сессии — `packages/core/src/remote/transfer.ts`,
  загрузка сессии в backend — `packages/backend/src/routes/sessions.ts`). Монотонный `seq` означал бы
  правку всех этих мест и переезд на «дырявую» уникальность. Новое поле `ord` ничего не ломает.
- **(б) Хранить сегменты хода внутри одного сообщения (части одного assistant-сообщения).**
  Отклонено: теряется граница «один вызов LLM = одно сообщение», а именно по ней считаются
  `usage`, шаги и точки применения вмешательств; шаг Tool Use нельзя будет адресовать отдельно, а
  части уже заняты содержимым (текст/reasoning/tool, ADR-115).
- **(в) Dual-emit: старые `stream.*` и новые события одновременно.** Отклонено: два конкурирующих
  источника истины в одном клиенте — расхождение неизбежно, а переходный период растягивается
  неопределённо. Переход делается **одним релизом** с удалением старых событий.
- **(г) Оставить адресацию мутаций по `index` с фоллбеком на `id`.** Отклонено: два способа
  адресовать одно сообщение — источник расхождений (индекс сдвигается после удаления соседа);
  при этом индекс уже нельзя получить надёжно, так как `ord` монотонный, а позиция в ленте
  определяется порядком материализации. Адресация только по `id` — единственный однозначный ключ.

## Последствия и риски

- **Хорошо:** приём подтверждается сразу и без висящего соединения; порядок в ленте не зависит от
  момента записи; перезагрузка во время хода не теряет начало хода; в UI один объект сообщения
  вместо двух; мутации адресуются устойчивым ключом; догон закрывает разрывы соединения.
- **Цена:** ломающее изменение публичного API (адресация мутаций, контракт приёма, набор событий);
  миграция данных необратима; внешние потребители (шлюзы, SDK, OpenAPI, webhook-подписки) должны
  выйти в одной волне; SDK — major.
- **Риск — PWA-кэш:** закешированный старый UI продолжит работать против нового сервера. Закрывается
  серверным гейтом минимальной версии клиента (`426`) и принудительным апдейтом; без гейта старый
  клиент молча потеряет события.
- **Риск — раскатка:** смешение протоколов v1/v2 (разные версии UI и сервера у разных клиентов)
  ломает порядок и догон. Закрывается fail-closed сверкой `GET /api/v2/meta` и единым релизом.
- **Риск — внешние потребители:** шлюзы и webhook-подписки, живущие на `stream.done`/`message.added`,
  перестанут получать события. Миграция обязана быть в той же волне, что и релиз.
- **Риск — атомарность `ord` при `storage.backend=postgres`:** выдача `ord` обязана идти под
  per-session локом (`StorageContext.locks`), иначе два параллельных запроса получат один `ord`.
- **Риск — необратимость миграции:** down-миграции нет; откат только через `synth backup`/`restore`.
  Перед релизом обязателен бэкап (ADR-091).
- **Наблюдаемость:** метрики очереди и хода (`synth_*`) сохраняют имена и лейблы (ADR-094);
  `message.accepted`/`queue.state` дают точку наблюдения за приёмом без утечки текста.

## Открытые вопросы

1. ~~**Двойная доставка `GET /api/v2/sessions/:id/events` в гибриде.**~~ **Решено (2026-10-30):
   сессионный SSE удалён.** Канал наблюдения один — глобальный `GET /api/v2/events` (WS
   `/ws/events` + SSE) с адресацией по `recipient`, нумерацией `eventSeq` и догоном
   (`?since=`/`Last-Event-ID`). Дедуп между «своими» и проксированными удалёнными событиями
   делается в этом единственном канале по `(sessionId, eventSeq)`; второго потока, который
   дублировал бы доставку, в контракте нет (инвариант 6 — новых каналов не заводим).
2. **Нужен ли `ord`-дедуп на клиенте при полном рефреше.** После `GET /:id/messages` клиент знает
   `ord` всех сообщений, а догоняемые события несут `ord` же: нужен ли клиентский дедуп по `ord`
   поверх окна «снапшот + события после него», или достаточно правила «события строго после
   снапшота» (окно `since`) без дедупа.

**Отложенные пункты (решение есть — реализации нет).**

1. **Адресация мутаций сообщений — только по `id` (§7).** Роуты `/messages/:sessionId/:index/*`
   и `POST /messages/:sessionId/batch {indices[]}` по-прежнему адресуют позицию; SDK/DTO содержат
   `index` (позиция в массиве). UI пересчитывает индекс из актуального массива, ключ списка — `id`.
   Зафиксировано в [API_V2.md](../API_V2.md) §5.6.
2. **`message.added` не удалён (§4).** Событие публикуется с прежней формой (усечённый до 500
   символов текст) для финального assistant-сообщения (`engine/orchestrator/persistence.ts`),
   сообщений вставок вложений тулов и сообщений дочерних сессий; клиенты читают его как
   совместимость. Удаление требует перевода этих трёх мест на `message.delivered` +
   `step.finished`/`part.updated`.

**Канал наблюдения — один.** Сессионный SSE `GET /api/v2/sessions/:id/events` (core-only)
удалён: у него не было ни гейта `messageModel`, ни нумерации `id:`, ни фильтрации по
`recipient` — он дублировал глобальный `GET /api/v2/events` и был готовым источником
двойной доставки. Контракт наблюдения держится только на WS `/ws/events` и глобальном SSE.

**Доводка 2026-10-31 — «финал хода = последний шаг».** Реализовано и зафиксировано: финальное
assistant-сообщение хода — это сообщение **последнего шага**, а не отдельная сводка хода.

- **Финал = последний шаг (без дублей).** Текст и reasoning финального сообщения — **только
  своего шага**: блоки прошлых шагов живут в сообщениях своих шагов
  (`engine/orchestrator/persistence.ts`, `engine/orchestrator/phases/process-finalize.ts`).
  Раньше сводка хода дублировала тексты шагов — в ленте появлялись повторы.
- **Tool-результаты — в сообщении своего шага.** `metadata.tool_results` (в DTO — `tool_calls`)
  пишется в сообщение шага, вызовы которого содержит; для сообщений хода (`step.turnId` задан)
  сводка вызовов **не** пишется — иначе карточки инструментов задваивались бы в финале.
  `metadata.intermediate_text_blocks` для сообщений хода тоже **не** пишется (legacy — только
  сообщения, созданные до ADR-118).
- **`current_stream.turn_id`** — метка живого хода в DTO сессии (аддитивное поле, `null` — хода
  нет): клиент восстанавливает ход после перезагрузки страницы по ней (`stream_id` — **не** id
  хода). Персистится в file-store (`current_stream.turn_id`) и PostgreSQL (тот же JSONB-документ).
- **Расход хода суммируется в финальном сообщении.** `usage` финального сообщения — сумма всех
  вызовов LLM хода (`turnUsage`, ADR-102); `step.finished.usage` — расход **своего** шага; сумма
  по шагам = расход хода (метрики Prometheus не меняются).
- **Шаг-лимит дополняет запись шага (без второго сообщения).** Исполненный шаг-лимит
  (`AgentDefinition.maxSteps`) — **ещё один обычный шаг** цикла: инструменты остаются в запросе,
  вызов запрещён `tool_choice: 'none'`, инструкция «только текст» приходит синтетическим
  assistant-префиллом. Отдельного сообщения в истории хода не появляется.
- **UI.** Плашка «обработка» у реплики — до первого контента хода (`turnHasContent`); placeholder
  между шагами; строка активности хода (`data-testid="turn-activity"`); восстановление
  `streamId`/`contentStarted` после reload (`restoreLiveTurnFromSession`); закрытие хода по
  `stream.error`/`stream.cancelled`.
