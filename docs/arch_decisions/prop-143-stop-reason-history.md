# PROP-143: Причина остановки хода — durable служебное сообщение в истории

> **Статус:** 🧩 Предложение — терминальные причины остановки (ошибка провайдера/модели, лимит шага, бюджет контекста, «Стоп», отказ прав, рестарт) фиксируются в истории как служебные `user`-сообщения с машиночитаемым конвертом; UI рисует их существующим системным блоком, и они не исчезают при возобновлении работы.
> **Решение до:** 2026-12-15
> **Дата:** 2026-11-18
> **Связано:** [ADR-041](./adr-041-llm-error-taxonomy.md) (таксономия ошибок), [ADR-104](./adr-104-mid-turn-steering.md) (границы хода), [ADR-111](./adr-111-background-subagent-sessions.md) / [ADR-113](./adr-113-background-processes.md) (уведомления фоновых прогонов), [ADR-118](./adr-118-message-stream-v2.md) (turn/step, статусы), [ADR-119](./adr-119-context-compaction.md) (сжатие), [ADR-089](./adr-089-external-events-automation.md) (события), [ADR-092](./adr-092-instance-lifecycle-maintenance.md) (рестарт, п. 7), [ADR-126](./adr-126-input-surface-commands-mentions-snippets.md) §14 (единый системный блок), [ADR-036](./adr-036-llm-gateway.md) (обфускация), [ADR-141](./adr-141-timers-alarms.md) (таймеры), [PROP-142](./prop-142-subagent-control-and-auto-recovery.md) (доставка сообщений сабагенту и восстановление прогонов)

## Контекст

Что происходит с терминальной причиной остановки сейчас:

| Место | Поведение |
|---|---|
| Основная сессия | Сообщение **не создаётся** (решение владельца 2026-11-06, `engine/orchestrator/errors.ts`): `handleLlmFailure` пишет `metadata.last_error` в user-реплику хода и aux-расход; пользователю — временная плашка `StreamErrorPanel` по `stream.error`. После reload/возобновления плашки нет |
| `last_error` | Очищается при успешном завершении хода (`queue/processor.ts`) — след ошибки исчезает намеренно |
| Саб-агент | Пишет сообщение `role: 'error'` (текст + `metadata.error_type`/`attempts`); UI рисует `Notice variant="error"` («Ошибка саб-агента · …»); в контекст ребёнка попадает (`messageToLLMMessage`: error → `user`) |
| Лимит шага | В историю — только финальный отчёт модели + `metadata.step_limit_reached`; причина видна лишь в tool-result родителю |
| Бюджет контекста | Assistant-сообщение с текстом `[context_budget] …` |
| «Стоп» | В основной — ничего; в ребёнке — INFO «Task stopped by the user» |
| Рестарт | В основной — INFO `restart_resumed` при автопродолжении; в ребёнке и у фонового прогона — ничего (`orphaned`) |

Контракт доставки системных событий в диалог **уже сложился** и используется несколькими подсистемами:

| Событие | Роль | `author` | Маркер | Контент для модели |
|---|---|---|---|---|
| завершение фонового прогона | `user` | `Subagent` / `Process` | `metadata.type='background_run_result'` | `<subagent …>` / `<process …>` |
| срабатывание таймера/будильника | `user` | `Timer` | `metadata.type='timer_fired'` | `<timer …>` + комментарий |
| сообщение шедулера | `user` | `Scheduler` | `metadata.scheduler` | текст задания |
| перенос сессии | `user` | `Session` | `metadata.type='session_moved'` | конверт/список эффектов |
| вложение из инструмента | `user` | `Tool` | `metadata.source='tool-attachment'` | плейсхолдеры вложений |

Классификация «это не реплика человека» — один шов `sessions/user-messages.ts`: `isServiceUserMessage` (авто-тайтл, счётчики диалога, интервью) и `isNonTurnServiceUserMessage` (границы хода, статистика авторов, наследование `disabled`). UI — один компонент `Notice` (`error`/`process`/`timer`/…): шапка «иконка + подпись», тело без конверта, действия.

## Проблема

1. **Причина остановки не durable**: живёт в transient-плашке и в `last_error`, который стирается при возобновлении. После resume её не видит ни человек, ни агент.
2. **Две модели одного явления**: у основной сессии — скрытая запись/плашка, у саб-агента — `role: 'error'`. Формат и поведение расходятся.
3. **Нет машиночитаемой причины**: `error_type`, `retryable`, `attempts` до модели не доходят (у основной сессии — вообще ничего), остаётся свободный текст провайдера, часто куцый.
4. **Лимит шага, бюджет и рестарт** в историю не попадают (шаг-лимит — только metadata, рестарт — ничего); «Стоп» неотличим от остановки родителем.
5. **Наивное «оставить текст ошибки»** ломает картину: в контексте это выглядит как новая реплика пользователя, сдвигает границы хода и авто-тайтл.

## Предложение (гипотеза)

### 1. Одна durable запись на терминальный переход

Сообщение пишется в историю **той сессии, где произошла остановка** (основной или дочерней), один раз за терминальный переход:

- `role: 'user'` — иначе причина не попадёт в контекст следующего хода (у основной сессии её сейчас нет вовсе);
- `author: 'System'` — системный автор, как `Timer`/`Process`;
- `metadata.type = 'execution_stopped'` + `reason`, `error_type`, `retryable`, `attempts`, `max_retries`, `provider`, `model`, `turn_id`, `stream_id`, `stopped_at`, `i18n`;
- контент — **конверт** (единственное, что видит модель):

```text
<execution_stopped reason="provider_error" error_type="rate_limit" retryable="true" attempts="3">
<текст провайдера>
</execution_stopped>
```

- `turnId` записи = id упавшего хода → блок встаёт в ленте сразу после упавшего шага, а не «в следующем ходе»; конверт отличает событие движка от реплики человека тем же приёмом, что `<subagent …>`/`<timer …>`.

`reason` — нормализованный код, одна точка (`engine/stop-reason.ts`):
`provider_error | steps_limit | context_budget | stopped_by_user | denied | internal | restart | orphaned`.
Никаких расходящихся текстов: сейчас «Task stopped by the user» пишется и когда остановили родителя.

### 2. Классификация — через существующий шов

- `isServiceUserMessage`: добавить `metadata.type === 'execution_stopped'` → не считается репликой человека (авто-тайтл, счётчики диалога, интервью).
- `isNonTurnServiceUserMessage`: тоже да → границу хода не сдвигает, наследует `disabled` выключенного хода (паритет с `session_moved`).
- `suppressDisabledTurns`/`stats.ts` начинают работать без правок логики.

### 3. UI — тот же формат, но в ленте навсегда

- Ветка в `ChatMessage`: `metadata.type === 'execution_stopped'` → `Notice variant="error"` (тот же блок, что у ошибки саб-агента): шапка «Остановлено: <локализованная причина> · <модель>», тело — текст провайдера (по умолчанию сворачиваемый), `retryable`/`attempts` — в тултипе и развёрнутом теле; действия — «Повторить» (recoverable и для основной сессии), «Продолжить» (дочерняя), «Копировать»; конверт не показывается.
- `StreamErrorPanel` остаётся для **живой** ошибки (до перезагрузки) — durable `Notice` её не дублирует: плашка над композером описывает текущее состояние, `Notice` — факт в истории.
- Дочерняя сессия: запись заменяет `role:'error'` (для legacy-записей рендер сохраняется); плашка «Продолжить» продолжает работать от последнего терминального состояния.

### 4. Точки записи

1. `engine/orchestrator/errors.ts` (`handleLlmFailure`) + финализация хода — основная сессия: ошибка провайдера (`provider_error`), «Стоп» (`stopped_by_user`, решение 2026-11-18), отказ прав (`denied`). `last_error` остаётся совместимой меткой, но источником истины становится запись.
2. `engine/tools/task/run-cycle.ts` — дочерняя сессия: заменить `role:'error'`; добавить запись для **шаг-лимита** и пустого отчёта (`steps_limit`), сохранив локализованный текст в теле.
3. `engine/background/service.ts` — `orphaned` после рестарта и потерянный процесс: запись в сессию-владельца (`restart`/`orphaned`), чтобы родитель узнавал о потере не только из реестра.
4. Таймеры/шедулер — не трогаем: они уже доставляют собственные сообщения.

### 5. Таксономия

- В `classifyLlmError` добавить `quota_exceeded` (`insufficient_quota`, `exceeded your current quota`, `billing`) и внести в unrecoverable: сейчас квота попадает в `unknown` (recoverable) и ретраится впустую.
- `retryable` = `isLlmErrorRecoverable(...)`; `attempts`/`max_retries` — как у саб-агента сейчас.
- Лимит шага/бюджет — запись с параметрами (`limit`, `tokens`), тело — локализованный текст.

### 6. Гигиена и совместимость

- **Обфускация** тела через `obfuscateUserMessageForHistory` (ADR-036): текст провайдера может нести ключи/URL.
- **Идемпотентность**: не более одной записи на `turn_id`; повторный терминальный статус того же хода второй не добавляет.
- **Ретраи**: запись — только после исчерпания попыток или при unrecoverable; recoverable-попытки по-прежнему дают только `stream.retry`.
- **Legacy не мигрируем**: `role:'error'` в детях и скрытые assistant-ошибки в основных рендерятся как раньше; `isLlmFailureMessage` остаётся для старых записей и не срабатывает на новую (у неё `role:'user'`).
- **Две подряд user-реплики** (запись + следующий ввод) — штатный случай: так уже приходят уведомления фоновых прогонов и таймеров; пары `toolUse`/`toolResult` не рвутся (запись идёт после терминального шага).
- Новых событий/каналов нет: публикуется обычный `message.added` (инвариант 27).

## Принятые решения по открытым вопросам (2026-11-18)

| # | Вопрос | Решение |
|---|---|---|
| 1 | `author` записи | **`System`** — нейтральный системный автор, как у `Timer`/`Process`; покрывает не только LLM-сбой, но и рестарт, бюджет, отказ |
| 2 | «Стоп» пользователя | **Писать запись** (`reason: 'stopped_by_user'`): после resume видно, что ход прерван намеренно, а не упал |
| 3 | Текст в `content` | **Сырой текст провайдера** (с обязательной обфускацией, ADR-036); в UI тело свёрнуто по умолчанию |
| 4 | `retryable`/`attempts` в UI | **Только в тултипе и развёрнутом теле**; подпись шапки короткая: «Остановлено: <причина> · <модель>» |
| 5 | Имя маркера | **`metadata.type = 'execution_stopped'`** — не привязано к LLM, покрывает шаг-лимит, бюджет, рестарт и «Стоп» |

### Остаточные технические вопросы (решаются на реализации)

1. Порядок записи относительно частичного ответа при «Стопе»: запись идёт **после** партиального assistant-сообщения, чтобы лента и контекст читались сверху вниз (сначала «что успело», потом «почему оборвалось»).
2. Семантика «Повторить» из записи: для основной сессии — повтор последней user-реплики хода; из записи в дочерней — resume-путь саб-агента (PROP-142), без второго механизма.

## Альтернативы (отклонены предварительно)

- **Оставить плашку + `last_error`** — причина исчезает при reload/resume, агент её не знает.
- **Просто перестать скрывать legacy assistant-ошибку** — ломает форму «ответ агента» (ADR-118): в контексте это ответ модели, а не событие движка.
- **Новый `role: 'error'` и для основной сессии** — роль вне пары user/assistant требует отдельной обработки у провайдеров и не даёт машиночитаемого конверта; для системных событий уже принята user-роль + конверт.
- **Отдельная подсистема диагностики** — избыточно: сообщение в существующей шине и ленте дешевле и не плодит сущности.
