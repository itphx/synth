# PROP-098: Форсированная отправка сообщения во время хода (steering)

> **Статус:** 🧩 Предложение — инъекция сообщения в активный ход без остановки сессии
> **Решение до:** 2026-11-14
> **Дата:** 2026-10-15
> **Парные документы:**
> - [ADR-005](./adr-005-json-storage.md) (надёжный «Стоп»/`cancelRequested`) — соседняя семантика отмены хода;
> - [ADR-039](./adr-039-plan-in-project.md) — состояние агента через Tool Use; место инъекции в цикле;
> - [ADR-089](./adr-089-external-events-automation.md) — надёжный «Стоп», события/видимость сессии;
> - [ADR-024](./adr-024-eventhub-transport.md) — доставка события инъекции в UI;
> - [PROP-096](./prop-096-background-subagent-sessions.md) — родственный контроль хода (фон/вмешательство);
> - `core/queue/processor.ts` — текущая очередь ходов (`pendingMessages`).

## Решение

Разрешить отправлять сообщение агенту **прямо во время его хода** (как в OpenCode), а не только ставить в очередь на следующий ход. Три режима:

- **`queue`** — текущее поведение (по умолчанию): сообщение ждёт окончания хода.
- **`steer`** — **инъекция без прерывания**: сообщение «дописывается» в контекст на ближайшей безопасной границе (перед следующим LLM-вызовом / после текущего шага инструмента); генерация не обрывается.
- **`interrupt`** — **прерывание и инъекция**: текущая генерация абортится, новый ход начинается с этим сообщением (отличается от «Стоп»: сессия не останавливается, а продолжает с новым вводом).

API: `POST /api/v2/sessions/:id/prompt` с полем `mode: 'queue' | 'steer' | 'interrupt'` (по умолчанию `queue` — обратная совместимость). UI: при активном ходе «Отправить» умеет `steer`/`interrupt` (по умолчанию — как решим), в истории виден маркер вмешательства.

## Контекст

Сегодня сообщения во время активного хода попадают в `pendingMessages` (`core/queue/processor.ts`) и обрабатываются **после** хода; единственный способ вмешаться — «Стоп» (`POST /sessions/:id/abort`, персистентный `cancelRequested`), который **завершает весь ход** и теряет текущую работу. Промежуточного «скорректировать агента на ходу, не убивая ход» нет. OpenCode позволяет писать агенту во время работы и, при необходимости, прерывать его — это важный сценарий для длинных многошаговых ходов (уточнить требования, изменить направление, добавить ввод).

## Детали

### Модель исполнения

- В сессии — **очередь инъекций** `steerInbox` (отдельно от `pendingMessages`), FIFO.
- Оркестратор **вычитывает** `steerInbox` на границах цикла (`engine/orchestrator.ts`, верх `while (toolIteration < maxIterations)` — там же, где проверяется `isCancelRequested`):
  - `steer`: до вызова LLM добавляет накопленные сообщения как обычные `user`-сообщения (с `metadata.steer=true`) — генерация продолжается уже с ними;
  - `interrupt`: абортит текущий LLM-стрим (отдельное событие `stream.interrupted`, **не** `stream.cancelled`/«Стоп»), затем подставляет сообщение и продолжает тот же ход.
- **Границы безопасны по построению:** инъекция применяется только между шагами (не посреди выполнения инструмента), чтобы не рвать tool-цепочку (пары `toolUse`/`toolResult`, ADR-070/инвариант истории).
- **Несколько инъекций** — по порядку поступления; лимит на ход (напр. N) с понятной ошибкой при превышении.
- **История** — инъецированное сообщение персистится как нормальная `user`-реплика (`metadata.steer`, автор, время) → видно в истории и в `listSessions`, попадает в LLM-контекст штатно.

### Отличия от соседних механизмов

| Механизм | Эффект |
|---|---|
| `queue` (сейчас) | сообщение ждёт окончания текущего хода |
| `steer` | дописывается в текущий ход, генерация не рвётся |
| `interrupt` | обрывает текущую генерацию, ход продолжается с новым сообщением |
| «Стоп» (`/abort`, ADR-005) | **завершает** ход (частичный ответ + `stream.cancelled`) |

### События, UI, аудит

- События: `message.injected` (steer), `stream.interrupted` (interrupt), `steer.dropped` (лимит/недоставлено).
- UI: при активном ходе отправитель выбирает режим; в ленте — маркер «вмешательство в ход»; `interrupt` визуально отличается от «Стоп».
- Аудит/безопасность: инъекция проходит обычные правила (permission-слой не обходится); при ожидании подтверждения прав (`ask`) — поведение оговаривается (см. вопрос 3).
- i18n-ключи для новых событий/статусов.

### Планирование и очередь

- `interrupt` не должен «терять» текущий незавершённый tool-результат: прерывание — только на границе шага (либо частичный tool_result помечается отменённым).
- Взаимодействие с очередью ходов: если сообщений несколько, `interrupt` поднимает приоритет (вставляется в начало следующего хода).

## Этапы

1. **MVP:** поле `mode` у `/prompt` + `steerInbox` + вычитка на границах + `steer` без прерывания + UI-маркер. ~2 дня.
2. `interrupt`: аборт генерации и продолжение хода + отдельное событие + UI. ~1–2 дня.
3. Лимиты/приоритеты, поведение при `ask`/`plan`, гибрид/фон. ~1–2 дня.

## Открытые вопросы

1. Какой режим по умолчанию в UI при активном ходе — `queue` (безопасно) или `steer` (аналог OpenCode)?
2. Границы применения: только «между итерациями LLM» или также «между параллельными tool-вызовами»?
3. Инъекция при ожидании подтверждения прав (`ask`): разрешать (и как) или откладывать до ответа?
4. `interrupt` при уже запущенном необратимом инструменте (shell/commit): ждать его или обрывать (риск побочных эффектов)?
5. Как сочетается с фоновыми саб-агентами (PROP-096) — можно ли steering в фонового ребёнка?
