# PROP-100: SSRF и TOCTOU/DNS-rebinding — привязка проверенного адреса к соединению

> **Статус:** 🧩 Предложение — соединяться с **тем же** адресом, который прошёл policy-проверку (пиннинг), а не перепроверять DNS при коннекте
> **Решение до:** 2026-11-14
> **Дата:** 2026-10-15
> **Класс:** предложение ([ARCH_DECISIONS.md](../ARCH_DECISIONS.md) §1–2): решения нет — есть гипотеза; выбор варианта (A/B/C) не сделан, кода по вариантам нет. Уже сделанная часть (единая нормализация адреса и расширенный список запрещённых CIDR) — обычный коммит, отдельного ADR не требует.
> **Связано:** [ADR-071](./adr-071-mcp-servers-prompt.md) §2.3.1 (дом сетевой политики), [ADR-052](./adr-052-public-api-platform.md) (webhooks), [PROP-088](./prop-088-http-proxy.md) (единый egress-слой), [ADR-041](./adr-041-llm-error-taxonomy.md) (ключи ошибок), [ADR-036](./adr-036-llm-gateway.md), [PROP-094](./prop-094-observability-metrics.md) (детект ребиндинга как метрика), [AUDIT-CHECKLIST](../security/AUDIT-CHECKLIST.md) §3 п.4 «SSRF / egress».

## Контекст

### Что уже закрыто (предмет документа — не это)

Обход SSRF-политики через IPv4-mapped IPv6 закрыт: введена единая нормализация адреса (`normalizeIp`/`mappedIpv4`, `packages/core/src/engine/mcp/network-policy.ts`), расширен `DEFAULT_MCP_PRIVATE_CIDRS` (`packages/shared/src/types/mcp.ts`: `0.0.0.0/8`, `100.64.0.0/10`, `::/128`, `::ffff:0:0/96`, …), все потребители ходят через один хелпер (`engine/tools/web.ts`, `engine/net/fetch.ts`, `engine/webhooks/network.ts`, `engine/mcp/manager.ts`, backend `routes/providers.ts`). Запись `::ffff:127.0.0.1`/`::ffff:169.254.169.254` теперь блокируется.

Редиректы тоже частично прикрыты: `web_fetch` и `fetchText` идут с `redirect: 'manual'` и проверяют каждый хоп (`engine/tools/web.ts:341-358`, `engine/net/fetch.ts:143-193`).

### Остаток: TOCTOU / DNS-rebinding

**Угроза.** Проверка адреса и установка соединения — это **два независимых DNS-резолва**:

1. policy-проверка: `evaluateMcpNetworkAccess(...)` → `dns.lookup(host, { all: true })` (`engine/mcp/network-policy.ts:23-26,191`) → адреса → сверка с CIDR;
2. собственно запрос: `fetch(url)` (`engine/tools/web.ts:345`) → рантайм (undici внутри Node) резолвит **тот же hostname заново** и коннектится к ответу второго резолва.

Если между (1) и (2) DNS отдаёт другой ответ (TTL≈0, round-robin flip-flop, атакующий авторитативный сервер, чередующий публичный и приватный адрес), соединение уйдёт на адрес, который policy не проверяла. Это классический **check-then-use (TOCTOU) / DNS-rebinding**.

**Почему перепроверка редиректов это не закрывает.** Каждый хоп редиректа повторяет ту же пару «проверка → запрос»: окно существует **на каждом хопе, включая последний**. Повторная проверка сужает множество достижимых имён (нельзя уйти по редиректу на приватный адрес, если он разрешился в приватный), но не устраняет разрыв между проверкой и коннектом. Формально: инвариант «адрес соединения ∈ множество проверенных адресов» не выполняется ни на одном шаге.

**Что важно для честной оценки.** Multi-A-ответ (публичный + приватный адрес в одном ответе) политикой уже отклоняется: в режиме `deny` достаточно одного запрещённого адреса среди resolved. Остаток — именно **разные ответы в разные моменты**, а не «несколько записей в одном ответе». Наиболее чувствителен режим `allow` (белый список): под него можно «провалиться» проверкой и подключиться в другое место.

## Варианты

### A. `node:http`/`node:https` + собственный `lookup` (без новых зависимостей)

Заменить `global fetch` в защищённых путях на запрос через `node:https`/`node:http` с кастомным `lookup` (или `createConnection` к уже проверенному IP при `servername`/`Host` = исходный hostname, чтобы TLS валидировался по имени, а не по IP).

- **Плюсы:** новых зависимостей нет; полный контроль над моментом резолва — проверка и коннект неразделимы **по построению**; доступен дешёвый дополнительный слой: после `connect` сверить `socket.remoteAddress` с политикой и оборвать запрос до отправки тела (закрывает и «слепой» коннект); единый транспорт-хелпер можно передать и в MCP-SDK (`fetch`-опция).
- **Минусы:** нужно заново собрать то, что даёт `fetch` бесплатно — декомпрессия (`gzip`/`deflate`/`br` — `node:http` её не делает), charset/декодирование, таймауты и `AbortSignal`, лимиты байт, поведение при редиректах, keep-alive/пул; в `web_fetch`/`fetchText` заменить `FetchLike`-seam на новый интерфейс (правки тестов); адаптер к web-`Response` для MCP-SDK.
- **Объём:** ядро сети + 4 подсистемы (`web.ts`, `net/fetch.ts`, `webhooks/service.ts`, `mcp/client.ts`) + backend `providers.ts`. Риск регрессий средний-высокий (стриминг, таймауты, декомпрессия, аборт).

### B. `undici` `Agent({ connect: { lookup } })` + `fetch(url, { dispatcher })` (новая зависимость)

Тот же принцип «проверка внутри резолвера», но без переписывания транспорта: `lookup`-хук агента сам резолвит, нормализует, сверяет с политикой и **возвращает только проверенные адреса**; undici коннектится ровно по ним.

- **Плюсы:** мало кода, поведение `fetch` (декомпрессия, `AbortSignal`, `redirect: 'manual'`, лимиты) сохраняется; единый хелпер `egressFetch(url, init)` без труда передаётся в MCP-SDK (`fetch`) и в webhooks (`fetchImpl`); предсказуемо тестируется (инъекция `lookup`).
- **Минусы:** **прямая зависимость `undici`** (сейчас её в `package.json` нет — встроенный в Node `fetch` не даёт импортировать `Agent`); нужно подтвердить совместимость внешнего `Dispatcher` с глобальным `fetch` Node 22 (разные версии undici внутри Node и в пакете — известный источник поломок) — это спайк до решения; меньше контроля «после коннекта» (проверка `socket.remoteAddress` неудобна); при смене мажорной версии undici — риск тихой несовместимости.
- **Объём:** новый модуль-хелпер + правки точек подключения + тесты. Риск регрессий низкий, риск зависимости — средний (supply-chain, ратчет зависимостей в аудите).

### C. Оставить как есть (компенсирующие меры)

Остаточный риск: окно — миллисекунды между двумя резолвами; атакующему нужен контроль DNS для запрашиваемого имени. Для `web_fetch` это реалистично: URL приходит от модели, а модель управляема содержимым (prompt injection с чужой страницы) — подконтрольный домен с flip-flop DNS даёт SSRF. Эффект: чтение внутренних HTTP-сервисов и — в облачных/управляемых развёртываниях — метаданных (`169.254.169.254`), причём тело ответа возвращается в сессию, то есть уходит провайдеру модели (эксфильтрация). Для локального standalone без metadata-service заметно ограниченнее, но локальные сервисы всё равно достижимы.

Что можно сделать без кода (компенсации, а не замена фиксу): сетевая изоляция процесса (K8s `NetworkPolicy`/egress-allowlist — для многих развёртываний сильнее и дешевле пиннинга); `webhooks.allowPrivateTargets: false` (default) и `deny`-режим политики; не возвращать в модель тело ответа при подозрении; детект flip-flop в логах. Вердикт: как «окончательно» вариант C принимается только для standalone-сценария с сетевой изоляцией; при `web_fetch` в managed/облаке остаточный риск признаётся неприемлемым — именно поэтому предложение заводится со сроком.

## Предложение

1. **Пиннинг резолвом-в-резолвере.** Соединяться только с адресом, прошедшим policy-проверку **в том же вызове**: `lookup(host, opts, cb)` → resolve → `normalizeIp` → CIDR-сверка → вернуть только допущенные адреса (иначе — ошибка резолва). Проверка и коннект сливаются в одну операцию, окно исчезает по построению.
2. **Первый шаг — B со спайком.** Спайк подтверждает совместимость `undici`-`Dispatcher` с глобальным `fetch` на Node 22 (заявленный `engines`: `node >= 22.0.0`). Спайк успешен → B (мало кода, покрывает и MCP через `fetch`-опцию SDK). Спайк провалился → A (без новых зависимостей), либо B2 — работа через `undici.request` напрямую, а не через глобальный `fetch`.
3. **Единая точка.** Один модуль-хелпер (~`engine/net/pinned-fetch.ts`) — все защищённые пути ходят только через него (принцип «новых каналов не плодить»); MCP-SDK получает его через `fetch`-опцию.
4. **Сопутствующее (в том же workstream):** DNS-проверка в `validateRemoteUrl` (дефект 1), `redirect: 'manual'` для webhooks (дефект 2), policy-проверка `resolved`-URL и лимит схемы в `fetch-icon` (дефект 3).
5. **Политика и конфиг не меняются по умолчанию:** пиннинг — безопасное поведение без флага (обратной совместимости не ломает). Флаг `network.pinDns` (default `true`) — только если спайк выявит реальный сценарий, который пиннинг ломает (см. открытые вопросы).
6. **Наблюдаемость:** фиксировать в логе случай, когда резолв по тому же имени дал другой ответ, чем предыдущий (детектор попытки ребиндинга); в перспективе — счётчик в [PROP-094](./prop-094-observability-metrics.md).

## Критерии готовности и способ проверки

1. **Структурный тест-страж:** для защищённых путей DNS-резолв происходит **только** внутри policy-хука — spy на `dns.lookup` фиксирует, что второй резолв (вне проверки) не выполняется.
2. **Тест с подменой DNS (flip-flop).** Инъекция `lookup`/`resolveHost`, возвращающего по очереди `93.184.216.34` (разрешён) и `127.0.0.1` (запрещён): ожидание — соединение идёт на **проверенный** адрес, ни одного коннекта на запрещённый (spy на `net.connect` + локальный сервер-ловушка на `127.0.0.1`, который не должен получить запрос). Тест детерминированный, реальный DNS не нужен.
3. **Policy-deny внутри резолвера:** адрес из `DEFAULT_MCP_PRIVATE_CIDRS` → отказ соединения без HTTP-запроса (для `web_fetch` — ошибка политики, для webhooks — `status:'failed'` с причиной).
4. **TLS-инвариант:** сертификат валидируется по **hostname** (`servername`/`checkServerIdentity`), а не по IP — тест: подключение к IP с самоподписанным сертификатом на другое имя должно падать; на совпадающее имя — проходить.
5. **Регрессии (функциональный паритет):** `gzip`/`deflate`/`br`, charset, `AbortSignal`/таймаут, цепочка редиректов, лимит байт, 5 URL за раз, webhook retry/backoff/дедуп/подпись, MCP connect/`tools/call` (HTTP и SSE), `web_search`.
6. **Существующие SSRF-тесты зелёные:** `network-policy.test.ts`, `webhooks/network.test.ts`, `skills/remote.test.ts` + тесты `web_fetch`.
7. **Аудит:** строка негативной матрицы по §3 п.4 [AUDIT-CHECKLIST](../security/AUDIT-CHECKLIST.md) с форматом «команда → вывод» и запись в `docs/security/releases/<version>.json`; прогон `pnpm typecheck && pnpm lint && pnpm test`, для доков — `node scripts/adr-check.mjs`.
8. **Интеграционный прогон в dev:** `web_fetch` по публичному URL (ожидаемо — успех) и по URL, резолвящемуся в приватный адрес (ожидаемо — отказ политики).

## Открытые вопросы

1. **MCP-SDK** — вопрос закрыт по факту (`fetch`-опция есть в 1.29.0), но остаётся: покрывать и `stdio`, и SSE-переподключения тем же хелпером? Что делать при мажорном обновлении SDK, если опция исчезнет?
2. **B: совместимость** внешнего `undici`-`Dispatcher` с глобальным `fetch` Node 22 — версия пакета, пиннинг версии, риск расхождения с bundled undici. Если несовместимо — A или B2 (`undici.request`)?
3. **A: объём** — писать декомпрессию/charset/таймауты руками или взять минимальную зависимость? Где граница «минимального фикса»?
4. **Round-robin с health-check:** пиннинг к одному адресу теряет failover. Достаточно ли возвращать **все** проверенные адреса (Happy Eyeballs по списку) и когда это ломает легитимные сайты?
5. **Прокси ([PROP-088](./prop-088-http-proxy.md)):** при egress через прокси адрес-политика не работает (резолвит прокси) — фиксируем ли правило «при прокси SSRF-политика переносится на прокси/allowlist» уже сейчас?
6. **Флаг `network.pinDns`** — нужен ли вообще, или пиннинг безусловен? Кто и как диагностирует «сайт перестал открываться»?
7. **Детект и лимиты:** считать ли flip-flop инцидентом (лог/событие/алерт) и не блокировать ли имя при повторных попытках?
8. **Соседние дефекты 1–3** — считать частью этого предложения (и тогда расширять объём) или отдельными задачами аудита? В документе они помечены как обязательные к закрытию в том же workstream.
