# PROP-126: Поверхность ввода — `/`-команды, `@`-упоминания, `$`-скиллы, `#`-сниппеты и `!`-shell

> **Статус:** 🧩 Предложение
> **Дата:** 2026-11-06
> **Решение до:** 2026-12-06
> **Связано:** [ADR-046](./adr-046-skills-and-slash-commands.md), [ADR-115](./adr-115-multimodal-input.md), [ADR-029](./adr-029-granular-permissions.md), [ADR-024](./adr-024-eventhub-transport.md), [ADR-036](./adr-036-llm-gateway.md), [ADR-070](./adr-070-system-prompt-composer.md), [ADR-104](./adr-104-mid-turn-steering.md), [ADR-118](./adr-118-message-stream-v2.md), [ADR-119](./adr-119-context-compaction.md), [PROP-057](./prop-057-loop-engine.md), [PROP-064](./prop-064-ui-browser-terminal.md), [PROP-068](./prop-068-skills-agents-registry.md)

## Контекст (что есть сейчас)

**В opencode и openchamber поверхность ввода устроена по-разному.**

| Префикс | opencode | openchamber | Synth сейчас |
|---|---|---|---|
| `/` | Команда; только начало сообщения | Команда; только начало сообщения | Команда; только начало сообщения |
| `@` | Файл, агент, скилл | Файл, агент | **Только агент** |
| `$` | Нет (скиллы через `@`) | Скилл | Нет |
| `#` | Нет | Сниппет (2 скоупа) | Нет |
| `!` | Shell-режим | Shell-режим | Нет |

**Что уже есть в Synth.**

- Реестр `/`-команд: `builtin`/`template`/`skill`/`bundle`, резолвинг в core, UI-автокомплит
  (`packages/core/src/engine/commands/*`, `packages/ui/src/components/chat/CommandAutocomplete.tsx`).
- Встроенные команды: `/help`, `/skills`, `/commands`, `/summary`, `/init`
  (`packages/core/src/engine/commands/builtin.ts`).
- `/summary` запускает суммаризацию; автоматическая компактизация — [ADR-119](./adr-119-context-compaction.md).
- `/skill-name` загружает тело скилла в промпт; тул `skill` — для инициативы модели
  (`packages/core/src/engine/commands/service.ts`, `packages/core/src/engine/tools/skill.ts`).
- `@agent` — единственное упоминание: клиент режет сообщение регуляркой `@(\w+)` на сегменты с
  `agentRole` (`packages/ui/src/components/chat/ChatInput.tsx:67,122`).
- Вложения — через UI-кнопку и blob-пайплайн [ADR-115](./adr-115-multimodal-input.md); `@file` в композере нет.
- Сниппетов и shell-режима композера нет.

**Проблема.** Текущий `@`-парсер агентский и уже неоднозначен: `@src/index.ts` даёт тег `src`,
`a@b.com` может дать тег `b`. Добавление файлов и пользователей «в ту же регулярку» сделает конфликт
неуправляемым. Одновременно `/`-поверхность рискует разрастись TUI-командами, которые в web не нужны.

## Решения владельца (основа предложения)

| № | Вопрос | Решение |
|---|---|---|
| 1 | Какие `/`-команды переносить | Только контентные. Острая необходимость — `/compact`; `/init` уже есть; `/review` — только для git-репозитория |
| 2 | TUI-команды (`/new`, `/undo`, `/redo`, `/sessions`, `/models`, `/connect`) | В web-`/` **не переносить**: это элементы UI/API; для мессенджеров — отдельный слой транспортных команд |
| 3 | Goal | Не команда этого PROP: это outer loop из [PROP-057](./prop-057-loop-engine.md), MVP-срез |
| 4 | `@` | Файлы, агенты, пользователи. Скиллы — только `$`. `@user` — граница: текст до него идёт агенту, текст от него — пользователю без запуска хода |
| 5 | `$` | Скиллы |
| 6 | `#` | Сниппеты, три уровня: `instance` / `project` / `user`; приоритет `user > project > instance`; без рекурсии |
| 7 | `!` | Shell-режим композера; вывод прикрепляется к следующему сообщению **по кнопке**; контракт исполнения — в [PROP-064](./prop-064-ui-browser-terminal.md) |
| 8 | `/review` для общих задач | Не вводить; достаточно git-гейта для кодового ревью |

## Предлагаемое решение

### 0. Карта префиксов

| Префикс | Где действует | Что означает | Позиция |
|---|---|---|---|
| `/` | начало сообщения | Команда (prompt/builtin/action) | Первый непробельный символ |
| `@` | в любом месте | Упоминание сущности: файл, агент, пользователь | Начало слова |
| `$` | в любом месте | Скилл | Начало слова |
| `#` | в любом месте | Сниппет | Начало слова |
| `!` | начало сообщения | Shell-режим | Первый непробельный символ |

**Общие правила парсинга.**

- Токен распознаётся только в начале слова (начало строки или после пробела/пунктуации), не внутри
  email, URL, `@scope/pkg` без совпадения с файлом, `$5`, `#123`.
- Внутри fenced/inline code блоков токены не распознаются.
- Неизвестный токен остаётся обычным текстом; ошибка не блокирует отправку.
- Экранирование — `\@`, `\$`, `\#`, `\!`.
- Для выбранного из пикера элемента вид известен точно (structured mention); для набранного вручную —
  разрешение по приоритету (см. §2).
- Парсер один — в core, чтобы UI/CLI/гибрид/шлюзы видели одно поведение ([ADR-046](./adr-046-skills-and-slash-commands.md)).

### 1. `/`-команды: что добавляем и что не добавляем

| Команда | Решение | Как |
|---|---|---|
| `/compact` | **Добавить** | Ручной запуск компактизации ([ADR-119](./adr-119-context-compaction.md)); отдельный статус резолва `compaction`, не `summarization` |
| `/summary` | Оставить | Текущая суммаризация; семантика не меняется |
| `/init` | Оставить | Уже реализован, генерирует prompt для `AGENTS.md` |
| `/review` | **Добавить условно** | Только если `project.workspace` — git-репозиторий и есть diff (uncommitted/commit/branch/PR). Иначе `available: false` с причиной `not_applicable` |
| `/new`, `/undo`, `/redo`, `/sessions`, `/models`, `/connect` | **Не добавлять** | Это UI-контролы и API; TUI-специфика. Для Telegram — транспортные команды шлюза |
| `/goal` | **Не добавлять** | Goal — outer loop [PROP-057](./prop-057-loop-engine.md); команда появится только вместе с его реализацией |
| `/skill-name` | **Deprecated** | Основной триггер — `$name`; старый `/skill-name` остаётся скрытым алиасом на переходный период |

`/review` не должен притворяться универсальным ревью. Для общих задач (документ, идея, план) —
отдельный скилл или шаблонная команда, а не встроенная `/review`.

**Транспортные команды шлюзов** (Telegram и др.) — отдельный слой: `/model`, `/session`, `/new` в
мессенджере мапятся на API-действия и не попадают в реестр промпт-команд Synth. Иначе один и тот же
`/` начинает означать разное в web и в Telegram.

### 2. `@` — упоминания файлов, агентов и пользователей

**Виды упоминаний.**

| Вид | Что делает | Ограничения |
|---|---|---|
| `file` | Добавляет файл в контекст сообщения | Только внутри `allowedRoots`/`project.workspace`; containment, symlink-escape, `storage.maxReadBytes`; текст встраивается до лимита, медиа — через blob-пайплайн ADR-115 |
| `agent` | Выполняет этот сегмент сообщения указанным агентом | Не повышает permissions; сегментация — как сейчас (`agentRole`), но парсер общий |
| `user` | Адресует сообщение участнику сессии/проекта | Только доступные пользователи; не раскрывает общий список; не даёт прав; уведомление + бейдж; **не запускает ход агента** |

**Payload.** Аддитивное поле в `POST /api/v2/sessions/:id/prompt`:

```json
{
  "content": "@src/index.ts @reviewer посмотри",
  "mentions": [
    { "kind": "file", "id": "src/index.ts", "label": "src/index.ts", "span": { "start": 0, "end": 13 } },
    { "kind": "agent", "id": "reviewer", "label": "reviewer", "span": { "start": 14, "end": 23 } }
  ]
}
```

Пример с пользователем:

```json
{
  "content": "Исправь баг X @alice проверь исправление.",
  "mentions": [
    { "kind": "user", "id": "u-alice", "label": "alice", "span": { "start": 14, "end": 20 } }
  ]
}
```

Текст сохраняет `@label` (пользователь видит, к кому/чему обратился); сервер валидирует `id` и
доступ. Неизвестный/недоступный id — `400 VALIDATION_ERROR` с перечнем проблемных, не молчаливое
исчезновение (как с вложениями, ADR-115).

**Разрешение набранного вручную `@token`.**

1. Точное совпадение с id агента сессии → агент.
2. Точное совпадение с username/display name доступного пользователя → пользователь.
3. Похоже на путь (есть `/` или `.`) и резолвится внутри roots → файл.
4. Иначе — литерал.

Если без пикера совпали агент и пользователь с одинаковым именем — показать диалог выбора перед
отправкой, не выбирать молча. Выбранный из пикера элемент всегда имеет фиксированный `kind`.

**Совместимость с текущим `@agent`.** Регулярку `@(\w+)` заменить на общий парсер упоминаний.
Сегментация по агентам сохраняется, но файлы и пользователи не должны попадать в `agentRole`.
Файлы и пользователи — уровень сообщения, а не отдельного агентского сегмента.

#### 2.1. `@user` — граница «агенту / пользователю»

Первое упоминание пользователя (вне code-блоков) делит сообщение на две части:

```text
Исправь баг X @alice проверь исправление.
└── агенту ──┘ └──── пользователю ────┘
```

| Часть | Куда идёт | Триггерит ход? |
|---|---|---|
| До первого `@user` | Текущему агенту (с обычной сегментацией по `@agent`) | **Да**, если непустая |
| От первого `@user` до конца | Пользователю (`@alice`), сразу в историю/чат | **Нет** |

Правила:

1. Если сообщение начинается с `@user` (до него нет текста) — агент не запускается вообще; создаётся
   только пользовательское сообщение.
2. В user-directed хвосте распознаются только `@user`-упоминания. `@agent`, `$`, `#` и `!` там —
   обычный текст: хвост не должен случайно запускать агента или раскрывать сниппет.
3. Несколько `@user` в хвосте — все получают уведомление и бейдж; сообщение одно, не по одному на
   каждого.
4. Упоминать можно только пользователей с доступом на чтение сессии. Недоступный/неизвестный
   пользователь — `400 VALIDATION_ERROR` до отправки, без частичной доставки. Self-mention
   допускается, но уведомление себе не отправляется.
5. Пользовательское сообщение сохраняется как `MessageRole.USER` с `author`/`principal` отправителя,
   `Message.mentions` и `metadata.userDirected = true`. Оно **не** ставится в очередь, не попадает в
   `steerInbox` и не запускает ход.
6. **Контекст.** Сообщение видно в истории и в UI сразу, но исключается из LLM-контекста текущего
   хода, если оно новее сообщения-триггера (сравнение по монотонному `seq`). В следующем ходе оно уже
   старше триггера и попадает в контекст. Если ход запущен не пользователем (scheduler/событие),
   исключаются сообщения новее `turn.startedAt`.
7. **Уведомления.** Публикуется событие `message.mentioned` в канал сессии: `{ message_id, user_ids,
   session_id }`. UI показывает бейдж в списке сессий и in-app уведомление; desktop/mobile push —
   если появится общий механизм уведомлений. Событие не создаёт ход.
8. **Порядок.** Агентская часть сначала проходит обычную очередь; пользовательская часть появляется
   внизу чата сразу. Агентская часть не ждёт пользовательскую и наоборот.
9. **Один запрос.** Клиент/CLI/гибрид присылают один `POST /prompt` с полным текстом и `mentions`;
   разбиение на очередь и user-directed сообщение делает core. Два отдельных запроса клиент не
   отправляет — иначе порядок и контекст разъедутся между клиентами.

**`@file` и шаблонные команды.** В `renderTemplate` уже есть серверная подстановка `@path`
(`packages/core/src/engine/commands/template.ts`). Новый парсер должен переиспользовать тот же
resolver/containment, а не заводить второй.

### 3. `$` — скиллы

- `$name` — пользовательский вызов скилла. Используется тот же резолвер, что у `/skill-name`.
- В контекст попадает **тело скилла**, а не вызов инструмента: `SkillRuntime.load` →
  `<skill_content>` + base dir + supporting-файлы; модель дальше сама вызывает тулы по permissions.
- Учитываются trust/scope/capabilities: недоверенный проектный скилл, отключённый scope или
  нехватка capabilities → `unavailable` с причиной; в промпт тело не грузится.
- `skill` tool остаётся для инициативы модели; `$` — только явный пользовательский выбор.
- Несколько `$` в сообщении допускаются, дубликаты схлопываются, порядок сохраняется.
- `/skill-name` — скрытый алиас на переходный период; `/skills` — список, не вызов.

**Физический ответ на вопрос «что делает скилл»:** подгружает инструкции в контекст сообщения.
Он не исполняет код и не даёт новых прав; supporting-файлы читаются по требованию (progressive
disclosure), а инструменты скилла — обычные тулы под permission-слоем.

### 4. `#` — сниппеты, три уровня

**Модель.** Сниппет — именованный текстовый фрагмент, который раскрывается в сообщении до отправки.
Не команда, не промпт, не скилл.

| Уровень | Где хранится | Кто пишет | Кто читает |
|---|---|---|---|
| `instance` | `{dataDir}/snippets/<name>.md` | ADMIN | все пользователи инстанса |
| `project` | `{project.workspace}/.synth/snippets/<name>.md` | OWNER/EDITOR проекта | участники проекта |
| `user` | `{dataDir}/snippets/users/<userId>/<name>.md` | сам пользователь | только он |

Хранение — через слой хранения/порт (`SnippetRepository`), не прямая запись в обход портов
([ADR-096](./adr-096-storage-layer.md)); проект — через workspace-провайдер.

**Формат.** Markdown с frontmatter: `description`, `aliases`. Имя — `[a-z0-9][a-z0-9_-]{0,79}`.
Тело — обычный текст. Рекурсия не поддерживается (решение владельца): `#` внутри тела сниппета
остаётся текстом. `<prepend>/<append>` — возможное расширение позже, в текущий объём не входит.

**Приоритет.** `user > project > instance`. Каноническое имя важнее алиаса. Коллизии — диагностика
`shadowed` (видно в настройках), проигравший не исчезает молча.

**Раскрытие.** В core, на входе промпта, до очереди и до LLM — чтобы CLI/гибрид/шлюзы получали одно
и то же. Один проход, без рекурсии; лимиты: не более 15 раскрытий и 64 КБ на сообщение; защита от
циклов; код-фенсы и inline-code не трогаются. Неизвестный `#token` остаётся текстом.

**Безопасность.** Проектные сниппеты — недоверенные, пока не доверен проект (как скиллы/команды).
Сниппеты раскрываются **только в пользовательском тексте**; в телах скиллов, шаблонных командах и
system-промптах — нет, иначе сниппет становится скрытым каналом инъекции. Содержимое не логируется;
пользовательские сниппеты изолированы по `userId`.

**UI.** Пикер `#` с группами по уровням; создание/редактирование; предпросмотр раскрытия; быстрые
сниппеты из выделения/сообщения — по образцу openchamber, но не в MVP.

### 5. `!` — shell-режим

- `!` в начале сообщения переводит композер в shell-режим; команда исполняется **тем же** путём, что
  `execute_shell`: ExecutionPort, permissions, containment, cwd проекта, timeout/лимиты. Отдельного
  PTY/exec-пути не появляется.
- Вывод — в панели терминала ([PROP-064](./prop-064-ui-browser-terminal.md)); по умолчанию в LLM не
  отправляется. Кнопка «прикрепить вывод» добавляет его к следующему сообщению; точный UX кнопки —
  при реализации терминала.
- `Esc` или пустой композер — выход из режима. В plan-режиме — read-only/запрет по общим правилам.
- Синтаксис и ограничения — здесь; PTY, транспорт и UI — в PROP-064.

### 6. Goal не входит в этот PROP

Goal — не ещё один префикс и не ещё одна команда. Это **outer loop** из
[PROP-057](./prop-057-loop-engine.md): objective, verification rubric (`judge`), termination guards
(`max rounds`, `no-progress`, `budget`). В PROP-057 добавлен MVP-срез «Goal Mode»; отдельная
подсистема не заводится.

## Не цели

- Перенос TUI-навигации и TUI-команд управления сессией/моделью/провайдером.
- Транспортные команды Telegram/мессенджеров в реестре `/` ядра.
- Реализация кода, миграции и API в рамках этого PROP.
- Замена `skill`-тула: `$` — пользовательский триггер, тул остаётся.

## Открытые вопросы

- `$` vs `/skill-name`: когда удалять скрытый алиас — сразу или после миграции документации/шаблонов?
- `@user`: один user-directed хвост на сообщение (предложение) или отдельное сообщение на каждого
  упомянутого? Сейчас зафиксирован один хвост.
- Контекстный фильтр `userDirected`: сравнение по `seq` сообщения-триггера (предложение) или
  отдельный `turnId`/`notBefore` в metadata?
- Уведомления: in-app + бейдж — в MVP; desktop/mobile push — когда появится общий механизм.
- Сниппеты: нужны ли `<prepend>/<append>` позже, или достаточно одного текстового тела?
- Единый парсер: где граница «core-парсер» vs клиентская подсветка/чипы, чтобы не дублировать
  правила разрешения?
