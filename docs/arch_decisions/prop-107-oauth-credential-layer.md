## Решение

Предлагается выделить в Synth **слой внешних доступов** — единую сущность «внешний доступ» (`ExternalCredential`),
которая:

- хранит OAuth-креды (access/refresh) и метаданные (провайдер, `client_id`, scope, срок, кто выдал);
- **шифруется мастер-ключом** (AES-256-GCM, формат `enc:v1:…`) — потому что токен нужен в исходном виде (как
  signing-секрет вебхуков), хеш не подходит (в отличие от service-key/binding-key, где секрет только проверяется);
- привязывается к **владельцу** (пользователь/инстанс) и к **коннектору** (MCP-сервер);
- **используется системой, а не агентом**: агент вызывает MCP-тул, токен подставляет транспорт — агент и модель
  токен не видят (это тот же инвариант, что у service-key: секрет — для машинной идентификации, не для промпта).

Предлагаемый состав слоя — пять частей:

| # | Часть | Суть | Ядро работы |
|---|---|---|---|
| 1 | **Порт хранилища** | `ExternalCredentialRepository` — доменный порт слоя хранения (ADR-096) | `storage/ports/external-credential-repository.ts` + file/memory/PG + контрактный suite |
| 2 | **OAuth-клиент** | Authorization Code + PKCE и Device Flow; refresh; revoke (RFC 7009) | `engine/oauth/` — через единый `egressFetch` (ADR-099) |
| 3 | **Биндинг «доступ → коннектор»** | коннектор ссылается на доступ, а не хранит `Authorization` в `headers` | `auth: { kind: 'credential', credentialId }` в `mcpServerConfigSchema` |
| 4 | **Аудит и метрики** | «кто и когда использовал доступ» без значения токена | аудит-скоуп/действие или отдельный append-only журнал (выбор — открытый вопрос) |
| 5 | **API/UI + обслуживание** | выдача/обновление/отзыв, ротация мастер-ключа, правила бэкапа и переноса | `createOAuthRoutes` (core) + раздел UI + `synth secrets rotate` |

Ключевая гипотеза: **доступ — это не «ещё один ключ», а ресурс с временем жизни**. Токен выдаётся внешним
провайдером, имеет `expires_at`, может быть отозван, требует refresh и должен уметь «истечь» — поэтому он
не ложится в существующие модели (`ServiceKey` — вечный, хешируемый; `WebhookSubscription` — секрет подписи,
выдаётся нашим кодом; `SSHKey` — приватный ключ агента).

## Детали

### 1. Модель сущности

Предлагаемая форма записи (набросок, не контракт):

```ts
interface ExternalCredential {
  id: string;
  /** Провайдер/коннектор: ключ описания OAuth-провайдера или id MCP-сервера. */
  provider: string;
  connectorId?: string;         // id записи реестра MCP (ADR-071)
  clientId: string;
  scopes: string[];
  /** Владелец: userId инстанса | 'local' (standalone) | 'instance' (инстансный доступ). */
  owner: { kind: 'user' | 'instance' | 'local'; id: string };
  projectId?: string;           // опциональная привязка к проекту
  /** Зашифровано мастер-ключом: access- и refresh-токен. */
  secretEnc: string;            // enc:v1:…
  refreshEnc?: string;          // enc:v1:…
  /** Открытые метаданные — для UI, поиска и аудита. */
  status: 'active' | 'expired' | 'revoked' | 'error';
  expiresAt?: string;
  revokedAt?: string;
  createdBy: string;
  createdAt: string;
  lastUsedAt?: string;
  scopesGranted?: string[];     // фактически выданные провайдером
}
```

Правила, которые предлагается зафиксировать:

- **Открыто** — `provider`, `clientId`, `scopes`, сроки, владелец, статус (метаданные нужны UI и аудиту).
- **Зашифровано** — только токены (`secretEnc`/`refreshEnc`): они нужны в исходном виде для подстановки в
  заголовок, поэтому хеш здесь неприменим (прецедент `webhook-store.ts`).
- **Маскирование** — в UI и в API-ответе токен не отдаётся никогда; показывается префикс/маска
  (по образцу `secretPrefix` у сервисных ключей), а `GET` отдаёт только метаданные.
- **Порядок владения** — `owner` — часть записи, а не вычисляемое поле: доступ может быть инстансным и не
  принадлежать ни одному пользователю (например, корпоративный доступ, выданный админом).

### 2. Владение и гранулярность

Предлагается различать три вида доступа (решение — открытый вопрос):

| Вид | Владелец | Кто выдаёт | Аналог в коде |
|---|---|---|---|
| **Пользовательский** | конкретный пользователь инстанса | сам пользователь | `ServiceKey` с `roles`/`scopes`/`allowedProjects` (ADR-052) |
| **Инстансный** | инстанс (`kind:'instance'`) | `ADMIN`/`LEAD` | `binding-key` привязки (ADR-089) |
| **Локальный** | `local` (standalone, single-user) | владелец инстанса | всё, что в standalone нормализуется к `local` (инвариант 19) |

Гранулярность «коннектор × владелец × проект» — предлагается как **минимальная единица доступа**: один доступ
привязан к одному коннектору; один и тот же провайдер у разных пользователей — разные записи. Привязка к проекту
(`projectId`) — опциональная: доступ уровня проекта виден его участникам, доступ уровня пользователя — только ему.

Делегирование между участниками проекта (передать доступ коллеге) — **отдельный вопрос**: если разрешить, нужен
явный «передал» и аудит; если запретить, то доступ привязывается к владельцу намертво.

### 3. Refresh

- **Где хранится** — `refreshEnc` рядом с access-токеном, тем же мастер-ключом.
- **Кто инициирует** — предлагается перехват `401`/`invalid_token` **в транспорте** MCP: клиент один раз
  обновляет токен и переподключается. Альтернативы: фоновая задача по расписанию (нужна инфраструктура
  планировщика — ADR-051) или явный вызов из UI/API.
- **Защита от гонки** — два параллельных refresh одного доступа: нужен «сема» на запись (по образцу `AsyncLock`
  в сторах) либо compare-and-swap по `refreshEnc` (ротация refresh-токена после использования — типичное поведение
  провайдеров). Предлагается CAS: кто первый обновил — тот и записал новый `refreshEnc`, второй увидел
  расхождение и перечитал.
- **`invalid_grant`** — refresh-токен отозван на стороне провайдера: доступ переводится в `status:'error'`,
  доступность коннектора — в «требуется переавторизация», в UI — явная кнопка; молчаливый отказ коннектора
  недопустим.

### 4. Revoke

- **Локальный отзыв** — запись помечается `revokedAt`, токены стираются (или остаются зашифрованными, но не
  используются — вопрос к владельцу: нужен ли «мягкий» отзыв с сохранением истории).
- **Вызов провайдера** — RFC 7009 (`revoke_refresh_token` уже есть в `packages/core/src/remote/device-flow.ts:311`);
  best-effort: провайдер может не поддерживать revoke.
- **Кто может отозвать** — владелец доступа; `ADMIN`/`LEAD` — инстансные; чужие пользовательские — нет.

### 5. Биндинг к MCP

Предлагается новое поле в `mcpServerConfigSchema` вместо `Authorization` в `headers`:

```ts
auth?: { kind: 'credential'; credentialId: string };
```

- Коннектор ссылается на доступ **по id**; сам токен в реестре не лежит.
- Что делать с существующими записями, где `Authorization` уже в `headers`: предлагается **валидация при записи**
  (предупреждение + отказ или флаг) и **миграция** существующих записей — либо оставить как есть с явным
  предупреждением в UI, либо предложить «перенести в доступ» (нужен одноразовый импорт значения из реестра).
- **Refresh при живом транспорте**: `requestInit.headers` в MCP-клиенте статичны (`client.ts:198-202`) — при
  обновлении токена транспорт нужно пересоздать (или перевести на динамический `fetch`, который подставляет
  заголовок на каждый запрос — предпочтительнее, но это правка SDK-обвязки).
- **Probe** (`POST /api/v2/mcp/probe`) должен использовать тот же доступ, что и рабочее подключение.

### 6. Запрет plaintext-секретов в конфиге

- `mcpServerConfigSchema` (`packages/shared/src/config/types.ts:275-300`) — валидация при записи реестра:
  заголовки вида `authorization`, `proxy-authorization`, `x-api-key`, `cookie` — **не принимаются** в `headers`
  (или принимаются только с явным флагом «миграция»).
- Клиентский `client_secret` коннектора — **не** в `config.yaml` и не в реестре: только env или файл
  (`{dataDir}/secrets/…`), по образцу паролей PostgreSQL и прокси (инвариант 13); API — write-only, значение
  не возвращается.
- Формулировка «в конфиге нельзя» — не абсолютная: `env` stdio-сервера технически может нести токен, но это
  отдельный канал (переменные окружения дочернего процесса), и его тоже стоит пометить как «секрет по
  соглашению», а не по гарантии.

### 7. Egress и безопасность

- **Host-binding заголовков**: `egress-guard.ts:386` спредится `init.headers` на каждый хоп редиректа. Для
  OAuth-вызовов нужен режим «заголовки только для исходного хоста» — иначе `Authorization` утекает на
  redirect-хост (и на чужой домен, если провайдер редиректит).
- **Токен — только в `Authorization`**: отдельные заголовки (`X-Api-Key` и пр.) — как правило, тоже секрет; если
  провайдер требует иной схемы, это описание провайдера, а не «произвольный заголовок из реестра».
- **Нет утечки в логи/телеметрию**: обфускация по образу ADR-036 (Gateway), метрики — только фиксированные
  лейблы ADR-094 (`provider`, `status`, `outcome`); `session_id`/`user_id`/сырые пути — запрещены.
- **Аудит использования**: запись «доступ X использован коннектором Y» без значения токена.

### 8. Аудит

Два варианта — оба с trade-off, выбор владельца:

| Вариант | Плюсы | Минусы |
|---|---|---|
| **А. Расширить общий security-аудит** (`SECURITY_AUDIT_SCOPES`/`ACTIONS` в `packages/shared/src/types/egress.ts:131-135`) | один журнал, одна выдача, привычный UI | это **публичный контракт `shared`** → breaking change; текущая модель записей — «снимок политики `before`/`after`», а не «событие использования» — семантика не совпадает |
| **Б. Отдельный append-only журнал credential-операций** (по образу `{dataDir}/audit/security.jsonl` и `audit/plugins.jsonl` из PROP-090) | не трогает публичный контракт; семантика «события доступа» выражается честно; можно задать свою retention | второй журнал, вторая выдача в UI, риск «разъедутся» с общим аудитом |

### 9. Порт и бэкенды

- Новый доменный порт `ExternalCredentialRepository` в `packages/core/src/storage/ports/` (конвенция
  `*Repository`), добавление в `StorageContext` (`storage-context.ts:245-326`), в `createFileStorage` (490) и
  `createMemoryStorage` (562), в async-каскад (`createStorageContextAsync` 884 / `buildStorageContext` 954) и в
  драйвер `packages/storage-postgres/src/ports/*`.
- **Контрактный suite** — в `packages/core/src/storage/contract/` (паспорт порта): уникальность, идемпотентность
  revoke, отсутствие plaintext в `list`/serialize, поведение при `invalid_grant`.
- **Деградация** — при `storage.degradedMode=fallback-file` порт на запись отдаёт `503
  STORAGE_DEGRADED_READONLY` (общее поведение read-only фоллбэка, `storage-context.ts:219,834`).
- **Шифрование** — через core-хелперы (`encryptSecret`/`decryptSecret`), в PG — как у SSH-ключей
  (`private_enc` + ленивый `import()` core, `packages/storage-postgres/src/ports/content.ts:605`): дублировать
  криптографию в драйвере нельзя.

### 10. Ротация и бэкап

- **Ротация мастер-ключа**: `synth secrets rotate` (`packages/core/src/security/rotate.ts:107-108`) сейчас
  перешифровывает **только** SSH-ключи. Новый порт обязан быть включён в тот же one-shot (preflight + `--dry-run`
  + `--yes`, счётчики `rotated`/`upgraded`/`skipped`). Отдельно: секреты вебхуков сейчас **не** перешифровываются —
  это существующий долг, который этот же файл ротации должен в итоге покрыть.
- **Бэкап** (`packages/core/src/maintenance/backup.ts:133`): без `--with-secrets` исключается только `secrets/`.
  OAuth-токены, лежащие в обычном JSON, попадут в архив **всегда**. Предлагается: токены — **не** в обычном
  JSON, а в отдельном каталоге, который бэкап по умолчанию исключает (как `secrets/`), либо явный флаг
  `--with-oauth-credentials` + предупреждение «архив содержит секрет».
- **Перенос проекта** (`synth project export/import`, ADR-091 §6) — по умолчанию **без** токенов: доступы
  инстанс-локальны и не переносятся (как binding-key).

### 11. Standalone vs managed vs гибрид

| Контур | Владелец по умолчанию | Особенности |
|---|---|---|
| **standalone** (`synth serve`) | `local` (единственный пользователь) | один «инстансный» доступ на коннектор по умолчанию |
| **managed** (backend + Keycloak) | конкретный пользователь; инстансные — `ADMIN`/`LEAD` | доступ проверяется на границе (инвариант 16), `requireScope`/проектная проекция — по образу service-key |
| **гибрид** (ADR-042, PROP-080/081) | локальный инстанс | креды **инстанс-локальны** (не переносятся publish/fork, как binding-key); политики `forbidden`/`remote-only`/`full` (PROP-081) должны решить, допустим ли вообще доступ к внешним сервисам в режиме `remote-only` |
| **local home** (ADR-079) | отдельное место | не смешивать с `<home>/credentials.json` (это креды самого Synth к серверу, а не к внешним сервисам) |

### 12. API/UI

Общая логика — в core-фабрике `createOAuthRoutes` (по образцу `createMcpRoutes`, `createServiceKeyRoutes`), backend
монтирует её и добавляет RBAC через `opts.writeGuard`/`opts.readGuard` (дублировать хендлеры в backend нельзя).

| Метод/путь | Назначение | Права |
|---|---|---|
| `POST /api/v2/oauth/credentials` | начать выдачу (PKCE/device flow) или принять код | владелец; `ADMIN`/`LEAD` — для инстансных |
| `GET /api/v2/oauth/credentials` | список **метаданных** (без токена) | свои; `ADMIN`/`LEAD` — все |
| `GET /api/v2/oauth/credentials/:id` | метаданные одной записи | владелец / участник проекта / `ADMIN`/`LEAD` |
| `POST /api/v2/oauth/credentials/:id/refresh` | форсированное обновление (диагностика) | владелец |
| `DELETE /api/v2/oauth/credentials/:id` | отзыв (локальный + best-effort вызов провайдера) | владелец; `ADMIN`/`LEAD` — инстансные |
| `POST /api/v2/oauth/credentials/:id/bind` | привязать доступ к MCP-коннектору | владелец / `ADMIN` |

Спека формата — в `docs/API_V2.md` (отдельным шагом; здесь — только карта).

UI: раздел **«Доступы»** — рядом с «MCP» (`personal`, `packages/ui/src/lib/settings-catalog.ts:98-104`) и, если
доступы институциональные, в `adminIntegrations` рядом с `serviceKeys`. Секреты в UI — **write-only**
(как в `ServiceKeysSettings`): значение токена не показывается, только маска и срок.

### 13. Роль плагинов

Открытый вопрос с двумя вариантами:

- **А. Плагин приносит только описание провайдера** (`client_id`, `authorize_url`, `token_url`, список scope) —
  креды живут в ядре, плагин получает доступ по ссылке, но не сам секрет. Совпадает с моделью доверия PROP-090:
  `community` — только наблюдение, `permissions.secrets` плагинам не выдаётся.
- **Б. Плагин приносит свой вид авторизации** (`provides.oauth` как новый вид вклада в `synth.pack` —
  `packages/shared/src/types/pack.ts:227-235` сейчас `.passthrough()`, места под новый вид нет). Тогда нужен
  sandbox: плагин получает «слепой» доступ (вызвать refresh по токену, не видя токена) — то есть контракт уровня
  «прокси-функции», а не «выдай мне секрет».

Предлагается начать с **А** (описание провайдера — данные, не код), **Б** — после появления Plugin SDK (PROP-090).

### 14. Этапы

Критерии приёмки — по образцу PROP-090 (фазы Ф0–Ф4).

**Ф0 — контракты.** Порт `ExternalCredentialRepository`; схема `ExternalCredential` в `@itphx/synth-shared`;
поле `auth` в `mcpServerConfigSchema`; **решение по аудиту** (вариант А или Б из §8) — зафиксировано здесь,
не отложено на Ф4.

**Ф1 — хранилище.** Реализации file/memory/PG + контрактный suite; шифрование `enc:v1:`; маскирование; тест
«в реестре, в бэкапе и в логах нет plaintext-токена».

**Ф2 — OAuth-клиент.** Выдача кода (PKCE и/или device flow), refresh, revoke; **всё через `egressFetch`**
(ADR-099); тест «заголовок `Authorization` не уходит на redirect-хост».

**Ф3 — биндинг к MCP.** Коннектор ссылается на доступ; запрет plaintext-`Authorization` в `headers`
(валидация + миграция существующих записей); refresh пересоздаёт транспорт; `probe` использует доступ.

**Ф4 — API/UI и обслуживание.** Роуты `createOAuthRoutes` + монтирование в backend; раздел UI; аудит и метрики;
включение порта в `synth secrets rotate` (preflight, счётчики); правила бэкапа и переноса проекта.

## Открытые вопросы

1. **Чей токен** — пользователя, инстанса или проекта по умолчанию? Что делает standalone без пользователей
   (единственный владелец `local`)?
2. **Гранулярность** — единица доступа: коннектор × владелец × проект? Нужен ли один доступ, пригодный для
   нескольких коннекторов одного провайдера?
3. **Refresh** — кто инициирует: перехват `401` в транспорте, фоновая задача или явный вызов? Как защищаемся от
   параллельного refresh (сема vs CAS по `refreshEnc`)?
4. **Отзыв** — кто может отозвать чужой пользовательский доступ? Нужен ли «мягкий» отзыв с сохранением истории
   или доступ удаляется безвозвратно?
5. **Делегирование** — можно ли передать доступ другому участнику проекта (и как это аудируется)?
6. **Перенос и бэкап** — токены по умолчанию исключаются из архива и из `project export`? Отдельный флаг или
   предупреждение?
7. **Гибрид** — как доступы соотносятся с политиками ADR-042/PROP-081 (`forbidden`/`remote-only`/`full`):
   допустим ли в `remote-only` доступ к внешним сервисам вообще?
8. **Аудит** — расширять публичный контракт `SECURITY_AUDIT_SCOPES`/`ACTIONS` в `shared` (breaking change) или
   заводить отдельный журнал credential-операций?
9. **PKCE или `client_secret`** — у backend'а OIDC confidential-клиент без PKCE
   (`packages/backend/src/auth/oidc.ts:8`); какой режим по умолчанию для внешних коннекторов и как живём с
   провайдерами, требующими `client_secret`?
10. **Каталог коннекторов** — PROP-068: это часть каталога скиллов/агентов или отдельная сущность
    «коннекторы»? Где хранится каталог и кто его наполняет?
11. **Кто владеет описанием провайдера** — конфиг инстанса, реестр MCP, пакет расширения (`synth.pack`) или
    внешний каталог?
12. **Ротация** — включать порт в `synth secrets rotate` отдельной задачей или частью Ф1? И заодно — покрывать
    ли там же существующий долг с секретами вебхуков?
13. **`web_fetch`/`web_search`** — нужны ли им заголовки авторизации (и тогда — с какими ограничениями), или
    доступы остаются только в MCP-коннекторах?
14. **Плагины** — может ли плагин принести свой OAuth-провайдер (`provides.oauth`), и если да — какой контракт
    доступа без выдачи секрета?
