## Решение

Переход физического хранилища истории с JSON-файлов ([ADR-005](./adr-005-json-storage.md)) на **PostgreSQL** с нормализованной схемой «сессия → сообщения → части» (миграции, схема БД).

---

## Контекст

Claude Code хранит историю в плоских JSONL-файлах (`~/.claude/transcripts/{sessionId}.jsonl`), саб-агенты — в sidechain. Это просто, но не даёт parent-child связей и запросов между сессиями. OpenCode использует нормализованную модель с parent_id — лучшая основа для командной работы.

---

## Детали

### Логическая модель

```
Сессия (id, parent_id, project_id, agent, title, ...)
  │
  ├── parent_id → Сессия (parent-child дерево)
  ├── project.plan → kanban-план (ADR-039; ранее plan_path)
  ├── branch_point → точка развилки для дочерних веток
  │
  └─1:N──→ Сообщение (id, session_id, seq, role, content, origin, source_msg_id, ...)
              │
              ├── seq — порядковый номер, уникален внутри сессии
              ├── origin: local | inherited | merged | crosspost
              ├── source_msg_id → Сообщение (откуда пришло)
              │
              └─1:N──→ Часть (id, message_id, type, data)
                          ├── type: text | tool_use | tool_result | reasoning
                          └── data — содержимое блока
```

### Ключевые сущности

| Сущность | Назначение |
|---|---|
| **Сессия** | Контейнер диалога. Имеет `parent_id` — дерево сессий. Хранит `agent`, `branch_point` |
| **Сообщение** | Одна реплика (user/assistant/tool/system). Имеет `seq` — порядок внутри сессии. Имеет `origin` — откуда пришло |
| **Часть (part)** | Блок контента внутри сообщения: text, tool_use, tool_result, reasoning. Одно сообщение → много частей |
| **context_snapshot** | Сжатый контекст для summary-режима саб-агентов. Создаётся через отдельный LLM-вызов |

### Origin tracking — отслеживание происхождения сообщения

| origin | Как попало в сессию | source_msg_id |
|---|---|---|
| `local` | Создано в этой сессии (дефолт) | NULL |
| `inherited` | Унаследовано от родительской сессии (ветвление) | ID оригинального сообщения |
| `merged` | Скопировано из другой сессии пользователем (smart paste) | ID оригинального сообщения |
| `crosspost` | Существует в нескольких сессиях одновременно | Синхронизировано |

### Физический уровень (не реализовано)

- Целевое хранилище: **PostgreSQL** (нормализованная схема). Идём сразу в PostgreSQL — SQLite как промежуточный вариант не используется.
- Логическая модель уже живёт в JSON-схеме ([ADR-005](./adr-005-json-storage.md)) и используется ветвлением/merge ([ADR-033](./adr-033-session-branching-merge.md)); миграция затрагивает только физический слой — схему БД и перенос данных.
- Сущность `context_snapshot` (сжатый контекст для `summary`-режима) пока не выделена — `summary` реализован через `ContextOptimizer.summarize()` с кэшем ([ADR-026](./adr-026-subagent-context-modes.md)).

## Альтернативы (выбор СУБД)

**Решение не меняется: целевое хранилище — PostgreSQL** (нормализованная схема, см. «Детали» и «Физический
уровень»). Раздел фиксирует, что альтернативы рассмотрены осознанно, и задаёт критерии, при которых выбор
пересматривается. Смена СУБД — не правка этого предложения, а отдельное решение.

### Рассмотренные варианты

- **PostgreSQL** — реляционная СУБД с полным SQL/DML, `WITH RECURSIVE` под дерево сессий (`parent_id`),
  зрелыми ORM/миграциями и предиктивным бэкапом (WAL/PITR). Дефолт по умолчанию. Уже упомянута целевой в
  [ADR-005](./adr-005-json-storage.md) и [PROP-094](./prop-094-observability-metrics.md).
- **YDB** — распределённая SQL-СУБД (YQL, частичная совместимость с PostgreSQL-диалектом), нативная
  горизонтальная масштабируемость и распределённые ACID-транзакции; есть K8s-оператор и managed-вариант.
  Рассматривается всерьёз как **альтернатива при требованиях распределённости/мульти-ДЦ** или если заказчик
  уже стандартизирован на YDB. Не выбран дефолтом: меньше зрелость экосистемы (ORM/миграции) и больший порог
  эксплуатации для self-host-инсталляции «из коробки».
- **SQLite и встроенные (libSQL, DuckDB, bbolt)** — кратко: нулевая внешняя зависимость, идеальны для
  standalone, но не дают сетевого доступа, распределённости и транзакций между процессами; серверный
  многопользовательский и managed-контур не покрывают. Остаются на уровне «локальный кэш», не хранилище
  истории (в текущем решении сразу идём в PostgreSQL, SQLite как промежуточный шаг не используется).
- **Документные (MongoDB, CouchDB)** — кратко: гибкая схема, но нет нормализованных связей «сессия →
  сообщение → часть», `parent_id`/`seq`/дедуп приходится эмулировать; PITR слабее/дороже, лицензия/opex
  менее предсказуемы. Не подходят под нормализованную модель [ADR-033](./adr-033-session-branching-merge.md).

### Матрица сравнения (PostgreSQL vs YDB)

| Критерий | PostgreSQL | YDB |
|---|---|---|
| SQL/DML-совместимость и переносимость запросов | Полный SQL; нормальные запросы, `JOIN`, `WITH RECURSIVE`; стандартные драйверы (`pg`) | YQL — SQL-подобный диалект; часть PostgreSQL-синтаксиса не переносится, запросы исторически пишутся под YDB |
| K8s-оператор / эксплуатация | Зрелые операторы (CloudNativePG, Zalando, Patroni); обширная практика, много готовых чартов | `ydb-operator`; практики меньше, топология сложнее (storage/compute-узлы) |
| Managed-варианты | Практически во всех облаках и on-prem-платформах | В первую очередь Yandex Cloud; вне него — self-host-развёртывание |
| HA / распределённость | HA через репликацию/Patroni (leader + replica); шардинг отдельными решениями (Citus и др.) | Нативные распределённые ACID-транзакции и горизонтальная масштабируемость «из коробки» |
| Бэкапы / PITR | WAL-архивирование + PITR, `pg_basebackup`, зрелые инструменты (pgBackRest и др.) | Средства YDB; PITR — да, но инструментов и практик меньше |
| Лицензия | PostgreSQL License (permissive, аналог BSD/MIT) | Apache 2.0 |
| Зрелость экосистемы (ORM/миграции) | Максимальная: Prisma/Drizzle/Kysely, `node-postgres`, миграции любого вида | Заметно уже: ORM/миграции и тулинг ограничены, часто «ручной» SQL |
| Стоимость эксплуатации | Ниже: кадры и компетенции доступны, ресурсы предсказуемы для одного инстанса | Выше порог (компетенции, топология); выгода проявляется на масштабе/мульти-ДЦ |
| Соответствие RU-enterprise требованиям | Широко принят, есть реестры и поддержка отечественных дистрибутивов/облаков | Входит в реестр отечественного ПО, часто предпочтителен там, где стандарт — Yandex-технологии |

### Вывод и критерии пересмотра

- **PostgreSQL — дефолт.** Для self-host-инстанса Synth (один узел, десятки–сотни сессий) PostgreSQL даёт
  максимальную зрелость, минимальный opex и предсказуемый PITR.
- **YDB пересматривается**, если выполнено хотя бы одно:
  1. появляются требования **распределённости/мульти-ДЦ** (геораспределение, отказоустойчивость уровня
     региона, нативная горизонтальная масштабируемость хранилища);
  2. **заказчик стандартизирован на YDB** (технологический стек, реестры, компетенции эксплуатации);
  3. объём истории/нагрузка выходят за пределы удобного шардинга PostgreSQL для целевой инсталляции.
- До наступления этих условий выбор — PostgreSQL; SQLite/встроенные и документные варианты не используются
  как хранилище истории (только как потенциальный локальный кэш).
