# PROP-138: Контур исполнения плагинных инструментов: capability → пул, `ctx.runtime`

> **Статус:** 🧩 Предложение — capability плагинного тула определяет контур: файловые/git/shell-тулы плагина идут на пул сессии через `ctx.runtime`, шлюзы остаются отдельными HTTP-сервисами

## Решение (предложение)

**Правило.** Capability плагинного тула определяет контур исполнения:

| Capability | Контур |
|---|---|
| `file_read`, `file_write`, `shell`, `search`, `git_read`, `git_write` | пул сессии — через узкий runtime-интерфейс |
| `web`, `memory`, `user` | control plane |

Плагинный тул **не получает** прямого доступа к ФС control plane как поддерживаемого пути.

**`ctx.runtime`.** Хост инжектит узкий объект, привязанный к пулу сессии: `exec(argv)`, `fs.read/write/list/stat/realpath`, `git` (через существующие операции). `ctx.extra`/`ctx.dataDir` по-прежнему **не передаются**. Использование `node:fs`/`child_process` в плагине — неподдерживаемый путь; сканер и ревью помечают его явно.

**Out-of-process.** Wire protocol v2: `POST /runtime/exec`, `POST /runtime/fs/*` — через хост (bearer-токен плагина, привязка к `sessionId` вызова). Плагин **не ходит** к исполнителю напрямую: единственная точка — хост, он же применяет permission-слой и аудит.

**Шлюзы.** Остаются отдельными деплойментами (HTTP-сервисы): приём и доставка сообщений, API, без ФС агента. Перенос шлюзов в контур исполнителя не предусмотрен.

**Совместимость.** Встроенные и MCP-тулы не меняются. Существующие плагины с ФС-capability переводятся на `ctx.runtime`; без миграции — предупреждение при загрузке и работа по старому пути только в `inline`/standalone (managed — запрет).

## Границы

Не входит: plugin-runtime внутри исполнителя (альтернатива, отдельное решение), доверие к недоверенным плагинам, каталог плагинов.

## Этапы

- **Ф1** — `ctx.runtime` в inline + capability-гейт.
- **Ф2** — wire v2 для out-of-process.
- **Ф3** — предупреждения/запрет прямого `node:fs` в managed, миграция существующих плагинов.
