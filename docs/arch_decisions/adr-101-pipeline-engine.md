## Контекст

[ADR-100](./adr-100-extension-packs-pipelines.md) ввёл пайплайн как **декларацию + учёт прогона**: определение
приходит пакетом расширения, шаг — обычная агентская сессия, порождённая funnel'ом
([ADR-089](./adr-089-external-events-automation.md)), состояние ведёт `PipelineTracker`. Для «декларации + учёта»
этого хватает, для движка — нет:

- **шаг закрывается не по факту хода** (хук «ход завершён» живёт в оркестраторе, вне контура funnel): трекер
  переводит шаг в `done` при следующем событии пайплайна;
- **поля шага не читаются**: `prompt`/`skill` не доходят до модели — вход шага = payload события;
- **нет переходов, версий и выхода**: ветвление, неизменяемая версия спецификации и «что делает прогон по
  завершении» не выразимы; правка определения молча меняет смысл идущих прогонов;
- **нет привязки к проекту**: определения инстансные, видимость — ADMIN, у прогона нет `projectId` — значит,
  нет ни прав, ни workspace, ни MCP-скоупа проекта; артефакт между шагами = payload события, то есть передача
  результата не отделена от транспорта событий.

При этом цикл «событие → шаг → подтверждение человеком → следующий шаг» уже нужен add-on'у `synth-media`, а
собственного движения шагов нет.

## Решение

1. **Пайплайн — второй движок.** `PipelineEngine` — самостоятельный оркестратор рядом с `ChatOrchestrator`.
   **Шаг пайплайна не является сессией**: сессия — только вход (запуск из сессии) или выход (финальный шаг
   создаёт/продолжает сессию). Шаг исполняет движок со своей локальной историей; в запрос к LLM уходит не
   вся история, а только то, что отображено **маппингом входа** шага (выход предыдущего шага / payload
   триггера / явно заданные переменные).
2. **Пайплайн принадлежит проекту** (`projectId`), видимость — как у сессий проекта. Пайплайны из пакетов
   расширений (`synth.pack`, `provides.pipelines[]`) — **шаблоны инстанса**; проект инстанцирует шаблон в свой
   пайплайн (копия → черновик со своими версиями).
3. **Формат фиксирован, но не избыточен.** Единый вход `PipelineRunTrigger` (имя `PipelineTrigger`
   занято legacy-контрактом ADR-100 в `types/pipeline.ts`; `kind` =
   `user|gateway|schedule|tool|webhook|manual`, `source`, `type`, `payload`, `dedupKey`) и единый выход шага
   `StepResult` (`status` = `ok|failed|skipped|awaiting_human`, `output`, `artifacts`, `error`, тайминги,
   `attempt`). **Опциональная** `io`-схема (JSON Schema) объявляется конкретным пайплайном — тогда границы
   валидируются строго.
4. **Виды шага:** `agent` (свой Tool-Use-цикл внутри движка), `script` (только через shell-policy — не голый
   `child_process`), `tool` (через `ToolRegistry`), `human` (HITL-гейт: пауза прогона, ожидание действия
   человека + таймаут).
5. **Условные переходы** — структурированный DSL `{path, op, value}`: пути `prev.output.x`,
   `trigger.payload.y`, `vars.z`; операторы `eq|ne|in|exists|gt|lt`. **Никакого `eval`/произвольного кода в
   ядре.**
6. **Разрешения.** У пайплайна свой режим (`plan|act|yolo`), объявляемый в спецификации. Тулы с
   `ask`-политикой в пайплайне **эскалируются в human-шаг (HITL)** — наблюдателя-сессии нет. Пайплайн не
   должен стать обходом permission-слоя.
7. **Версии.** Спецификация версионируется: черновик (`draft`) редактируется, публикация (`published`)
   фиксирует неизменяемую версию; прогон всегда ссылается на конкретную `pipelineId@version`.
8. **Журнал выполнения — append-only:** заголовки прогонов и события прогона (шаг начался/завершился, переход
   по ребру, ожидание человека, падение). Прецедент в репо: `scheduler/jobs.jsonl`,
   `webhooks/deliveries.jsonl`, `audit/maintenance.jsonl`.
9. **Выход пайплайна:** `session` | `file` (в workspace проекта) | `gateway` (событие/webhook наружу) | `none`
   — задаётся exit-спецификацией.
10. **Переиспользуется существующее ядро** (не дублируется): `GatewayProvider` (ADR-036),
    `PermissionEvaluator` (ADR-025/028/029), `ToolRegistry` + `executeToolDef`
    (`engine/tools/tool-execution.ts`), `SystemPromptComposer`/`ContextBuilder` (ADR-070 — контракт сужается
    до минимального «session-like» интерфейса, обычная `Session` остаётся структурно совместимой), MCP-скоуп
    по проекту (ADR-071), резолвер проектных инструкций (ADR-069), shell-policy/protected paths, i18n-ключи
    `shared/i18n`, реестр метрик (ADR-094), шина событий — новые **типы** событий `pipeline.run.*` в
    существующей шине (новых каналов не заводим).
11. **Границы.** Loop Engine ([PROP-057](./prop-057-loop-engine.md)) не трогаем; rollback/exit-стратегия,
    мониторинг-дашборд и отдельное хранилище артефактов остаются за §«Открытые вопросы»
    этого ADR. Визуальный редактор — `@xyflow/react` (новая зависимость,
    разрешена владельцем), но **IR — собственный `PipelineSpec`**, а не формат React Flow (JSON/YAML — источник
    истины).

## Статус в коде

- **Есть ([ADR-100](./adr-100-extension-packs-pipelines.md)):** контракт манифеста `synth.pack` и валидация;
  установка пакета одной операцией (`POST /api/v2/packs`) с одобрением администратора; порты
  `PipelineRepository`/`PackRepository` (ADR-096) и файловая реализация
  (`{dataDir}/pipelines/{definitions,instances}.json`); типы пайплайна в `shared` (`types/pipeline.ts`);
  `PipelineTracker` (учёт экземпляров в funnel); роуты `/api/v2/packs`, `/api/v2/pipelines`; раздел «Аддоны» в
  UI. Это **промежуточная** реализация: «декларация + учёт», без движения шагов. После Э6–Э7 она
  остаётся **legacy-контуром** (работает, удаления не планируется): основной контур пайплайнов —
  §5.35 API и UI нового движка; legacy-определения по-прежнему показываются в разделе «Аддоны» и
  доступны как **шаблоны инстанса** (конвертация на лету — см. «Закрытые вопросы»).
- **Сделано (Э1):** контракты `shared` — `packages/shared/src/types/pipeline-engine.ts` —
  Zod-схемы и типы (`PipelineSpec`/`PipelineNode`/`PipelineTransition`/`PipelineCondition`/`PipelineExit`/
  `PipelineRunTrigger`/`StepResult`/`PipelineRun`/`PipelineRunEvent`) + валидатор графа `validatePipelineSpec`
  (проблемы строками, без throw). Legacy-контракты ADR-100 (`types/pipeline.ts`) не тронуты — они
  остаются в коде (имя `PipelineTrigger` занято ими, поэтому новый триггер — `PipelineRunTrigger`).
- **Сделано (Э2):** порты слоя хранения (ADR-096) — `ProjectPipelineRepository` (черновик + журнал
  опубликованных версий) и `PipelineRunRepository` (прогоны + append-only журнал), файловая и in-memory
  реализации, контрактный suite; порты доступны в `StorageContext` как `projectPipelines`/`pipelineRuns`.
- **Сделано (Э3):** движок — `packages/core/src/engine/pipelines/` (`PipelineEngine`): цикл прогона по
  опубликованной версии спецификации, вычисление условий (структурированный DSL, fail-soft), маппинг
  входа, выбор следующего узла (порядок переходов, линейный переход, лимит переходов), ретраи и
  таймауты шага, HITL-пауза (`awaiting_human`) и возобновление (`resume`), отмена через `AbortSignal`,
  журнал прогона (append-only, санитизация payload'а от секретов). Исполнители видов шагов — Э4;
  выходы пайплайна — только фиксируются (точка расширения `PipelineExitHandler` — Э5).
- **Сделано (Э4.1):** контекст шага — `packages/core/src/engine/pipelines/step-context.ts`
  (`buildPipelineStepContext`): проект (порт проектов), рабочий каталог (ADR-075; каталог не
  создаётся молча, нет workspace → `workspaceReady: false` и file/shell/git-тулы недоступны с
  причиной `workspace`), режим пайплайна (ADR-025), инструменты (`ToolRegistry` + MCP-тулы,
  доступность — общий `computeToolAvailability`, ADR-070 §2.9.1), MCP-скоуп по системе и проекту
  без сессионного снапшота (`resolveMcpProjectScope`, ADR-071), проектные инструкции (ADR-069),
  каталог скиллов system/project (ADR-046) и агент шага (`AgentRegistry`). Контракт Composer'а
  сужен до `ComposerSessionLike = Pick<Session, 'settings' | 'promptStates' | 'projectId'>`
  (`engine/context/composer.ts`) — обычная `Session` остаётся структурно совместимой.
  Исполнители видов шагов — Э4.2/Э4.3.
- **Сделано (Э4.2):** permission-обёртка пайплайна (`engine/pipelines/permissions.ts` —
  `checkPipelineToolPermission` поверх `PermissionEvaluator.check()`; режим пайплайна идёт как
  `sessionMode`, `planApproved: true`; `deny` → шаг `failed` с `permission.denied`, `ask` →
  эскалация в гейт) и исполнители видов `tool`/`script`/`human`
  (`engine/pipelines/executors/`): `tool` — через `executeToolDef`, `script` — только через
  shell-тул `execute_shell` (не голый `child_process`), `human` — пауза с вопросом и
  **активным таймаутом** (`node.timeoutSec`, таймер в процессе с `unref`; по истечении шаг
  `failed` с `pipeline.gate_timeout`). Общая механика гейта: исполнитель может встать на
  паузу **на любом узле** (исход-гейт `StepOutcome` — расширение уровня ядра, контракт
  `StepResult` в `shared` не менялся); движок пишет `gate.awaiting` с данными гейта (в
  журнале, контракт записей и схема хранилища не менялись), ставит `awaiting_human` и
  возвращает управление. `resume()` продолжает прогон **с узла паузы**: одобрение
  `tool_approval` — повторный вызов инструмента с выданным правом, одобрение `human` —
  выход гейта, отклонение — `failed` с `pipeline.gate_rejected`.
- **Сделано (Э4.3):** исполнитель вида `agent`
  (`engine/pipelines/executors/agent-step.ts`) — **свой Tool-Use-цикл внутри движка**
  (шаг ≠ сессия, ADR-101 §1):
  - системный промпт — тем же `SystemPromptComposer` по суженному «session-like»
    контракту (ADR-070), проект/инструкции/скиллы/тулы — из контекста шага;
  - провайдер/модель — через инъекцию (`ctx.llm`), LLM-вызов — только через
    `GatewayProvider` (ADR-036), ошибки — по таксономии `classifyLlmError` (ADR-041);
  - **цикл вызовов тулов**: ответ модели с `toolCalls` → право на каждый вызов
    (`checkPipelineToolPermission`, тот же permission-слой, что у tool-шага) →
    `allow` — вызов тула, `deny` — результат-отказ в локальную историю (шаг не
    валится, модель продолжает), `ask` — **пауза-гейт** `tool_approval`; результаты
    тулов — только в локальную историю шага (ни сессия, ни хранилище); затем
    повторный LLM-вызов — до ответа без вызовов тулов;
  - **лимит итераций** цикла (`maxIterations`, по умолчанию 25) → шаг `failed` с
    `pipeline.agent_iterations`;
  - выход шага — `text` + расход токенов + **сводка вызовов** (имя тула и признак
    ошибки; полные выводы тулов наружу не попадают);
  - отмена — гонкой с `ctx.signal` (`pipeline.cancelled`), как у остальных шагов.
- **Сделано (Э4.3b):** доведён цикл Tool Use agent-шага:
  - `ask` → гейт → `resume`: одобрение оператора применяется **к тому же вызову**
    (данные гейта восстанавливаются движком из журнала прогона — `ctx.gate`), право
    на инструмент считается выданным (permission-чек по `ask`-политике не
    повторяется); отклонение — вызов не исполняется, в историю уходит
    результат-отказ, цикл продолжается;
  - пауза-гейт возвращается **до** исполнения партии вызовов — иначе уже
    исполненные вызовы повторились бы после `resume`;
  - общая логика «проверка права + вызов тула» вынесена в
    `engine/pipelines/executors/common.ts` (`checkStepToolPermission`,
    `executeStepTool`) — её используют и tool-шаг, и agent-шаг.
- **Сделано (Э5):** наблюдаемость прогонов и реальные выходы пайплайна:
  - **события `pipeline.run.*`** (`started`/`node_started`/`node_finished`/`awaiting_human`/
    `finished`/`failed`) — в **существующей** шине (`packages/core/src/events/bus.ts`):
    прогон — не сессия (ADR-101 §1), поэтому события идут в **инстансный канал**
    `EventBus.publishInstance` (канал `instance`) той же шины — их видят глобальные
    подписчики (SSE-хаб `GET /api/v2/events`, watch-all клиенты `EventHub`, движок исходящих
    webhooks), а per-session подписки — нет; **новых транспортных каналов не заводим**
    (ADR-024/ADR-089, инвариант 6). Типы — в `shared` (`EventType`); в payload — только
    идентификаторы и технические поля (без payload'а прогона, секретов и сырых путей);
  - **метрики `synth_pipeline_*`** (ADR-094) — `packages/core/src/metrics/collectors/pipelines.ts`
    (`createPipelineMetrics`): лейблы **только** из фиксированного списка (`status`/`source`/
    `kind`/`outcome`), значения приведены к конечным наборам (неизвестное → `other`), id
    прогона/узла/сессии в лейблах нет — кардинальность серий ограничена; ошибка метрик не
    влияет на прогон; каталог — [docs/OBSERVABILITY.md](../OBSERVABILITY.md);
  - **реальные обработчики выходов** — `engine/pipelines/exits.ts`
    (`createPipelineExitHandler`): `session` (новая или продолжаемая сессия; владелец —
    владелец проекта, ADR-089; `session.created` публикуется — хабы подписывают владельца),
    `file` (артефакт в workspace проекта с **containment'ом**: путь относительный, выход за
    пределы workspace — отказ, ADR-075), `gateway` (публикация наружу через ingress внешних
    событий, ADR-089, + инстансный канал шины), `none` (ничего); сбой обработчика не роняет
    прогон — фиксируется в `run.finished.exits[i].error` (`pipeline.exit_failed`);
  - **точка сборки движка** — `packages/core/src/server/app/deps.ts` (standalone) и
    `packages/backend/src/app/deps.ts` (managed): `PipelineEngine` + исполнители шагов +
    обработчики выходов + метрики, тем же окружением, что у сессий (порты хранилища,
    permission-слой, промпт, Gateway). **HTTP-роутов у движка нет** (Э6) — он живёт в `deps`;
    глобальных синглтонов нет.
- **Сделано (Э6):** HTTP-контур и права:

  - **center-tabs `pipeline`/`pipeline-run`** (`stores/useUIStore.ts` — `CenterTabType` + поля
    `pipelineId`/`runId`; иконки `links-line`/`time` — `components/layout/CenterTabs.tsx`; `case` —
    `components/layout/CenterPanel.tsx`): страница пайплайна (`components/pipelines/PipelineTab.tsx` —
    черновик, опубликованная версия, провенанс, «Сохранить»/«Опубликовать»/«Запустить»/«Удалить»,
    список прогонов с фильтром по статусу) и страница прогона
    (`components/pipelines/PipelineRunTab.tsx` — заголовок, статус, текущий узел, журнал событий,
    HITL-действия «Одобрить»/«Отклонить» при `awaiting_human`, отмена активного прогона);
  - **визуальный редактор** (`components/pipelines/editor/`, `@xyflow/react`): **IR — собственный
    `PipelineSpec`**, а не формат React Flow (адаптер `specToFlow`/`flowToSpec` — чистый модуль без
    React, round-trip без потерь); палитра узлов `agent`/`script`/`tool`/`human`, инспектор полей по
    виду узла, редактор условий переходов, добавление/удаление/перестановка узлов, рисование рёбер;
    переключатель «Визуальный / JSON» и кнопка «Проверить» (`validatePipelineSpec`) — невалидная
    спецификация на сервер не уходит; атрибуция React Flow не скрывается (лицензия);
  - **живой прогон** — по событиям `pipeline.run.*` инстансного канала шины (§2.12.3):

    не заводим (ADR-024/ADR-089, инвариант 6);
  - **актуализация `AGENTS.md`** — корневого и пакетных (`core`, `backend`, `shared`,
    `storage-postgres`, `ui`).
- **Этапы Э0–Э7 закрыты** (2026-10-21): контракты, порты хранения, движок, виды шагов,

## Альтернативы

- **Переиспользовать сессии для шагов** — отклонено: у шага своя локальная история и свой режим; сессия видна
  человеку в UI — шаг не должен ею быть.
- **Шаги как ходы оркестратора сессий** — отклонено: другой цикл жизни (шаг живёт между прогонами, пауза
  HITL, возобновление) и другой режим разрешений.
- **`eval`-условия / произвольный код в ядре** — отклонено: неконтролируемый доступ к данным и запись
  исполняемого кода в ядро — только структурированный DSL.
- **React Flow как IR** — отклонено: формат редактора ≠ формат хранения; IR — собственный `PipelineSpec`,
  редактор — один из клиентов.

## Последствия

- **Плюсы:** шаг закрывается по факту хода; артефакты, переходы и выход выразимы; пайплайн живёт в проекте
  (права, workspace, MCP-скоуп); прогоны воспроизводимы (версия + журнал); ядро не дублируется.
- **Минусы:** в ядре второй оркестратор (цикл, ретраи, отмена, таймауты) — новая поверхность для тестов и
  наблюдаемости; вход шага требует явного маппинга (его отсутствие = потеря контекста); оба движка делят
  permission-слой — риск обхода через пайплайн (закрыт: `ask` → HITL, режим объявляется явно).
- **Следствия:** `PipelineTracker` уходит в замену движку; определения из пакетов становятся инстанцируемыми в
  проекты; UI получает новый экран редактора; появляются метрики `synth_pipeline_*` и события `pipeline.run.*`.

## Открытые вопросы

- Нужен ли отдельный тул `pipeline_run` (запуск пайплайна из сессии, триггер `kind: 'tool'`) или
  ограничиться API и событиями? В коде такого тула **нет**; триггер `kind: 'tool'` доступен через API
  (`POST /api/v2/projects/:id/pipelines/:pid/runs` — [API_V2.md](../../API_V2.md) §5.35), решение
  (добавлять тул или оставить API) — открыто.
- **Rollback/exit-стратегия на уровне цепочки** (переход к альтернативной ветке; для необратимых шагов
  push/deploy — компенсирующие действия, а не откат). Сейчас у прогона есть только `exit`-семантика
  (`session|file|gateway|none`) и ретраи/таймауты шага; отката в границах прогона нет.
- **Мониторинг-дашборд пайплайнов** (статус прогонов/шагов в UI, история, метрики по прогонам). Сейчас
  есть журнал прогона (append-only) и события `pipeline.run.*` + метрики `synth_pipeline_*` (ADR-094);
  отдельной дашборд-страницы нет.
- **Отдельное хранилище артефактов между шагами.** Выход `file` пишет артефакт в workspace проекта
  (ADR-075), артефакты шага — в контракте `StepResult.artifacts`; общего хранилища артефактов,
  независимого от workspace, нет. **Решение 2026-10-27:** там, где артефакту нужен общий домен (не
  workspace), он кладётся в существующий blob-порт (`BlobStore`, `artifacts/<runId>/…`), отдельного
  хранилища не заводим; реализация — блок 1.1 roadmap.
- **Кто и как определяет точки HITL** — автор пайплайна или политика инстанса (частично закрыто узлом
  `human` с таймаутом; политика инстанса — нет).

## Закрытые вопросы

- **Где живут выход `file` и артефакты — закрыт (Э5).** Выход `file` пишет артефакт в **workspace
  проекта** с containment'ом (ADR-075): путь только **относительный**, абсолютный путь, выход за
  пределы workspace и отсутствие workspace — **отказ**; каталоги создаются, файл перезаписывается
  (`engine/pipelines/exits.ts`). Отдельного хранилища артефактов в ADR-101 нет — оно остаётся в
  §«Открытые вопросы». Артефакты шага в прогоне — контракт
  `StepResult.artifacts` (ADR-100, `types/pipeline.ts`). **Решение 2026-10-27:** артефакты прогонов,
  которым нужен общий домен (не workspace), кладутся в уже существующий blob-порт (`BlobStore`,
  `artifacts/<runId>/…`) — отдельного хранилища не заводим; блок 1.1 roadmap.
- **Вывод старых определений из пакетов в шаблоны инстанца — закрыт (Э6).** Миграции данных
  **нет**: источник шаблонов — legacy-реестр ADR-100 (`{dataDir}/pipelines/definitions.json`,
  наполняет установщик пакета) **плюс** записи `scope:'instance'` нового порта
  `ProjectPipelineRepository`; список шаблонов объединяет оба источника и помечает формат
  (`format: 'adr-100' | 'adr-101'`). Конвертация legacy-определения в `PipelineSpec` выполняется
  **на лету при инстанцировании** (`legacyDefinitionToPipelineSpec`): шаги `agent` → узлы
  `agent`; шаги `loop` **не конвертируются** (Loop Engine вне объёма, PROP-057) — инстанцирование
  отклоняется `409 PIPELINE_TEMPLATE_UNSUPPORTED` со списком проблем; `waitsFor` не переносится
  (триггер ADR-101 задаётся при запуске прогона, HITL — узлом `human`); провенанс `installedBy`
  сохраняется. Исходное определение остаётся в реестре и продолжает работать в legacy-контуре
  (`/api/v2/pipelines*`, §5.34 API); UI переведён на новый контур (Э7), legacy-определения по-прежнему
  показываются в разделе «Аддоны».
- **Канал live-обновлений прогона — закрыт (Э5).** Отдельный поток **не нужен**: хватает событий
  `pipeline.run.*` в существующей шине (ADR-024/ADR-089) — инстансный канал `publishInstance`
  (`packages/core/src/events/bus.ts`); транспортных каналов не заводим. Путь доставки:
  - **standalone** — SSE `GET /api/v2/events` (глобальная подписка) и WS `/ws/events` (клиент
    подписывается на инстансный канал, `server/app/ws-events.ts`);
  - **managed** — `EventHub` watch-all: `ADMIN`/`LEAD` и service-key (ADR-052); обычный `USER`
    per-session событий прогонов **не получает** — прогон здесь инстансный админ-ресурс; точные
    права определены в Э6 — чтение/изменение по правилам проекта (§2.15
    [docs/PIPELINES.md](../PIPELINES.md)).
  Подробности — [docs/PIPELINES.md](../PIPELINES.md) §2.12.3.
