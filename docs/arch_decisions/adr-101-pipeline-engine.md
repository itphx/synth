## Контекст

[ADR-100](./adr-100-extension-packs-pipelines.md) ввёл пайплайн как **декларацию + учёт прогона**: определение
приходит пакетом расширения, шаг — обычная агентская сессия, порождённая funnel'ом
([ADR-089](./adr-089-external-events-automation.md)), состояние ведёт `PipelineTracker`. Для «декларации + учёта»
этого хватает, для движка — нет:

- **шаг закрывается не по факту хода** (хук «ход завершён» живёт в оркестраторе, вне контура funnel): трекер
  переводит шаг в `done` при следующем событии пайплайна;
- **поля шага не читаются**: `prompt`/`skill` не доходят до модели — вход шага = payload события;
- **нет переходов, версий и выхода**: ветвление, неизменяемая версия спецификации и «что делает прогон по
  завершении» не выразимы; правка определения молча меняет смысл идущих прогонов;
- **нет привязки к проекту**: определения инстансные, видимость — ADMIN, у прогона нет `projectId` — значит,
  нет ни прав, ни workspace, ни MCP-скоупа проекта; артефакт между шагами = payload события, то есть передача
  результата не отделена от транспорта событий.

При этом цикл «событие → шаг → подтверждение человеком → следующий шаг» уже нужен add-on'у `synth-media`, а
собственного движения шагов нет.

## Решение

1. **Пайплайн — второй движок.** `PipelineEngine` — самостоятельный оркестратор рядом с `ChatOrchestrator`.
   **Шаг пайплайна не является сессией**: сессия — только вход (запуск из сессии) или выход (финальный шаг
   создаёт/продолжает сессию). Шаг исполняет движок со своей локальной историей; в запрос к LLM уходит не
   вся история, а только то, что отображено **маппингом входа** шага (выход предыдущего шага / payload
   триггера / явно заданные переменные).
2. **Пайплайн принадлежит проекту** (`projectId`), видимость — как у сессий проекта. Пайплайны из пакетов
   расширений (`synth.pack`, `provides.pipelines[]`) — **шаблоны инстанса**; проект инстанцирует шаблон в свой
   пайплайн (копия → черновик со своими версиями).
3. **Формат фиксирован, но не избыточен.** Единый вход `PipelineTrigger` (`kind` =
   `user|gateway|schedule|tool|webhook|manual`, `source`, `type`, `payload`, `dedupKey`) и единый выход шага
   `StepResult` (`status` = `ok|failed|skipped|awaiting_human`, `output`, `artifacts`, `error`, тайминги,
   `attempt`). **Опциональная** `io`-схема (JSON Schema) объявляется конкретным пайплайном — тогда границы
   валидируются строго.
4. **Виды шага:** `agent` (свой Tool-Use-цикл внутри движка), `script` (только через shell-policy — не голый
   `child_process`), `tool` (через `ToolRegistry`), `human` (HITL-гейт: пауза прогона, ожидание действия
   человека + таймаут).
5. **Условные переходы** — структурированный DSL `{path, op, value}`: пути `prev.output.x`,
   `trigger.payload.y`, `vars.z`; операторы `eq|ne|in|exists|gt|lt`. **Никакого `eval`/произвольного кода в
   ядре.**
6. **Разрешения.** У пайплайна свой режим (`plan|act|yolo`), объявляемый в спецификации. Тулы с
   `ask`-политикой в пайплайне **эскалируются в human-шаг (HITL)** — наблюдателя-сессии нет. Пайплайн не
   должен стать обходом permission-слоя.
7. **Версии.** Спецификация версионируется: черновик (`draft`) редактируется, публикация (`published`)
   фиксирует неизменяемую версию; прогон всегда ссылается на конкретную `pipelineId@version`.
8. **Журнал выполнения — append-only:** заголовки прогонов и события прогона (шаг начался/завершился, переход
   по ребру, ожидание человека, падение). Прецедент в репо: `scheduler/jobs.jsonl`,
   `webhooks/deliveries.jsonl`, `audit/maintenance.jsonl`.
9. **Выход пайплайна:** `session` | `file` (в workspace проекта) | `gateway` (событие/webhook наружу) | `none`
   — задаётся exit-спецификацией.
10. **Переиспользуется существующее ядро** (не дублируется): `GatewayProvider` (ADR-036),
    `PermissionEvaluator` (ADR-025/028/029), `ToolRegistry` + `executeToolDef`
    (`engine/tools/tool-execution.ts`), `SystemPromptComposer`/`ContextBuilder` (ADR-070 — контракт сужается
    до минимального «session-like» интерфейса, обычная `Session` остаётся структурно совместимой), MCP-скоуп
    по проекту (ADR-071), резолвер проектных инструкций (ADR-069), shell-policy/protected paths, i18n-ключи
    `shared/i18n`, реестр метрик (ADR-094), шина событий — новые **типы** событий `pipeline.run.*` в
    существующей шине (новых каналов не заводим).
11. **Границы.** Loop Engine ([PROP-057](./prop-057-loop-engine.md)) не трогаем; rollback/exit-стратегия,
    мониторинг-дашборд и отдельное хранилище артефактов остаются за
    [PROP-059](./prop-059-pipeline-automation.md). Визуальный редактор — `@xyflow/react` (новая зависимость,
    разрешена владельцем), но **IR — собственный `PipelineSpec`**, а не формат React Flow (JSON/YAML — источник
    истины).

## Статус в коде

- **Есть ([ADR-100](./adr-100-extension-packs-pipelines.md)):** контракт манифеста `synth.pack` и валидация;
  установка пакета одной операцией (`POST /api/v2/packs`) с одобрением администратора; порты
  `PipelineRepository`/`PackRepository` (ADR-096) и файловая реализация
  (`{dataDir}/pipelines/{definitions,instances}.json`); типы пайплайна в `shared` (`types/pipeline.ts`);
  `PipelineTracker` (учёт экземпляров в funnel); роуты `/api/v2/packs`, `/api/v2/pipelines`; раздел «Аддоны» в
  UI. Это **промежуточная** реализация: «декларация + учёт», без движения шагов.
- **Сделано (Э1):** контракты `shared` — `packages/shared/src/types/pipeline-engine.ts` —
  Zod-схемы и типы (`PipelineSpec`/`PipelineNode`/`PipelineTransition`/`PipelineCondition`/`PipelineExit`/
  `PipelineRunTrigger`/`StepResult`/`PipelineRun`/`PipelineRunEvent`) + валидатор графа `validatePipelineSpec`
  (проблемы строками, без throw). Legacy-контракты ADR-100 (`types/pipeline.ts`) не тронуты — заменяются в Э2–Э3.
- **Сделано (Э2):** порты слоя хранения (ADR-096) — `ProjectPipelineRepository` (черновик + журнал
  опубликованных версий) и `PipelineRunRepository` (прогоны + append-only журнал), файловая и in-memory
  реализации, контрактный suite; порты доступны в `StorageContext` как `projectPipelines`/`pipelineRuns`.
- **Сделано (Э3):** движок — `packages/core/src/engine/pipelines/` (`PipelineEngine`): цикл прогона по
  опубликованной версии спецификации, вычисление условий (структурированный DSL, fail-soft), маппинг
  входа, выбор следующего узла (порядок переходов, линейный переход, лимит переходов), ретраи и
  таймауты шага, HITL-пауза (`awaiting_human`) и возобновление (`resume`), отмена через `AbortSignal`,
  журнал прогона (append-only, санитизация payload'а от секретов). Исполнители видов шагов — Э4;
  выходы пайплайна — только фиксируются (точка расширения `PipelineExitHandler` — Э5).
- **Осталось:** Э4–Э7 — виды шагов, журнал и наблюдаемость (метрики `synth_pipeline_*`, события
  `pipeline.run.*` в шине), API/права/проектная привязка, UI и визуальный редактор (`@xyflow/react`).
  План этапов — в журнале задач (`.opencode/tasks/log.md`), формат и устройство — в
  [docs/PIPELINES.md](../PIPELINES.md).

## Альтернативы

- **Переиспользовать сессии для шагов** — отклонено: у шага своя локальная история и свой режим; сессия видна
  человеку в UI — шаг не должен ею быть.
- **Шаги как ходы оркестратора сессий** — отклонено: другой цикл жизни (шаг живёт между прогонами, пауза
  HITL, возобновление) и другой режим разрешений.
- **`eval`-условия / произвольный код в ядре** — отклонено: неконтролируемый доступ к данным и запись
  исполняемого кода в ядро — только структурированный DSL.
- **React Flow как IR** — отклонено: формат редактора ≠ формат хранения; IR — собственный `PipelineSpec`,
  редактор — один из клиентов.

## Последствия

- **Плюсы:** шаг закрывается по факту хода; артефакты, переходы и выход выразимы; пайплайн живёт в проекте
  (права, workspace, MCP-скоуп); прогоны воспроизводимы (версия + журнал); ядро не дублируется.
- **Минусы:** в ядре второй оркестратор (цикл, ретраи, отмена, таймауты) — новая поверхность для тестов и
  наблюдаемости; вход шага требует явного маппинга (его отсутствие = потеря контекста); оба движка делят
  permission-слой — риск обхода через пайплайн (закрыт: `ask` → HITL, режим объявляется явно).
- **Следствия:** `PipelineTracker` уходит в замену движку; определения из пакетов становятся инстанцируемыми в
  проекты; UI получает новый экран редактора; появляются метрики `synth_pipeline_*` и события `pipeline.run.*`.

## Открытые вопросы

- Как выводить старые определения из пакетов (`provides.pipelines[]`) в шаблоны инстанса — миграция при первом
  старте новой версии ядра или при обновлении пакета?
- Канал live-обновлений прогона: достаточно ли событий `pipeline.run.*` в существующей шине (ADR-024/ADR-089) для
  UI или нужен отдельный поток?
- Нужен ли отдельный тул `pipeline_run` (триггер `kind: tool` — вызов пайплайна из сессии) или ограничиться API
  и событиями?
- Где живут выход `file` и артефакты до отдельного хранилища (PROP-059) — workspace проекта или
  `{dataDir}/pipelines/`?
