# AD-081: Политики гибрида и защита от утечек

> **Статус:** 🧩 Предложение — Политики гибрида и защита от утечек: серверные политики, явные эндпоинты переноса, discovery, аудит
> **Решение до:** 2026-11-14
> **Дата:** 2026-09-29
> **Источник:** согласовано 2026-09-29
> **Опирается:** [AD-073](./ad-073-client-integrity-hybrid.md) (клиент недоверенный, enforcement на сервере)

**Решение:** централизованно управлять гибридом и обменом данными между мирами через **серверные политики** (источник истины — сервер), с явными эндпоинтами переноса, discovery политики на локальный клиент, аудитом и админ-панелью. Дефолт: **гибрид разрешён, publish разрешён, fork (server→local) запрещён**; для запрещённых направлений доступен вариант **«по одобрению LEAD/ADMIN»**. Риск модифицированного клиента принимается осознанно и документируется.

## Контекст и модель угроз

Лёгкий доступ к гибриду и переносам повышает риск утечки данных. Данные двигают не переключения сами по себе, а **обмен между мирами** и **локальный мир**:

| Вектор | Что происходит | Направление |
|---|---|---|
| publish (local→server) | локальные файлы/сессии заливаются в центральный мир | ingestion |
| fork (server→local) | серверные данные скачиваются на endpoint, вне центрального контроля | **egress** |
| локальные сессии в гибриде | контент локальных файлов уходит на серверный LLM (в гибриде локальные провайдеры запрещены — AD-042 §2) | через LLM |
| чисто локальный режим | локальные провайдеры → обход Gateway/аудита/rate limit | вне контроля |
| shadow-копии | fork создаёт неуправляемые копии: нет retention/revoke/soft-delete (AD-074) | egress |

## Сила энфорса (AD-073: клиент недоверенный)

| Политика | Как энфорсится | Сила |
|---|---|---|
| `mode: forbidden` | сервер отвергает токены CLI-клиента (`azp`=`synth-cli`) при auth | 🟢 сильная |
| `transfer.publish` | явный серверный эндпоинт переноса | 🟢 сильная |
| `roles` | claims из IdP | 🟢 сильная |
| `transfer.fork` | серверный эндпоинт выдачи для fork | 🟡 трение, не граница: авторизованный пользователь всё равно читает данные обычным API; левер — least privilege + аудит |
| `mode: remote-only` | клиент прячет локальный мир/бейджи | 🔴 кооперативная: модифицированный core соврёт |
| `localSessions` | сервер не отличает локальную сессию от серверной без серверной регистрации | 🔴/🟡 слабая |

Правило: `forbidden`, `publish`, `roles` — настоящая граница; `remote-only`/`localSessions` — кооперативная политика соответствия, в UI/доке так и подаётся.

## Политики (сервер, источник истины)

- `hybrid.mode`: `forbidden` | `remote-only` | `full` (дефолт managed — `full`).
- `hybrid.transfer.publish`: `allow` | `deny` | `approval` (дефолт `allow`).
- `hybrid.transfer.fork`: `allow` | `deny` | `approval` (**дефолт `deny`**).
- `hybrid.localSessions`: `allow` | `deny` (дефолт `allow`).
- `hybrid.localProviders`: `allow` | `deny` (дефолт `deny` — согласовано с `remote.llm: server`).
- `hybrid.roles`: кому разрешён гибрид (дефолт — все аутентифицированные).
- `hybrid.approvers`: роли, которые одобряют переносы (дефолт `LEAD`, `ADMIN`).

Хранение: дефолты в config/Helm, runtime-оверрайд — `RuntimeSettingsStore`, API `GET/PUT /api/v2/settings/hybrid` (AD-072-kit для UI).

## Одобрение переносов (`approval`)

- Запрос переноса при `approval` создаёт на сервере запись `pending` (+ аудит) и **не выполняется** до решения.
- `LEAD`/`ADMIN` одобряют или отклоняют (`approve`/`reject`, аудит); по одобрению перенос выполняется под инициатора.
- Если для данного направления политика `allow`/`deny` — запросы не создаются (эндпоинт сразу разрешает/отклоняет).

## Явные эндпоинты переноса (сервер)

Политика и аудит — в одной точке, а не на размазанных общих REST:

- `POST /api/v2/hybrid/transfer/publish` — приём локального проекта/сессий/файлов;
- `GET /api/v2/hybrid/transfer/projects/:id/export` — выдача для fork;
- `POST /api/v2/hybrid/transfer/requests` + `GET /api/v2/hybrid/transfer/requests/:id` + `POST /api/v2/hybrid/transfer/requests/:id/{approve,reject}` — режим одобрения.

Локальный core в гибриде ходит **только** через них (вместо общих `/sessions/import`, `/sessions/:id/export`, `/fs/*` для transfer). Локальные эндпоинты `POST /api/v2/projects/:id/publish` и `.../fork-local` (`packages/core/src/server/routes/project-transfer.ts`) остаются фасадом UI/CLI.

## Discovery политики

- `GET /auth/oidc-meta` (public, AD-043) дополняется сигналом `hybrid_allowed` — чтобы локальный core решал, предлагать ли гибрид вообще, без 401-циклов.
- `GET /api/v2/settings/hybrid` (auth) возвращает эффективную политику для вызывающего; UI/ядро адаптируются (скрывают локальный мир/перенос, показывают «сервер запрещает гибрид»).

## Аудит

- Аудит **всех** операций `/api/v2/hybrid/transfer/*` (кто, что, направление, результат) и решений approve/reject — сейчас transfer **не аудируется**.
- Коды ошибок/строки — через i18n (AD-041).

## Панель настроек «Гибрид»

- **Managed backend:** категория `hybrid` (ADMIN) в SettingsModal (AD-072-kit): режим, направления переноса, одобрение, локальные сессии/провайдеры, роли, аудит.
- **Локальный core (standalone/hybrid):** та же панель для настройки локального инстанса; **редактируема для ADMIN**, **скрыта для не-ADMIN** (как прочие админ-категории). При подключении к серверу серверная политика **авторитетна** и отображается (для не-ADMIN — read-only/скрыто).

## Инстанс-локальные секреты

Часть данных **не является переносимым контентом** и не должна попадать в publish/fork и межмировой обмен:

- **API-ключи привязок событий** ([AD-089](./ad-089-external-events-automation.md), первый срез
  [AD-052](./ad-052-public-api-platform.md)) — секреты конкретного инстанса
  (`{dataDir}/events/api-keys.json`, только sha256-хеш). При publish/fork **не переносятся**;
  после переноса привязки ключи создаются заново на целевом инстансе.
- Тот же принцип распространяется на прочие инстанс-локальные секреты (мастер-ключ, SSH-ключи
  агентов — AD-076, credentials гибрида — AD-045/AD-079): они живут вне переносимого контента.

## Последствия

- Данные не покидают периметр «по умолчанию»: fork запрещён, publish под контролем, переносы аудируются.
- Инстанс-локальные секреты (API-ключи привязок) остаются периметром инстанса и не «утекают» через переносы.
- Появляется управляемое исключение (approval) без постоянного ослабления политики.
- `remote-only` даёт «локальный UI к серверу» без локального мира (кооперативно).

## Ограничения

- `fork: deny` — трение, не защита от чтения: авторизованный пользователь может выгрузить данные иначе (левер — роли/least privilege/аудит).
- `remote-only`/`localSessions` не энфорсятся против модифицированного клиента (принятый риск).
- Усиление (опция на будущее): обязательная **серверная регистрация локальных сессий** (тогда сервер верифицирует origin и может жёстко ограничить LLM/переносы); сигналы целостности клиента (mTLS/DPoP, AD-073).
- Approval-поток требует хранения очереди заявок и UI для LEAD/ADMIN.
