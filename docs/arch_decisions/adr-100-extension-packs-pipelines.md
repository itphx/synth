# ADR-100: Пакет расширения и пайплайн в ядре: единый контракт доставки (`synth.pack`) и учёт прогонов

> **Статус:** ⚠️ Частично — **поставка пакета расширения `synth.pack` остаётся в силе**: контракт манифеста валидируется в ядре, установка пакета выполняется одной операцией `POST /api/v2/packs` (скиллы → MCP → агенты с ролями → определения пайплайнов → порождённые правила маршрутизации), пакеты с capability-грантами требуют одобрения администратора, экземпляры пайплайнов учитываются в funnel; **часть решения (пайплайн = декларация + учёт прогона) заменена [ADR-101](./adr-101-pipeline-engine.md)** — собственный движок шагов. **Движок пайплайна — [ADR-101](./adr-101-pipeline-engine.md) — реализован**; остаток — legacy-контур «декларация + учёт прогона» (`PipelineTracker`): остаётся рабочим и устаревает.
> **Дата:** 2026-10-20
> **Обновлено:** 2026-10-21 — **движок пайплайна ([ADR-101](./adr-101-pipeline-engine.md)) реализован** (этапы Э1–Э7 закрыты); остаток ADR-100 — legacy-контур «декларация + учёт прогона» (`PipelineTracker`): остаётся рабочим и устаревает.
> **Обновлено:** 2026-10-21 — часть решения (пайплайн = декларация + учёт прогона) заменена [ADR-101](./adr-101-pipeline-engine.md); поставка пакета расширения `synth.pack` остаётся в силе; текущий `PipelineTracker` — промежуточная реализация, будет заменён движком; статус `✅ Реализовано` → `⚠️ Частично`.
> **Связано:** [ADR-086](./adr-086-extensibility-plugins-editions.md) «Классы расширений» (зонтик; манифест `synth.pack` — §5),
> [ADR-051](./adr-051-scheduler-pipelines.md) «Шедулер и пайплайны», [ADR-089](./adr-089-external-events-automation.md) «Внешние события и автоматизация»
> (правила маршрутизации, funnel), [ADR-052](./adr-052-public-api-platform.md) «Публичная API-платформа» (scope `automation:install`),
> [ADR-096](./adr-096-storage-layer.md) «Слой хранения» (порты `PackRepository`/`PipelineRepository`),
> [ADR-071](./adr-071-mcp-servers-prompt.md) «MCP», [ADR-046](./adr-046-skills-and-slash-commands.md) «Скиллы»,
> [ADR-030](./adr-030-hooks-agent-events.md) «Hooks», [ADR-101](./adr-101-pipeline-engine.md) «Pipeline Engine: пайплайн как второй движок»
> (заменяет часть этого решения), [PROP-059](./prop-059-pipeline-automation.md) «Pipeline Automation»,
> [PROP-090](./prop-090-extension-api.md) «Extension API v1», [PROP-057](./prop-057-loop-engine.md) «Loop Engine».

**Решение:** доставлять расширение в инстанс **одним пакетом** по декларативному контракту
`synth.pack` и учитывать пайплайны как **декларацию + состояние прогона**, а не как отдельный
движок шагов.

- **Манифест** `synth.pack` — единый для всех классов расширений (ADR-086 §5). Ядро **валидирует**
  его (структура — Zod, целостность — список правил) и **устанавливает** пакет одной операцией.
- **Пайплайн** — декларация шагов в пакете + учёт экземпляров в ядре. Шаг пайплайна — обычная
  агентская сессия, порождённая существующим funnel'ом (ADR-089); собственного движка шагов нет.

Формат HTTP-контракта — [docs/API_V2.md](../API_V2.md) §5.33–§5.34 (пакеты, пайплайны).

## Контекст

Расширения доставлялись в инстанс **поштучно**: MCP-сервер — в реестр MCP, скилл — в реестр
скиллов, роль агента — файлом в каталог ролей, правило маршрутизации — отдельной записью.
Каждый шаг — отдельный вызов API с отдельными правами, отдельной идемпотентностью и отдельной
ошибкой; частичная установка оставляла инстанс в промежуточном состоянии (например, агент без
роли). Пайплайны же в ядре **не существовали**: ADR-051 отправлял их в PROP-059, а PROP-059
фиксировал «не реализовано» — при том, что цикл «событие → шаг → подтверждение человеком →
следующий шаг» уже был нужен add-on'у `synth-media` (публикация поста: черновик → одобрение →
публикация).

## Детали

### 1. Контракт манифеста

`packages/shared/src/types/pack.ts`: `packManifestSchema` (поля `name`/`version`/`kind`/
`host?`/`contracts?`/`description`/`provides`/`packType?`; `packType` обязателен для
`kind: 'pack'` и запрещён у остальных), `provides` — `mcp[]`/`skills[]`/`agents[]`/`pipelines[]`
(списки нормализованы, неизвестные ключи сохраняются), `normalizePackProvides` (legacy-форма
`provides.mcp` **объектом** — как у выпущенных манифестов `synth-media`/`synth-gateway-telegram` —
разворачивается в массив), `validatePackManifest` — **11 правил** целостности, возвращает
**список проблем** строкой (без throw).

### 2. Установка одной операцией (`POST /api/v2/packs`)

`packages/core/src/server/routes/packs.ts` — `createPacksRoutes` (общая фабрика для core и
backend). Тело: `{ manifest, files }` — манифест + карта файлов пакета, на которые ссылается
манифест. Порядок установки (идемпотентный upsert по имени пакета):

1. **скиллы** — `SKILL.md` + supporting-файлы, `metadata.synth.*` (ADR-046 §4/§9);
2. **MCP** — запись реестра: `origin: 'instance'`, `enabledByDefault: true` (иначе сервер не попадёт
   в дефолты новых сессий, ADR-071 §2.4);
3. **агенты** — **роль сначала, потом агент** (fail-closed: агент без роли — сломанный агент);
   роль — `{dataDir}/context/roles/<contextFile>`, файл перекрывает системный `prompts/roles/`;
4. **определения пайплайнов** — `definition` или файл `path` (JSON/YAML) → `saveDefinition`
   с провенансом `installedBy: {pack, version}`;
5. **правила маршрутизации** — по шагам с `waitsFor`: `match = waitsFor`,
   `target = {mode: 'ephemeral', agentTemplate: step.agent, pipeline: {id, step}}`; id правила
   стабильный (`pack-<пакет>-<пайплайн>-<шаг>`) — повторная установка **обновляет** правило.

### 3. Одобрение администратора

Пакет, дающий **capability-гранты** (непустые `capabilities` агента), объявляющий пайплайны
(порождаемые правила маршрутизации) или расписания, **не устанавливается фактически**: в реестр
пишется запись `status: 'pending_approval'`, ответ — **202**. Фактическую установку выполняет
`POST /api/v2/packs/:name/approve` (только ADMIN) — по сохранённым в реестре манифесту и файлам
(обойти проверку целостности манифеста нельзя). `DELETE /api/v2/packs/:name` (только ADMIN) снимает
установку: удаляет поставленные артефакты (агент + роль, скилл, MCP-запись, определение пайплайна,
порождённые правила) — идемпотентно.

### 4. Реестр установок и провенанс

Порт `PackRepository` (`packages/core/src/storage/ports/pack-repository.ts`), файл
`{dataDir}/packs.json` (`storage/file-pack-store.ts`). Запись: имя (ключ), версия, класс, статус
(`active|pending_approval|disabled`), флаг `requiresApproval`, что пакет поставил (id'ы — нужно
для снятия), сырой манифест + файлы пакета, `installedBy` (кто поставил) и провенанс определений
пайплайнов.

### 5. Пайплайн в ядре: объект, экземпляры, семантика

Порт `PipelineRepository` (`packages/core/src/storage/ports/pipeline-repository.ts`): определения
(`PipelineDefinitionRecord` — шаги, `onError`, `maxAttempts`, `ttl`, `installedBy`) и
**экземпляры** (`PipelineInstanceRecord` — статус `pending|running|waiting|done|failed|cancelled`,
состояния шагов, `currentStep`, `attempts`); файлы — `{dataDir}/pipelines/definitions.json` и
`{dataDir}/pipelines/instances.json`.

**Семантика автомата:**

- **первый** шаг с `waitsFor` — **триггер**: совпавшее событие **создаёт** экземпляр;
- **последующие** шаги с `waitsFor` — **гейты** (HITL): событие означает «предыдущий шаг завершён
  и подтверждён человеком» — автомат **продвигается** в существующем экземпляре;
- **артефакт между шагами = payload события** (например `{draftId}`): payload сохраняется в
  артефакте шага и в `trigger.payload` — следующий шаг получает его оттуда. В ядре хранится только
  значимая часть payload (без секретов).

Учёт ведёт **funnel**: решение Router'а несёт `pipeline: {id, step}` (`eventRouteTargetSchema` →
`RouteDecision`), трекер (`engine/events/pipeline-tracker.ts`) создаёт/продвигает экземпляр,
шаг закрывается при следующем событии пайплайна.

### 6. Права, режимы, доставка роли

Зонтичный scope `automation:install` — «установщик пакетов расширений»: агенты и их ролевые
промпты, пайплайны, порождаемые пакетом правила маршрутизации и расписания. На ресурсных гейтах
он заменяет `routes:write`/`schedules:write`; `addons:install` создание агентов **не** открывает.
Гейты: `requireScopeOrAdminRole` (core) и `requireAdminRoleOrScope` (backend); одобрение и снятие
пакета — **только ADMIN** (они снимают чужие артефакты инстанса). Установка работает и в
standalone (core), не только в managed. `POST /api/v2/agents` принимает `role_prompt` (содержимое
роли) и `groups`; встроенный агент `publisher` **удалён из ядра** — роль приезжает из пакета
(`synth-media`).

## Что не реализовано (границы решения)

- **Собственный движок шагов** (loop'и, верификация, termination guards) —
  [PROP-057](./prop-057-loop-engine.md). Шаг пайплайна — обычная агентская сессия.
- **Автоматическое закрытие шага по факту окончания хода**: хук «ход завершён» живёт в
  оркестраторе, вне контура funnel, поэтому шаг переводится в `done` при следующем событии
  пайплайна (ограничение зафиксировано в коде трекера).
- **Rollback/exit-стратегия, мониторинг-дашборд, отдельное хранилище артефактов** —
  [PROP-059](./prop-059-pipeline-automation.md).
- **Plugin SDK и in-process плагины** (`kind: 'plugin'`) —
  [PROP-090](./prop-090-extension-api.md) (🧊 Icebox). Класс `Plugin` в контейнере манифеста
  существует, но код в процессе ядра не загружается.
- **Каталог пакетов и trust-уровни** — [PROP-068](./prop-068-skills-agents-registry.md).

## Альтернативы

- **Отдельные эндпоинты на каждый вид вклада** (как было) — отклонено: частичная установка и
  разнобой прав; единый манифест делает установку идемпотентной и проверяемой целиком.
- **Устанавливать пакет без одобрения** — отклонено: пакет может выдать агенту capability-гранты
  и породить правила маршрутизации (то есть влиять на поток событий инстанса) — это решение
  администратора, а не установщика.
- **Свой движок шагов в ядре** (PROP-057) вместо учёта на событиях — отложено: цикл
  «событие → шаг → подтверждение → шаг» уже выражается существующим funnel'ом; собственный
  движок — отдельное решение.

## Последствия

- **Плюсы:** расширение доставляется одной операцией и одним артефактом (манифест + файлы);
  состав установки проверяется ядром; снятие симметрично установке; провенанс (кто и каким
  пакетом поставил) — в реестре; пайплайн получает наблюдаемое состояние (прогоны, шаги,
  артефакты) без нового движка.
- **Минусы:** пакет с capability-грантами требует второго шага (одобрение администратора) —
  автоматическая установка в CI без администратора невозможна; в пайплайне нет автоматического
  закрытия шага по окончанию хода (учёт ведётся по событиям); определения пайплайнов нельзя
  создать через API в обход манифеста (роут только читает и запускает вручную).
- **Следствия для внешних add-on'ов:** `synth-media` поставляется пакетом; `publisher` и skill
  `media-hub` в ядре больше не дублируются.

## Открытые вопросы

- Каталог пакетов и trust-уровни (переиспользование инфраструктуры PROP-068) — не реализовано.
- Семантика `onError: 'retry'|'rollback'` и `maxAttempts` в декларации — заявлены в контракте,
  но не исполняются (движка шагов нет).
- Политика одобрения: нужен ли пакет «без одобрения» для доверенных источников (каталог/trust) —
  сейчас одобрение требуется всегда при capability-грантах.

## Обновлено (2026-10-21)

- **Часть решения заменена [ADR-101](./adr-101-pipeline-engine.md).** «Пайплайн = декларация + учёт
  прогона» — промежуточная реализация: шаг = сессия, порождённая funnel'ом, состояние ведёт
  `PipelineTracker`. Целевая модель (ADR-101): **пайплайн — второй движок** (`PipelineEngine`), шаг —
  не сессия, спецификация версионируется (`draft`/`published`), прогон ссылается на
  `pipelineId@version`, есть переходы, журнал прогона (append-only), выход (`session`/`file`/`gateway`/
  `none`) и привязка к проекту.
- **Поставка пакета расширения `synth.pack` остаётся в силе** — контракт манифеста, валидация, установка
  одной операцией, одобрение администратора, реестр установок, порождённые правила маршрутизации и
  провенанс определений. ADR-100 остаётся владельцем **поставки расширений**; ADR-101 — владельцем
  **движка пайплайна**.
- **Текущий `PipelineTracker` — промежуточная реализация**, будет заменён движком ADR-101 (шаг
  закрывается по факту хода, а не по следующему событию пайплайна). Определения из пакетов
  (`provides.pipelines[]`) станут **шаблонами инстанса**, которые проект инстанцирует в свой пайплайн.
- **Статус `✅ Реализовано` → `⚠️ Частично`.** Остаток — движок пайплайна (этапы Э1–Э7 по ADR-101; план
  этапов и критерии приёмки — в журнале задач `.opencode/tasks/log.md`).
- **Движок пайплайна реализован ([ADR-101](./adr-101-pipeline-engine.md); этапы Э1–Э7 закрыты 2026-10-21).**
  Запись выше об остатке «движок пайплайна (этапы Э1–Э7)» больше не актуальна: движок — в коде, UI
  переведён на новый контур (ADR-101 §5.35 API). Остаток ADR-100 — legacy-контур «декларация + учёт
  прогона» (`PipelineTracker`): он остаётся рабочим и устаревает (удаления не планируется).
