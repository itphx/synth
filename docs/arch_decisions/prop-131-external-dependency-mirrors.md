# PROP-131: Зеркала внешних зависимостей сборки

> **Статус:** 🧩 Предложение
> **Дата:** 2026-11-08
> **Решение до:** 2026-12-08
> **Связано:** [ADR-038](./adr-038-npm-packages.md), [ADR-077](./adr-077-runtime-toolchain.md), [ADR-078](./adr-078-runtime-dependency-availability.md), [ADR-121](./adr-121-offline-portable-distribution.md), [ADR-099](./adr-099-egress-tls-trust.md), [ADR-036](./adr-036-llm-gateway.md), [docs/PUBLISHING.md](../PUBLISHING.md)

## Контекст

**Инцидент 2026-11-08.** У GitHub глобальная деградация: прямые ссылки на релизы
(`github.com/<owner>/<repo>/releases/download/...`) отвечали `504`, затем — полный timeout.
Сборка `synth-executor:*-full` остановилась: четыре инструмента toolchain'а качаются именно оттуда.
При этом публикация в Gitea (образы, чарт, npm-пакеты) и бета-канал работали — блокер был только
на этапе `docker build`.

**Что именно зависит от внешних хостов.** Ниже — инвентарь по состоянию на 2026-11-08 (сборка
образов; публикация в Gitea сюда не входит).

|---|---|---|---|
| `github.com/mikefarah/yq` | `yq` v4.54.1 | `docker/install-tier-0.sh:91` — executor (core/dev/browser/full), backend (core/dev/devops/browser/full) | sha256 |

| `registry.npmjs.org` | зависимости workspace (`pnpm install`) | build-стадии backend/ui/executor | lockfile |

**Проблема.** Сборка и поставка образов зависят от доступности чужих хостов. Один внешний сбой
(как 2026-11-08) останавливает выпуск toolchain-образов, хотя наш собственный реестр и пайплайн
публикации живы. Контрольные суммы уже пинятся — то есть **байты** защищены, но **доступность** нет.

**Что не сломалось** (важно для границ): slim-образ backend и образ UI не используют внешние
бинарники (в slim-стадии нет `RUN`, UI — nginx + SPA), поэтому они собирались и деплой на test
прошёл. Пострадал только executor `full` (split-режим) и backend `full` (all-in-one, сейчас выключен).

## Цели и не-цели

**Цели**

1. Сборка образов не зависит от доступности GitHub (и, по возможности, других чужих хостов).
2. Источник артефакта выбирается явно и проверяемо; подмена источника не меняет содержимое (sha256).
3. Обновление зеркала — воспроизводимая операция с ревью, а не ручное копирование «на удачу».

**Не-цели**

- Полностью автономная (air-gapped) поставка продукта — это [ADR-121](./adr-121-offline-portable-distribution.md).
- Зеркалирование всего npm-мира и проксирование трафика агентов в рантайме.
- Изменение формата публикации (Gitea остаётся реестром образов, чартов и пакетов).

## Варианты

| Вариант | Суть | Плюсы | Минусы | Оценка |
|---|---|---|---|---|
| **A. Зеркало в Gitea (Generic)** | артефакты лежат в `git.itphx.ru` как generic-пакеты; сборка качает оттуда | свой контур, тот же TLS/токен, версии и sha256 рядом | нужно поддерживать синхронизацию | 1–2 дня |
| **B. Pull-through кеш** | Nexus/Verdaccio/apt-cacher и т.п. перед внешними реестрами | автоматически, без ручных релизов | новый сервис, квоты, отказоустойчивость, отдельная эксплуатация | 4–8 дней |
| **C. Vendor в git** | бинарники в репозитории / git-lfs | всё в одном месте | раздувает репозиторий, лимиты git, плохо для 35 МБ архивов | 1 день |
| **D. Список fallback-хостов** | основной GitHub, при сбое — зеркало/API | дешево, уже проверено в инциденте | зависимость от чужих зеркал; доверие только за счёт sha256 | 0,5 дня |

**Рекомендация:** A как основа + D как аварийный путь (явно включаемый, не по умолчанию).

## Предлагаемое решение

### 1. Манифест внешних артефактов

Единый источник истины — `docker/external-deps.json` (или `.yaml`): имя, версия, архитектура,
исходный URL, sha256, путь в зеркале, какие flavor'ы используют. Сейчас эти данные размазаны по
`install-tier-*.sh`; манифест делает зависимость видимой и проверяемой.

```json
{
  "kustomize": {
    "version": "5.8.3",
    "files": {
      "amd64": {"source": "https://github.com/.../kustomize_v5.8.3_linux_amd64.tar.gz",
                 "sha256": "cb9e3119…", "mirror": "toolchain/kustomize/5.8.3/kustomize_linux_amd64.tar.gz",
                 "flavors": ["devops", "full"]}
    }
  }
}
```

### 2. Хранилище и схема URL

Generic-реестр Gitea: `https://git.itphx.ru/api/packages/itphx/generic/synth-mirror/<путь>`.
База переопределяется переменной `SYNTH_ARTIFACT_MIRROR` (config/env, приоритет — как в
[ADR-023](./adr-023-configuration.md)); пусто → поведение прежнее (напрямую из upstream).

### 3. Загрузчик

`synth_install_upstream_binaries` (`docker/install-lib.sh`) получает порядок источников:

1. зеркало (если `SYNTH_ARTIFACT_MIRROR` задан и артефакт есть);
2. upstream (текущее поведение);
3. аварийный путь (опционально, только при явном `SYNTH_ALLOW_FALLBACK=1`).

Контрольная сумма проверяется **всегда**, независимо от источника. Несовпадение — падение сборки
(fail-closed, как сейчас). Выбранный источник пишется в лог сборки.

### 4. Авторизация

Сборка ходит в Gitea с токеном только на чтение пакетов; токен передаётся build-secret'ом
(BuildKit `--secret`) и **не попадает в слои образа**. Для локальной сборки — `GITEA_READ_TOKEN`
из окружения. Публичный анонимный доступ к зеркалу не предполагается.

### 5. Синхронизация

`scripts/mirror-sync.sh`:

- `--check` — сверить манифест с зеркалом (чего нет, что разошлось по sha256);
- `--upload` — загрузить недостающее (идемпотентно, без перезаписи при совпадении);
- `--prune --keep N` — ретеншн (по умолчанию только план).

Запуск: вручную при bump версий + отдельная CI-джоба `mirror-sync` (ручной dispatch), по аналогии
с `beta-prune`.

### 6. Базовые образы (отдельное решение)

`node:22-alpine`, `node:22-bookworm-slim`, `nginx:alpine` сейчас берутся по тегу с Docker Hub.
Предлагается: зеркалировать их в Gitea и пинить **по digest** (`FROM …@sha256:…`) — это и снимает
зависимость от Docker Hub, и делает сборку воспроизводимой. Требует отдельного решения (см. вопросы).

### 7. npm-зависимости (отдельное решение)

`pnpm install` в build-стадии и 6 tarball'ов MCP идут с `registry.npmjs.org`. Минимально достаточно
lockfile + повторов; полноценно — pull-through npm-прокси (вариант B) или зеркало конкретных
tarball'ов в том же generic-хранилище. Решение — за владельцем.

## Этапы

| Этап | Что | Оценка | Критерий готовности |
|---|---|---|---|
| Ф0 | Манифест + зеркало 4 GitHub-артефактов (yq, kustomize, tofu, hadolint) + поддержка `SYNTH_ARTIFACT_MIRROR` в `install-lib.sh` | 0.5–1 день | сборка executor `full` проходит при заблокированном GitHub; sha256 совпадает |
| Ф1 | `mirror-sync.sh` + CI-джоба + документация (`docs/PUBLISHING.md`, `docs/DEVELOPMENT.md`) | 0.5–1 день | повторный прогон идемпотентен; `--check` в CI |
| Ф2 | Зеркало базовых образов + пин по digest | 0.5 дня | Dockerfile'ы без тегов; сборка не ходит в Docker Hub |
| Ф3 | Решение по npm (прокси или зеркало tarball'ов) и реализация | 1–2 дня | сборка образов не зависит от npmjs (или зависимость явно принята) |

## Риски

| Риск | Мера |
|---|---|
| Зеркало устарело / расхождение версий | `mirror-sync --check` в CI; манифест — единственный источник версий |
| Токен утечёт в образ | только build-secret; проверка `docker history` перед публикацией |
| «Своё» зеркало станет единственной точкой отказа | оно в том же Gitea, что и образы/чарты; бэкап Gitea — [ADR-091](./adr-091-backup-restore-transfer.md) |
| Ручная синхронизация забывается | CI-джоба + предупреждение сборки при отсутствии артефакта в зеркале |
| Подмена содержимого | sha256 из манифеста; никаких «доверенных» зеркал без сверки |

## Открытые вопросы (нужно решение владельца)

1. **Хранилище**: Gitea Generic (рекомендуется) или отдельный Nexus/Verdaccio?
2. **Базовые образы**: зеркалировать `node`/`nginx` и пинить по digest — да/нет?
3. **npm**: достаточно lockfile+retry или нужен pull-through прокси (вариант B)?
4. **Синхронизация**: ручной скрипт при bump версий или CI-джоба по расписанию?
5. **Ретеншн**: сколько версий артефактов хранить (по умолчанию 5)?
6. **Аварийный fallback**: разрешать ли автоматическое переключение на GitHub API/зеркало при сбое основного источника — или только явное включение?
