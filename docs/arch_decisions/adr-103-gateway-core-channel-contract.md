# ADR-103: Ядро шлюзов (`@itphx/synth-gateway-core`) и контракт канала

> **Статус:** ⚠️ Частично
> **Дата:** 2026-10-21
> **Связано:** [ADR-087](./adr-087-gateways.md) (класс Gateway),
> [ADR-089](./adr-089-external-events-automation.md) (внешние события, Binding, claim-flow),
> [ADR-086](./adr-086-extensibility-plugins-editions.md) (классы расширений),
> [ADR-052](./adr-052-public-api-platform.md) (service-key, scopes)

## Контекст

Telegram-шлюз — единственная реализация класса Gateway
([ADR-087](./adr-087-gateways.md)). Его код разделился на две части: около половины
канал-независимо (аутентификация в API Synth, SSE-watcher доставки, конфиг тенантов,
`FileStore`, MCP-транспорт, инсталлятор ресурсов) и половина канал-специфична
(Bot API, нормализация `Update`, разметка под Telegram-HTML, `tg_*`-тулы).

Второй канал (email: IMAP/SMTP) и ещё два запланированных показали, что копирование
эталона даёт ~4000 LOC дублирования на канал и — что хуже — расхождение правил:
дедуп, фоллбэк `stream.done`/`message.added`, fail-closed allowlist, приоритет
конфига, формат ошибок MCP. Каждое расхождение в этих правилах — расхождение
идемпотентности и безопасности, а не только кода.

[ADR-087](./adr-087-gateways.md) §4 отложил общий интерфейс канала: решение было
принято при одном шлюзе. При трёх и более оно пересмотрено.

## Решение

Вынести общую часть в **отдельный npm-пакет `@itphx/synth-gateway-core`**
(репозиторий `addons/synth-gateway-core`, публикуется в npmjs.org). Пакет
определяет **контракт канала** — порт, который реализует каждый шлюз:

| Элемент контракта | Назначение |
|---|---|
| `source` | идентификатор источника событий (`source` в `POST /api/v2/events`) |
| `capabilities` | `streaming` / `editing` / `drafts` / `threads` / `attachments` |
| `start(ctx)` / `stop()` | приём: подключение к внешнему миру и цикл чтения |
| `send(req)` | доставка ответа в канал |
| `notify?(req)` | служебное уведомление каналу (код линковки, отказ) |

**Ядро** владеет: политикой приёма (allowlist fail-closed, дедуп, политика
неизвестного отправителя, claim-flow), доставкой (SSE `GET /api/v2/events`, дедуп
`stream:<id>` / `message:<sessionId>:<index>`, фоллбэк `message.added` с
grace-паузой), конфигом тенантов, состоянием, аутентификацией в API Synth,
MCP-транспортом, инсталлятором ресурсов, health и логированием.

**Канал** владеет: wire-протоколом, нормализацией входящего сообщения в
`InboundMessage` (`dedupKey`, `identity`, `text`, `meta`, `target`), адресатом
ответа (`target`), доставкой (`send`), тулами MCP.

Границы: канал не знает про API Synth (кроме `ctx.publish`), ядро не знает про
wire-протокол; ни то, ни другое не реализует LLM. Контракт опубликован как
[`docs/contract.md`](https://gitverse.ru/itphx/synth-gateway-core) пакета и
версионируется по semver; шлюз фиксирует диапазон версий.

### 3.1. Операции канала

Интерфейс операций задан [ADR-087](./adr-087-gateways.md) §4: `send`/`edit`/
`delete`/`actions`/`subscribe`. Реализация в `ChannelAdapter`:

| Операция ADR-087 | В контракте | Обязательность |
|---|---|---|
| `subscribe` | `start(ctx)` + `stop()` | обязательно |
| `send` | `send(req)` | обязательно |
| `edit` | `edit?(req)` | опционально (`capabilities.editing`) |
| `delete` | `delete?(req)` | опционально (`capabilities.deleting`) |
| `actions` | `actions?(req)` | опционально (`capabilities.actions`) |
| — | `markRead?(req)` | опционально (аналог IMAP `\Seen`) |
| — | `notify?(req)` | опционально (код линковки) |

Операции **опциональны**, иначе канал без правок (почта) не реализует интерфейс;
поддержка объявляется флагами `ChannelCapabilities`.

## Альтернативы

- **Копия кода в каждый шлюз** — отклонено: ~4000 LOC дублирования на канал и
  расхождение правил идемпотентности/безопасности между шлюзами.
- **Общий код в монорепо `synth/packages/`** — отклонено: версия общего пакета
  была бы связана с релиз-поездом продукта, а потребители (шлюзы) живут
  независимыми циклами выпуска.
- **«Платформа каналов»** с адаптерами `send/receive/edit/attach` и общим ядром
  (отложенный путь [ADR-087](./adr-087-gateways.md) §4) — отклонено как
  переусложнение: контракт из четырёх методов покрывает и мессенджер, и почту;
  конкретика (живое сообщение, черновики, MIME, треды) остаётся в канале.
- **Общий интерфейс без общего ядра** (только типы) — отклонено: типы не удержат
  правила дедупа и фоллбэка, они и разъезжаются между шлюзами.

## Последствия

- Telegram-шлюз переводится на пакет **отдельной задачей** (v0.4.0); поведение
  для пользователей не меняется — совместимость проверяется выкаткой в `test`.
- Email-шлюз строится сразу на пакете.
- Появляется точка версионирования: контракт — semver, шлюз фиксирует диапазон;
  обновление общего пакета — независимое решение шлюза.
- [ADR-087](./adr-087-gateways.md) §4 обновляется: «адаптеры каналов» реализованы
  в виде контракта канала (без общего интерфейса адаптеров `send/receive/edit/attach`).
- Внешняя зависимость для шлюзов: пакет публикуется в npmjs.org по тегу, как и
  сами шлюзы.

## Статус в коде

- Репозиторий `addons/synth-gateway-core`: контракт (`docs/contract.md`) и
  реализация ядра — **готовы** (пакет `@itphx/synth-gateway-core`, версия 0.1.0;
  публичный API: 15 модулей, контракт канала, политика приёма, доставка через
  SSE, конфиг тенантов, состояние, аутентификация, MCP-транспорт, инсталлятор).
- Потребители: `synth-gateway-email` (в работе), `synth-gateway-vk` и
  `synth-gateway-max` (в работе, оба ждали появления каркаса),
  `synth-gateway-telegram` (перевод на пакет — отдельная задача).
- Остаток: публикация пакета в npmjs.org; перевод Telegram-шлюза; правка
  `ChannelCapabilities` в потребителях (новые обязательные поля `deleting` и
  `actions` — breaking change, релиз minor 0.2.0).

## История
