# PROP-106: Файловые порты инстанса в SQL: единое состояние при нескольких репликах

> ⚠️ **Принято как [ADR-116](./adr-116-instance-state-and-blob-ports.md) (2026-10-27).** Файл оставлен как история: правило каталога — файлы не удаляются (см. [ARCH_DECISIONS.md](../ARCH_DECISIONS.md) §4 «Канонические статусы»).

> **Статус:** ✅ Принято (ADR-116) — перевод четырёх файловых портов инстанса в SQL (`packs`, `skills`, `contextFiles`, legacy `pipelines`); `blobs` остаётся файловым по конструкции, в БД — только `blob_refs`
> **Дата:** 2026-10-22
> **Источник:** 2026-10-22 (аудит готовности Synth к backend.replicaCount > 1)
> **Связано:** ADR-046, ADR-069, ADR-086, ADR-096, ADR-097, ADR-098, ADR-100, ADR-101, ADR-077, PROP-085

**Решение:** четыре файловых порта слоя хранения, которые остаются файловыми даже под PostgreSQL
(`packs`, `pipelines` (legacy), `skills`, `contextFiles`), переводятся в SQL, чтобы состояние
инстанса было единым независимо от числа реплик control plane. Пятый порт — `blobs` — **в SQL не
переводится**: байты (вложения сообщений, артефакты прогонов, содержимое скиллов, логи процессов)
живут на томе, а в БД заводится только учёт ссылок (`blob_refs`) для дедупа и детерминированного GC.
Владение томом решается деплоем: по умолчанию один том (`{dataDir}`), отдельный блоб-том — опция;
при `backend.replicaCount > 1` том с блобами обязан быть `ReadWriteMany`.

## Решение

Ключевой инвариант: **реплика control plane — не владелец состояния**. Всё, что меняет поведение инстанса
для всех пользователей (реестр установленных пакетов расширений, instance-скиллы, ролевые промпты и
пользовательские промпты, определения пайплайнов), должно лежать в общем хранилище с транзакциями, а не в
каталоге конкретной реплики.

Сегодня слой хранения (ADR-096) разделён надвое:

- **42 порта** из 47 реализованы в PostgreSQL поверх SQL — это и есть общее состояние инстанса
  (цифры на 2026-10-27; в первой редакции документа было «31 из 36» — с тех пор добавились порты
  ADR-101/105/107/111/112/113/114);
- **5 портов** в драйвере PostgreSQL подменены файловыми реализациями core — они лежат в `{dataDir}` и при
  `backend.replicaCount > 1` расходятся между репликами. Четыре из них (`packs`, `pipelines`, `skills`,
  `contextFiles`) переводятся в SQL; пятый (`blobs`) остаётся файловым **по конструкции** (см. ниже).

Четыре «оставшихся» порта — это не случайный хвост: ровно те, чьё состояние пишет **установщик пакета
расширения** (ADR-086/ADR-100) одной операцией — реестр установок, legacy-определения пайплайнов, метаданные
скиллов и ролевые промпты. Порознь они не переводятся: перенос реестра в SQL без переноса артефактов даёт
худший вариант — «реестр говорит, что пакет установлен, а артефактов нет». Поэтому перевод идёт
**группой**.

Что переводится:

| Порты | Куда | Что снимается |
|---|---|---|
| `packs` | SQL (`pack_installations`) | расхождение реестра установок между репликами; потерянное «снятие пакета» на одной реплике |
| `pipelines` (legacy ADR-100) | SQL (`pipeline_definitions`, `pipeline_instances`) | расхождение legacy-определений/экземпляров; несогласованность с `packs` при снятии пакета |
| `skills` | SQL (`instance_skills` + содержимое в `blobs`) | расхождение instance-скиллов и supporting-файлов; поломка ленивой инвалидации кэша по mtime/size между репликами |
| `contextFiles` | SQL (пользовательская часть: `{dataDir}/context/user`, `{dataDir}/context/roles`) | расхождение ролей и пользовательских промптов; агент, поставленный пакетом, на другой реплике не резолвится |

### Байты (`blobs`) остаются на томе

`blobs` — единственный файловый порт, который **не** переводится в SQL, и это решение, а не остаток:

- содержимое — write-once неизменяемые объекты (вложения сообщений по PROP-085, артефакты прогонов
  пайплайнов, дерево скиллов, логи фоновых процессов);
- `bytea` в PostgreSQL тянет WAL, TOAST и размер `pg_dump`; бэкап инстанса при `storage.backend=postgres`
  и без того не содержит данных БД (ADR-097 в манифесте `synth backup`), поэтому перенос байтов в БД
  сделал бы `pg_dump`/PITR обязательным условием сохранности вложений;
- при деградации хранилища (ADR-098) сервис поднимается read-only на ФС — файловые вложения в этот
  момент остаются читаемыми, байты в БД были бы недоступны.

Вместо байтов в БД заводится **учёт ссылок** — новая порт-запись `blob_refs`
(`blob_path`, `owner_kind`, `owner_id`): она даёт дедуп по содержимому и детерминированный GC
(удаление сессии/прогона/скилла освобождает объект, но только когда на него не осталось других
ссылок). Файловая и PostgreSQL-реализации `blob_refs` — по общему правилу ADR-096, включая
контрактный suite.

**Том.** По умолчанию — один том (`backend.persistence`, `{dataDir}`), блобы лежат в `{dataDir}/blobs`
(существующий root `BlobStore`). Отдельный блоб-том — **опция** чарта. При `backend.replicaCount > 1`
том с блобами обязан быть `ReadWriteMany`; это ограничение деплоя, а не кода.

Что **не** переводится и остаётся на ФС осознанно:

- **`blobs`** — байты (вложения, артефакты прогонов, содержимое скиллов, логи процессов); в БД —
  только `blob_refs` (см. выше);
- **системные промпты пакета** (`{packageRoot}/prompts`) — часть образа, одинакова на всех репликах, read-only;
  переносить в БД нечего;
- **`workspaces/`** — рабочие каталоги проектов (ADR-075), пользовательское содержимое, а не состояние инстанса;
  в split-режиме это общий RWX-том исполнителя (ADR-077);
- **`secrets/`** — мастер-ключ, ключи сервисов, токен метрик (инвариант 13, ADR-076): файловые по политике;
- **`audit/llm-gateway.jsonl`** — журнал LLM Gateway вне портов (в БД есть отдельный порт `securityAudit`);
- **`meta.json`** — версия схемы файлового периметра (ADR-092); у PostgreSQL свой контур версионирования схемы;
- **`backups/`** — архивы бэкапов.

## Почему файловые порты плохи именно при нескольких репликах

1. **Расхождение состояния.** Реплика A и реплика B читают и пишут разные файлы. Пользователь видит разные
   списки пакетов/скиллов/ролей в зависимости от того, на какой под попал его запрос; админ, снявший пакет,
   увидит, что на половине инстанса пакет ещё «установлен». Обратная ситуация опаснее: агент, поставленный
   пакетом, на реплике A резолвится (есть ролевой промпт в `contextFiles`), а на реплике B — нет
   (`agentTemplate → null`, сессия не создаётся), и это выглядит как «мистический» сбой маршрутизации.

2. **Нет транзакций и claim-семантики.** Файловая реализация `packs` защищена `AsyncLock` **внутри процесса**
   (`file-pack-store.ts:26`) — это не межпроцессная и не межрепличная блокировка. Операция «установить пакет»
   пишет артефакты (скиллы, роли) и только потом пишет реестр — при обрыве между шагами реестр и файловая
   часть расходятся **внутри одного инстанса** (`packs.ts:485-529` → `:889`). Claim-семантика очереди
   (обсуждается в PROP-105) на файловом порте не выражается вовсе.

3. **Несовместимость с `StorageContext.locks`.** Advisory-локи БД (`PgMutex`/`PgLeader`,
   `packages/storage-postgres/src/locks.ts:243-261`) защищают SQL-порты и файловые локи миграций. Файловые
   порты под advisory-лок не попадают — «транзакция» файлового порта и «транзакция» SQL-порта не могут
   быть одной.

4. **Свой бэкап/восстановление/миграции.** `synth backup` снимает файловый периметр и **не содержит данных
   БД** (`docs/MAINTENANCE.md:114-116`); `synth restore` БД не трогает (`:357-359`); `synth storage migrate`
   не переносит `skills`/`contextFiles` и не переносит `packs`/legacy `pipelines`
   (`storage-migrate.ts:11-24`). Пока часть состояния — в файлах, часть — в БД, восстановление инстанса
   требует **двух** независимых процедур и не даёт согласованного среза. Байты `blobs` — отдельная история:
   они и после перевода остаются в файловом периметре (по конструкции), поэтому в бэкап БД не попадают.

5. **Поведение при `helm uninstall` и `keepOnUninstall`.** PVC `data` по умолчанию удаляется при
   `helm uninstall` (`charts/synth/values.yaml:56`), а при `keepOnUninstall: true` переживает снятие релиза
   (аннотация обязана быть в манифесте — `backend-pvc.yaml:9-13`). Данные БД при этом по умолчанию **не**
   удаляются (`uninstall --purge-db` — только по явному флагу, `docs/MAINTENANCE.md:360`). Смешанная модель
   «часть в томе, часть в БД, части — с разным TTL» плохо предсказуема при откате релиза.

6. **Разный backend — разное поведение.** Тот же инстанс на `storage.backend=file` и на
   `storage.backend=postgres` сегодня даёт разный ответ на вопрос «где лежит реестр пакетов» (ADR-005 vs
   ADR-097). Для нескольких реплик это превращается в «состояние зависит от того, какой backend выбран и на
   каком поде попал запрос».

## Том: один по умолчанию, отдельный — опция

**Что даёт общий (`ReadWriteMany`) том.** Один PVC с `accessMode: ReadWriteMany` вместо `ReadWriteOnce`
(`charts/synth/values.yaml:51` → `ReadWriteMany`) монтируется во все реплики. Файловая часть — прежде всего
`blobs` (байты вложений/артефактов/скиллов) — начинает видеть одно и то же состояние; расхождение между
репликами по ней исчезает **без изменений в коде**; попутно снимается проблема managed-режима: второй под
не может смонтировать RWO-том (`backend-pvc.yaml:16-17`). Класс `nfs-rwx` в кластере уже есть и уже
используется под общий workspace исполнителя (`charts/synth/README.md:667-671`).

Решение 2026-10-27 по раскладке: **том один по умолчанию** (блобы внутри `{dataDir}/blobs`), отдельный
блоб-том — **опция** чарта; при `backend.replicaCount > 1` том, где лежат `blobs`, обязан быть `RWX`.

**Чего общий том не даёт.**

- **Это не транзакции.** Файловая семантика: атомарная запись — это tmp→rename в пределах одной ФС
  (ADR-005), а не атомарность набора записей. «Установить пакет» по-прежнему может оставить артефакты без
  записи в реестре — поэтому `packs`, `skills` и `contextFiles` и переводятся в SQL.
- **Нет claim-семантики.** Файловый лок (`FileMutex` — mkdir-лок) умеет только «встать в очередь», но не
  выражает «я забрал эту задачу» в смысле PROP-105.
- **«Hot data» на NFS.** Каталог данных инстанса — это то, что backend читает и пишет на каждом запросе
  (сессии, события, настройки). Они уже в SQL; на общем томе остаются только холодные объекты, поэтому
  аргумент про NFS к ним не применяется.
- **Свой бэкап.** Общий том — это ФС: снятие согласованного среза с работающим инстансом по-прежнему не
  гарантировано (`--live` полноты не гарантирует — `docs/MAINTENANCE.md:356`).

**Совместимость с целевым состоянием.**

- байты `blobs` **не переезжают** ни при каком переводе портов: порт не меняет backend, том может быть
  один или отдельный;
- остальные четыре порта при переводе в SQL снимаются с тома **через порты**
  (`synth storage migrate` — идемпотентный перенос по доменным методам, `storage-migrate.ts:4-9`),
  а не копированием файлов;
- после перевода в SQL файловая часть `{dataDir}` остаётся для `blobs/` и **вне-портового** периметра
  (`workspaces/`, `secrets/`, `audit/*.jsonl`, `meta.json`, `backups/`);
- двойного источника истины не возникает: в каждый момент времени либо порт читается из SQL (истина в БД),
  либо — из файла (истина на томе), но не оба сразу; переключение — миграция с откатом (см. «Обратная
  совместимость»).

**Риски для `storage-postgres`.** Новые таблицы и индексы (уникальность `pack_installations.name`,
`instance_skills.name`, `context_files(category, filename)`, PK `blob_refs`); новая миграция в собственном
контуре версионирования (`migrations/index.ts`, следующий номер после `023`); риск «схема в БД новее
ожидаемой» (`STORAGE_POSTGRES_SCHEMA_TOO_NEW`, fail-closed) — при откате релиза с новой миграцией старый
драйвер не поднимется, это **штатное** поведение, но его надо держать в голове при раскатке.

**Риски для контрактного suite.** Каждая реализация обязана пройти общий suite
(`packages/core/src/storage/contract/*` — «паспорт» порта, эталон — memory-backend). Для новых SQL-портов
это значит: (а) контрактные блоки уже существуют и должны начать проверять SQL-реализацию, а не файловую
(достаточно снять пометку «file-backed»); (б) `describeSkillRepository` и `describeContextFileRepository`
проверяют поведение, а не ФС-детали, — но после снятия `root()`/`skillDir()` из порта контрактные блоки
должны быть переписаны под новый интерфейс (иначе они не сойдутся с портом); (в) контракт для `blobs`
(`contract/misc.ts` — round-trip, рекурсивный `list`, containment) остаётся как есть: порт не меняет
backend, блок продолжает проходить на файловой реализации.

## Порядок реализации

1. **Том и его режим.** По умолчанию — **один** том (`backend.persistence`), блобы живут в
   `{dataDir}/blobs`. Отдельный блоб-том — **опция** чарта (второй PVC, `existingClaim`/`accessMode` по
   значениям). При `backend.replicaCount > 1` том с блобами обязан быть `ReadWriteMany` (класс `nfs-rwx`
   в кластере уже есть). Ни строчки доменного кода. Проверка: `kubectl -n synth get pvc` — ожидаемый набор
   claim'ов и режимов доступа.
2. **Инвентаризация и замеры.** Зафиксировать фактические размеры и карту использования четырёх
   переводимых портов (кто читает/пишет, какие файлы, сколько занимает `packs.json`/`skills/`/`context/`)
   плюс объём `blobs` (логи процессов; будущие вложения/артефакты). Проверка: таблица
   «порт → потребители → объём» в задаче; ни одного потребителя мимо порта.
3. **Перевод группы 1: `packs` + legacy `pipelines`.** SQL-реализации в драйвере + миграция `024_*`;
   сборка контекста переключается с `file.packs`/`file.pipelines` на SQL
   (`packages/storage-postgres/src/storage-context.ts:212-213`); контрактные блоки `packs`/`pipelines`
   перестают быть «file-backed». Проверка: контрактный suite на живой PostgreSQL (`SYNTH_TEST_POSTGRES_DSN`)
   зелёный; `synth storage migrate --to postgres` переносит реестр.
4. **Учёт ссылок `blob_refs`.** Новая порт-запись (`file`/`memory`/`postgres`) + контрактный блок; ссылки
   пишутся при появлении/удалении вложений, артефактов, скиллов; GC удаляет объект, когда ссылок не осталось.
   Проверка: удаление сессии/прогона освобождает объект; дедуп-копия (вторая ссылка на тот же `sha256`)
   остаётся.
5. **Перевод группы 2: `skills`.** `instance_skills` (метаданные) + содержимое в `blobs`; **переработать
   порт** — убрать `root()`/`skillDir()` (`ports/skill-repository.ts:14-16`), перевести
   `engine/skills/{service,loader}.ts` и `discovery.ts` с чтения ФС на чтение содержимого из blob-порта.
   Проверка: контракт `describeSkillRepository` переписан под новый интерфейс и зелёный на file/memory/PG;
   `GET /api/v2/skills` показывает те же данные.
6. **Перевод группы 3: `contextFiles` (пользовательская часть).** Таблица `context_files`; **системная**
   часть (промпты образа) остаётся на ФС и читается как раньше; геттеры порта — из процесс-локального кэша,
   обновляемого по сигнатуре версии (по образу `filesSignature`/`dirsSignature`,
   `packages/core/src/engine/file-signature.ts`). Проверка: ролевой промпт, записанный на реплике A,
   виден на реплике B; сборка системного промпта не изменилась (golden-снимки).
7. **Миграция данных.** `synth storage migrate --to postgres` переносит четыре порта (идемпотентно,
   по доменным методам — `storage-migrate.ts:4-9`); список «что переносится» в шапке модуля обновляется
   (`storage-migrate.ts:11-24`); добавляется обратное направление (postgres → file) для отката.
   `blobs` не переносится **никогда** — байты не меняют backend. Проверка: прогон на копии боевого `dataDir`
   — счётчики `copied`/`skipped` совпадают с ожидаемыми, повторный прогон даёт `skipped` (идемпотентность).
8. **Сужение рантайм-импорта core в драйвере.** После перевода четырёх портов из драйвера уходит
   `createFileStorage` — остаётся только `FileBlobStore` для порта `blobs` (`storage-context.ts:32`, `:71-79`,
   `:206`). Полностью снять импорт нельзя: `blobs` файловый по конструкции. Проверка: в драйвере нет
   рантайм-импортов core, кроме `FileBlobStore`; `pnpm --filter @itphx/synth-storage-postgres build`
   и `pnpm test` зелёные.

### Обратная совместимость

- **Существующие инстансы** (`storage.backend=file`): файлы продолжают работать как раньше — файловые
  реализации остаются в core и выбираются по-прежнему; перевод меняет только **драйвер PostgreSQL**
  (`storage-context.ts:195-215`), то есть затрагивает инстансы с `storage.backend=postgres`. Файловый backend
  standalone/local home (ADR-005, ADR-079) не трогаем — это его штатный режим.
- **Миграция данных** — только через порты (`synth storage migrate`), идемпотентно, с отчётом по сущностям.
- **Что с `data`-томом в итоге:** он не исчезает и **не обязан становиться общим**: файловый периметр
  (`blobs/`, `workspaces/`, `secrets/`, `audit/*.jsonl`, `meta.json`, `backups/`) остаётся файловым.
  Один том — режим по умолчанию; отдельный блоб-том — опция. При `replicaCount > 1` общий (`RWX`) нужен
  **только тому, где лежат `blobs`**, — остальное состояние уже в БД.
- **Откат:** пока в БД нет новых таблиц (шаги 1–2) — откат свободный. После шага 3 откат требует либо
  обратного переноса (`migrate --to file`), либо сохранения БД как есть; схема «новее ожидаемой»
  (`STORAGE_POSTGRES_SCHEMA_TOO_NEW`) блокирует старт старого драйвера — это fail-closed, штатное поведение.
  Байты `blobs` при откате не трогаются вовсе.
- **Стыковка с PROP-105** (координация в нескольких репликах): claim-семантика очереди требует, чтобы
  «взял задачу» было атомарным и наблюдаемым — файловый порт этого не даёт, SQL-порт даёт. Поэтому шаги
  3–6 — предусловие для полноценной claim-семантики (шаг 1 снимает только симптом).
- **Стыковка с PROP-104** (внешний транспорт событий): доставка внешнего события в сессию опирается на
  `eventBindings`/`eventRoutes`/`eventJournal` — они уже в SQL, поэтому файловые порты на неё не влияют;
  влияние косвенное — через `packs`/`skills`/`contextFiles` (агент, чей ролевой промпт или скилл не виден
  на реплике, не отработает).

## Открытые вопросы

1. **`contextFiles`: где граница ФС и БД.** Предлагается: системные промпты (часть образа, одинаковы на всех
   репликах) — всегда ФС; пользовательские override (`{dataDir}/context/{user,roles}`) — БД. Подтвердить.
2. **Синхронные геттеры `contextFiles`.** Порт синхронный (сборка промпта на горячем пути), SQL-чтение
   асинхронно → нужен кэш в процессе. Как часто он инвалидируется: по TTL, по сигнатуре версии в БД
   (как `secretPatterns`/`protectedPaths` сейчас — процесс-локальный кэш, см. «Известные расхождения»
   в `packages/storage-postgres/AGENTS.md`) или по событию?
3. **Размер `packs.files`.** Порт хранит содержимое файлов пакета целиком (`ports/pack-repository.ts:56-65`),
   в JSONB это может быть крупно (TOAST). Отдельная таблица `pack_files` или оставить в `jsonb`?
4. **GC и `blob_refs`.** Когда удалять объект: сразу при потере последней ссылки, с отсрочкой (окно
   безопасности на «гонку» с записью) или только периодическим sweep? Кто владельцы ссылок для логов
   процессов (у них свой retention) и для артефактов прогонов (retention прогонов)?
5. **Чарт: параметры тома.** Блобы внутри `data` по умолчанию; опция отдельного PVC — как называется
   (`blobs.persistence.enabled`/`blobs.existingClaim`) и должна ли схема чарта падать (`fail`) при
   `replicaCount > 1` и `accessMode: ReadWriteOnce` на томе с блобами.
6. **Миграция без простоя и приоритет при двойном чтении.** `synth storage migrate` требует остановки
   инстанса? Сейчас перенос идемпотентен и идёт по доменным методам, но «живая» миграция (порты
   переключаются на работающем инстансе) не описана. Если она появится — нужен явный приоритет
   (read-old/write-new на время переноса четырёх портов). Байты `blobs` в этом вопросе не участвуют.

- **ADR-096/ADR-097** — рамка: доменные порты, контрактный suite, драйвер.
- **ADR-091/ADR-092** — бэкап/восстановление/миграции схемы: после перевода состояние инстанса живёт в

  и архив файлового периметра.

## История

- 2026-10-27 — решение по границе «файлы vs SQL»: `blobs` **не переводится** в SQL (write-once байты на
  томе; против `pg_dump`/WAL и ради читаемости при деградации хранилища), в БД заводится только
  `blob_refs`; том — один по умолчанию, отдельный блоб-том — опция, `RWX` обязателен при
  `replicaCount > 1`; в SQL идут четыре порта (`packs`, `pipelines`, `skills`, `contextFiles`).
  Инвентарь пересчитан: 47 портов, из них 5 файловых (было «36/5»).
- 2026-10-22 — документ создан по итогам аудита готовности Synth к `backend.replicaCount > 1`: зафиксировано,
  что 5 портов (`packs`, legacy `pipelines`, `skills`, `contextFiles`, `blobs`) остаются файловыми даже под
  PostgreSQL; общий RWX-том `data` — промежуточная мера; целевое состояние — перевод этих портов в SQL.
