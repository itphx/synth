# PROP-073: Целостность клиента в гибридном режиме — клиент недоверенный, enforcement на сервере

> **Статус:** 🧩 Предложение — Целостность клиента в гибриде: enforcement на сервере; сигналы целостности (подписи, DPoP/mTLS) — опционально
> **Решение до:** 2026-11-14
> **Дата:** 2026-09-23
> **Парные документы:**
> - [ADR-042](./adr-042-hybrid-mode.md) «Гибридный режим — локальный core + централизованный сервер» — задаёт модель A (удалённые сессии исполняет сервер) и LLM Proxy; PROP-073 фиксирует границу доверия внутри этой модели;
> - [ADR-043](./adr-043-unified-identity-login.md) «Единая идентичность в гибриде» — вход в UI, ROPC/device flow, токены; PROP-073 определяет, что токен подтверждает канал, а не целостность клиента;
> - [ADR-045](./adr-045-hybrid-server-profiles.md) «Профили серверов и лёгкий runtime-вход в гибриде» — единый dataDir, `profiles.json`, ConnectionWatcher; enrollment device-ключей опирается на этот реестр;
> - [ADR-036](./adr-036-llm-gateway.md) «LLM Gateway — независимый слой безопасности» — guard, обфускация, rate limit и аудит на сервере, недостижимые клиенту;
> - [PROP-037](./prop-037-commit-security-step.md) «Security step перед коммитом» — образец enforcement, который нельзя обойти уровнем ниже (git hook), а не заявлением агента;
> - [ADR-029](./adr-029-granular-permissions.md) «Гранулярные permissions» — allow/deny/ask per tool, применяются server-side;
> - [ADR-022](./adr-022-typescript-stack-runner.md) «Единый TypeScript стек + Runner-архитектура» — движки stateless: история и состояние на бэкенде.

**Решение:** в гибридном режиме (ADR-042) клиент (`synth serve` / локальный core + UI) считается **недоверенным**. Граница доверия — сервер (backend). Все security-инварианты обеспечиваются server-side и не зависят от заявлений клиента (`userId`, роль, `origin`, версия/хеш сборки). Строгая криптографическая аттестация клиента как граница безопасности **осознанно не применяется**; механизмы целостности — только опциональные сигналы defense-in-depth (Ф2+).

---

## 1. Контекст и проблема

Гибрид (ADR-042) добавляет третью топологию: локальный core на машине пользователя + централизованный backend в K3s. Удалённые сессии исполняет сервер, локальные — локальный core, а LLM-трафик централизован на сервере (LLM Proxy + Gateway ADR-036). Возникает вопрос: **насколько сервер может доверять локальному клиенту** — его заявлениям о личности, роли, происхождении сущностей и версии сборки.

Соблазн — построить security-границу на «доверенном клиенте» (аттестация бинаря, проверка целостности установки). Этот путь принципиально недостижим для нашего стека и создаёт ложное чувство защиты. Поэтому решение фиксируется жёстко: **доверенной стороной является только сервер**, а любые клиентские сигналы — необязательный вклад в риск-скор, не гейт безопасности.

## 2. Граница доверия

```
Доверенная зона (сервер, K3s)                Недоверенная зона (машина пользователя)
┌────────────────────────────────┐           ┌────────────────────────────────────┐
│ synth-backend                  │           │ synth serve (локальный core)       │
│  ├─ OIDC/RBAC/canAccess        │  HTTPS    │  ├─ UI (SPA)                       │
│  ├─ ChatOrchestrator (движок)  │◄─────────►│  ├─ RemoteBackendClient            │
│  ├─ LLM Proxy + Gateway        │  токен    │  ├─ RemoteEventBridge              │
│  ├─ аудит (append-only)        │           │  └─ JS-процесс под контролем юзера  │
│  └─ хранилище сессий/проектов  │           └────────────────────────────────────┘
└────────────────────────────────┘
```

- **Доверенная сторона** — backend: аутентификация, авторизация, применение permissions, LLM Gateway, аудит, исполнение remote-сессий.
- **Недоверенная сторона** — всё, что исполняется на машине пользователя: локальный core, UI, сетевой канал до сервера (в смысле «гарантий о содержимом»). Клиент может быть легитимным, модифицированным или скомпрометированным — сервер не различает это по заявлениям.
- **Следствие:** сервер никогда не выводит права и решения безопасности из данных, присланных клиентом. Личность определяется по токену, владение — по серверным записям, `origin`/`userId` из тела запроса игнорируются.

## 3. Почему строгая аттестация недостижима

Строгая аттестация («докажи, что бинарь не модифицирован») для нашего клиента не работает:

1. **Клиент — обычный Node.js/JS-процесс с полными правами пользователя.** JS патчится (правка `node_modules`, monkey-patching, подмена точки входа), память читается отладчиком, сеть перехватывается MITM/прокси. Ничто на уровне процесса не даёт криптографической гарантии «исполняется именно наш код».
2. **Аппаратная аттестация рассчитана на другой контур.** TPM / Secure Enclave / remote attestation удостоверяют **подписанный нативный бинарь**, запущенный в изолированном окружении с измеренной цепочкой загрузки. У нас — интерпретируемый JS + дерево npm-зависимостей, чей результат не воспроизводится побайтово (версии транзитивных зависимостей, окружение, лоадеры). Доказывать «бинарь не модифицирован» не над чем: бинаря в этом смысле нет.
3. **Клиент подконтролен пользователю по определению.** Гибрид существует ровно для того, чтобы пользователь работал на своей машине с локальными файлами/провайдерами. Владелец машины всегда может изменить клиент; любая «проверка целостности» на его же машине обходится им же.
4. **Вывод.** Аттестация клиента не может быть границей безопасности. Граница — сервер; клиентские сигналы допустимы только как defense-in-depth.

## 4. Что достижимо: сигналы, а не гарантия

| Механизм | Что даёт | Где обходится |
|---|---|---|
| **Подписанные релизы** (npm provenance / Sigstore, code signing) + серверный allowlist версии/хеша сборки | Ловит дрейф версий и «левую» сборку; отсекает забытые/сторонние дистрибутивы | Целевой атакующий патчит уже установленный код после проверки; хеш установленных файлов можно подделать в self-report |
| **Привязка канала/токена** (mTLS device-сертификат после enrollment или DPoP proof-of-possession + короткоживущие токены) | Украденный токен нельзя переиграть с другого клиента; привязка запроса к ключу | Это целостность **канала**, не бинаря: легитимный ключ на скомпрометированной машине остаётся валидным |
| **Self-report целостности** (хеш установленных файлов vs манифест релиза) | Индикатор/риск-скор для аудита и предупреждений | Подделывается модифицированным клиентом; годится только как сигнал |

Все три механизма — **опциональные** и не заменяют server-side enforcement. По умолчанию (Ф1) достаточно того, что уже enforced на сервере (§5).

## 5. Что уже enforced server-side

- **RBAC и `canAccess` на каждый запрос.** `packages/backend/src/auth/middleware.ts` (`requireAuth`, `requirePermission`, `isAdmin`, `hasRole`); владелец сессии или ADMIN — `packages/backend/src/routes/sessions.ts` (`canAccess`). Заявления клиента о роли/личности не используются.
- **LLM-трафик только через LLM Proxy + Gateway (ADR-036/042).** Ключи провайдеров, guard, обфускация, rate limit и cost-трекинг живут на сервере; клиент их не видит и не может обойти. В гибриде локальные провайдеры запрещены (`remote.llm: server`).
- **Permissions и режимы (ADR-025/028/029)** применяются на сервере для remote-сессий; allow/deny/ask не хардкодятся в клиенте.
- **Неизменяемый аудит на сервере.** `packages/backend/src/routes/audit.ts` (RBAC ADMIN/AUDITOR), JSONL append-only (ADR-036). Клиент не может подавить или переписать серверные записи.
- **Remote-сессии исполняются сервером (ADR-022/042).** Оркестратор, история, tool-loop и применение прав — на бэкенде; клиент для них — тонкий клиент.
- **`remote:` id не дают прав.** Маршрутизация по полю `origin` (ADR-042); id — только адрес, авторизация проверяется отдельно по токену и серверным записям.

## 6. Модель угроз

| Угроза | Контрмера |
|---|---|
| Модифицированный клиент (патч JS, MITM) | Server-side enforcement: RBAC/`canAccess`, Gateway, permissions, аудит; заявления клиента не принимаются на веру |
| Token theft / replay | DPoP (proof-of-possession) или mTLS device-сертификат; короткоживущие access-токены + rotation refresh |
| Confused deputy (легитимный токен к чужим данным) | RBAC/`canAccess` на каждый запрос; `remote:` id не дают прав; проверка владельца/проекта по серверным записям |
| Подавление клиентского аудита | Аудит пишется на сервере (ADR-036/037); клиентский лог — только вспомогательный |
| Обход guard на локальных сессиях | В гибриде локальные провайдеры запрещены; LLM — только через серверный LLM Proxy + Gateway |
| Эксфильтрация данных | Централизация LLM на сервере, rate limit, аудит; remote-данные не покидают сервер без политики |
| Подмена `origin`/`userId` в запросе | Сервер игнорирует клиентские `origin`/`userId`; личность — из токена, владение — из серверных записей |

## 7. Инварианты

1. **Сервер не доверяет клиентским заявлениям** — `userId`, роль, `origin`, версия/хеш сборки не являются основанием для доступа.
2. **Версия/сборка — сигнал, не гейт по умолчанию.** Строгий build-allowlist — опциональный режим (может ломать dev-сборки).
3. **Аудит пишется на сервере** и не зависит от клиента.
4. **Права и режимы** применяются server-side (ADR-025/028/029), а не на клиенте.
5. **Сигналы целостности (§4)** — defense-in-depth, включаются опционально и не отменяют пункты 1–4.

## 8. Открытые вопросы

- **DPoP vs mTLS** для привязки канала: что проще эксплуатировать в гибриде (device-сертификат после enrollment vs proof-of-possession на короткоживущем токене).
- **Режим строгого allowlist** (версия/хеш сборки): `block` / `warn` / `audit` — и как не сломать локальные dev-сборки.
- **Как считать риск-скор** из self-report целостности (какие расхождения считать критичными).
- **Где хранить device-ключи** (OS keystore vs файл с правами `0600`, как credentials ADR-045).
- **Enrollment** device-ключей: привязка к `profiles.json` (ADR-045) и поведение при переустановке клиента.

## 9. Реализация (предполагаемые файлы)

- `packages/backend/src/auth/*` — привязка канала (DPoP/mTLS), строгий allowlist версии/хеша, риск-скор.
- `packages/core/src/remote/*` — `client.ts`, `credentials.ts`, `session.ts` (device-ключ, proof-of-possession, self-report).
- `packages/core/src/profiles.ts` — привязка device-ключей к серверным профилям (ADR-045).
- `packages/core/src/server/routes/hybrid.ts` — статус/диагностика сигналов целостности.
- Release/CI: `.gitverse/workflows/release.yaml` — подписи релизов (npm provenance / Sigstore, code signing) и публикация манифеста сборки.
- `docs/HYBRID.md` — раздел о границе доверия и сигналах целостности.

## 10. Вне объёма

- Аппаратная аттестация / remote attestation / TEE (см. §3 — неприменимо к интерпретируемому JS).
- Обязательная аттестация клиента как условие доступа.
- Замена server-side enforcement клиентскими проверками.

## 11. Статус в коде и прототипе

- В коде сейчас есть только server-side база (§5): RBAC/`canAccess`, LLM Proxy + Gateway, серверный аудит, исполнение remote-сессий. Привязки канала (DPoP/mTLS), подписей релизов и self-report целостности нет.
- В прототипе `~/dev/aic/t11` темы целостности клиента нет: единственный близкий артефакт — `synth/context/ROLE_SECURITY_AUDITOR.md` (роль-промпт «Аудитор ИБ»). Готовых решений по аттестации/привязке канала в прототипе не заимствуем.
