# ADR-141: Таймеры и будильники — автоматизация проекта без своего промпта

> **Статус:** ✅ Реализовано
> **Дата:** 2026-11-17

## Контекст

Агенту нужно вернуться к работе позже. Единственный способ — `sleep` в shell: он занимает процесс (в фоне) или блокирует ход (в foreground на минуты). Расписание (`Schedule`, ADR-051) для этого не годится: у него **свой текст задания**, который инъецируется в сессию, а для «проснись и пойми по контексту» нужен только комментарий. Кроме того, расписания были инстансными: `GET /schedules` отдавал все записи любому аутентифицированному.

## Решение

1. **Отдельная сущность `Timer`** (`timer` | `alarm`), не расширение `Schedule`: `comment` (1…500) — единственный смысл срабатывания, своего промпта нет; `projectId` и `sessionId` **обязательны** (инстансных автоматизаций нет).
2. **Повторы:** `once`, `daily HH:MM` (IANA-таймзона явным параметром), `every N` (10…2 592 000 с). Горизонт one-shot — 30 суток; ≤50 активных на сессию.
3. **Движок `TimerService`** (`engine/timers/`): персистентный порт, единичный `setTimeout` на ближайшее срабатывание + страховочный тик 30 с, точность ~1 с; лидер-выбор **общий** с шедулером (`SharedLeader`); просроченный one-shot срабатывает один раз при старте (catch-up), повторяющиеся пересчитываются без серии; дедуп по `(timerId, scheduledFor)`.
4. **Доставка — гибрид:** событие `{source:'timer', type:'timer_fired'}` через `EventIngress`/Router, решение `bound` + `delivery:'steer'`; доставка — `createBackgroundParentNotifier` (steer в текущий ход → очередь → фоллбек), ровно одна копия в истории. Сообщение — конверт `<timer …>` с комментарием, `metadata.type:'timer_fired'`.
5. **UI:** вкладка «Автоматизация» (расписания/таймеры/будильники) со скоупом «сессия → проект», фильтрами, счётчиками и единой карточкой; значки активных таймеров/будильников в дереве сессий; live-события `timer.*`.
6. **Тулы:** `timer` (`create|list|cancel`) и `alarm` (`create|list|update|cancel`), capability `schedule`; в описаниях — «используй вместо `sleep`» и отличие от `schedule_*`.

## Альтернативы

- **Расширить `Schedule` через `kind`** — отклонено: расписание обрастает union целей и полей, а таймеру не нужны `ephemeral`/`pipeline`.
- **`setTimeout` без персистентности** — отклонено: рестарт и multi-replica теряют срабатывания.
- **Доставка только через очередь** — отклонено: владелец потребовал вклинивание в текущий ход, как у завершения фонового процесса.

## Последствия

- Срабатывание не запускает «задание»: агент трактует комментарий по контексту — это осознанно.
- Комментарий — пользовательский текст: в live-события и метрики он не попадает.
- Ошибка доставки не ретраится автоматически: `once` → `fired` с `lastError`, повторяющиеся — следующий цикл.
- Расписания стали проектными; легаси без проекта отключаются с `project_required` (миграция 038).
