# ADR-029: Гранулярные permissions

> **Статус:** ✅ Реализовано
> **Источник:** перенесено из AGENTS.md

**Решение:** права доступа на основе модели OpenCode — allow/deny/ask для каждого инструмента с поддержкой glob-паттернов для файлов.

**Контекст:** у Claude Code система прав — `disallowedTools` (простой список запрета). У OpenCode — allow/deny/ask на каждый инструмент + паттерны файлов с разрешением на glob-уровне. Модель OpenCode **строго лучше** — даёт точный контроль без оверхеда.

```yaml
permission:
  # Глобальные правила
  "*": "allow"                    # всё разрешено по умолчанию
  doom_loop: "ask"                # подозрительные циклы — переспросить
  question: "deny"                # саб-агентам нельзя переспрашивать пользователя
  plan_enter: "deny"              # саб-агентам нельзя входить в план
  plan_exit: "deny"               # саб-агентам нельзя выходить из плана

  # Внешние директории
  external_directory:
    "*": "ask"                    # любые внешние файлы — спросить
    "/tmp/*": "allow"             # кроме tmp

  # Чтение файлов
  read:
    "*": "allow"
    "*.env": "ask"                # .env — всегда спрашивать
    "*.env.example": "allow"      # .env.example — можно
    "**/credentials.*": "deny"    # credentials файлы — никогда

  # Редактирование (переопределяется в plan mode)
  edit:
    "*": "deny"                   # plan mode: ничего не трогаем
```

**Три уровня действия (action):**

| Action | Поведение | Пример |
|---|---|---|
| `allow` | Выполняется без спроса | `read: "*": "allow"` |
| `deny` | Блокируется с пояснением причины | `edit: "*.env": "deny"` |
| `ask` | Показывается пользователю на подтверждение | `external_directory: "*": "ask"` |

**Fail-closed для внешних директорий (ADR-075).** Путь **вне** рабочего каталога проекта (`workingDir`) не разрешается молча даже при отсутствии правил. Правило `permission.rules.external_directory` приоритетнее групповых и `*` (явное `allow`/`deny` переопределяет дефолт); если правило не задано или внешний путь не покрыт ни одним паттерном — дефолт `ask` (требуется явное подтверждение), а в `plan` / `strict` без утверждённого плана — `deny`. Абсолютные пути и разворачивание `~`/`$HOME`/`$PWD` (`resolvePath`) подпадают под то же правило; пути внутри `workingDir` не затрагиваются. Тулы с `cwd` (`execute_shell`) проверяются по эффективному `cwd`.

**Наследование саб-агентами:** саб-агент получает permissions родительской сессии + свои deny-правила (edit-ограничения от plan mode родителя) + блокировку `question`, `plan_enter`, `task`. Реализуется через `deriveSubagentSessionPermission()` по аналогии с OpenCode.

**«Разрешить в сессии» (once:false):** при ответе пользователя на `ask` с `once:false` в сессию добавляется allow-правило для тула — повторные вызовы не спрашивают. `once:true` — разрешение только на один вызов.

**Deny от пользователя:** при отказе (ask → deny) тул не исполняется, промежуточные результаты сохраняются в истории; отказ возвращается модели как `tool_result` с причиной, и ход **продолжается** (модель может выбрать другой инструмент).

> **Обновлено 2026-10-29.** Ранее deny (и пользовательский, и ролевой `role.unavailable`, и запрет политики) обрывал обработку: публиковалось `stream.done.stopped_by_deny`, финальный текст — `session.stopped`. Теперь **любой deny не останавливает ход**: `tool_result` с причиной уходит модели, следующая LLM-итерация запускается. Защита от зацикливания — doom-loop, лимит шагов/итераций и счётчик одинаковых deny-вызовов (5 подряд → ход завершается фоллбек-текстом `session.denied_blocked`). Поля `stopped_by_deny`/`deny_reason` в `stream.done` больше не публикуются; `session.role_tool_blocked` — только фоллбек при пустом финальном ответе модели. То же поведение у саб-агента `task` (`task.stopped_by_deny` — только фоллбек).

**Саб-агенты:** проходят permission-check; `ask` публикуется в родительскую сессию (`permission.asked`), ответ пользователя применяется к дочерней сессии.

**MCP-инструменты:** доступность по режимам plan/act — `SessionSettings.mcpToolSettings[server].default|tools[tool] = { plan, act }` (настройки в UI). В текущем режиме недоступный тул → deny.

> **Обновлено 2026-11-11. Сессионный shell-грант строится по сегменту-виновнику (сверка с opencode и hermes-agent).**
> «Разрешить в сессии» для `execute_shell` больше не предлагает командный паттерн «на всю команду»:
> грант считается по **сегменту-виновнику** (`shellGrantPlan` в `engine/security/shell-guard.ts`).
>
> - **План гранта.** `shellGrantPlan(command, trigger, { cwd })` → `{ commands, patterns, directories }`:
>   `commands` — все исполняемые сегменты команды (тот же разбор `splitShellSegments`, что у
>   `shellSavePatterns`; trim, служебные строки heredoc/комментарии/shebang отброшены) — они
>   показываются человеку; `patterns` — паттерны правила `execute_shell: { "<cmd> *": "allow" }`;
>   `directories` — каталоги для правила `external_directory: "<dir>/*"`.
> - **`askKind: 'dynamic'`** (непроверяемый glob/динамика) — командный паттерн **не выдаётся никогда**
>   (`patterns: []`): он шире конкретной команды. Вместо него предлагается каталог виновника
>   (`grantDirectoryForToken`: токен с `/` → его каталог-часть; bare-glob (`*.js`) → `cwd` сегмента;
>   `$VAR`/`$(...)`/backtick → каталог не определяется). Снятие ask требует, чтобы **все** фактические
>   совпадения glob'а (`ShellCheckResult.askPaths`, абсолютные пути реальных совпадений из `checkShellCommand`)
>   были внутри периметра или под **явным** `allow` правила `external_directory` (`evaluator.ts`,
>   ветка `liftedByDirectoryGrant`); дефолтный `external_directory: ask` снятием не считается.
> - **`protected`/`mutation`/`cwd`/`deny`** — жёсткий слой выше правил: не снимаются ни командным
>   паттерном, ни каталогом (`save: []`, `saveDirectories` пуст). Карточка показывает «Только один раз».
> - **Провод.** `permission.asked` и DTO `GET /api/v2/sessions/:id/permissions` несут аддитивные
>   `commands?: string[]` (точные сегменты), `save?: string[]` (паттерны; `[]` — грант не предлагается)
>   и `saveDirectories?: string[]` (каталоги; в payload — camelCase, как исторически). Выдача гранта
>   пишется в аудит (`scope:'permission'`, `action:'grant'`) через `OrchestratorOptions.onPermissionGrant`.
>

> **Обновлено 2026-11-11. Граница доступа одна — реальные пути и `external_directory`.**
> Дополняет блок «Сессионный shell-грант строится по сегменту-виновнику»: shell-периметр
> проверяется **по файловой системе**, а не по строке команды.
>
> - **Классификация по реальным путям.** Литералы, `~`, `..`, цели редиректов и `cd`, а также
>   **совпадения глобов** разрешаются (`realpath`, лимит 2000 совпадений) и сравниваются с
>   периметром (`workingDir` + `project.workspace`). Защищённое совпадение → `deny`
>   (`messageId: 'deny-protected-path'`, `params.path` — конкретный файл, а не маска);
>   внутри периметра → `allow`; снаружи → `ask` с `askKind: 'external'`,
>   `messageId: 'ask-external-directory'` и `askPaths` (абсолютные пути всех внешних
>   совпадений — по ним считается грант, наружу они не публикуются).
> - **Решение принимает правило.** `permission.rules.external_directory` (дефолт `ask`,
>   в `plan`/`strict` — `deny`, явный `allow` снимает вопрос). Грант «Разрешить в сессии» —
>   каталогом `<dir>/*` (каталоги из `askPaths`); строковое `execute_shell: 'allow'` грантом
>   не выдаётся. Исключения периметра — `/dev/null`, `/dev/stdin|stdout|stderr|tty`,
>   `/dev/fd/N`, `/proc/self/fd/N` (перенаправления в них не спрашивают).
> - **Сверка с opencode.** У них граница — `packages/core/src/file-access.ts`: правило
>   `external_directory` (`resource: "<dir>/*"`), containment по реальным путям; **аргументы
>   shell-команд они не проверяют** — файловые операции идут через tools-слой. Наш shell-guard
>   проверяет и аргументы (литералы/глобы/редиректы/`cd`), и это осознанное расширение:
>   shell — самый короткий путь обойти файловый периметр. Семантика правила и форма гранта
>   при этом совпадают с opencode — граница остаётся одна.
> - **Вывод: защищённые пути — defense-in-depth, не граница.** `protected-paths.json`
>   (единый файл для файловых тулов и shell) остаётся deny-списком (опасные префиксы, секреты),
>   но «что считать внешним» он не определяет: это делают реальные пути и `external_directory`.
>   Второй границы доступа не заводим — иначе правила расходятся.

## Обновлено 2026-11-13

- **Path-политика применяется к фактическим файлам.** Периметр (`workingDir` + `project.workspace`)
  проверяется по каноническим путям **точки исполнения**: при `execution.mode=remote` файловые тулы
  идут через `ExecutionPort.fs` на исполнителе, `realpath`/`stat` приходят оттуда, а решение принимает
  control plane по этим путям (ADR-135). Правило `external_directory` и гранты не меняются — меняется
  только источник реальных путей.
- **shell-guard — guardrail, не граница безопасности.** Проверка аргументов, `external_directory`,
  `askKind: 'external'` и protected-paths остаются UX/defense-in-depth: shell — произвольный код, и
  границей он не становится. Наблюдаемость и внешнее решение — аудит исполнений и `CommandPolicyProvider`
  (ADR-136); сетевой контроль — CNI/профиль (ADR-137).
- **`external_directory`/`askKind` не меняются.** Семантика правила, `ask`/`deny`, `askPaths` и форма
  гранта прежние; расширение path-политики на фактические файлы не добавляет второго правила доступа.

### Обновлено 2026-11-13: shell-guard сокращён до явных правил

Решение владельца: shell-проверки — **только явные правила**, без эвристик разбора команд
(ADR-029/ADR-136: парсинг не граница; границу несут изоляция исполнителя, аудит и внешний чекер).

- **Что осталось.** `protected-paths.json` (deny/ask — тот же файл, что у файловых тулов);
  `external_directory` (путь вне периметра `workingDir` + `allowedRoots` → `ask` с
  `askKind: 'external'`, `askPaths`); `deniedCommandPrefixes` (явный список опасных команд);
  кандидаты-пути: токен, который после резолва известных префиксов (`~`, `$HOME`, `${HOME}`,
  `$PWD`, `$SYNTH_DATA_DIR`) существует на ФС или разрешается в защищённый путь; цель редиректа
  (всегда путь); не-флаговый операнд команды-писателя (`cp mv ln install mkdir rmdir touch rm
  chmod chown tee truncate shred dd`); glob с существующим литеральным каталогом (совпадения
  проверяются, лимит 2000); цель `cd`/`pushd` (проверяется и меняет cwd следующих сегментов).
  Приоритет: deny (protected/префиксы) > protected ask > external ask > allow.
- **Что удалено.** `shell-variables.ts` (биндинги/раскрытие переменных), `loadShellPolicy` и
  `definitions/shell-policy.json`, разбор обёрток (`sh -c`/`sudo`/`env`/`nohup`/`nice`/`xargs`…),
  рекурсивная проверка кода интерпретаторов, `awk system(...)`, `find -exec`, `git -c`/
  `tar --to-command`/`rsync -e`, heredoc/herestring как код, brace/динамика-эвристики, «маркерный»
  fail-closed на неразрешимой динамике, `cd`-динамика (`askKind: 'cwd'`) и `mutation`-ask.
- **Принятые риски.** `$VAR` (кроме известных), `$(...)`, backticks, awk/sed/find-программы,
  heredoc, обёртки `sh -c`/`sudo`/`env`, интерпретаторы, `for`/присваивания, `xargs`,
  `git -c`, `tar --to-command`, `rsync -e` **не анализируются**. Это осознанно: эвристики давали
  ложные deny/ask и всё равно обходились; shell — произвольный код.
- **Что не изменилось.** Семантика `askKind: 'external'`/`askPaths`, правило
  `external_directory`, форма гранта каталогом, `shellSavePatterns`/`shellGrantPlan`/
  `isShellCommandGranted`/`matchShellCommandPattern` (контракт сохранён; командные паттерны для
  `dynamic`-ask не выдаются), plan-режим (`isMutatingCommand`), `sandbox_exec` (свой контур).

### Обновлено 2026-11-20: наследование грантов стало живым (chain-no-copy)

Решение владельца: правила прав больше **не копируются** в дочернюю сессию при её создании —
эффективный конфиг резолвится по цепочке `parentId` в момент проверки.

- **Резолвер.** `engine/permission/effective.ts`: `resolveEffectivePermission({session, getSession,
  fallback})` поднимается от сессии к корню (лимит `MAX_PERMISSION_PARENT_DEPTH = 16`, гард от
  циклов по множеству посещённых id), сливает правила **root → leaf** (ключ ребёнка приоритетнее
  родительского), `askTimeoutMs` — свой ?? ближайшего предка ?? `fallback` ?? `DEFAULT_ASK_TIMEOUT_MS`.
  Отсутствующий/упавший `getSession` и превышение глубины прекращают подъём с `warning`
  (fail-open на резолв), исключений наружу нет. Резолвер ничего не пишет и не кеширует.
- **`deriveSubagentPermission`** больше не копирует `parentConfig.rules`: остаются `deny`-дополнения
  роли (`question`/`plan_enter`/`plan_exit`/`task`) и `askTimeoutMs`. Это ограничения **роли**
  саб-агента, а не родительская политика, поэтому их место в `settings.permission` ребёнка
  сохраняется; композер — `applySubagentRoleDenies(resolved)`.
- **Что теперь работает живьём.** Грант родителя, выданный после создания ребёнка, виден ребёнку
  (и внуку) без перезапуска; отзыв/`deny` родителя тоже доходит. `deny` ребёнка остаётся сильнее
  `allow` родителя. Грант ребёнка по-прежнему дописывается родителю (виден siblings).
- **Точки применения.** Оркестратор (`_effectivePermission(session)` вместо
  `session.settings.permission ?? this._permissionConfig`), цикл саб-агента (резолв от сессии
  ребёнка, затем `applySubagentRoleDenies`), создание дочерней сессии/форка.
- **Принятый риск.** У уже существующих дочерних сессий в `settings.permission` остались копии
  правил родителя: они перекрывают более поздние отзывы. Разовая миграция **не делается**
  (осознанно): поведение старых сессий не меняется задним числом, новые живут по цепочке.
