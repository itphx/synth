# Маршрутизация запросов: Быстрые ответы и выбор модели

Synth обрабатывает каждый запрос в два слоя:

1. **Быстрые ответы** — мгновенный ответ на простые запросы без вызова большой модели
2. **Маршрутизация** — автоматический выбор модели для запросов, которые не обработали Быстрые ответы

Оба слоя настраиваются в разделе настроек: «Быстрые ответы» и «Маршрутизация».

## Общий поток запроса

```
Запрос пользователя
   │
   ▼
┌─ Быстрые ответы (включены) ────────┐
│  Классификация → каскад моделей    │
│  уверен? ────── да → готовый ответ │
│  нет (fallback)                    │
└───────────────┬────────────────────┘
   │
   ▼
┌─ Маршрутизация (включена) ────────┐
│  Классификация → выбор модели     │
└───────────────┬───────────────────┘
   │
   ▼
LLM
```

Если Быстрые ответы выключены — запрос сразу идёт в Маршрутизацию (или напрямую в модель сессии, если выключена и она). Если Маршрутизация выключена — используется модель, выбранная в сессии.

---

## Быстрые ответы

Быстрые ответы обрабатывают простые запросы — приветствия, да/нет, классификацию задач — мгновенно и без вызова большой модели. Это ускоряет ответ и экономит токены.

### Классификация задачи

Первый шаг — определить, к какому классу относится запрос:

| Класс | Примеры | Что дальше |
|-------|---------|------------|
| **small_talk** | привет, спасибо, пока | Готовый ответ (приветствие/благодарность) |
| **classify** | «почини баг», «напиши тесты», «что такое...» | Определение интента: вопрос/команда/ревью/фикс/тест |
| **enum_decision** | да, нет, отменяю, планируй | Выбор варианта: да/нет/подтвердить/отменить/режим |
| **llm_task** | всё остальное | Пропуск — запрос уходит в Маршрутизацию |

Классификация работает по словарям ключевых слов (загружаются из `packages/core/dictionaries/`):

- **small_talk** — точное совпадение слов из словаря приветствий/прощаний/благодарностей
- **classify** — вопрос (содержит «?» или начинается с «что/как/почему/зачем/какой») либо intent-слова («напиши», «исправь», «почини», «проанализируй» и т.д.)
- **enum_decision** — слова по границам слова («да», «нет», «отменяю», «планируй»), чтобы «да» не срабатывало внутри «кода» или «падает»

Если запрос не попал ни в один класс — он классифицируется как `llm_task` и уходит дальше.

### Каскад моделей

Для классов `small_talk`, `classify`, `enum_decision` запускается каскад из четырёх моделей. Каждая следующая подключается, только если предыдущая не была уверена:

1. **Правила (rules)** — самый быстрый слой (миллисекунды, 0 токенов). Сравнение со словарями.
2. **Эмбеддинги (embedding)** — семантическая классификация. Понимает смысл запроса, даже если слов в словаре нет.
3. **Decision-модель** — класс System One (Clef/Jev/Decision-1 и совместимые): за один forward-pass отвечает на типизированные вопросы и возвращает вероятности по вариантам. Для классов `classify`/`enum_decision` это `choice`-вопрос — выбор метки из набора. Генерирует текст она не умеет — только классифицирует.
4. **Микро-LLM** — маленькая локальная LLM для структурированной классификации (используется редко).

Модель возвращает метку и уверенность (0–1). Если уверенность >= порога (`microConfidenceThreshold`, по умолчанию 0.8) — Быстрые ответы дают готовый ответ. Иначе — запрос уходит дальше (fallback).

**Decision-уровень** подключается между эмбеддингами и микро-LLM и только если включён мастер-выключатель `decision.enabled` (по умолчанию выключен) и в сессии не выставлен явный opt-out `decisionFirst: false` (отсутствие значения наследует глобальную настройку). Ответ считается принятым при уверенности >= порога `decision.confidenceThreshold` (по умолчанию 0.6); иначе (низкая уверенность, ошибка, таймаут) уровень считается неуверенным и каскад идёт дальше — fail-safe. Если задана необязательная **модель эскалации** (`escalationProvider`/`escalationModel`), перед фоллбеком запрос прогоняется по тиру `escalation` (единый каскад `primary → escalation`). Если decision-провайдер не задан или уровень выключен, он просто пропускается — поведение прежнее. Агрегатная статистика decision-слоя — в админ-разделе «Decision-модели» (AD-084).

### Как работают эмбеддинги

Эмбеддинг-классификатор определяет интент запроса семантически — по смыслу, а не по словам.

**При инициализации** (первый запрос, лениво) модель подготавливает эталоны:
- Для каждой возможной метки (question, command, review, explain, debug, fix, test, yes, no, approve, reject, mode_plan, mode_act) берётся эталонный текст на языке сессии (русский/английский)
- Эталонный текст превращается в вектор — эмбеддинг (числовой массив, например 768 чисел для `nomic-embed-text`)
- Векторы вычисляются через выбранную эмбеддинг-модель (по умолчанию `local.nomic-embed-text:latest` через Ollama)

**При обработке запроса:**
1. Текст запроса превращается в вектор той же эмбеддинг-моделью
2. Вычисляется косинусная близость вектора запроса с каждым эталоном
3. Побеждает метка с максимальной близостью
4. Если близость >= 0.5 — уверенность нормализуется (`близость × 1.2`, максимум 0.99); если результат >= порога — метка принята

Косинусная близость показывает, насколько два текста похожи по смыслу: 1 — почти идентичны, 0 — не связаны.

**Настройка эмбеддингов:** раздел «Embedding» в настройках сессии (виден, когда включены Быстрые ответы): эмбеддинг-модель и провайдер. Если эмбеддинги выключены или недоступны — классификация работает по правилам, а сложные случаи уходят в fallback.

## Маршрутизация

Маршрутизация решает, **какой моделью** отвечать на запросы, которые не обработали Быстрые ответы. Выбор зависит от типа задачи и стратегии.

### Классификация запроса

Первый шаг — определить категорию запроса:

| Категория | Сигналы | Примеры |
|-----------|---------|---------|
| **coding** | вызовы инструментов кода (write_file, edit и т.д.), ключевые слова «напиши», «исправь», «реализуй» | «напиши функцию», «почини баг» |
| **research** | ключевые слова «исследуй», «проанализируй», «почему», «объясни» | «проанализируй архитектуру» |
| **chat** | всё остальное (fallback) | обычный диалог |

Классификация работает по ключевым словам из тех же словарей (`packages/core/dictionaries/`) — это быстрый слой без LLM.

Если словарный классификатор неуверен (уверенность ниже порога) и в сессии не задана явная категория (`routingCategory` из `classify_conversation`), категория `coding`/`research`/`chat` определяется **decision-моделью** (тот же decision-слой, что и в Быстрых ответах). Решение принимается только при уверенности >= `decision.confidenceThreshold`; иначе (низкая уверенность, ошибка, уровень выключен) роутер откатывается к словарной категории — fail-safe. Приоритеты не меняются: вызовы инструментов, ключевые слова и `routingCategory` остаются выше decision-слоя.

### Стратегии выбора модели

| Стратегия | Как работает | Когда использовать |
|-----------|-------------|-------------------|
| **Контентная** | Категория запроса → модель из настроек (coding/chat/research) | Разные модели под разные типы задач |
| **По стоимости** | Оценка сложности (длина сообщения, число вызовов инструментов) → дешёвая или дорогая модель | Экономия на простых запросах |
| **Контентная + стоимость** | Сначала контентная; короткий chat-запрос → дешёвая модель | Комбинированный подход |
| **Авто** | Как контентная | Универсальный вариант |

### Контентная стратегия

Для категории запроса ищется сопоставление «категория → провайдер/модель»:

1. Настройки сессии (раздел «Контентная» в настройках Маршрутизации)
2. Если в сессии не задано — глобальный конфиг (`routerConfig.content`)
3. Если и там нет — используется модель сессии по умолчанию

### Стратегия по стоимости

Сложность запроса оценивается по эвристике:

- **Простой** (cheap): текст короче 50 символов и нет вызовов инструментов → дешёвая модель
- **Сложный** (expensive): 2+ вызовов инструментов или текст длиннее 200 символов → дорогая модель
- **Средний** — по длине текста (больше 100 символов → дорогая, иначе дешёвая)

### Контроль качества (эскалация)

После ответа модели работает контроль качества (если включён):

- **Минимальная длина** — слишком короткий ответ считается неуверенным
- Если ответ не прошёл проверку — запрос пересылается на fallback-модель (запасную)

Это позволяет перехватывать явно неудачные ответы до показа пользователю.

## Примеры прохождения запросов

| Запрос | Быстрые ответы | Маршрутизация | Итог |
|--------|---------------|---------------|------|
| «привет» | small_talk → «Привет! Чем могу помочь?» | не вызывается | мгновенный ответ |
| «да» | enum_decision → «Да.» | не вызывается | мгновенный ответ |
| «напиши тесты для функции sum» | classify → интент test → «Понял, нужны тесты...» | не вызывается | мгновенный ответ |
| «объясни, как работает авторизация» | classify → UNSURE (сложный вопрос) | research → модель анализа | ответ LLM |
| «проверь интеграцию с PostgreSQL» | llm_task (нет сигналов) | coding → модель кодинга | ответ LLM |

## Настройка

| Настройка | Где | Назначение |
|-----------|-----|------------|
| Быстрые ответы вкл/выкл | Настройки → Быстрые ответы | Включить/выключить слой мгновенных ответов |
| Порог уверенности | Настройки → Быстрые ответы | Ниже порога — запрос уходит в fallback |
| Embedding модель | Настройки → Быстрые ответы → Embedding | Модель для семантической классификации |
| Маршрутизация вкл/выкл | Настройки → Маршрутизация | Включить/выключить выбор модели |
| Стратегия | Настройки → Маршрутизация | content / cost / content+cost / auto |
| Модели под категории | Настройки → Маршрутизация → Контентная | coding/chat/research → модель |
| Контроль качества | Настройки → Маршрутизация → Контроль качества | fallback-модель, мин. длина |
| Decision-уровень (сессия) | Настройки → Быстрые ответы → Decision-уровень | Per-session opt-out `decisionFirst`: выключение принудительно отключает decision-уровень в этой сессии |
| Decision-модели (админ) | Настройки → Decision-модели | Общий decision-слой: мастер-выключатель, основная и эскалационная пары провайдер/модель, порог уверенности, статистика |

### Decision-модели (админ)

Раздел «Decision-модели» задаёт общий decision-слой для Быстрых ответов, Маршрутизации и классификации внешних событий:

- **Мастер-выключатель** `enabled` (по умолчанию выключен) — при выключенном decision-слое decision-модель не вызывается нигде.
- **Провайдер и модель** — селект провайдера decision-протокола и модели из раздела «Модели». Тип провайдера задаёт транспорт: `decision` (RouterAI, `POST {base}/decisions`) или `systemone` (Ollama, `POST {base}/v1/systemone`). Модель — например, `clef-flash`.
- **Модель эскалации** (`escalationProvider`/`escalationModel`, необязательно) — вторая пара провайдер/модель (напр. `clef`). Единый каскад `primary → escalation`: если основная модель дала низкую уверенность, невалидную метку, не ответила или упала, запрос уходит на тир эскалации. Пусто — эскалация выключена.
- **Порог уверенности** `confidenceThreshold`.
- **Статистика** — read-only счётчики decision-каскада: обращения, принятые, фоллбеки, эскалации, попытки по тирам, статусы попыток и разбивка по моделям (латентность avg/max). Сброс — кнопкой.

Настройки применяются сразу (runtime), без перезапуска. Per-session тумблер «Быстрые ответы → Decision-уровень» (`decisionFirst`) — точечный opt-out: выключение принудительно отключает decision-уровень в конкретной сессии, включение наследует глобальную настройку.

Если decision-провайдер не задан или decision-слой выключен, decision-модель не используется — Быстрые ответы и Маршрутизация работают как раньше. Если тир эскалации не задан, каскад состоит из одной основной пары (поведение как до Ф6).

## Примечания

- Быстрые ответы возвращают 0 токенов — это чистая экономия на простых запросах
- Порядок обработки жёсткий: Быстрые ответы → Маршрутизация → LLM
- Словари классификации хранятся в `packages/core/dictionaries/` (YAML, русский/английский)
- Эмбеддинги можно выполнять через Ollama (локально) — по умолчанию `local.nomic-embed-text:latest`
