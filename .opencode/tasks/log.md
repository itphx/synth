## 2026-11-04 — standalone: реплика пользователя задваивалась в ленте

- **Задача:** репорт владельца — в standalone каждая user-реплика рисуется дважды, в истории (и для модели) сообщение одно. **Тип:** bug fix (ui/core). **Исполнитель:** @fixer.
- **Причина:** нарушен инвариант ADR-118 §3 в core-роуте `POST /sessions/:id/prompt`: `message.id` генерировался заново (`SessionRoutesOptions.promptMessageId`, дефолт `'generated'`), а `202 {messageId}`/`message.accepted`/`message.enqueued` несли клиентский `messageId`. `message.delivered` приходил с серверным id → UI не находил оптимистичный пузырь, догружал сообщение по id и добавлял второй. В managed (`promptMessageId: 'stream'`) id совпадали — поэтому баг был только в standalone.
- **Фикс:** сообщение всегда сохраняется с `id = streamId` (клиентский `messageId` либо выданный сервером), `acceptedMessageId = message.id` (единый источник истины для `202`/событий/`blob_refs`); опция `promptMessageId` удалена (backend-проводка тоже); клиентский id нормализуется `normalizeClientMessageId` (не строка/пусто/пробелы → серверный id), общая точка для standalone- и hybrid-ветки.
- **Тесты:** `packages/core/src/server/routes/sessions-prompt.test.ts` — +2 регресса (клиентский id = id в истории/списке/`GET /messages/:id`/`message.delivered`; мусорный `messageId` `'   '`/`''`/`42` → серверный id, всё согласовано). ## 2026-11-05 23:31 — мобильный экран входа: форма уезжала вверх при клавиатуре

## 2026-11-07 — PROP-127: параллельное исполнение инструментов в шаге (паритет с opencode)

- **Задача:** владелец сообщил: сабагенты выполняются только друг за другом; если агент в одном шаге вызывает несколько `task` **не** в фоне — они не могут идти одновременно. **Тип:** research + proposal (ADR оформлять не сейчас — по решению владельца сначала PROP). **Исполнители:** @researcher ×2 (разбор opencode и инвентаризация Synth), оркестратор (сведение, документ).
- **Причина (подтверждена в коде):** вызовы инструментов шага исполняются строго последовательно — `for (const tc of toolCalls)` c `await` в трёх местах: `orchestrator.ts:5166` (основная сессия), `run-cycle.ts:1561` (цикл саб-агента), `agent-step.ts:368` (агентский шаг пайплайна). Тул `task` без `background` ждёт ребёнка (`detachable.ts:75`), поэтому N таких вызовов в одном шаге идут по очереди. Фоновый `task` (`tool.ts:979`, `void runSubagent(...)`) уже перекрывается — fire-and-forget.
- **opencode (источник в `refs/opencode`):** `session/runner/step.ts:110-135` — каждое событие `tool-call` из потока провайдера порождает файбер (`Effect.forkScoped`), вызовы одного assistant-сообщения идут одновременно. Свойства, взятые как образец: результат привязан к `id` вызова; порядок в истории = порядок вызовов модели (не порядок завершения); `ask` проверяется внутри файбера (параллельные подтверждения), отказ каскадирует на пакет ожидающих (`permission.ts:315-328`); ошибка вызова не роняет остальные; предела на число вызовов нет; шаги не перекрываются.
- **Что мешает перенести схему (инвентаризация состояния цикла):** порядок tool-сообщений в LLM-запросе — по одному `tool` на каждый `tool_call` (OpenAI) и подряд идущие `tool_result` в одном user-сообщении (Anthropic, `providers/anthropic.ts:735`), поэтому порядок завершения вместо порядка вызовов даёт `400`; общее состояние цикла — `currentMessages`/`allToolCalls`, `doomLoopTracker`, `denyRepeatKey`/`denyRepeatCount` (смысл «подряд»), `effectivePermissionConfig`/`permissionEvaluator`, `sessionMode`/`planApproved`, `tools`/`workingDir`/`allowedRoots`; `withLock` не реентерабелен (дедлок), а `appendMessage` и `saveSession` берут разные локи → точечная дозапись + полная перезапись в одном батче = потеря сообщений.
- **Решения владельца:** полный паритет с opencode (параллельно во всех трёх циклах); подтверждения прав — параллельно, с каскадом отказа; сначала PROP, реализация позже.
- **Что сделано:** `docs/arch_decisions/prop-127-parallel-tool-execution.md` — контекст (три цикла + свойства opencode + таблица «что ломается при параллели»), решения владельца, предлагаемое решение (трёхфазная модель: планирование последовательно → исполнение параллельно → фиксация последовательно, с инвариантами порядка и барьерами на смене режима/проекта), параллельные `ask` с каскадом, требование точечной записи сессии вместо полной перезаписи, изменения порядка событий, не-цели, открытые вопросы (барьер смены режима, предел параллелизма, порядок событий в шине, место общего планировщика), «Статус в коде» (что есть/нет по каждому пункту), связи. ## 2026-11-08 — Гонка черновика шага: терминальный статус больше не откатывается в `streaming`

- **Задача:** разобраться, откуда берётся запись шага со `status: 'streaming'` при давно закрытом ходе (продолжение задачи про фантомную активность). **Тип:** bug fix (core + storage-postgres).
- **Что установлено по дампу:** дубликатов `seq`/`id`/`ord` нет; перезапуска процесса в окне не было (`metadata.streaming` остался `true` — стартовый recovery его снимает); финализация шага точно вызывалась (тул `iteration: 39` выполнен, т.е. ветка `tool_calls` отработала); тайминги: черновик 21:52:49.986, стрим ~9 с, тул стартовал 21:52:58.866, результаты дописаны в 21:53:14 — и на этот момент запись уже была `streaming`, т.е. финальная запись (~21:52:58.8) не легла/была перетёрта. Точную причину по финальному состоянию доказать нельзя — остаются два класса.
- **Класс 1 (подтверждён и воспроизведён тестом):** `StreamMessageDraft.flush()` не проверял `_closed` — после `finalize()`/`abort()`/`dispose()` поздняя троттлинг-запись снова писала `status: 'streaming'` и затирала финальную запись целиком (metadata/content/parts/toolCalls). На старом коде тест падал: `updateMessage` вызывался дважды, второй — со `streaming`.
- **Класс 2 (тихая потеря финальной записи):** `finalize()`/`abort()` игнорировали `null` от `updateMessage` («сообщение/сессия не найдены»; файловый `load` глотает любую ошибку чтения) — шаг оставался `streaming` без строки в логе.
- **Что сделано:** (1) инвариант порта хранения (ADR-096/ADR-118 §5): «терминальная цель + запись черновика» игнорируется **целиком**, без записи и без `updatedAt` — file/memory/postgres, единые предикаты `isTerminalMessageStatus`/`isDraftMessageWrite`/`isStaleDraftWrite` в `storage/message-write.ts` (PG-драйвер дублирует предикат — core не тянется рантаймом, ADR-097); (2) `flush()`/`_write()` не пишут после закрытия; (3) `null` от `updateMessage` в `finalize`/`abort`/`_write` теперь предупреждает с id сообщения. Контракт `SessionRepository` расширен кейсами «поздний черновик поверх терминального игнорируется (включая metadata-only)» и «норма не сломана».

## 2026-11-10 — shell-одобрения: три причины ложных ask, восстановление pending-запросов, переносы в опроснике

- **Задача:** (1) владелец: «постоянно возникает необходимость одобрения вот таких команд» — в панели «Сессионные одобрения» копились правила вида «Shell — команда `cd *`», «`ls *`», «`EOF *`», «`chmod *`» (скриншоты); (2) «в опроснике поле ввода своего ответа должно поддерживать переносы строк»; (3) баг владельца: в standalone «нажал разрешить, но запрос не ушел — протухла аутентификация; обновил страницу, ввел ключ, сессия отобразилась, но запрос на разрешение пропал» — надо восстанавливать запросы после обновления страницы / открытия сессии с запросом, и проверить то же для опросника. **Тип:** bug fix (core, security) + feature (core, backend, ui). **Исполнители:** @fixer ×4, оркестратор (исследование, верификация, журнал).
- **Диагноз 1 (главный — ask «из коробки», не из правил):** `resolveCdCwd` (`packages/core/src/engine/security/shell-guard.ts`) при аргументе `cd` с динамикой делал early-return `ask` (`askKind:'cwd'`) **мимо** `tryResolvePath`, который `$HOME`/`${HOME}`/`$PWD`/`$SYNTH_DATA_DIR`/`~` резолвить умеет (`knownVarValue`). Типичный скрипт агента начинается с `cd "$HOME/..."` → **каждый** вызов даёт свежий ask, а `askKind:'cwd'` грантом **никогда** не снимается (`evaluator.ts`: грант снимает только `dynamic` — осознанное решение от 2026-11-06, не менялось). На скриншотах `cd *` — первая строка каждого списка.
- **Диагноз 2 (грант «Разрешить в сессии» не работал):** `_applyShellAllow` (`orchestrator.ts`) пишет паттерны в `rules.execute_shell`, а `_checkRuleLayers` резолвит правило по имени тула через `_resolveRule` — **матчинг по пути** (у `execute_shell` единственный path-параметр — `cwd`); командные паттерны резолвит только `_resolveShellRule` для **группы** `shell`. Проверено на evaluator: `{shell:'ask'}` + грант в `execute_shell` → **ask** (грант инертен); `{execute_shell:{'ls *':'allow'}}` для `rm -rf x` → **allow** (грант не сматчился, сработал дефолт — шире одобренного).
- **Диагноз 3 (мусор в панели):** `shellSavePatterns` режет команду через `splitShellSegments` (режет по `\n`) и не вырезает тела heredoc (хотя `stripHeredocBodies` в том же файле есть и применяется в `checkShellCommand`). Heredoc-скрипт давал 12 паттернов: `cat *`, `#!/bin/bash *`, `set *`, `cd *`, `ls *`, `mkdir *`, `chmod *`, `tee *`, `hello *`, `INNER *`, `EOF *` — ровно то, что видел владелец.
- **Диагноз 4 (потеря запросов):** `permission.asked` существовал только как live-событие; серверного состояния (реестр ожиданий) не было, HTTP-эндпоинта для списка pending-разрешений нет, механизм догона (ADR-118 §6) после reload не работает (`lastEventSeqBySession` — модульная память вкладки, `TransportClient.since` — поле экземпляра, клиент создаётся заново). Вопросы восстанавливались (`GET /sessions/:id/questions`), но только из `QuestionDock`, смонтированного условно (`!inputExpanded && !isSubagent`) → при развёрнутом композере не восстанавливались. Подводный камень: при таймауте сервер `permission.replied` **не** публикует — карточку снимает только локальный таймер клиента, поэтому восстановленный запрос обязан получить таймер на **остаток** срока, иначе «залипнет» навсегда.
- **Фикс (shell, core):** `resolveCdCwd` — перед `ask` пробует `tryResolvePath`; `source==='literal'` → cwd найден, иначе ask как раньше (fail-closed для `$UNKNOWN`/`$(...)`/backtick сохранён). `_resolveToolRule` в evaluator — объектное правило `execute_shell` резолвится **по команде** (legacy-ветка по путям сохранена; `allow` по команде не снимает гейт `external_directory`). `_applyShellAllow` — при строковом `'ask'` в объект переносится catch-all `'*':'ask'` (неодобренные команды спрашиваются дальше), `'deny'` — грант не выдаётся, `'allow'` — не сужается. `shellSavePatterns` — `stripHeredocBodies` + отсев shebang/комментариев/закрывающих делимитеров heredoc/пустых строк/строк только из метасимволов (тот же фильтр в `isShellCommandGranted` — иначе грант не покрывал бы собственные паттерны и остался бы инертным); дедуп и потолок 20 сохранены.
