# Аналитический HTML-отчёт

Отчёт — это артефакт для принятия решения, а не пересказ исследования. Читатель должен за пять минут понять вывод, а за двадцать — проверить его по фактам.

Вызов скилла — `$synth-html-report` (или тул `skill` с `name: 'synth-html-report'`). Никакого `/synth-html-report` нет: `/` — это команды, скиллы вызываются только через `$` (ADR-126 §7).

## Когда применять

- «Сведи всё в отчёт», «оформи анализ», «сделай документ для обсуждения».
- Итог исследования кодовой базы, пайплайнов, инфраструктуры, сравнение вариантов решения.
- Нужен документ, который можно отправить руководителю или приложить к обсуждению: один файл, открывается в браузере, печатается.

Не применять для README/справочной документации продукта (для этого есть `developer-documentation`) и для коротких ответов в чате.

## Обязательный каркас

1. **Титул + мета**: дата, статус («черновик для обсуждения»), «код не изменялся», для кого.
2. **Содержание** со ссылками-якорями.
3. **Резюме**: 5–8 пунктов, каждый — законченный вывод; последний — рекомендация.
4. **Постановка задачи и критерии**: что просят, какие развилки/уровни потребности, по каким критериям сравниваем.
5. **«Как есть»**: схема потока (`<pre>`), таблица фактов с `файл:строка`, список узких мест.
6. **Варианты**: для каждого — как работает, плюсы, минусы (таблицей «проблема → последствие»), что менять.
7. **Отдельный спорный вопрос** (версионирование, миграция, права) — самостоятельным разделом, если он всплывает в обсуждении.
8. **Матрица сравнения**: критерии × варианты, статусы цветом (`.badge ok/warn/bad`).
9. **Рекомендация и план**: этапы, оценка, что затрагивается. Оценки помечать как экспертные.
10. **Сводная таблица рисков**: риск → где → влияние → мера.
11. **Открытые вопросы**: нумерованные; без ответов на них выбор варианта — гадание.
12. **Приложение**: карта изменений «файл → что менять → для какого варианта», глоссарий, что изучено и **что не проверено**.

## Шапка отчёта

Верх документа — ровно такой блок (меняются только логотип и тексты):

```html
<header class="doc">
  <div class="brand">
    <a class="brand-link" href="https://synth.itphx.ru/" target="_blank" rel="noopener noreferrer" aria-label="Synth — synth.itphx.ru">
      <!-- сюда инлайнится assets/logo.svg -->
    </a>
    <span class="brand-slogan">Синтез человека и ИИ</span>
  </div>
  <div class="kicker">ОТЧЁТ · ЧЕРНОВИК ДЛЯ ОБСУЖДЕНИЯ</div>
  <h1>Заголовок отчёта</h1>
  <p class="meta">Дата · для кого · «код не изменялся»</p>
  <div class="theme-switch" role="group" aria-label="Тема">
    <input type="radio" name="theme" id="t-auto" checked />
    <label for="t-auto">Авто</label>
    <input type="radio" name="theme" id="t-light" />
    <label for="t-light">Светлая</label>
    <input type="radio" name="theme" id="t-dark" />
    <label for="t-dark">Тёмная</label>
  </div>
</header>
```

- Логотип — инлайн SVG из `assets/logo.svg` (раздел «Ассеты скилла»), не `<img>` и не внешний файл. Вставляй `logo.svg` **как есть**: класс `brand-logo` и `aria-hidden="true"` уже внутри файла, `fill="currentColor"` наследует цвет темы (размер задаёт `report.css`; подпись даёт `aria-label` ссылки). Ссылка на сайт — `https://synth.itphx.ru/`.
- Слоган берётся по языку отчёта: RU — «Синтез человека и ИИ», EN — «Synthesis of human and AI».
- `kicker`, `meta` и подписи переключателя темы — тоже на языке отчёта (см. «Язык отчёта»), подписи `Авто`/`Светлая`/`Тёмная` в EN — `Auto`/`Light`/`Dark`.
- Все внешние ссылки в документе — `target="_blank" rel="noopener noreferrer"`: в песочнице предпросмотра это единственный работающий переход, а обычный `<a href="https://…">` открывает пустоту.

## Язык отчёта

- Язык определяет агент — по языку запроса. Если пользователь явно указал язык, его указание главнее.
- Если запрос двуязычный — по языку проекта/документации, к которой он относится.
- Один язык на весь документ: заголовки, таблицы, подписи, врезки, шапка. Смешивать нельзя.
- Технические термины, пути, имена файлов/команд/флагов и код **не переводятся**.
- Блоки шапки (`kicker`, `meta`), «Содержание», «Резюме» — на языке отчёта.
- Слоган — по таблице: RU «Синтез человека и ИИ», EN «Synthesis of human and AI».

## Ассеты скилла

Стили, логотип и чекер берутся **только** тулом `skill`:

```text
skill({ name: 'synth-html-report', file_path: 'assets/report.css' })
skill({ name: 'synth-html-report', file_path: 'assets/logo.svg' })
skill({ name: 'synth-html-report', file_path: 'scripts/check_html.mjs' })
```

Base directory скилла лежит вне рабочего каталога проекта — файловыми тулами (`read_file`, `glob`, `grep_files`) туда не ходить: путь вне периметра, будет отказ. Чтение — только через тул `skill`.

- CSS вставляется целиком в `<style>` документа.
- Логотип инлайнится в шапку вместо комментария `<!-- сюда инлайнится assets/logo.svg -->`; `fill="currentColor"` наследует цвет темы.
- Чекер копируется в workspace (см. «Проверка»).

## Сборка HTML

- Файл: `<project>/tmp/reports/<slug>.html` — внутри workspace проекта, вне git, ничего не коммитить. Если проект просит иначе, уточни путь.
- Один файл: CSS вставляется в `<style>`, без внешних ссылок, шрифтов и JS.
- Якоря: `id` у каждого `h2`, `href="#id"` в содержании.
- Схемы — `<pre><code>` с ASCII-стрелками (`──▶`), не картинки: их видно в диффе и в печати.
- Длинные таблицы — с `vertical-align: top`; первая колонка уже через `table-narrow`.
- Печать: `@media print` с `page-break-inside: avoid` для таблиц, `pre`, callout (это уже есть в `report.css`).

## Тёмная тема и печать

- Переключатель темы обязателен. Он работает **только на CSS** (radio + `:has`/`:checked` в `report.css`, «Авто» — через `prefers-color-scheme`).
- **JS в отчёте запрещён**: в предпросмотре UI скрипты отключены, скрипт просто не выполнится и переключатель «умрёт».
- Печать: `@media print` уже даёт светлую тему — тёмная тема на бумагу не попадает.
- Для PDF предложи пользователю «Скачать HTML и открыть локально»: предпросмотр в iframe не даёт нормальной пагинации и колонтитулов.

## Превью в UI

- Отчёт кладётся в `tmp/reports/<slug>.html` внутри workspace проекта.
- UI открывает его во вкладке файла — в песочнице (sandbox-iframe): скрипты, формы и сеть отключены. Поэтому: никакого JS, внешних шрифтов/картинок, `<link rel="stylesheet">`; всё в одном файле.
- HTML в предпросмотре не отдаётся через `/fs/raw` (kind `html` там вне allow-list) — документ рендерит сам UI.

## Процесс

### 1. Разведка — параллельно

Запускай 2–3 сабагента `@researcher` с **узкими** вопросами, чтобы не получить общий пересказ. Каждый промпт:

- называет конкретные каталоги/файлы;
- требует ответы с `файл:строка` и цитатами;
- **запрещает** дизайн-предложения («верни факты, без предложений»);
- требует отдельно перечислить, чего в репозитории нет («не выдумывай»);
- задаёт уровень тщательности (medium/very thorough).

Шаблон:

```text
Исследование (very thorough, read-only): <каталоги/репозитории>.

Задача: <один узкий вопрос>.

Ответь конкретно, с ссылками файл:строка:
1. <подвопрос>
2. <подвопрос>
...
Отдельно перечисли места, которые придётся менять для <вариант A> и <вариант B>.
Верни фактический отчёт с цитатами; без предложений по дизайну.
```

Пока сабагенты работают, сам прочитай 3–5 ключевых файлов — это нужно, чтобы проверять их выводы, а не доверять пересказу.

### 2. Верификация

- Каждую цифру и каждую строку кода проверь `read`/`grep` перед включением в отчёт.
- Отдельно проверь то, что «все знают»: README часто расходится с кодом (в одном разборе README говорил `ENV=DEV`, а автодеплой писал историю IFT).
- Расхождения фиксируй в отчёте как факт, а не сглаживай.
- Всё, что не удалось проверить, вынеси в «не проверено» с причиной (нет кода внешней джобы, нет доступа к UI и т.п.).

### 3. Сборка

Собери документ по каркасу: шапка (раздел «Шапка отчёта»), содержание, резюме, разделы, приложение. Стили — из `assets/report.css`, логотип — из `assets/logo.svg`, и то и другое получено тулом `skill` и вставлено инлайном.

### 4. Проверка

1. `skill({ name: 'synth-html-report', file_path: 'scripts/check_html.mjs' })` — получить скрипт.
2. Один раз записать его `write_file` в `tmp/reports/.tools/check_html.mjs` (внутри workspace).
3. Прогнать: `node tmp/reports/.tools/check_html.mjs tmp/reports/<slug>.html` — **exit code 0** означает «ошибок нет».

Скрипт проверяет DOCTYPE, `<html lang>`, `<meta charset>`, баланс тегов, дубли `id`, разрешимость `href="#…"`, внешние ресурсы и `@import`, наличие `<style>`, и печатает статистику. Коды: `0` — ок, `1` — ошибки, `2` — неверное использование.

Дополнительный чек-лист:

- [ ] Резюме читается без остального документа и содержит рекомендацию.
- [ ] У каждого факта есть `файл:строка` или оговорка «не проверено».
- [ ] Рекомендация одна; альтернативы описаны с ценой, а не «тоже можно».
- [ ] В матрице сравнения нет варианта, который «просто лучше» без цены.
- [ ] Риски не повторяют минусы дословно, а говорят, что делать.
- [ ] Все `href="#..."` ведут на существующие `id`.
- [ ] Нет внешних `<link>`, `<script src>`, `<img src="http...">`, `@import`.
- [ ] Тема переключается без JS; в документе нет ни одного `<script>`.
- [ ] Печать (Ctrl+P) не рвёт таблицы; для PDF предложено скачать файл локально.

### 5. Правки по фидбеку

Правка факта — это правка **во всех местах**, где он повторяется: резюме, раздел варианта, матрица сравнения, таблица рисков, открытые вопросы, приложение. Порядок:

1. `grep` по ключевому слову — собрать все вхождения.
2. Точечные замены скриптом с проверкой `count == 1` для каждой; при `count != 1` — остановиться и разобраться.
3. Перезапустить `check_html.mjs`.
4. В чате ответить коротко: что изменено и где; не пересказывать отчёт.

**Не оставляй в документе мета-комментарии о правках** («в предыдущей редакции было…», «учтено уточнение…»). Финальный артефакт говорит только по существу; история правок — в чате или в git.

## Правила качества

- Рекомендация должна быть одна и с условиями применимости («если нужна одновременность — тогда D, иначе C»).
- Уточнения пользователя принимай как факт и проверяй, не рушит ли он всю линию аргументации: если аргумент отпал — убери его из всех разделов, а не ослабь формулировку.
- Оценки трудозатрат — только как экспертные, с оговоркой; не выдавай за измеренные.
- Не смягчай выводы: если вариант ломает инвариант (например, «артефакт PREPROD = артефакт PROD»), пиши это прямо.
- Не смешивай «как есть» и «как предлагается»; предложения — только в разделе вариантов и плана.
- Код в рамках отчёта не меняется; если изменение всё же нужно — предупреди и жди подтверждения.

## Анти-паттерны

| Плохо | Почему |
|---|---|
| Отчёт-пересказ без рекомендации | Читатель не понимает, что делать |
| «Вариант A хороший, вариант B тоже хороший» | Нет решения, обсуждение возвращается к началу |
| Факты без ссылок на файлы | Непроверяемо, доверие теряется на первой ошибке |
| Дизайн-предложения в промпте сабагенту | Агент подгоняет факты под дизайн |
| «Все секреты — риск» без проверки модели доступа | Ложный аргумент рушит весь вывод (проверяй, кому что реально доступно) |
| Риск, который действует только в одном контуре, описан как риск всей системы | Перезапись docker-тега возможна в облачном реестре, но не в контуре поставки — вывод о расхождении артефакта неверен. Проверяй, где именно действует ограничение |
| Мета-комментарии о правках в документе | Шум для читателя, выглядит как черновик |
| Скриншоты схем | Не редактируются, не печатаются, не дифаются |
| Внешний CSS/шрифты | Файл перестаёт открываться offline и в контуре заказчика |
| JS в отчёте (свой скрипт, внешний виджет) | В предпросмотре UI скрипты отключены — интерактив не работает и вводит в заблуждение |
| Логотип через `<img src="https://…">` | Внешний ресурс: offline-открытие ломается, чекер падает; логотип инлайнится из `assets/logo.svg` |
