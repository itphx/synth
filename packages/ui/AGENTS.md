# @itphx/synth-ui

Пакет `@itphx/synth-ui` — единый React 19 SPA (чат, панели, админка), собирается Vite и раздаётся статикой. Это **не библиотека**: `exports` отдаёт только `./package.json`, `files: ["dist"]`, а `@itphx/synth` резолвит `dist/` по npm-пути (`packages/synth/src/cli.ts:99`) — импортировать `@itphx/synth-ui/*` из кода нельзя. Общие инварианты, команды, стиль и мобильные конвенции — в корневом [`AGENTS.md`](../../AGENTS.md); здесь только локальные правила пакета.

## Место и точка входа

- Вход — `src/main.tsx`: `I18nProvider` → `ThemeSystemProvider` → `App` (порядок провайдеров важен).
- `initializeLocale()` и `initDeviceClasses()` вызываются до `createRoot` (`src/main.tsx:10-11`); `initDeviceClasses()` вешает классы `device-*`/`pointer-coarse` на `<html>`.
- `App.tsx` собирает каркас: `Sidebar`/`MobileDrawer` + `LeftPanel`/`CenterPanel`/`RightPanel`, глобальные `SettingsModal`, `LogsModal`, `ConfirmDialog`, `ToastContainer`, `PwaUpdatePrompt`.
- Алиас `@/` → `src/` (vite/tsconfig/vitest). Dev-прокси `/api`, `/ws`, `/auth`, `/admin` → backend (`vite.config.ts:27-32`), порт 5002, backend по умолчанию `VITE_BACKEND_URL`/`:5000` (`:6-7`).
- Роутера нет: экран определяется состоянием `useUIStore` (center-tabs + вкладки панелей), URL его не отражает — не вводить react-router и не кодировать экран в `pathname`.
- `DefaultsSync` (`App.tsx:96-143`) при инициализации авторизации подтягивает серверные preferences (`profileService`), масштаб UI и умолчания отображения чата (вид, плотность, масштаб области); личный выбор пользователя они не перекрывают — приоритет local > профиль > серверный дефолт > встроенный.
- `ResizeObserver` в `App.tsx:188-217` вешает `html.central-narrow` при ширине центральной колонки < 800px; на этот класс реагирует CSS (`styles/index.css:423+`). Логику не дублировать в компонентах — читать класс/`centralNarrow` из стора.
- UI-строки/события/ошибки приходят с backend тем же контрактом, что у core/backend — не изобретать свои форматы.

## Тема и экран входа

- Последняя использованная тема хранится в `lib/theme/theme-persistence.ts`: cookie `synth_theme*` (приоритет при чтении; доступна pre-paint-скрипту `index.html`) + legacy-ключи localStorage (`theme`, `themeMode`, `selectedThemeId`, `selectedThemeVariant`, `splashBgLight/Dark`). Значения — `encodeURIComponent`, `path=/; SameSite=Lax; Max-Age=1 год`, `Secure` только на https.
- Boot: `ThemeSystemContext.buildInitialPreferences` читает `readThemePersistence()` (раньше — мёртвая ветка `readStorePrefs()`, т.к. `useUIStore.partialize` не сохраняет тему); эффект записи localStorage зеркалит тему в cookie через `writeThemePersistence(...)`.
- После логина побеждает профиль: `DefaultsSync` (авторизован) берёт `prefs.theme/themeMode` из `GET /auth/profile` и записывает их в cookie/localStorage тем же эффектом.
- `DefaultsSync` (гость) тему/режим **не** сбрасывает; `authStore.logout()` не чистит ключи темы — экран входа остаётся в последней теме.
- Экран входа (`components/auth/LoginForm.tsx`) — карточка кита: `bg-card` + `ring-1 ring-foreground/10` + `shadow-xl`, радиус `rounded-xl` (концентрично с полями `rounded-lg`).
- Наклонное освещение экрана входа (свет из верхнего-левого угла): brand-градиент логотипа диагональный, у верхнего радиального градиента фона (`.login-screen`, `styles/index.css`) origin смещён влево (`at 30% 0%`, интенсивность 12%/60%), у блика верхней кромки карточки (`bg-gradient-to-r from-transparent via-primary/70 via-30% to-transparent`) стоп `via` — на 30%. Нижний правый (`at 100% 100%`, 10%/55%) — тихий ambient. Ореол за логотипом (`bg-primary/20 blur-2xl`, контейнер `relative isolate`) сохранён.
- Brand-градиент логотипа (`SynthLogo variant="brand"`) — диагональный `x1=0,y1=0,x2=1,y2=1` (из верхнего-левого в нижний-правый); сам `SYNTH_LOGO_PATH` вынесен в `lib/theme/logo-path.ts` (импортируется в `SynthLogo.tsx` и используется favicon-ом, без дублирования).
- Favicon вкладки красится в `--primary` текущей темы: `lib/theme/favicon.ts` (`applyThemedFavicon`) вызывается в layout-эффекте `ThemeSystemContext` (`cssGenerator.apply`), подменяя `href` у `link[rel="icon"]` на data-URI-SVG. `public/favicon.svg` — статический фолбэк до загрузки JS; PNG-иконки PWA/manifest не темизируются.

## Точки расширения

**Новый center-tab = ровно 3 правки** (тип-система не даст забыть):
1. тип в `CenterTabType` (`stores/useUIStore.ts:69`) и при необходимости поля в `CenterTab.data` (`:71`);
2. иконка в `TAB_ICONS` (`components/layout/CenterTabs.tsx:25`);
3. `case` в `renderTabContent` (`components/layout/CenterPanel.tsx:35`).

**Новая вкладка панели**: `RIGHT_TABS` (`components/panels/RightPanel.tsx:14`) / `LEFT_TABS` (`components/panels/LeftPanel.tsx`). Role-gating — по образцу `secrets` (`RightPanel.tsx:31-34`): вкладка добавляется условно + эффект-нормализация, если активной стала недоступная. Схлопывание подписей в иконки при переполнении даёт `useAdaptiveIcons` (`hooks/useAdaptiveIcons.ts`, используется в `LeftPanel.tsx`/`RightPanel.tsx`) — он измеряет `span[data-tab-label]`, поэтому подпись вкладки оборачивать в этот маркер.

**Новая левая вкладка с тулбаром**: toolbar выбирается по `leftPanelTab` в `App.tsx:243-245` (`ProjectsTabToolbar`/`FilesTabToolbar`/`GitTabToolbar`) — добавить свой `case`, иначе шапка панели останется пустой.

**Контекст-ориентированные вкладки Files/Git.** Обе вкладки строятся как закреплённый блок «Текущий проект» (авто-раскрыт) + сворачиваемые «Другие проекты ({count})»; активный проект — хук `useActiveProject` (`hooks/useActiveProject.ts`: чат → `project_id` сессии, file/commit-таб → `projectId` вкладки). Ключ сворачивания блока «другие» — `OTHER_PROJECTS_COLLAPSE_KEY` (`stores/useUIStore.ts`). Тумблер «Только текущий проект» — `ProjectScopeToggle` (`components/panels/ProjectScopeToggle.tsx`, persist `useUIStore.onlyActiveProject`, disabled без валидного workspace у текущего проекта); в разметке помечен `data-project-scope-toggle`. При включённом тумблере expand/collapse-all действует только на видимые проекты — учитывать это в новых тулбарах. Обновление дерева — `filesStore.refreshProject` (точечно перечитывает загруженные каталоги и инкрементит `revisionByProject`), `refreshDirs` (точная инвалидация только родительских каталогов из `fs.changed` со `scope:'file'`, ошибка перечитывания каталога удаляет его ключ) и его debounce-обёртка `scheduleRefresh` (вызывается из `fs.changed`; коалесинг `all`-событий и «последняя операция по пути» для `op`). Файловые `fs.changed` инкрементят `fileRevisions[projectId::path]` и ведут `deletedFiles` (op `delete` → пометка, `write`/`mkdir` → снятие, `move` → без изменений; `markDeletedFile` — детект по факту: чтение вернуло 404/`NOT_FOUND`, например после `execute_shell rm`/`git_checkout`, где `op` нет); `FileEditorTab` по росту ревизии перечитывает открытый файл, при расхождении показывает баннер `file.changedOnDisk`, при удалении — состояние `file.deletedOnDisk` с кнопкой `file.reload`. Перенос/переименование (`filesStore.moveEntry`) перемапливает префиксные ключи поддерева в `treesByProject`/`expandedDirs`/`fileRevisions`/`deletedFiles`/`draftContents` (включая переписывание `entry.path` в кэшированных листингах; без `removeSubTree`; перечитываются только родители src/dst), а вкладки viewer/editor переводит `useUIStore.remapFileTabs` — открытые редакторы переезжают прозрачно; при ремапе коллизия id разрешается в пользу перемапленной вкладки (чужая удаляется). Перемап вынесен в `filesStore.remapPath`; перенос из shell (`execute_shell mv`/`git mv`) приходит как `fs.changed` с `op:'move'`/`from`/`to` — транспорт (`transportStore`) синхронно до debounce вызывает `remapPath` → `remapFileTabs` → `scheduleRefresh`, чтобы редактор не потерял черновик. Черновики (`filesStore.draftContents`, ключ `${projectId}::${path}`, runtime-only, экшены `setDraft`/`clearDraft`) восстанавливаются `FileEditorTab` и переживают переключение вкладок и перенос между проектами; межпроектный перенос DnD идёт серверным `POST /fs/move` с `targetProjectId` (файлы и каталоги; черновики переносятся вместе с поддеревом). Диалог переноса (`LeftPanel`) первым пунктом показывает корень workspace (`''` → `/`, title `file.workspaceRoot`), далее — каталоги, подгруженные рекурсивным листингом (`synthApi.listDirectory(projectId, '', showHidden, 10)`, `maxDepth` до 10; кэш по проекту на время сессии диалога, пока идёт загрузка — индикатор; при ошибке — fallback на каталоги загруженных веток дерева). Целевой путь и его потомки из списка исключаются. Закрытие вкладки viewer/editor с несохранёнными изменениями (`editingState === 'dirty'`) подтверждается через `confirm()` (title `center.closeTab`, message `file.unsavedChanges`, variant `warning`); `useUIStore.closeTab` при закрытии очищает черновик (`filesStore.clearDraft`), чтобы он не «залипал».

**Новый раздел настроек**: элемент `SETTINGS_CATEGORIES` (`lib/settings-catalog.ts`) с `labelKey` + `icon` + `group`. Админ-раздел помечается `roles[]`, скрытый до включения режима «Расширенные» — `advanced: true`. Сайдбар группируется по `SETTINGS_GROUPS` (у `personal` заголовка нет), поиск идёт по `SETTINGS_CATALOG` (записи уровня секций, `sectionId` = `data-settings-section`). Ключ `labelKey` добавлять в **оба** словаря. `CATEGORIES`/`resolveActiveSettingsPage` в `SettingsModal.tsx` — совместимые обёртки над каталогом; состояние режима — `useUIStore.settingsShowAdvanced` (persist), разовый фокус — `settingsFocus`/`focusSettings` (runtime).

**Новый store**: `create<T>()(...)`, при необходимости `persist` (образец `stores/useUIStore.ts:326-327`). Пользовательские настройки — только через `persist`; runtime-флаги (дроверы, `centralNarrow`, наведение) не персистятся. Селекторы — `useStore(s => s.x)`; в экшенах/вне React — `useStore.getState()`. Подтверждения — `confirm()` (`lib/confirm.ts:9`) + `confirmStore`, не `window.confirm`.

**Новый метод API** (ADR-095): метод добавляется в доменный модуль `lib/api/<домен>.ts` (типы/DTO — рядом с доменом) и попадает в публичный объект `synthApi` через barrel `lib/api/synthApi.ts`; общие `BASE_URL = '/api/v2'`, `fetchJSON`, `encodeFilePath` — в `lib/api/base.ts`. Полный состав `synthApi` фиксирует контрактный тест `lib/api/synthApi.contract.test.ts`. Прямой `fetch` из компонентов/сторов — нарушение.

## Соглашения

### Примитивы и иконки
- UI-примитивы — в `components/ui/`. Barrel `components/ui/index.ts` намеренно частичный (только `SynthLogo`, `ContextMenu`, `Popover`); остальное импортируется прямыми путями — это норма, не «чинить» реэкспортами.
- Тумблер (`components/ui/Toggle.tsx`) — единый канон курсора: обычный — `cursor-pointer`; `pending` (идёт сохранение, сохраняем сразу) — `cursor-progress` + лёгкое затемнение, без атрибута `disabled`; `disabled` (реально недоступно: system/project, нет прав) — `cursor-default` + `opacity-40` **без** `cursor-not-allowed`, причина показывается текстом рядом. Зафиксировано в `Toggle.test.tsx`.
- Кнопка (`components/ui/button.tsx`) — размеры `sm`/`md`/`icon`. `icon` — квадратная кнопка только под иконку: 32px на десктопе, 40px при `pointer-coarse` (ADR-044) через `pointer-coarse:size-10`. В правой панели тач-таргет держит глобальное правило `html.pointer-coarse .mobile-drawer-panel button…` (`styles/index.css`), но оно покрывает только мобильный дровер — десктопная раскладка (планшет в ландшафте) требует `pointer-coarse:` в самом классе.
- Коллекция настроек — `components/ui/settings/` (`SettingsPanel`/`Section`/`Field`/`Row`/`Actions`, контролы `TextField`/`NumberField`/`SliderField`/`TextArea`/`SelectField`/`ToggleField`/`ListField`/`KeyValueField`/`SegmentedControl`/`Tabs`, хук `useSettingsDraft`) — обязательный стандарт (ADR-072). Все разделы настроек и админ-категории мигрированы; legacy `components/settings/settings-layout.tsx` (`SettingsPage`/`SettingsCard`) удалён — новых импортов оттуда быть не должно.
- **Сегментированные контролы кита** (`SegmentedControl`, `Tabs` с вариантом `segmented`): дорожка с внутренним отступом `p-0.5` и контуром-inset, сегмент — `h-[calc(var(--control-height)-0.25rem)]`, поэтому общая высота контрола остаётся канонической (30px = `--control-height`), а активная «таблетка» не касается рамки. Вариант `Tabs` `underline` не менялся (`h-[var(--control-height)]` + нижняя граница). Тесты — `SegmentedControl.test.tsx`, `Tabs.test.tsx`.
- Панель настроек: один вертикальный скролл (скроллится только тело, шапка — `shrink-0`), `min-w-0`/`break-words` для текста, базовая сетка `grid-cols-1`, центрирование `max-w-3xl`, симметричные паддинги (без `pr-2`); порядок в шапке — `title` (+ `actions`) → `description` → `meta` (счётчики идут **ниже** описания, ADR-072); кнопка раскрытия продвинутых секций («Показать дополнительные настройки (N)») — **в шапке панели** перед `actions` (в конце тела её не видно за таблицей); действия (`SettingsActions`) — **в конце содержимого**, не фиксированным футером (у `SettingsPanel` нет footer-пропов). В `SettingsActions` кнопка Reset цветная (`outline-primary`) только когда текущие значения отличаются от дефолтных; при дефолтных (`isDefault`) — серая (`outline-muted`) и неактивна; Save/Cancel активны только при несохранённых изменениях (`dirty`).
- **Скролл-контейнер панели отдаётся наружу.** Вложенный длинный список не создаёт своего скролла (иначе — второй вертикальный скролл): `SettingsPanel` принимает необязательный проп `scrollRef` (`RefObject<HTMLElement | null>`) и кладёт в него тело панели. Виртуализированный список использует его как scroll-элемент (`ModelsPanel`): смещение списка внутри тела — `scrollMargin`, строки позиционируются как `translateY(item.start - scrollMargin)`.
- **Шапка панели на телефоне.** На телефоне (≤768px) заголовок занимает отдельную строку во всю ширину и не рвётся посреди слова (`break-normal`), а кнопки (`actions` + раскрытие продвинутых секций) переносятся под него по правому краю; кнопка раскрытия на телефоне компактная (иконка + счётчик), полная формулировка — в `title`/`aria-label`. На планшете и десктопе шапка прежняя: заголовок и кнопки в одну строку, полная формулировка кнопки в тексте.
- **Админ-панель «Модели» на телефоне.** Ниже брейкпоинта телефона строка модели — карточка, а не строка таблицы: название + звезда «по умолчанию» + удаление, затем «Контекст» + «Вкл», затем «Цены /1М» (валюта + четыре поля с подписями вход/выход/чтение кэша/запись кэша). Фиксированная ширина таблицы (`min-w-[35rem]`) на телефоне снимается, sticky-шапка становится компактной легендой («Модель | Контекст · Цены /1M · Вкл»), горизонтального скролла нет (ADR-072). `estimateSize` виртуализатора зависит от зоны: строка модели 168px на телефоне против 33px на десктопе (группа — 64px против 48px); `measureElement`/`scrollMargin` — как раньше. Тач-таргеты — через `--control-height-touch`.
- Иконки — только `<Icon name="..." />` из `components/icon/Icon.tsx` (реестр `icons.ts`). Не тащить svg/`@remixicon` напрямую (единственное исключение — `SynthLogo.tsx`); неизвестное имя не в `iconMap` → `Icon` вернёт `null`.
- Иконки/подписи инструментов — `lib/toolIcons.ts` (`getToolIcon`, `getToolDisplayName`); новый тул добавлять в `TOOL_ICON_MAP`, а не маппинг inline в компоненте.
- Иконка/цвет проекта и сессии — только через `lib/entityIcon.ts` (`resolveIconName`/`resolveIconColor`) и общий пикер `components/ui/EntityIconPicker.tsx` (ключи реестра + палитра CSS-переменных, без загружаемых картинок). Реестры ключей и маппинги — `lib/projectMeta.ts` из shared (`PROJECT_ICON_KEYS`/`PROJECT_COLOR_KEYS`); в UI их не дублировать.
- Пикер используется внутри `components/ui/EntityEditDialog.tsx` — единого центрального окна редактирования проекта/сессии (имя; у проекта — ещё описание; иконка + цвет). Открывается из контекстного меню дерева (проект/сессия) и по клику на имя/иконку во вкладках «Сессия» (`SessionSettingsTab`) и «Проект» (`ProjectTab`); один экземпляр монтируется в `App.tsx` через `stores/entityEditStore`. Сохранение — черновик + кнопка Save (`useSettingsDraft` + `SettingsActions`); «Отмена» всегда активна и закрывает окно без сохранения. Отдельные поповеры/диалоги иконки/цвета и компонент `EntityIconTrigger` удалены. Инлайн-переименование в дереве — по-прежнему быстрый путь и доступно как для сессий, так и для проектов (мобильный фикс: `stopPropagation` на пунктах в `components/ui/contextMenu.tsx`). Иконка выводится инлайн (`<Icon>`): дерево, табы, шапка, панели.
- Резолвер — единственная точка перевода серверного значения в имя реестра `Icon`/CSS-переменную; неизвестное даёт `undefined` (компонент подставляет фоллбек). У закрытых сессий (нет таба и не активны) иконка серая (`text-muted-foreground`), у открытых — цвет сессии (без цвета — `text-primary`); у проектов иконка всегда цветная. Дефолтный цвет иконки сессии — `--primary` (акцент открытой сессии; `resolveSessionIconColor`/`DEFAULT_SESSION_ICON_COLOR`), в панели «Сессия» и табе сессии — тоже `--primary`, у проекта дефолт остаётся нейтральным.

### Чат: упоминания агентов
- Вызов агента через `@` (`components/chat/ChatInput.tsx`, `splitMessageWithTags`) сохраняет сам тег `@<agentId>` в тексте сообщения (иначе пользователю неясно, почему ответил другой агент); тег одновременно уходит как `agentRole` в `sendMessage`. Не вырезать тег из `part.text`.
- В пользовательских сообщениях `@<agentId>` известных агентов подсвечивается цветом агента (`AgentInfo.color` через `resolveColor`) — `components/chat/SecretPlaceholder.tsx` (`SecretPlainText`), реестр из `agentsStore`. Неизвестный агент или пустой реестр → обычный текст, без поломки вёрстки и переносов.

### Чат: отправка во время хода и очередь (ADR-104, ADR-118)
- **Переключателя «В очередь / В ход» в UI больше нет** (коммит `4ca9829d`): `components/chat/SteerModeSwitch.tsx` удалён, состояние `selectedMode` из `ChatInput` убрано. Композер режим не выбирает — `effectiveMode = sendMode` (`DEFAULT_STEER_MODE`, всегда `queue`); во время хода сообщение **всегда** уходит в очередь, кнопка отправки подписана «Добавить в очередь» (`chat.input.enqueue`). Режимы `steer`/`interrupt` остаются **только в контракте API** (шлюзы, фоновые уведомления, `POST /queue/:id/steer`); UI их не выставляет — для обрыва есть отдельная кнопка «Стоп». Ключи `chat.steer.mode.*`/`*_steer`/`*_interrupt` удалены.
- Режим уходит третьим аргументом `onSend(text, agentRole?, mode?)` → `transportStore.sendMessage` → `POST /sessions/:id/prompt` с полем `mode`; `queue` в тело **не попадает** (`lib/api/sessions.ts` отбрасывает).
- **Приём — синхронный HTTP: `202 {messageId, mode, position}` (ADR-118 §3).** WS-кадр `send_message`, ack-кадр `queued` и `SEND_TIMEOUT` («не подтверждено») **удалены**: `POST /:id/prompt` больше не отвечает `text/event-stream` и не висит до конца хода. Контракт приёма — ответ `202` (его и возвращает `sendMessage` как `PromptAcceptedResponse`); адресное `message.accepted` — дополнительное подтверждение доставки отправителю (маркер в ленте, состав очереди), а не замена ответа.
- **Оптимистичная реплика по `messageId` из `202`.** `transportStore.sendMessage` показывает user-сообщение сразу с `id = accepted.messageId` и маркером доставки `delivery` (`accepted` | `queued` | `steering`: `steer`/`interrupt` → `steering`; `queue` с `position > 1` → `queued`). Реальная ошибка (сеть/401/валидация) **бросается** — сообщение не показывается, `ChatTab` даёт тост `chat.error.sendFailed`; успех — тост `chat.message.sent`. Строка очереди (`QueuedMessage.sending: true`) добавляется отдельно, только для `queue` при идущем ходе, и сверяется по `id` (`upsertPendingMessage`; ошибка снимает её — `removePendingById`).
- **`message.accepted` — адресное событие** (`recipient === userId` отправителя): `messageId`, `mode`, `position`, **без текста**. Обработчик ставит маркер доставки (`setMessageDelivery`), обновляет строку очереди по `id` и пересверяет состав очереди с сервером (`reconcileQueueFromApi` → `GET /sessions/:id`): тексты и авторы — только из API, события их не несут. В гибриде локальный пользователь один — подтверждение видят все локальные клиенты (известное ограничение ADR-118).
- **`message.enqueued` — адресное событие со снимком сообщения** (ADR-118 §4): `messageId`, `delivery` (`queue`/`steer`), `position`, `message` (id/role/author/content/parts/metadata/created_at; **без `ord`**, уже обфусцирован). Адресат — **отправитель сообщения**, иначе владелец сессии (`ownerId ?? userId`; в standalone — `local`); владельца нет — событие **не публикуется** (fail-closed: снимок с текстом в общий канал сессии попадать не должен), реплика всё равно появится по `message.delivered`. Обработчик (`stores/transportStore.ts`) показывает в ленте **только `delivery: 'steer'`** (вклинивание в текущий ход — видно сразу, до материализации, обычным user-пузырём **без пометок**); `delivery: 'queue'` — обычная очередь, она живёт **только в панели очереди** (`QueuePanel`), в ленте её нет. Дедуп по `id` (повторное событие/догон не даёт второго пузыря). `message.delivered` **примиряет** запись по `id`: `ord`/`turn_id` + снятие маркера `steerPending` — второго пузыря не появляется. Досева очереди в ленту из `pending_messages` **нет** — после reload очередь видна только в панели очереди.
- **Вклинивание снимается из ленты только по явным сигналам.** Прежняя эвристика «id есть в `pending_messages` → убрать пузырь» **удалена**: ядро публикует `message.enqueued` **до** того, как снимет сообщение из очереди, поэтому такая проверка снимала бы вклинивание сразу после его показа. Сигналы снятия (`removeSteerPendingMessages`): `message.delivered` — примирение по `id` (маркер `steerPending` снят, пузырь остаётся как обычное сообщение); `steer.dropped` (сброс/лимит/отмена) — по id из payload, если событие их несёт (`message_id`/`message_ids`), иначе по сессии (только вклинивания `delivery: 'steer'`); терминал хода (`turn.finished`, `stream.cancelled`/`stream.error`) — снятие тех вклиниваний, что висели на момент терминала. Терминал хода **сначала перечитывает очередь** (`reconcileQueueFromApi` → `GET /sessions/:id`), **потом** снимает пузырь (`finishTurnAndRefreshQueue`): пока ответ не пришёл, вклинивание остаётся в ленте — сообщение не пропадает из UI совсем; вернувшееся в очередь (после «Стопа») видно в панели очереди.
- **`queue.state` — счётчики + статусы элементов** (`pendingCount`, `steerCount`, аддитивно `items: [{id, status}]`, `status: 'queued'|'starting'`) → `setQueueCounts` + `setQueueItems`; ни текста, ни автора (устранена утечка прежнего `message.queued`). Статус строки в `QueuePanel` — `starting` = «берётся в работу»; неизвестный/отсутствующий статус — `queued`. **Состав панели обновляется при изменении счётчиков**: серверные значения хранятся отдельно (`QueueState.serverCounts` — серверный `pendingCount` включает сообщение текущего хода, поэтому со счётчиком показанных строк не сравнивается), и при их изменении очередь перечитывается у API (`reconcileQueueFromApi`) — гейт «в ленте есть неразрешённое вклинивание» удалён.
- **«Стоп» — очередь сохраняется, возобновление вручную.** «Стоп» (`POST /sessions/:id/abort`) останавливает **только активный ход**; очередь при этом **не теряется** (ядро её не чистит, автозапуска нет) — продолжить обработку можно кнопкой «Продолжить» в панели очереди (`POST /queue/:sessionId/resume`, `chat.queue.resume`). Кнопка доступна, когда очередь непуста и активного хода нет (`canResume`), а не только при `queue.stalled`. Сообщение, не дошедшее до истории, при «Стопе» **убирается из ленты** (терминал хода) и **становится видно в панели очереди** (состав перечитывается у сервера).
- **DnD-переупорядочивание очереди.** `QueuePanel` — `draggable` строки и `onReorder(ids)` (`ids` — серверные id в желаемом порядке, перестановка адресуется **по id**); включается только на точном указателе (`isTouch` → DnD выключен, ADR-044), при `pending.length > 1` и когда у **всех** строк есть серверный `id` и нет `sending`. `ChatTab.handleReorderQueue` сначала применяет порядок локально (`chatStore.reorderPending`: элементы из `ids` по порядку, остальные — в конце), затем `POST /api/v2/queue/:sessionId/reorder {ids}` (`queueApi.reorderQueue`). `409 QUEUE_CHANGED` (`isQueueChangedError`, код `QUEUE_CHANGED_CODE`) → тост `chat.queue.changed` и **перечитывание** очереди у сервера (`refreshQueueFromApi`) — локальный порядок недостоверен; прочие ошибки — тост `chat.error.reorderQueue` + перечитывание. `steerInbox` не трогается (ADR-104).
- **`message.delivered` — точечная догрузка.** Событие несёт `messageId`/`ord`/роль/автор (и `turnId?` — аддитивно, ход сообщения) без содержания: известное сообщение обновляется по `id` (заодно снимается маркер ожидания — `steerPending: false`), неизвестное → **одно** сообщение `GET /api/v2/sessions/:id/messages/:messageId` (`messagesApi.getSessionMessage` → `upsertMessage` с патчем `ord`/роль/автор), а не полная история — событие приходит на каждое материализованное сообщение, полный `GET /messages` на каждое был бы лишним трафиком. Ответ без `message`/ошибка/`404` → прежний фоллбек на `mergeHistory`; границы живого хода — `restoreLiveTurnFromHistory`.
- **Очередь и лента — разные вещи.** Обычная очередь (`delivery: 'queue'`) в ленте **не показывается**: только строка в панели очереди (`QueuePanel`, DnD/«вклинить»/возврат/удаление). В ленте видно только **вклинивание** (`delivery: 'steer'`) — до материализации, обычным пузырём без пометок; оно снимается из ленты по доставке/сбросу/терминалу хода, а не по факту наличия в `pending_messages`. Отправка «в разрыв» из UI — кнопка «Вклинить» в панели очереди (`POST /queue/:sessionId/steer`); тумблер в композере не возвращается.
- **`step.tools.started`/`step.tools.finished` — исполнение инструментов шага** (ADR-118 §4, аддитивно): `step.finished` = «вызов LLM завершён», а эта пара говорит UI, что шаг ещё работает. Флаг `ActiveTurn.toolsRunning` поднимает `started` (только для активного хода и его `turnId` — опоздавшее событие чужого хода индикатор не переключает), снимают `finished` и любое терминальное событие хода (`finishTurn`). Пока флаг стоит, у последнего assistant-сегмента хода в шапке точки (ход жив), а пустой сегмент нового шага рисуется только заголовком.
- **Ход и шаги (`turn.*`/`step.*`/`part.*`).** `turn.started`/`turn.finished` — границы хода (`startTurn`/`finishTurn`, терминальный статус; на финише снимается полоса подтверждений); `step.started` создаёт assistant-сообщение (`messageId`, `turn_id`, `step_index`, статус `streaming`), `step.finished` ставит терминальный статус **сразу** (не дожидаясь `GET /messages`) и несёт `usage`/`provider`/`model`/`agent_role`/стоимость/`timings`/`attachments` — это **замена** удалённых `stream.usage` и `stream.done`, поэтому live-статистика и вложения ответа берутся оттуда. `part.delta` (`field: text|raw`) и `part.updated` — **upsert** по `{messageId, partId}` в `partsBySession`.
- **Открытие сессии во время хода.** `mergeServerMessages` (`stores/transportStore.ts`) сводит снимок `GET /messages` с живым состоянием стора (общий мерж с `mergeHistory`), а не заменяет его: прямые `setMessages` затирали показанный контент более старым снимком (переключение вкладок посреди хода — ход «мелькал» и пропадал до следующего чанка). Пока ход активен, более богатый известный `content`/`parts` не затирается; сообщения без серверного `id` сохраняются; границы хода восстанавливаются тем же мержем. Отображение не зависит от прихода очередного чанка.
- **Гонки live-состояния (ADR-118 §1/§5).** События хода могут прийти с опозданием (догон/реконнект/задержка). Опоздавшее событие **старого** хода не должно ломать текущий: сегменты закрываются только **того же** `turn_id`, что и в событии (`finalizeStreamingSegments(..., { onlyTurnId })`; если ход события — текущий активный, закрываются и заведомо мёртвые сегменты прошлых ходов); границы текущего хода не переписываются; сообщение не создаётся, если у сессии нет активного хода или событие — другого хода (нет фантомных пузырей); финальное сообщение (`completed`/`cancelled`/`error`) не воскрешается — поздняя дельта к нему игнорируется. Мерж истории (`mergeHistory`) не затирает живое состояние серверными `null` (`status`/`turn_id`/`step_index`/`parts`/`content`), а у сообщения со статусом `streaming` части/контент не перезаписываются вовсе (источник — live).
- **Старые события** — `stream.chunk`, `stream.usage`, `stream.done`, `stream.interrupted`, `message.queued`, `message.injected` **удалены без dual-emit** (ADR-118 §4). В диспетчере остались только ветки чтения с комментарием «совместимость со старым ядром» (гибрид): это не контракт, новый код на них не опирается. `stream.interrupted` больше нет — прерывание приходит `step.finished` со статусом `cancelled`.
- **Один источник сообщений.** `streamingBySession` и отдельная плашка `StreamingPlaceholder` **удалены**: лента — `messagesBySession`, живой ход — `turnBySession` (`ActiveTurn`), части — `partsBySession` (`Record<messageId, Record<partId, LivePart>>`). Рендер — `buildPartsView(message.parts, liveParts, fallback)` (`lib/messageParts.ts`: текст `msg:text:<ordinal>` / reasoning / tool-вызовы + фоллбек на `content`/`reasoningBlocks`/`toolCalls`); сортировка — `sortMessagesByOrd` (`ord`, tie-break по `id`, черновик без `ord` — по `index`; **живое сообщение** (`status: 'streaming'`) — предпоследним среди «ещё не записанных»: его `created_at` — клиентское время, смешивать с серверным нельзя; **вклинивание** (`steerPending: true`, `ord` не выдан) — **последним**, после живого сегмента: это самая свежая реплика пользователя, она не может стоять выше ответа, который уже печатается; между собой вклинивания — по `created_at`; при отсутствии `index` в tie-break берётся 0 — `NaN` не допускается); склейка сегментов хода — `groupMessagesByTurn` по `turn_id` (вставленная user-реплика **разделяет** сегменты); ключ списка и всех мутаций в сторе — `id` (`updateMessageById`, `debugModalMessageId`). Индикатор активности, live-статистика и «В фон» живут в самой `ChatMessage` (`message.status === 'streaming'`), отдельного live-компонента нет; «Стоп» — только общая кнопка в композере (`ChatInput`), в теле ответа её нет.
- **Догон по журналу.** `lastEventSeqBySession` (`maxEventSeq()`) → `client.connect(mode, { since })` / `?since=`; SSE-кадры несут `id:` (курсор догона). Страховка от разрывов, а не подписка «с нуля». Номер события **глобальный** (сквозной по всем сессионным каналам инстанса, ADR-118 §6) — поэтому максимум по всем сессиям и есть корректная точка догона: при per-session нумерации события «хвостовой» сессии терялись. Инстансный канал (`pipeline.run.*`) номера не получает — в максимум не входит.
- **Fail-closed сверка версий.** Перед подключением `synthApi.getInstanceCapabilities()` (`GET /api/v2/meta`) + `supportsMessageModel(caps)`: несовпадение `messageModel` → подключения нет, `versionMismatch: true`, тост `chat.error.messageModelMismatch` (тихая деградация запрещена). Мета недоступна — подключаемся: гейт на сервере всё равно отклонит несовместимый клиент (WS close `1008`, SSE `426`).
- **Дельты прогресса саб-агента.** `subagent.progress` несёт приращения `content_delta`/`reasoning_delta`; в блоке `task` они **дописываются** к последнему live-блоку итерации (`appendDeltaBlock` — `subagentReasoningBlocks`/`subagentIntermediateTextBlocks`), а не заменяют накопленный текст. Совместимость с гибридом (старое ядро шлёт полный текст): `progressDelta` вычитает уже известный префикс — текст не задваивается.
- **Карточка живого саб-агента (в т.ч. синхронного).** Пока прогон идёт, `result.metadata` ещё нет: `getSubagentData` (`components/chat/ChatMessage.tsx`) строит `SubagentPartData` из аргументов вызова и **живых данных части** — `subagentReasoningBlocks`/`subagentIntermediateTextBlocks` (копируются в `partToToolCall`, `lib/messageParts.ts`), а шаги ребёнка берутся из вызовов с `parent_call_id` (= `callId` карточки) и не рисуются отдельными карточками. Без этого синхронный `task` в основной сессии показывал только PROMPT до завершения. У завершённого прогона источник — `result.metadata` (`tool_calls`/`reasoning_blocks`/`final_content`).
- **Фоновая карточка (`background: true`) — шаги догружаются из истории ребёнка.** У фонового `task` в `result.metadata` нет ни `tool_calls`, ни `steps` (тул вернул управление сразу, публикация в родительский стрим отключена) — шаги лежат в **истории дочерней сессии**: финальное assistant-сообщение ребёнка несёт `metadata.tool_results` (→ DTO `tool_calls`), `metadata.intermediate_text_blocks` и `reasoning`. Их читает стор `stores/subagentRunsStore` (`ensure`/`invalidate` по id дочерней сессии; дедуп конкурентных запросов, поколение ответа против устаревшего, `clear` — для тестов). Загрузка **ленивая**: по раскрытию карточки и по терминальному статусу прогона (`stores/processesStore`: запись `kind:'subagent'` с тем же `childSessionId` → `invalidate()` + `ensure()`). Пока прогон идёт, шагов нет — бейдж «N шагов» не рисуется; состояния загрузки и ошибки — `chat.subagent.stepsLoading` / `chat.subagent.stepsFailed` + кнопка «Повторить» (`chat.subagent.stepsRetry`). Итог ребёнка в карточке не рисуется — родитель получает его отдельным уведомлением (`metadata.type='background_run_result'`). Тесты — `stores/subagentRunsStore.test.ts` (сборка шагов из истории ребёнка), `components/chat/ChatMessage.subagent-background.test.tsx` (фоновая карточка: ленивая загрузка, бейдж, ошибка с повтором, терминальный статус, синхронная карточка не меняется).
- Маркеры в ленте (`components/chat/ChatMessage.tsx`): `metadata.interrupt` — «прерывание хода» (`chat.steer.interruptMarker`); прерванная генерация (`metadata.status === 'interrupted'`) — бейдж «Прервано» (`chat.messageStats.interrupted`). Маркера «вмешательство в ход» (`metadata.steer`) **больше нет** — вклинившаяся реплика рисуется обычным пузырём (ADR-118 §4); сама `metadata.steer` остаётся в данных (аудит/аналитика).

### Чат: вложения (ADR-115)
- Композер: `components/chat/attachments/` — `AttachmentButton` (выбор файла/камера), `useAttachmentDrop` (drag&drop), `useAttachmentPaste` (вставка из буфера, вместе с `lib/attachments/large-text-paste.ts`), `AttachedFilesList` (чипы, ошибки, прогресс), `AttachmentGallery`; вывод частей в ленте — `MessageAttachments` (URL байтов — `attachmentContentUrl(sessionId, partId)`, не blob-путь).
- **Превью не тянет оригинал (2026-11-02).** Сетка изображений в ленте и превью восстановленного в композер вложения используют **серверную миниатюру** (`attachmentThumbnailUrl` → `?variant=thumb`, ADR-115): 92-МБ видео и полноразмерное фото не скачиваются ради квадратика. Нет миниатюры (сервер ответил `404`) — **однократный** фоллбек на `attachmentContentUrl` (`attachmentContentUrlFromThumb` разбирает URL обратно); повторной подмены нет — цикла ошибок не возникает. Галерея по клику показывает **полный оригинал** (`AttachedFilesList`→`AttachmentGallery` тоже разворачивает миниатюру в оригинал). Видео в ленте — `preload="none"` + `poster`-миниатюра: файл не грузится до нажатия Play; миниатюры нет — poster не показывается (остальное поведение прежнее). Аудио/файлы не менялись.
- Подготовка — `lib/attachments/*`: `accept.ts` (единый allowlist `ACCEPTED_ATTACHMENT_TYPES` + MIME по расширению; HEIC/HEIF намеренно вне — конвертация отдельным шагом до отправки), `mime.ts`, `file-size.ts`, `prepare.ts` (`prepareAttachmentFiles` — MIME по содержимому, группы элементов `groupId`/`groupSize`), `document-extract.ts`. Своих проверок MIME/размера в компонентах не писать.
- **Загрузка: raw-stream и chunked.** `uploadSessionAttachment` (`lib/api/attachments.ts`) выбирает транспорт по размеру: меньше `CHUNKED_UPLOAD_THRESHOLD_BYTES` (16 МиБ) — **raw XHR** (тело запроса — сам `File`, `POST …/attachments?name=…`, прогресс `xhr.upload.onprogress`), иначе — **chunked** (`POST …/uploads` → `PUT ?offset=N` частями ≤ min(`maxChunkBytes` сервера, `MAX_UPLOAD_CHUNK_BYTES` 8 МиБ) → `complete`). `onProgress` в chunked агрегирует уже принятые части; отмена — `signal` (+ `DELETE` сессии best-effort). Сервер не знает chunked (`404`/`405` на инициализации) — прозрачный откат на raw; ошибки обоих транспортов разбирает общий `parseUploadError` (`413` → `details.maxBytesPerFile`/`maxChunkBytes`). Процент виден в чипе (`AttachedFilesList`).
- Черновики — `stores/attachmentsStore.ts` (`DraftAttachment`: локальный `id`, `previewUrl`, `upload: pending|uploading|ready|error`, `partId`/`blobPath`; причины отказа `too_many`/`too_large`/`upload_failed`; каскадное удаление по `groupId`, восстановление из истории — `RestorableAttachment`). Загрузка — `uploadSessionAttachment` (`lib/api/attachments.ts`); id готовых вложений уходят в `POST /prompt` (`attachments: string[]`) через `onSend(..., attachmentIds)`. Композерные `MAX_FILES_PER_MESSAGE`/`MAX_FILE_BYTES` — UX-пределы; истина — серверные `attachments.*`.
- **Черновик композера переживает reload и переключение вкладок (2026-11-02).** Текст — `lib/composer-drafts.ts` (localStorage `synth.composer.drafts.v1`, per-session, дебаунс записи 300 мс, `flush` на `pagehide`/`beforeunload`/`visibilitychange:hidden`, прунинг 50 по `updatedAt`) + `stores/composerDraftsStore.ts` (`textBySession`; `ChatInput` читает/пишет только стор). Байты вложений — `lib/draft-attachments.ts` (IndexedDB `synth-composer-drafts`, ключ `sessionId::draftId`): `put` при добавлении, `patch` после загрузки (`partId`/`blobPath`/mime/size/name) и при ошибке, `remove`/`removeSession` при удалении чипа/очистке. `attachmentsStore.hydrate(sessionId)` поднимает черновик (`ready`/`error`/`pending`; `pending` дозагружается), идемпотентен на сессию. `ChatInput` больше **не** зовёт `dispose` на unmount; текст и вложения очищаются **после успешной** отправки/постановки в очередь — ошибка отправки черновик сохраняет.
- **Лимиты и ошибки вложений.** UX-фоллбеки (`lib/attachments/limits.ts`: `MAX_FILE_BYTES` = 100 МиБ, `MAX_FILES_PER_MESSAGE` = 10) — только значения до ответа сервера/при недоступном `/meta`; эффективные лимиты приходят из `GET /api/v2/meta` (`attachments`, тип `InstanceAttachmentCapabilities`) через `loadAttachmentLimits` (кэш 60 с, дедуп одновременных вызовов, ошибка сети → дефолт) и лежат в `attachmentsStore.limits` (`loadLimits`/`setLimits`; вызов `loadLimits` — в эффекте `ChatInput` по `sessionId`). Их используют предпроверка `addFiles`/`retry`/`hydrate` и тексты ошибок (`attachmentErrorText(..., hints)`); `normalizeAttachmentLimits` защищает от битого/старого ответа. `413` несёт `error.details.maxBytesPerFile` — фактический предел кладётся в `DraftAttachment.maxBytes` (runtime-only, в IndexedDB не персистится) и важнее лимита стора в тексте. Ошибка загрузки (`413` → `too_large`, сеть/прочее → `upload_failed`) показывает оверлей на превью (`attachment-image-error`: иконка, текст, «Повторить») и тост на пачку; `attachmentsStore.hasFailed(sessionId)` блокирует «Отправить»/«В очередь» (тултип `chat.attachments.fixErrors`) до удаления или повтора.
- **`accept` и модальности.** `buildAttachmentAccept(limits.modalities)` собирает `accept` из MIME+расширений и исключает выключенные семейства (по умолчанию включены все); список включает видео (mp4/m4v/webm/ogv/mov) и аудио (mp3/wav/ogg/oga/flac/m4a/aac/opus), SVG/HEIC/EXE по-прежнему не принимаются. Выключенные админом вложения (`attachments.enabled: false`) блокируют кнопку с подписью `chat.attachments.disabled`. Чип видео — иконка `file-video`.
- **Гейт модальностей.** `attachmentModalityKind` + модальности выбранной модели (`selectedModelModalities`): если модель **точно** не принимает семейство — тост `chat.attachments.modelUnsupported` (отправка не блокируется, сервер сам отбросит/обработает). Модальности неизвестны — фильтра нет: тихая потеря запрещена.
- **Вложение из инструмента — служебный блок.** `metadata.source === 'tool-attachment'` (тулы `attach_workspace_file`, `read_file` с картинкой/PDF, `web_fetch({include_media})`, MCP) рисуется центрированным `Notice` (вариант `attachment`, иконка `attachment-2`), подпись «Агент · <имя> · вложение» (`chat.notice.toolAttachment`/`...Anonymous`), имя — из `metadata.agent_role` через `agentsStore`, fallback — роль. Внутри — `MessageAttachments`; действия — полный набор как у `background_run_result` (включая Retry/Copy); `MessageList.isHumanReply` для него `false`. `author` сообщения — системный `'Tool'`, не пользователь. Ядро относит его к служебным user-сообщениям (авто-заголовок), не считает границей автора в `buildUserStats` и границей хода в `suppressDisabledTurns`.
- i18n — `chat.attachments.*` (ru/en, паритет). Тесты — `lib/attachments/*.test.ts`, `stores/attachmentsStore.test.ts`, `stores/transportStore.send-attachments.test.ts`.

- **Переведённые в фон (ADR-111 §detach).** Запись появляется **без** `process.started` — по событию `process.detached` (общий разбор `process.*` в `processesStore.applyEvent` заводит её со статусом `running`); карточка обычная: вид, команда/cwd, лог по `offset`, остановка. Отдельного «detached»-флага в UI нет — источник истины один реестр.
- Автообновление: список перечитывается каждые 5 с, **пока вкладка активна** (компонент смонтирован ровно тогда, когда вкладка открыта); лог догружается каждые 2 с, пока процесс выполняется; тикер «идёт уже N» — раз в секунду.
- i18n — `processes.*` (ru/en, паритет). Тесты — `stores/processesStore.test.ts`, `stores/transportStore.processes.test.ts`, `components/panels/ProcessesTab.test.tsx`.
- **Карточка результата фонового прогона в чате.** Уведомление о завершении приходит сообщением роли USER (так его видит модель), поэтому обычным user-пузырём его не нарисовать: рисуем **системным блоком** (`Notice`, вариант `process` — как у сообщений планировщика): шапка с иконкой прогона (`robot-2` — саб-агент, `terminal-box` — процесс) и подписью «Фоновый процесс/саб-агент · <имя> · <статус>» (`chat.notice.backgroundProcess`/`backgroundSubagent` + `chat.notice.backgroundState.*`), а внутри — **карточка результата**: тот же `ToolCallPart`, что у результата тула в ответе агента (свёрнута по умолчанию, `resultFirst`, `plain` — без рамки, чтобы не было «карточки в карточке»; раскрытие — по маркеру `data-tool-call-toggle`). Данные карточки собирает `backgroundToolCall` (`components/chat/background-notice.ts`) из `metadata` сообщения (`kind`/`state`/`command`/`description`/`cwd`/`started_at`/`finished_at`) и тела сообщения: конверт модели `<process …>`/`<subagent …>` (и обёртка `<summary>`) **вырезается** — в карточке только лог/итог прогона. Вид прогона выбирает тула-источник: `kind:'subagent'` → карточка `task`, иначе → карточка `execute_shell`. Действия сообщения (`MessageActions`, `embedded`) — **внутри `Notice`** (в его футере), копия — кнопкой самого `Notice`.
- **UI-уведомления старта/финиша фоновой работы.** `notifyBackgroundRun` в диспетчере `stores/transportStore.ts` (события `process.started`/`process.exited`/`process.stopped`, `child.started`/`child.completed`/`child.failed`/`child.cancelled`): тост через `notifyMessage` (`category:'system'`) — имя прогона берётся из реестра (`stores/processesStore.ts`), иначе из payload. Уведомление на старте и завершении, дедупа нет: каждое пришедшее событие даёт тост (корневая причина дублей устранена в ядре). i18n — `notify.background.*` (ru/en, паритет: `started`/`completed`/`failed`/`cancelled` и `subagentStarted`/`subagentCompleted`/`subagentFailed`/`subagentCancelled`).

### Чат: «В фон» (ADR-111 §detach)
- Переводят три места: шапка running-парта `task` (`SubagentPart`), живая часть хода в `ChatMessage` (`message.status === 'streaming'`; прежняя отдельная плашка стрима удалена в ADR-118) и хоткей `ctrl+b` (`useBackgroundHotkey`; внутри `contenteditable` не перехватывается — `ctrl+b` остаётся браузеру).
- Общий шов — `lib/backgroundDetach.ts` `moveSessionToBackground(sessionId, { type?, callIds? })`: `POST /sessions/:id/background` → снятие live-партов переведённых `task`/`execute_shell` из активного хода (`chatStore.dropDetachedToolCalls`) → тост `notify.background.moved` (`{count}`); ошибка — `notify.background.moveFailed`. Пустой `detached` — не ошибка («нечего переводить», тост с нулём).
- Дальше прогон живёт в реестре «Процессы»: сервер публикует `process.detached` (**не** `process.started` — прогон уже шёл), общий разбор `process.*`/`child.*` в `transportStore` (`processesStore.applyEvent`) заводит запись как `running`; лог/остановка — обычным путём вкладки.
- В гибриде удалённая сессия отвечает **400 `DETACH_UNSUPPORTED`** — показывается ошибка, «тихого» успеха нет.
- i18n — `chat.background.move`/`chat.background.hint`, `notify.background.moved`/`moveFailed`.

### Чат: рендер хода (ADR-118)

Полная спецификация цикла обработки сообщений (приём → очередь → ход/шаги → финал, события, индикаторы, сценарии, карта файлов) — [../../docs/MESSAGE_FLOW.md](../../docs/MESSAGE_FLOW.md).

- Один компонент на живое и финальное состояние: `ChatMessage` рендерит **части** сообщения (`buildPartsView` по `message.parts` + `partsBySession`), а не накопленный текст стрима. Отдельной плашки стрима (`StreamingPlaceholder`) нет — `partsView` мемоизирован (`useMemo`) по частям и фоллбеку, `<MarkdownContent>` — по отображаемому тексту, а отложенный разбор стрима живёт внутри `MarkdownContent` (см. «Markdown в ответах» ниже).
- Живость определяется статусом сообщения (`message.status === 'streaming'`, ADR-118 §5): индикатор активности, live-статистика (`liveSegments` из `usage`/`cost_usd`) и «В фон» — в том же `ChatMessage`; «Стоп» — общая кнопка в композере. «Финал» — смена статуса (`step.finished`), а не замена объекта, поэтому последний фрагмент текста не теряется.
- **Финал хода = последний шаг.** Финальное сообщение хода несёт текст и reasoning **только последнего шага**; карточки инструментов лежат в сообщениях **своих** шагов (`metadata.tool_results` → DTO `tool_calls`), в финале их нет — переносить их в последний сегмент нельзя (иначе дубль карточек). `usage` финального сообщения — суммарный расход **хода**, `step.finished.usage` — расход **своего** шага: live-статистика берёт `step.finished`, а не `usage` финала.
- **Финал шага — статус сразу.** `step.finished` ставит терминальный статус **синхронно** (индикатор «идёт» гаснет в момент финала шага, а не после ответа `GET /messages` — иначе точки «работы» висели в середине склеенного блока хода), затем сверяется с историей (`mergeHistory`). Live-части шага при этом **не снимаются**: карточка инструмента должна остаться видимой (ядро публикует `step.finished` **до** запуска тулов, результат приходит позже через `tool_call.result`), а вызов тула вешается в сообщение шага даже если шаг уже закрыт (`ensureLiveMessage(..., { allowTerminal: true })`).
- **Live-части финального сообщения** (`lib/messageParts.ts` `resolveLiveParts`): пока части из истории не пришли — все live-части (фоллбек, текст не пропадает); когда пришли — **текст и reasoning только из dto** (id `msg:text:<ordinal>` совпадают у разных шагов, «застрявший» live-текст прошлого шага попал бы в блок хода), а **tool-части** (id = `callId`) мержутся с dto по `id` — карточка инструмента не пропадает и несёт результат (live-часть важнее dto-снимка: dto сохраняется на финале шага, результат приходит позже). Нормализация сырого вызова провайдера → `{name, args}` — **внутри** `buildPartsView` (`normalizeLiveToolPart` в `lib/messageParts.ts`): любой вызов сборки даёт карточку тула с именем.
- **Признак «контент хода уже был» — один предикат** (`turnHasContent(messages, turn, fallback?)` в `lib/messageParts.ts`): флаг `contentStarted` хода **или** непустой контент assistant-сообщения хода (`turn_id`/id сообщения шага). Используют его восстановление живого хода (`transportStore`) и точки «обработка» у реплики (`MessageList`) — свои предикаты в этих местах не заводить. Пустой live-сегмент (новый шаг до первого токена) рисуется **только заголовком с точками** при `turn.contentStarted === true` или `turn.toolsRunning === true`; на самом первом шаге индикатор живёт у реплики. Кнопка «Отладка» доступна у любого сегмента хода: `debug_data` пишется только в финальное сообщение, `MessageList` передаёт `debugTarget` (финал хода) — клик открывает дебаг именно его. Флаг поднимает и вызов инструмента (`tool_call.started`): шаг «только вызовы инструментов» — тоже контент хода.
- **Восстановление хода и ретрая после reload** (`restoreLiveTurnFromSession`): id хода — `current_stream.turn_id` → `activity.turnId` (ядро отдаёт `activity` и без `current_stream`) → `turn_id` последнего сообщения сессии → `current_stream.stream_id`/`activity.streamId` (legacy). Признаки активного хода — `current_stream`, `status.blocked` (ждёт подтверждения) и `activity.type: 'busy'|'retry'`; `idle`/нет `activity` активным ходом не считается. `activity.type === 'retry'` сразу восстанавливает плашку «Повтор N/M» (`setStreamRetry` из `attempt`/`maxRetries`/`retryAt`/`error`) — иначе после reload событие `stream.retry` уже не придёт. `stream_id` (`stream-…`) — **не** id хода: с ним live-сообщения получали `turn_id = stream-…`, а история `turn_…` — блок хода рвался на два, а закрытие сегментов по `onlyTurnId` не срабатывало (индикатор застревал). `ChatTab` зовёт `restoreLiveTurnFromSession` **после** `setMessages` (сообщения уже в сторе).
- **Инструменты шага** (`step.tools.started`/`step.tools.finished`, ADR-118 §4): между финалом шага и результатом инструмента живого сегмента с контентом в ленте нет — `ActiveTurn.toolsRunning` держит точки в шапке последнего assistant-сегмента хода (шаг уже `completed`, ход ещё идёт). Флаг снимается `step.tools.finished` и на любом терминальном статусе хода. Тесты — `components/chat/MessageList.turn-header.test.tsx`, `components/chat/MessageList.turn-indicator.test.tsx`.
- **Живой шаг после reload/переключения вкладок (2026-11-02).** `stepMessageForTurn` берёт сообщение шага: живой `streaming`-сегмент, иначе **последнее assistant-сообщение хода** (ядро публикует `step.finished` до запуска инструментов, и во время длинного тула `streaming`-сообщения уже нет). `seedInFlightToolParts` сеет live-части **выполняющихся** вызовов (`status: 'running'`, по `parts`/`tool_calls` сообщения шага), `restoreLiveTurnFromSession`/`patchTurnFromSession` ставят `toolsRunning`; вызовы, у которых есть `tool`-сообщение истории, не сеются. Если `turn.messageId` пропал из ленты, он перепривязывается к шагу.
- **`liveToolMessageId()` ≠ `liveMessageId()`.** `tool_call.*`/`subagent.progress` адресуются по `liveToolMessageId` (сообщение шага или последнее assistant хода), а `part.delta`/`part.updated` — по строгому `liveMessageId`; после reload/смены вкладок карточки инструментов и прогресс саб-агентов не теряются.
- **Исторические результаты инструментов.** Снимок истории не несёт `tool_calls[].result` (результаты — скрытые `role: 'tool'` с `metadata.tool_chain`): `mergeServerMessages` сводит их в `tool_calls` (`hydrateHistoricalToolResults`), иначе карточка после reload висит без результата. Снимок **не удаляет** сообщения активного хода (`turn_id` = активный ход), а отстающий снимок не затирает `tool_calls` живого шага.
- **Дочерние tool-события.** Вкладка саб-агента получает `tool_call.started`/`tool_call.result` в **свой** канал (в родительский — как раньше, с `parent_call_id`); assistant-сообщения шага ребёнка сохраняются с `turnId`/`stepIndex`/`status` (ADR-111).
- **Одна шапка на визуальный блок** (новая UX-модель индикатора): заголовок «агент · модель · время» — у **первого** сегмента группы-блока (`showHeader={first}`, `compact={!first}`); ход, разорванный user-репликой (уведомлением о фоне — `metadata.type === 'background_run_result'`), даёт вторую группу с тем же `turn_id` — это отдельный блок со своей шапкой. Пока ход идёт (`turn.status === 'streaming'`), шапка **последнего блока активного хода** (`turn.turnId === group.turnId`, группа — последняя assistant-группа этого `turn_id`) вместо времени показывает три точки (`headerProcessing` → `MessageHeader processing`, `data-testid="processing-indicator"`) — независимо от того, какой сегмент сейчас стримится (шаг может быть уже `completed`). Строки активности (`turn-activity`, «Выполняется…») в ленте больше нет; `RetryStatus` живёт **внизу ответа** последнего сегмента (у реплики — только точки «обработка»).
- **Автор user-реплики** — `MessageHeader` показывает `message.author`, если это чужой автор (другой пользователь, внешний отправитель), и имя из профиля только для своих (`author` пуст/`local`/`user`/username, сравнение без учёта регистра — legacy `User`). Внешнее событие без `author` (`metadata.event_id`) — «Внешний отправитель» (`chat.author.external`), имя зрителя не подставляется. Тест — `components/chat/ChatMessage.author.test.tsx`.
- Замер задержки сервер даёт в `step.finished` (`timings`/`usage`; см. `docs/API_V2.md` §3.3) — прежние `stream.chunk.seq`/`t_ms` и `stream.done.*` **удалены**.
- **Копирование сообщения** — `lib/messageCopy.ts`: копируется **видимый** текст, а не legacy-`content` (тот собирает `buildContentFromParts` в `shared` и содержит `<reasoning>`/`<tool_call>`/`<tool_result>`): источник — `buildPartsView(...).text`, фоллбек на `content` со стрипом служебных блоков (`stripKernelBlocks`), результат `trimEnd()`. `ChatTab.handleCopy(msg, plain?)` берёт live-части из `chatStore.partsBySession` через `resolveLiveParts` (как рендер). Обычный клик — markdown, **Shift+клик** — без разметки (`markdownToPlainText`, обход токенов `marked.lexer`), подпись кнопки — `chat.actions.copyHint`.
- **«Развернуть» ответ** — кнопка в `MessageHeader` (только ответ агента), иконки `fullscreen`/`fullscreen-exit`, подписи `chat.message.expand`/`collapse` («Развернуть»/«Свернуть»). Разворот — **одна** полноэкранная панель `data-testid="message-expanded"` внутри `MessageList`: состояние — `useUIStore.expandedChatGroup: string | null` (ключ — `MessageGroup.key`, `persist`; `toggleChatExpanded`: другой ключ заменяет текущий, повторный по тому же — закрывает; ключ снимается `pruneChatViewState`, когда группа исчезла из ленты), пропсы `expandKey`/`expanded`/`onToggleExpand` стабильные/примитивные (иначе слетает `memo(ChatMessage)`), `expanded` = `true` только у сегментов **внутри** панели. Панель **заменяет ленту** (лента в это время не рендерится — DOM не дублируется) и занимает всю область чата по ширине и высоте; внутри `.chat-column` панели свой вертикальный скролл. Высоту задаёт CSS `.message-expanded-pane` (`styles/index.css`): цепочка `flex` доводит растяжение до `[data-bubble]`/`turn-block`, содержимое не сжимается под высоту (`flex-shrink: 0`) — длинный ответ растит пузырь, а скроллится панель, не страница. `data-view-mode`/`data-density` и `--chat-scale` действуют и внутри панели (те же атрибуты на её `.chat-column`). Закрытие — повторный клик или `Esc` (не перехватывается, если фокус в `input`/`textarea`/`select`/`contenteditable`); позиция прокрутки ленты сохраняется (`savedScrollTopRef`) и восстанавливается после закрытия (`useLayoutEffect` + `requestAnimationFrame`-коррекция), фокус возвращается на кнопку разворота; при исчезновении группы из ленты состояние сбрасывается. `TURN_BLOCK_CLASS_EXPANDED` (`max-w-full`) используется только внутри панели; тач-зона кнопки расширена `.message-expand-btn::after` на `pointer-coarse` (ADR-044).
- **Блоки кода: копирование и скачивание** — шапка `.md-code-head` содержит `.md-code-actions`: `[data-copy-code]` и `[data-download-code]` (оба в `MARKDOWN_ALLOWED_ATTR`; кнопки — **иконки**, подпись только в `aria-label`/`title` — детали в «Markdown в ответах» ниже); текст берётся из `pre code.textContent` с обрезкой `\n+$` (номера строк — CSS-счётчик, в `textContent` их нет; после подсветки shiki текст исходный). Имя файла — `code.<ext>` по `data-lang` (`lib/markdown/codeFile.ts`: канон через `resolveHighlightLanguage`, алиасы не дублируются; неизвестный → `txt`), скачивание — `lib/download.ts` (`downloadBlob`), MIME `text/plain;charset=utf-8`. Зазор до правой рамки — `margin-inline-end` у `.md-code-pre` (логическое свойство, RTL-безопасно: `pre` — скролл-контейнер, и внутренний `padding-right` уезжал бы при прокрутке).
- **Источники вида/плотности/масштаба (приоритет).** local (`persist`/localStorage) > профиль (`UserPreferences.chatViewMode`/`chatDensity`/`chatScale`, managed) > серверное умолчание инстанса (`AppearanceDefaults.chatViewMode`/`chatDensity`/`chatScaleMobile`/`chatScaleDesktop`; порт `core/storage/ports/defaults-repository.ts`, файловая реализация `core/storage/defaults-store.ts` + паритетная санитизация `storage-postgres/src/ports/principals-defaults.ts`; `GET/PUT /auth/defaults`, whitelist полей — `backend/routes/auth.ts`) > встроенный (`detailed`/`normal`/1). Применение — `DefaultsSync` (`App.tsx:96-143`): сначала личные значения профиля (`applyPersonalChatDisplay`/`applyPersonalChatScale`), затем серверные умолчания (`setServerChatScaleDefaults`/`applyServerDefaultChatScale`, `setServerChatDisplayDefaults`). Умолчания действуют только при отсутствии личного выбора: вид/плотность — `hasPersonalChatDisplay` (признак считывается **до** гидратации стора — `persist` перезаписывает ключ на каждый `set`), масштаб — `hasPersonalChatScale` (localStorage + применённое в сессии). В standalone `/auth/defaults` нет — `getDefaults()` глушит ошибку и отдаёт новые поля `null` (= умолчание не задано → встроенный дефолт). Save в «Настройках → Чат» дублирует личный выбор в профиль best-effort (`profileService.syncChatViewModeToProfile`/`syncChatDensityToProfile`/`syncChatScaleToProfile`, ошибки глушатся). Секции раздела — `chat-view-mode` (вид), `chat-density` (плотность), `chat-scale` (масштаб), `chat-intermediate-text` (промежуточные ответы; `chatSettings.*`). Админ задаёт умолчания в разделе «Оформление» (`DefaultsPanel`, категория `defaults`): секции `defaults-chat-display` (вид/плотность) и `defaults-chat-scale` (масштаб для мобильных/десктопа; клиентский кламп `clampChatScale` 0.75…1.5, мобильный минимум 0.85 применяется на устройстве).
- **Плотность ленты** — `chatDensity: 'normal' | 'compact'` (`useUIStore`, persist; настройка «Настройки → Чат», секция `chat-density`). В `compact` у **завершённых** ходов не рендерятся размышления, промежуточные тексты и карточки инструментов (остаются карточки сабагентов — это результат); вместо них `<button data-testid="service-summary">` с `aria-expanded`: «N инструментов · M размышлений» (`chat.compact.*`, ICU-плюрал), раскрытие — `useUIStore.revealedServiceGroups` (массив ключей группы, `persist`; хвост ограничен 200, `pruneChatViewState` убирает исчезнувшие). Эффект в `MarkdownContent` подсвечивает только «устоявшиеся» блоки (`data-highlighted`, не во время `streaming`), сверяет текст после `await` (гонки), подменяет содержимое `code` на `<span class="line">` и вешает класс `shiki` на `pre`. Два инварианта: (1) эффект переживает двойное монтирование (StrictMode) — начатая подсветка не отменяется cleanup'ом, промисы переиспользуются через module-level `WeakMap<HTMLElement, Promise<string|null>>` по блоку; (2) объект `dangerouslySetInnerHTML` **стабилен** между рендерами (`useMemo` по `html`) — React 19 сравнивает пропсы по идентичности и пересоздаёт `innerHTML` при новом объекте, иначе любой ререндер чата стирал бы разметку блоков кода и применённую подсветку; номера строк для подсвеченных блоков — те же CSS-счётчики (`.md-code-pre.shiki .line`). **Смена темы перекрашивает блоки:** цвета shiki записаны инлайном, поэтому старые остались бы от прежней палитры — `lib/markdown/highlight.ts` ловит смену темы (`MutationObserver` на `<html>` по `class`/`style`, `MutationObserver` на `<head>` по `childList`/`subtree`/`characterData` — замена `<style id="opencode-theme-variables">`, `matchMedia('(prefers-color-scheme: dark)')`), сверяет отпечаток темы (вариант + содержимое style-элемента), сбрасывает кэш и увеличивает `themeEpoch` (`getThemeEpoch`/`subscribeThemeChange`/`resetThemeWatcher`); `MarkdownContent` подписан через `useSyncExternalStore`, при смене epoch снимает `data-highlighted`/класс `shiki` и возвращает `code` в исходный текст, после чего эффект подсветки рисует блок заново (в полёте — гонка epoch'а отбрасывает устаревший результат). ### Пагинация: список сессий и история ленты (ADR-089)
- **Список сессий всегда пагинирован.** `GET /api/v2/sessions` → объект-страница `{sessions, total, offset, limit, next_offset}` (`synthApi.getSessionsPage`; `getSessions()` — обёртка, только массив). Сводка сессии (`GET /sessions/:id`) **не содержит истории**; полная история — `GET /sessions/:id/messages` (тоже постранично).
- **Дерево сессий.** `sessionsStore`: `total`/`nextOffset`/`loadingMore`/`listProjectId`; `loadSessions(projectId?)` — первая страница (`limit=100`), `loadMoreSessions()` — дописывает следующую (дедуп по `id`). Кнопка **«Показать ещё»** внизу дерева (`ProjectsTab`, `data-testid="load-more-sessions"`) — только при `nextOffset !== null`; при загрузке disabled. Страница **дописывается** в стор: раскрытые проекты, выбранная сессия и порядок не сбрасываются. Создание сессии добавляет её в начало, не перезагружая список.
- **История ленты.** `GET /sessions/:id/messages?limit&before` → `{messages, session_id, has_more, next_before}`; без `before` — **последняя** страница, с `before` — строго старше курсора (`seq`). `MESSAGES_PAGE_LIMIT = 200` (`lib/api/messages.ts`).
- **Кнопка «Загрузить старые»** — над лентой (`MessageList`, `data-testid="load-older"`), видна при `has_more`. Клик (`ChatTab.handleLoadOlder`) грузит `before: next_before` и **добавляет** сообщения в начало (`chatStore.prependMessages`), обновляя `has_more`/`next_before` (`chatStore.historyPageBySession`). Позиция скролла сохраняется (`MessageList`: компенсация разницы `scrollHeight` в layout-эффекте, автоскролл вниз на время догрузки выключается).
- **Правило `has_more`.** Снимок с `has_more: true` — это **только последняя страница**: сообщения старше границы страницы (`seq` меньше минимального `seq` снимка) удалёнными на сервере **не считаются** и сохраняются при мерже (`mergeServerMessages(sid, messages, { hasMore })`). При `has_more: false` снимок авторитетен по всему составу. `setMessages` — всегда авторитетная замена (очистка истории).
- **Курсор пагинации не сбрасывается мержем.** `applyHistoryPage` (мерж снимка с живым состоянием) курсор **не трогает**: снимок последней страницы не знает про старые страницы, догруженные пользователем (его `next_before` указывал бы на уже загруженный диапазон). Курсор инициализируется первичной загрузкой сессии (один раз на сессию) и обновляется только явной догрузкой старых страниц.
- **Места, где история перечитывается** (`Header.afterBulkReload`, `ReferencesTab.handleRemove`, карточка ссылки в `ChatMessage`, `ChatTab` — удаление/ретрай), идут через `applyHistoryPage`, а не `setMessages`: иначе догруженные старые страницы ленты терялись бы. `clearSession` (очистка истории) — авторитетный `setMessages` + сброс пагинации.
- **Неполная история — не ложь в счётчиках.** «Контекстное окно» (`hooks/useContextWindowUsage`) считается по **последнему** ответу (`usage.total_tokens` последнего assistant-сообщения), а не по сумме загруженного — при неполной истории число остаётся верным. Счётчика сообщений в админ-панели сессий нет (список не содержит истории) — ключ `admin.sessions.messageCount` удалён.
- i18n — `chat.loadOlder`/`chat.loadingOlder`/`chat.error.loadOlder`, `leftPanel.loadMoreSessions`/`leftPanel.loadingMoreSessions`, `admin.sessions.showMore`/`admin.sessions.loadingMore` (ru/en, паритет). Тесты — `stores/sessionsStore.test.ts` (страницы/`loadMore`), `components/chat/ChatTab.load-older.test.tsx` (последняя страница, догрузка, prepend), `components/chat/MessageList.load-older.test.tsx` (кнопка/спиннер), `components/panels/left-panel/ProjectsTab.pagination.test.tsx` (кнопка дерева), `stores/transportStore.merge-delete.test.ts` (мерж и границы страницы), `components/admin/SessionsPanel.test.tsx` (total, без счётчика сообщений).

### Каталог моделей: страницы, поиск на сервере, лимиты файлов и diff (ADR-095, C1)
- **Каталог моделей постраничный.** `GET /api/v2/models` → страница `{models, total, offset, limit, next_offset}`; поиск (`search`) и фильтры (`provider`/`modality`/`enabled`) — **на сервере**. Старый ответ `{groups}` не приходит — UI разворачивает его в страницу (`lib/api/models.ts`, фоллбэк `getModelsPage`).
- **Домен API.** `modelsApi.getModelsPage(query?)` — сырая страница; `modelsApi.getModelGroups(query?)` — `{groups, page}`: группы склеиваются из плоского списка + метаданные провайдера из `GET /providers` (`type`/`icon`/`currency`/`defaultModel` — в ответе `/models` их больше нет); `modelsApi.getModels(query?)` — совместимая обёртка (только группы страницы). Хелперы — `groupModelsByProvider`/`mergeModelGroups` (склейка страниц по провайдеру и `id` модели).
- **Стор.** `providersStore`: `models`/`modelGroups` — загруженная страница, `modelsTotal`/`modelsNextOffset` — счётчик и курсор, `modelsQuery` — последний запрос. `loadModels(query?)` — первая страница (поиск/фильтры), `loadMoreModels()` — следующая (кнопка «Показать ещё»), `applyModelGroups(groups, {authoritative:false})` — **неполный** список (страница/поиск) не сбрасывает выбор модели. `ensureModelLoaded(ref)` — точечная догрузка модели по ссылке `provider/model`; `ensureSelectedModelVisible()` — догружает модель сессии, если её нет на странице.
- **Списки выбора модели не остаются пустыми.** `ModelPairSelect` добавляет текущее значение в список, даже если модели нет в загруженной странице; хук `useEnsureModelsLoaded(refs)` (`hooks/useEnsureModelsLoaded.ts`) догружает метаданные выбранных моделей (`SessionSettingsTab`, `RoutingSettings`, `DecisionSettings`, `MultimodalSettings`, `useContextWindowUsage` — окно контекста).
- **Селекторы получают полный каталог.** `hooks/useCatalogModels.ts` + `providersStore.loadCatalogModels()` грузят все страницы по 500 (до 5000 моделей, один раз) в `catalogModels`; до загрузки/при ошибке возвращается текущая страница `models`. Подключено в `SessionSettingsTab`, `RoutingSettings`, `DecisionSettings`, `MultimodalSettings`, `AnalyticsModal` — любая модель каталога доступна в выборе без ручного «Показать ещё». Админ-панель и чат по-прежнему используют страницу/серверный поиск (`loadModels`/`loadMoreModels`); `refreshCatalog` сбрасывает кэш каталога.
- **Админ-панель «Модели»** (`components/admin/ModelsPanel.tsx`): поиск с задержкой 300 мс уходит на сервер, фильтры `provider`/`modality`/`enabled` — серверные, кнопка **«Показать ещё»** (`data-testid="models-load-more"`) догружает страницу. Селектор модели в чате (`components/chat/ModelSelector.tsx`): поиск с задержкой 250 мс + «Показать ещё» (`data-testid="model-selector-load-more"`).
- **Файлы: лимит чтения.** `GET /fs/read` — файл больше лимита (5 МиБ) или бинарный → `413` с машинным кодом `FILE_TOO_LARGE` и `details.{maxReadBytes,size,reason}`. `FileEditorTab`/`FileViewerTab` показывают понятный блок (`file.tooLarge`/`file.binaryNotReadable`, `data-testid="file-too-large"`) со ссылкой «Скачать», а не пустой экран.
- **Файлы: обрезка листинга.** `GET /fs?maxDepth>0` — глубина режется сервером до 3, при `maxDepth > 0` обход обрывается по лимиту записей (10 000) и в ответе `truncated: true`. `filesStore.truncatedDirs` хранит признак по каталогам; диалог переноса (`FilesTab`) просит `maxDepth = 3` и показывает пометку `file.listTruncated` (`data-testid="move-dirs-truncated"`).
- **Git: обрезанный diff.** `GET /git/commit` → `commit.diff_truncated: true` — diff обрезан сервером по лимиту размера (1 МиБ). `CommitDetailTab` показывает плашку `commit.diffTruncated` и рисует не более 500 строк diff (в DOM не превращаются мегабайты).
- i18n — `admin.models.showMore`/`loadingMore`/`modality*`, `settings.help.models.filterModality`, `chat.modelControls.showMore`/`loadingMore`, `file.tooLarge`/`file.binaryNotReadable`/`file.listTruncated`, `commit.diffTruncated` (ru/en, паритет). ### Просмотр файла проекта (`FileViewerTab`)

- **Ветвление по `fileKind(filePath)`** — общий контракт `@itphx/synth-shared/types` (runtime-импорт только из subpath `/types`): UI и сервер (`GET /api/v2/fs/raw`) одинаково понимают семейство файла.
  - `markdown` (`.md/.markdown/.mdown`) — `synthApi.readFile` → `<MarkdownContent>` (тот же пайплайн, что в чате: `marked` → DOMPurify allowlist → shiki). Переключатель «Просмотр / Исходник» (по умолчанию просмотр; «Исходник» — `<pre>`), ключи `file.markdownPreview`/`file.markdownSource`.
  - `image`/`video`/`audio`/`pdf` — inline-предпросмотр через `synthApi.rawFileUrl(projectId, path)` → `GET /api/v2/fs/raw` (`<img>`, `<video controls preload="metadata">`, `<audio controls preload="metadata">`, `<iframe>`). `preload="metadata"` не тянет файл целиком до нажатия Play. Перед рендером — `synthApi.probeRawFile` (`HEAD /fs/raw`): `413` с `details.reason:'preview_size'` (файл больше `storage.maxPreviewBytes`) даёт сообщение `file.previewTooLarge`; `404/403` — текст сервера; ошибка проверки/сети показ не блокирует — решает `onError` элемента (`file.previewFailed`).
  - `text`/`code`/`binary`/неизвестное (`.html`, без расширения) — прежний путь `readFile`: текст в `<pre>`, `413 FILE_TOO_LARGE` (`reason:'size'`/`'binary'`) — блок причины (`file.tooLarge`/`file.binaryNotReadable`).
- **HTML/код/текст никогда не inline**: allow-list `INLINE_PREVIEW_KINDS` (image/video/audio/pdf), остальное сервер отдаёт как `attachment`/`application/octet-stream` — `<img>`/`<iframe>` для них не ставим (XSS); SVG показывается только через `<img>` (сервер добавляет CSP-песочницу).
- **«Скачать» доступна во всех режимах** (`synthApi.downloadFile`): при предпросмотре медиа, в блоке отказа, у бинарного файла. `FileEditorTab` исправлен так же (раньше ссылка пряталась при `reason:'binary'`). «Редактировать» в `Header` предлагается только для `markdown`/`text`/`code`; для `image/video/audio/pdf/binary` кнопка скрыта (`NON_EDITABLE_FILE_KINDS`).
- Остаток: относительные ссылки/картинки внутри `.md` рендерятся как есть (база — origin приложения, а не workspace).

### Сохранение немедленных настроек панели
- Немедленное сохранение настройки правой панели (тумблер, селект, автосейв поля) — только через общий хук `usePanelSettingSave` (`hooks/usePanelSettingSave.ts`): `run({ key, run, onSuccess, onError, errorKey })`.
- Шаблон элемента: `pending` контрола по `isPending(key)` → единый success-тост `panel.saved` → при ошибке единый error-тост `panel.saveError` и **откат** контрола/формы к актуальному серверному состоянию. «Залипающих» оптимистичных значений быть не должно (`onError`/`onSuccess` возвращают состояние; для форм — `applyFormValues(formValuesFromSettings(...))`).
- `pending` — по конкретному контролу/сущности (`isPending(\`mcp:${name}\`)`), а не «всё сразу»; во время запроса контрол `pending`, но не `disabled` (повторы гасит обработчик через `isPending`).
- Повторные success-тосты подавляются окном троттлинга (`throttleMs`, по умолчанию ~1.5 с); error-тосты показываются всегда. Спец-ошибки (403 forbidden, 409 confirm-required) — через `errorKey` (строка или функция от ошибки) либо `silentError` + собственный тост. Общие формулировки — ключи `panel.saved`/`panel.saveError` (не плодить доменные синонимы).

### API и i18n
- API v2 — только через `synthApi` (`lib/api/synthApi.ts` — barrel; доменные модули — `lib/api/<домен>.ts`, база `BASE_URL`/`fetchJSON`/`encodeFilePath` — `lib/api/base.ts`); `/auth` — `lib/api/client.ts` (`BASE_URL = '/auth'`, `:75`). Ошибки бросаются как `Error` — ловить и показывать через i18n.
- Строки — только `useI18n().t('ключ')`, не хардкодить. `messages/en.ts` — базовый словарь, `messages/ru.ts` — ленивая загрузка (`import()`); ключ добавлять в оба. Плюрализация — ICU-подобным синтаксисом прямо в значении словаря: `'{count, plural, one {# сервер} few {# сервера} many {# серверов}}'` (ru — формы `one`/`few`/`many`, en — `one`/`other`). `#` внутри формы — само число, также работают обычные `{param}`-плейсхолдеры. `t(key, { count })` сам выбирает форму по локали (правила — `lib/i18n/plural.ts`, `pluralCategory`); если формы нужной категории нет — fallback `other → many → one → few → zero → two`.
- Движковые ключи синхронизируются с `@itphx/synth-shared/i18n` по контракту ADR-041; проверка автоматическая — `messages/engine-keys.test.ts`.
- Системные сообщения ядра несут `metadata.i18n = { key, params }`: для отображения использовать `resolveI18n`/`isValidI18nMeta`/`useResolveI18n` (`lib/i18n/`), а не собирать строку в UI.

### Транспорт
- Единственный `TransportClient` (`lib/api/transport.ts:23`) + `stores/transportStore.ts` (`:626`). События обрабатывать через стор; не открывать второй WebSocket/EventSource (ADR-024).
- `fs.changed` — мутирующий тул ядра изменил workspace: стор вызывает `filesStore.scheduleRefresh` (debounce) и debounce-refresh реестра Git (`scheduleGitRefresh`). `session.moved` — сессия перенесена между проектами (в т.ч. `project_create`/`project_attach` агентом): патч `project_id`, refresh сессии, `loadProjects` и `filesStore.refreshProject`.
- `event.routed` (ADR-089) — внешнее событие материализовано в сессию: полный refresh сессии (`refreshSessionFromApi`); изменения приходят отдельными событиями очереди/сообщений.
- **Пробуждение и реконнект (2026-11-02).** `TransportClient.resume()` пересоздаёт транспорт, если соединение «зомби» (нет активности > 90 с) — вызывается на `online`/`pageshow`/`visibilitychange:visible`; слушатели вешаются в конструкторе и снимаются только в `disconnect()`. `transportStore.restart()` перезапускает транспорт в обход guard'а идемпотентности `connect()`; `ConnectionGuard` использует его при возврате связи, слушает `pageshow` и сам закрывает confirm «перезагрузить» при восстановлении. После реконнекта `noteConnected()` → `resyncAfterReconnect()`: перечитывает список сессий, закрывает табы удалённых сессий (и чистит ленту), перечитывает историю активного чата.
- **Синхронизация мутаций между клиентами.** Диспетчер обрабатывает (ADR-118 §4/§7): `message.deleted` — убрать сообщение и live-части; `message.updated` — патч `pinned`/`disabled`; `session.messages.cleared` — перечитать снимок и поставить `setMessages` (авторитетно, очередь 0); `session.messages.merged` — свести добавленные сообщения; `project.deleted` — убрать проект, его сессии, чат-табы и ленты; `plan.updated` — refresh сессии; `project.updated` — refresh проекта/файлов/Git. `fs.changed` приходит и от HTTP-FS (`source: 'http'`) — тот же refresh дерева/Git.

Итог = `--ui-scale × --chat-scale`. Применяется **только** в `.chat-column` (`styles/index.css`): локально переопределяются `--text-*` как `calc(<база>rem * var(--chat-scale))` и `--padding-scale` (утилиты Tailwind компилируются в `calc(Xrem * var(--padding-scale,1))`). Композер, очередь, док вопроса и панели — вне зоны. Pre-paint — `index.html`, финальная нормализация (мобильный минимум) — `src/main.tsx`. Не масштабируются arbitrary `text-[…]` и rem-величины тач-таргетов — осознанно.

## Промпт и статистика (ADR-070)

- **`StatsTab`** (`components/panels/StatsTab.tsx`, правая панель «Статистика») — read-only; данные из
  `GET /api/v2/sessions/:id/prompt` и `GET /api/v2/sessions/:id/stats`.
- **«Последний ответ» = один вызов провайдера; «Контекстное окно» = total последнего ответа
  (паритет с opencode `contextUsage`).** Сообщение = вызов LLM (ADR-118): `usage` сообщения —
  расход **своего** шага, сумма по сообщениям хода = расход хода (счётчики сессии). «Последний
  ответ» берёт `usage` последнего assistant-сообщения с usage; «Контекстное окно» —
  `lastAssistantContextTokens` (`hooks/useContextWindowUsage.ts`) = `total_tokens`, иначе
  `input + output`, последнего ответа. В Synth `input_tokens` уже включает cache read/write, а
  reasoning входит в output — отдельно их **не** прибавлять. «Сессия» показывает счётчики
  `Session` (сумма всех ходов) — это корректно и не меняется.
- **TPS/«Длительность» последнего ответа** — от **своего** вызова: `metadata.step_duration_ms ??
  metadata.duration_ms` (`StatsTab.lastDurationMs`, `MessageStats`), при наличии
  `step_duration_ms` TPS = output последнего вызова / его длительность. `duration_ms` остаётся
  длительностью хода для отчётности/аналитики.
- **«Состав промпта»** — таблица записей манифеста в реальном порядке отправки (тир
  `stable`/`context`/`volatile`, блок по i18n-ключу `promptBlock.*`, `Симв.`/`~Токенов`/`Статус`,
  provenance), строки «Всего символов/~токенов» и «Статический префикс», строка «Описание инструментов»
  (`tools`), hit/miss последнего хода (`promptMeta` → `promptHit`/`promptMiss`). Секция «История» —
  раскрывающаяся таблица state-сообщений по типам + исключённые (`disabled`/`hidden`/`info`,
  `disabled` включает подавленные ходы)/вложения/число секретов.
- **Отключение сообщения (`disabled`)** — серверная семантика хода: отключённая user-реплика
  гасит assistant/tool/error до следующей user-реплики (`suppressDisabledTurns` в core).
  UI не удаляет сообщение: показывает его зачёркнутым (`opacity-50 line-through`) и

## Git и SSH-ключи (ADR-076)

- **Git-вкладка** (`components/panels/left-panel/GitTab.tsx`, `stores/gitStore.ts`): реестр `project.repos` с `destination`/`type`/`url`/`ssh-key`/`lastFetch`; `scan → register`, `clone`/`init` с полями `name`/`path` и селектором SSH-ключа, `fetch`, `remove` (через `ConfirmDialog`, опц. `deleteLocal`). Методы — `synthApi.*GitRepo*`.
- **Busy-состояния и отмена (клоны идут минутами — форма не должна «висеть»).** Клон — `isCloning`, инициализация — `isInitializing`, регистрация существующего — `isRegistering`; операция над записью реестра — `busyRepo: { projectId, path, kind: 'fetch' | 'remove' }`. Во время работы кнопка показывает `loader-2` + `animate-spin` и подпись «Клонирование…»/«Инициализация…» (`git.cloning`/`git.initializing`), `aria-busy`, `disabled`; в строке репозитория при fetch/remove — спиннер + текст (`git.fetching`/`git.removing`, `data-testid="git-busy-<projectId>::<path>"`), остальные сетевые действия записей заблокированы (guard по `busyRepoRef`). Рядом с формой клона — подсказка про длительность (`git.cloneNetworkHint`).
- **Отмена — `AbortController`.** `cloneAbortRef` живёт в компоненте: `signal` доходит до `synthApi.cloneGitRepo` через `fetchJSON` (спредит `RequestInit`). Прерывают три пути: кнопка «Отмена» (`git.cloneCancel`), `closePopover` (закрытие поповера, переключение проекта, уход вкладки — cleanup-эффект). Отмена — **не** ошибка: тост `notify({type:'info'})` `git.cloneCancelled`, форма и введённые значения остаются, состояние сбрасывается. `AbortError` в `gitStore` не пишет `error`/`lastError` (пользователь отменил сам).
- **Защита от двойного сабмита — на `useRef`, не на state.** `cloneInFlightRef`/`initInFlightRef` проверяются **синхронно** в начале обработчика: два клика до перерисовки (кнопка ещё не `disabled`) не отправляют второй параллельный запрос. Один guard `cloneInFlightRef` покрывает весь цикл «clone → refreshRepos», а также register-after-409 и delete-and-retry.
- **409 «путь занят» — actionable-действия.** Сервер (`POST /git/repos/clone`) отдаёт `409` с `details {path, occupied: 'repo'|'stub'|'dir', entries?}`; `fetchJSON` пробрасывает `details` в `Error`, `gitStore.lastError` хранит их структурно (`{message, code?, details?}`; строковый `error` сохранён для совместимости). Разбор и выбор действия — чистая функция `lib/gitOccupancy.ts` (`repoOccupiedDetails`/`repoOccupiedAction`/`canDeleteOccupiedPath`): `repo` → «Зарегистрировать существующий» (`registerRepo({path, url, name})` + `refreshRepos` + success-тост), `stub` → «Удалить и повторить» (`synthApi.deleteEntry(projectId, details.path)` → повторный клон теми же параметрами; `DELETE /fs` не сносит непустой каталог, поэтому при `400` след клона откладывается переносом в `<path>.incomplete` и путь освобождается — данные не теряются), `dir` → «Указать другой путь» (фокус на поле пути, поповер не закрывается). Нет `details` — прежний текст без кнопок; удаление корня workspace (`''`/`.`) не предлагается.
- **Температура агента в админке «Агенты»** (`admin/AgentsPanel.tsx`): `AgentForm.temperature` — `number | undefined`, где `undefined` = **Auto (дефолт модели)**. В форме — чекбокс `admin.agents.temperatureAuto` (включён при `undefined`) и `SliderField` со значением `form.temperature ?? 0.3`; при Auto слайдер `disabled`, а подпись значения — `admin.agents.temperatureAutoShort` («Авто»). Включение Auto → `undefined`, выключение → `0.3`; сохранение отправляет `temperature: form.temperature ?? null` (`null` = сброс на сервере, см. `POST /api/v2/agents`). Пустая форма и `buildForm` **не** подставляют `0.7` — значение из ответа берётся как есть, отсутствие = Auto. Тесты — `AgentsPanel.test.tsx` («Auto включён → `temperature: null`», «слайдер отправляет число», «переключение Auto»); в jsdom нужен стаб `HTMLElement.prototype.scrollIntoView`.
- **SSH-ключи** (`components/settings/SshKeysSettings.tsx`, встраивается в админ-категорию «Агенты» `admin/AgentsPanel.tsx`): CRUD per-agent ключей, привязка к агентам (`agentIds`), редактирование без обязательной замены ключа. Поля «Тип» нет (дублировало имя) — в shared `SSHKey.type?`/`sshKeyCreateSchema.type?` сохранены для обратной совместимости, UI их не задаёт и не показывает. API `synthApi.*SshKey*` отдаёт только `SSHKeyMeta` (без `privateKey`/`passphrase`); ошибки — ключи `sshkey.*` (в т.ч. `sshkey.env_failed`), i18n ru/en. Ключи с `passphrase` поддерживаются (git-операция — через askpass).
- **i18n и тесты.** Ключи `git.cloning`/`git.initializing`/`git.fetching`/`git.removing`/`git.cloneCancel`/`git.cloneCancelled`/`git.cloneNetworkHint`/`git.occupied.*`/`git.registerOccupiedSuccess` (ru/en, паритет). Тесты — `stores/gitStore.test.ts` (`signal` доходит до API, `lastError.details`, `AbortError` не пишет ошибку), `lib/gitOccupancy.test.ts` (`repo`/`stub`/`dir`/`undefined`, удаление корня), `components/panels/GitTab.test.tsx` (двойной клик → один запрос, индикация, «Отмена» и закрытие поповера, fetch-спиннер и блокировка остальных, три действия по 409).

- **Админ-раздел «Плагины»** (`components/settings/PluginsSettings.tsx`; категория `plugins`, `labelKey: settings.category.plugins`, icon `plug`, `roles: ['ADMIN']` — рядом с «Аддонами»): слой плагинов инстанса поверх `/api/v2/plugins*` и `/api/v2/settings/plugins`. В managed локальные источники запрещены: `403 LOCAL_INSTALL_DISABLED` показывается текстом ответа, в форме — постоянное пояснение про managed и сетевые источники.
- **Политика слоя** (секция «Политика»): `GET/PUT/DELETE /settings/plugins` через `useSettingsDraft`; ключи `enabled`, `executionEnabled`, `runtimeInstall`, `trustFloor`, `scan`, `promptBlockMaxChars`, `llmFilterTimeoutMs`. `restartRequired` (API возвращает `true` всегда — рантайм собирается при старте, инвариант 24) — баннер с кнопкой перезапуска (ADR-092).
- **Журнал плагинов** (секция «Журнал плагинов»): хвост журнала действий — `synthApi.listPluginAudit()` (`GET /api/v2/plugins/audit`; DTO локально: `PluginAuditEntry`/`PluginAuditListResponse`/`PluginAuditListOptions` в `lib/api/plugins.ts`). Список: время, плагин, действие (`action` — код), итог (`ok`/`rejected`), код причины (`reason`); пустое состояние, ошибка и кнопка «Обновить» (`plugins-audit-refresh`). Чтение журнала — **не действие над плагином**: состояние плагинов не меняется.
- **Роли:** раздел и политика — ADMIN; install/enable/disable доступны также service-key со scope `addons:install`, approve и DELETE — только ADMIN. UI лишь прячет недоступное (`canManage` из `useAuthStore`), enforcement — на сервере; 403 без машинного кода читается как `plugins.forbidden`.

Тесты — `PluginsSettings.test.tsx` (23: список/бейджи, бейдж серверной политики и подсказка для `unverified`, пустое состояние, управляемый плагин, enable/disable, удаление через `confirm()`, update, установка и `403 LOCAL_INSTALL_DISABLED`, `202` → подтверждение, политика + `restartRequired`, сброс, вспомогательные функции, **журнал плагинов**: записи/пустое состояние/обновление/ошибка), `settings-catalog.test.ts` (поиск категории), `synthApi.contract.test.ts` (317 методов).

## Совместимость провайдеров и моделей (ADR-117)

- **Блок «Расширенные параметры»** — `components/admin/CompatibilityFields.tsx` в формах провайдера (`ProvidersPanel`) и модели (`ModelsPanel`, теперь create/edit): сворачиваемый, по умолчанию развёрнут, если у сущности уже сохранён `compatibility`, иначе свёрнут; бейдж «изменено» (`hasCompatibilityDraftChanges`).
- **Контролы:** `reasoningField` — селект известных имён (`reasoning_content`/`reasoning`/`reasoning_text`) + «своё значение» (`COMPATIBILITY_CUSTOM`), `maxTokensField` — авто/`max_tokens`/`max_completion_tokens`, остальные четыре — tri-state «Авто / Да / Нет» (`CompatibilityTristate` = `''|'true'|'false'`): черновик строковый, поэтому явный `false` не схлопывается в «авто».
- **Payload (`buildCompatibilityPayload`):** «авто» → поля в теле нет; полная очистка у сущности, где параметры были сохранены (`isCompatibilitySaved`), отправляет `compatibility: null` — сервер трактует объект как **полную замену**, поэтому частичный объект означает «остальное — авто». У сущности без сохранённых параметров пустой черновик не отправляет поле вовсе.
- **Нативные медиа (ADR-117).** `supportsNativeVideo` — tri-state «Авто / Да / Нет» (провайдер принимает видеофайл нативно, блок `video_url`). `nativeAudioFormats` — режим + мульти-селект чипов: «Авто» (эвристика сервера), «Задать список» (`COMPATIBILITY_CUSTOM` + чипы `wav`/`mp3`/`ogg`) и «Не принимает нативно» (явный пустой список). Явные значения (`false`, `[]`) — **не** «авто»: уходят в payload как есть. Поля и форматы — **общий контракт shared** (`ModelCompatibility.supportsNativeVideo`/`nativeAudioFormats`, тип `NativeAudioFormat`, реестр `NATIVE_AUDIO_FORMATS`) — берутся subpath-импортом из `@itphx/synth-shared/types` (корневой `@itphx/synth-shared` в UI не импортировать); локальных дублей в UI нет.
- **API-слой** — `lib/api/compatibility.ts` (`CompatibilityDraft`, `emptyCompatibilityDraft`/`draftFromCompatibility`/`compatibilityFromDraft`, `hasCompatibilityDraftChanges`, `buildCompatibilityPayload`, `isCompatibilitySaved`); типы `ModelCompatibility` — из `@itphx/synth-shared/types` (без бандла core). Домены `lib/api/providers.ts` и `lib/api/models.ts` несут `compatibility` в DTO.
- **i18n** — `admin.compatibility.*` (ru/en, паритет). Тесты: `ProvidersPanel.test.tsx`, `ModelsPanel.test.tsx` (payload/round-trip/сброс), `lib/api/compatibility.test.ts`.
- **«Усилие рассуждений» в форме агента** (`admin/AgentsPanel.tsx`, ключи `admin.agents.effort*`): `SelectField` сразу после «Размышлений» — «Авто (из уровня размышлений)» + все `EFFORT_LEVELS` (`low|medium|high|xhigh|max`, реестр из `@itphx/synth-shared/types`; подписи `low|medium|high` — общие с уровнями размышлений, `xhigh`/`max` — как есть). `AgentForm.effort` хранит строку, `''` = «Авто»; `buildForm` читает `a.effort`/`detail.effort`, пустая форма и «создать» сбрасывают в `''`. Payload: выбран тир — `effort: form.effort`; «Авто» — поля нет, но если у агента тир был сохранён (`savedEffort`) — явный `effort: null` (иначе сервер оставил бы прежнее значение, как у `temperature`). Хинт (`admin.agents.effortHint`) говорит, что параметр уходит провайдеру только при включённом `supportsEffortUpdates` у модели/провайдера, а `xhigh`/`max` задаются только здесь. Тесты — `AgentsPanel.test.tsx` (`agent-effort`: «Авто» → `null` при сохранённом, отсутствие поля у нового, выбранный тир).

## Мобильный / PWA

- Полные конвенции (зоны ≤768 / 769–1199 / ≥1200, дроверы, touch-first, PWA-шелл, авто-обновление и аварийный баннер) — в [ADR-044](../../docs/arch_decisions/adr-044-mobile-adaptive-ui-pwa.md) и кратко в корневом `AGENTS.md`; классами/баннером конкретно здесь не дублируются.
- Локально: `initDeviceClasses()` (`lib/device.ts:38`) вешает классы на `<html>`; для логики использовать `useDevice()`/`useMediaQuery()` (`hooks/`), а не `window.innerWidth` вручную.
- Мобильный CSS гейтится `html.device-*`/`html.pointer-coarse`; JS-признак — `deviceType !== 'desktop'`.
- **Системная кнопка «назад» закрывает верхний оверлей.** Пока оверлей открыт, `useBackClose` (`hooks/useBackClose.ts`) кладёт запись в `history` (`synthBackOverlay`) и на `popstate` закрывает верхнюю запись стека; программное закрытие (крестик/backdrop/Esc) снимает запись через `history.back()` с подавлением своего `popstate`, чтобы не закрыть нижележащий оверлей. Подключено: общий `Dialog` (все Base UI-диалоги, включая `AttachmentGallery`), `MobileDrawer`, `DebugModal`, развёрнутый ответ (`MessageList`, `expandedChatGroup`). Новые оверлеи подключать к этому хуку, а не заводить собственный `popstate`; вложенные оверлеи закрываются по одному. Тесты — `hooks/useBackClose.test.tsx`, `components/ui/dialog.back.test.tsx`.
- `PwaUpdatePrompt` — **авто-обновление**: `SW.waiting` → `SKIP_WAITING` + reload по `controllerchange` (страховка 1.5 с); расхождение версии (`GET /health` vs `SYNTH_VERSION`) → немедленный reload. Баннер «Позже/Обновить» — только **аварийный фоллбек**: после `MAX_AUTO_RELOADS = 2` авто-попыток на один ключ (ключ — `workerKey`/`ver:<version>`, счётчик в `sessionStorage synth.pwa.autoReload`; смена ключа сбрасывает). Проверка — при монтировании, раз в 30 мин, по `visibilitychange` и на первом действии после простоя >1 ч; версия `sw.js` подставляется плагином `vite.config.ts` (`serviceWorkerVersionPlugin`) из `packages/shared/package.json`. Компонент вне `AuthGate` — работает и на экране входа.
